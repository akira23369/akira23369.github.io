# 私有构造函数
如果不能 new，那它还有什么用？

## 引言：把大门焊死，只留 VIP 通道

默认情况下，如果你不写任何构造函数，编译器会送你一个 `public` 的无参构造函数。
但如果你显式地写了一个 `private` 构造函数，你就向全世界宣告了一件事：
**“除了我自己（类内部），没有任何人可以使用 `new` 关键字来创建我的实例！”**

既然大门被焊死了，我们要怎么使用这个类呢？通常有以下 **三大经典使用场景**。

---

## 场景一：单例模式

这是私有构造函数最著名的应用场景。
假设我们要写一个 `AppConfig`（系统配置类）或者 `DatabasePool`（数据库连接池）。这种类在整个应用程序的生命周期中，**必须且只能存在一个实例**。如果允许别人到处 `new`，会导致读取配置混乱或者数据库连接爆炸。

怎么保证全局只有一个实例？**把构造函数私有化，内部自己建一个，然后通过静态属性发给所有人用。**

```csharp
public class AppConfig
{
    // 1. 静态私有字段，用来保存唯一的那个实例
    private static AppConfig _instance;

    // 2. 核心：私有构造函数！外部绝对无法 new AppConfig()
    private AppConfig()
    {
        Console.WriteLine("读取本地配置文件，初始化系统设置...");
        // 假设这里有很多耗时的初始化操作
    }

    // 3. 对外暴露的 VIP 通道（全局唯一访问点）
    public static AppConfig Instance
    {
        get
        {
            // 如果还没创建过，就创建一个；如果有了，直接返回老实例
            // （注：此处未考虑多线程加锁，仅作原理演示）
            if (_instance == null)
            {
                _instance = new AppConfig(); // 内部是可以调用私有构造函数的！
            }
            return _instance;
        }
    }
    
    public string GetConfigValue(string key) => "某个配置值";
}
```

**调用方视角：**
```csharp
// AppConfig config = new AppConfig(); // 💥 编译直接报错！保护成功！

// 只能通过 Instance 获取
AppConfig config1 = AppConfig.Instance; // 输出：读取本地配置文件...
AppConfig config2 = AppConfig.Instance; // 毫无输出，直接拿到了已存在的对象

Console.WriteLine(object.ReferenceEquals(config1, config2)); // 输出 True，它们是同一个对象！
```

## 场景二：静态工厂方法
语义化创建与异步验证

在上一篇笔记中我们提到，构造函数重载多了会让人眼花缭乱：
`new User("张三")` 和 `new User("张三", "123456")`，鬼知道哪个是普通用户，哪个是管理员？

而且构造函数有两个**致命的弱点**：
1. **名字只能叫类名**，无法表达“创建的意图”。
2. **不能是异步的（`async`）**，不能在构造函数里写 `await` 去查数据库。

这时候，私有构造函数 + 静态工厂方法 完美解决痛点：

```csharp
public class User
{
    public string Name { get; private set; }
    public string Role { get; private set; }

    // 把构造函数藏起来
    private User(string name, string role)
    {
        Name = name;
        Role = role;
    }

    // 提供语义清晰的“静态工厂方法”
    public static User CreateGuest()
    {
        return new User("匿名访客", "Guest");
    }

    public static User CreateAdmin(string name)
    {
        if (string.IsNullOrWhiteSpace(name)) throw new ArgumentException();
        return new User(name, "Admin");
    }

    // 解决构造函数不能异步的痛点！
    public static async Task<User> CreateUserFromDatabaseAsync(int userId)
    {
        string name = await Db.QueryNameAsync(userId); // 模拟异步查库
        return new User(name, "StandardUser");
    }
}
```

**调用方视角（代码变得像读散文一样清晰）：**
```csharp
User guest = User.CreateGuest();
User admin = User.CreateAdmin("超级张三");
User dbUser = await User.CreateUserFromDatabaseAsync(1001);
```

## 场景三：纯工具类

有时候，我们写的类只是一堆**静态方法**的集合，比如计算器、通用帮助类。
这种类里面没有实例字段，连状态都没有，把它实例化（`new` 出来）是毫无意义甚至浪费内存的。

在早期的 C# 1.0 中，为了防止别人无聊去 `new` 你的工具类，标准做法就是给一个空的私有构造函数：

```csharp
public class MathHelper
{
    // 阻止别人 new MathHelper()
    private MathHelper() { }

    public static int Add(int a, int b) => a + b;
    public static double PI => 3.14159;
}
```

> **⭐ 现代 C# 的语法糖（补充）：**
> 从 C# 2.0 开始，微软为了简化这个操作，引入了 `static class`（静态类）关键字。
> 当你声明 `public static class MathHelper` 时，编译器在底层**自动**帮你把它编译成一个带有私有构造函数（甚至无法被继承）的类。所以在现代开发中，如果是纯工具类，直接用 `static class` 即可，不需要手动写私有构造函数了。

## 冷知识

### 私有构造函数能被继承吗？
**绝大多数情况下：不能！**
上一篇笔记我们学过，子类的构造函数执行前，必须先调用父类的构造函数（`base()`）。如果父类的构造函数是 `private` 的，子类根本看不见它，自然也就无法调用它。
所以，**只包含私有构造函数的类，变相地成为了“密封类（Sealed Class）”，无法被外部继承。**

**唯一的例外：内部嵌套类（Nested Class）。**
如果子类是写在父类的**大括号里面**的，那它就能看见父类的私有成员，从而实现继承（这在极度复杂的“构建者模式 Builder Pattern”中有时会用到）。

### 反射能打破私有构造函数的防御吗？
**能！** 
C# 的反射是“上帝视角”，它可以强行调用私有构造函数。
```csharp
// 强行通过反射调用私有构造函数，破坏单例模式！
var constructor = typeof(AppConfig).GetConstructor(
    BindingFlags.Instance | BindingFlags.NonPublic, 
    null, new Type[0], null);

AppConfig illegalInstance = (AppConfig)constructor.Invoke(null); 
```
*防守策略：如果真要在框架级别防反射，可以在私有构造函数内部加个判断，如果 `_instance != null` 就抛出异常。*

## 总结：何时该使用私有构造函数？

当你在写代码时，如果脑海中闪过以下三个念头之一，请立刻敲下 `private`：

1. **“我只需要一个实例，多了会出事！”** ➔ 用作 **单例模式**。
2. **“new 这个词太宽泛了，我要给创建对象的方法起个好名字，或者我需要异步创建！”** ➔ 用作 **静态工厂方法**。
3. **“我这全都是静态方法，千万别给我分配内存实例化！”** ➔ （虽然现代更推荐 `static class`，但底层原理依然是私有构造函数）。

私有构造函数，就像是代码世界的“海关”：它拒绝了杂乱无章的随便进出（`new`），强制所有的实例化操作都必须经过你设定的安检通道。这就是高质量面向对象设计的魅力。
