# C# 多线程同步与 Monitor 类

## 核心概念与背景
在多线程环境中，当多个线程（如 Thread 1 和 Thread 2）同时尝试访问和修改同一个**共享资源**（Shared Resource，可以是变量、属性、文件或数据库等）时，如果不加以控制，会导致**竞态条件（Race Condition）**，进而引发数据损坏、输出不一致或死锁等问题。

为了解决这个问题，需要引入**线程同步**。实现线程同步的基础机制被称为**线程同步原语**。常见的同步原语包括 `Monitor`、`Mutex`、`Semaphore` 以及 `lock` 语句等。

原语的“原”字取自“原子”（Atom），意为**不可再分割**。”语“指由**若干条指令组成的程序段**
- **不可中断：** 原语一旦开始执行，就必须一气呵成。操作系统保证它在执行过程中不会被线程调度器切换走，也不会被中断信号打断。
- **结果唯一：** 对于外部观察者（其他线程）来说，原语只有“没开始”和“已完成”两种状态，不存在“执行了一半”的中间状态。

## Monitor 类的作用与工作原理
`Monitor` 类的核心目标是：**允许线程并发执行，但绝对禁止多个线程并发访问同一个共享资源。**

可以将 `Monitor` 想象成银行的保险箱系统：
*   **Lock Object（锁对象）：** 相当于保险箱的钥匙。它本身不存储任何业务数据，仅作为一个标记，供多个线程识别和争夺。
*   **获取锁：** 线程在访问共享资源前，必须向 `Monitor` 申请这把钥匙。如果钥匙可用，线程获取钥匙并进入执行；如果钥匙正在被其他线程使用，当前线程必须排队等待（Monitor 内部维护一个 FIFO 先进先出队列）。
*   **释放锁：** 线程操作完成后，必须归还钥匙，以便队列中的下一个线程可以获取钥匙并执行。

## 代码实现：使用 Monitor 实现计数器同步
以下代码模拟了两个线程同时对一个共享变量进行递增和递减操作。如果不使用 `Monitor`，最终结果往往不是 0。使用 `Monitor` 后，保证了结果的一致性。

```csharp
using System;
using System.Threading;

class Program
{
    // 1. 定义共享资源
    private static int _sharedCount = 0;

    // 2. 定义锁对象 (必须是引用类型，且通常声明为 readonly)
    private static readonly object _lockObject = new object();

    static void Main()
    {
        Thread t1 = new Thread(CountUp);
        Thread t2 = new Thread(CountDown);

        t1.Start();
        t2.Start();

        t1.Join();
        t2.Join();

        Console.WriteLine($"最终的共享资源值为: {_sharedCount}"); // 预期输出始终为 0
    }

    // 线程1执行的方法：递增
    static void CountUp()
    {
        for (int i = 0; i < 100000; i++)
        {
            // 申请获取锁
            Monitor.Enter(_lockObject);
            
            // --- 临界区 (Critical Code) 开始 ---
            // 此时只有当前线程能执行这段代码
            _sharedCount++;
            // --- 临界区结束 ---
            
            // 释放锁
            Monitor.Exit(_lockObject);
        }
    }

    // 线程2执行的方法：递减
    static void CountDown()
    {
        for (int i = 0; i < 100000; i++)
        {
            // 申请获取锁
            Monitor.Enter(_lockObject);
            
            // --- 临界区 (Critical Code) 开始 ---
            _sharedCount--;
            // --- 临界区结束 ---
            
            // 释放锁
            Monitor.Exit(_lockObject);
        }
    }
}
```

## 补充完善与进阶知识点（非常重要）

**为什么锁对象必须是 `static readonly object`？**
*   **必须是引用类型 (`object`)：** `Monitor.Enter()` 需要一个对象的引用。如果传入值类型（如 `int`），每次调用都会发生装箱（Boxing），生成一个全新的对象。这会导致多个线程实际上锁住了不同的对象，同步机制彻底失效。
*   **为什么用 `readonly`：** 如果锁对象在程序运行期间被意外重新赋值（例如 `_lockObject = new object();`），那么后续等待的线程和当前持有旧锁的线程之间将失去同步联系，同样会导致并发问题。
*   **尽量避免锁定的对象：** 
    *   **不要锁定 `typeof(T)` 或 `this`：** 这可能导致死锁，因为锁的作用域暴露到了外部，外部代码可能也在锁定同一个实例或类型对象。
    *   **不要锁定字符串（`string`）：** 受到 C# 字符串驻留（String Interning）机制的影响，程序中相同字面量的字符串实际上指向内存中的同一个对象。这可能会导致完全不相关的代码块因为锁定了同一个字符串而发生意外的相互阻塞。
    *   **最佳实践：** 始终创建一个私有的、专门用于锁定的新 `object`（如 `private static readonly object _lock = new object();`）。

**Monitor 代码的严重隐患与修复：异常处理**
上面给出的基础代码存在一个逻辑漏洞：如果在 `Monitor.Enter` 和 `Monitor.Exit` 之间的**临界区代码抛出了异常**，那么 `Monitor.Exit` 将永远不会被执行。这会导致这把“锁”变成死锁（Deadlock），其他所有排队等待的线程将无限期挂起。

**正确的企业级写法（结合 `try...finally`）：**

```csharp
static void CountUpSafe()
{
    for (int i = 0; i < 100000; i++)
    {
        Monitor.Enter(_lockObject);
        try
        {
            // 临界区代码
            _sharedCount++;
        }
        finally
        {
            // 确保无论是否发生异常，锁都会被强制释放
            Monitor.Exit(_lockObject);
        }
    }
}
```

**语法糖预告：`lock` 语句**
正因为每次使用 `Monitor` 都需要配合 `try...finally` 非常繁琐，C# 提供了一个语法糖——`lock` 关键字。`lock(_lockObject) { ... }` 在底层编译后，实际上就是完美的 `Monitor.Enter` 配合 `try...finally` 中调用 `Monitor.Exit` 的结构。理解了 `Monitor`，就彻底理解了 C# 中最常用的 `lock` 的本质。


# Monitor类详解

## 一、Monitor是什么？跟lock是什么关系？

**大白话理解**：Monitor是**lock的"真身"**。你写`lock(obj)`时，编译器会把它翻译成`Monitor.Enter`和`Monitor.Exit`的调用。lock是语法糖，Monitor是底层实现。

**核心关系**：
- `lock` = `Monitor.Enter` + `try-finally` + `Monitor.Exit`
- Monitor提供了lock做不到的高级功能（超时、等待/通知）
- 99%场景用lock就够了，但理解Monitor能帮你深入理解同步本质

---

## 二、Monitor的基本用法（等同于lock）

**lock 的写法**：
```csharp
private static object _lock = new object();

lock (_lock)
{
    // 临界区
    _counter++;
}
```

**Monitor 的原始写法**：
```csharp
private static object _lock = new object();

Monitor.Enter(_lock); // 获取锁，如果锁被占用就等待
try
{
    // 临界区
    _counter++;
}
finally
{
    Monitor.Exit(_lock); // 必须在finally里释放，否则死锁
}
```

**编译器真会翻译**：用ILDASM工具看IL代码，`lock(obj)`会被翻译成：
```il
call void [mscorlib]System.Threading.Monitor::Enter(object)
...
call void [mscorlib]System.Threading.Monitor::Exit(object)
```

## 三、Monitor的核心方法（5个必会）

### `Monitor.Enter` 与 `Monitor.Exit`
- `Enter`：获取锁，拿不到就**死等**
- `Exit`：释放锁，让其他等待的线程进来

**陷阱**：必须在`finally`里调用`Exit`，否则中间代码抛异常，锁永远无法释放，导致**死锁**。

```csharp
// 错误示范：忘记finally
Monitor.Enter(_lock);
_counter++; // 这里抛异常，锁没释放，永远卡住
Monitor.Exit(_lock); // 这行执行不到
```

### `Monitor.TryEnter` —— 锁的超时机制
lock只能死等，Monitor可以**尝试获取锁，超时就算了**。

```csharp
private static object _lock = new object();

public bool TryDoWork(int timeoutMs)
{
    // 尝试进入锁，最多等 timeoutMs 毫秒
    if (Monitor.TryEnter(_lock, timeoutMs))
    {
        try
        {
            // 拿到锁了，干活
            Console.WriteLine("成功获取锁，开始工作");
            Thread.Sleep(500); // 模拟工作
            return true;
        }
        finally
        {
            Monitor.Exit(_lock);
        }
    }
    else
    {
        // 没拿到锁，做别的
        Console.WriteLine($"等待{timeoutMs}ms后超时，放弃");
        return false;
    }
}

// 使用
static void Main()
{
    // 先让另一个线程持有锁
    new Thread(() => {
        Monitor.Enter(_lock);
        Thread.Sleep(2000);
        Monitor.Exit(_lock);
    }).Start();
    
    Thread.Sleep(100); // 确保另一个线程先拿到锁
    
    var result = TryDoWork(500); // 等500ms，拿不到就放弃
    Console.WriteLine($"结果: {result}"); // 输出 false
}
```

**重载**：
```csharp
Monitor.TryEnter(_lock); // 立即尝试，不等待
Monitor.TryEnter(_lock, 1000); // 等1000毫秒
Monitor.TryEnter(_lock, TimeSpan.FromSeconds(1)); // 用TimeSpan
```

### `Monitor.Wait` —— 在锁内主动等待
**Wait 的神奇之处**：在锁内部调用`Wait`，会**临时释放锁**，然后自己进入等待队列，让别人先干。等别人`Pulse`叫它，它再回来重新抢锁。

**使用场景**：生产者-消费者，仓库没货时消费者先让出锁等着。

```csharp
private static object _lock = new object();
private static Queue<int> _queue = new Queue<int>();

// 消费者：没货就等着
static void Consumer()
{
    lock (_lock)
    {
        while (_queue.Count == 0) // 必须用while，别用if
        {
            Console.WriteLine("仓库为空，消费者等待...");
            Monitor.Wait(_lock); // 1. 释放锁 2. 进入等待队列 3. 阻塞
            // 被唤醒后，会重新获取锁，从Wait下面继续执行
        }
        
        int item = _queue.Dequeue();
        Console.WriteLine($"消费者取走: {item}, 剩余: {_queue.Count}");
    }
}

// 生产者：生产完货叫醒消费者
static void Producer()
{
    lock (_lock)
    {
        _queue.Enqueue(1);
        Console.WriteLine($"生产者添加1个，当前: {_queue.Count}");
        Monitor.Pulse(_lock); // 叫醒一个等待的消费者
    }
}
```

**Wait 的完整流程**：
1. 释放锁（让其他线程可以进入）
2. 进入等待队列（睡觉）
3. 被 Pulse 叫醒后，重新竞争锁
4. 拿到锁后，从 Wait 下一行继续执行

**为什么必须用 while 而不是 if**？
```csharp
lock (_lock)
{
    if (_queue.Count == 0) // 错误！
    {
        Monitor.Wait(_lock);
    }
    // 醒来后可能队列又空了（被其他消费者抢先）
    // 用 while 会再检查一次，安全
}
```

### `Monitor.Pulse` 与 `Monitor.PulseAll`
- `Pulse`：叫醒**一个**等待的线程（公平排队）
- `PulseAll`：叫醒**所有**等待的线程（让它们一起抢锁）

**注意**：Pulse 必须在锁内调用，且**不立即释放锁**，只是发了个"通知"。等到调用者执行完 lock 块，真正释放锁后，被叫醒的线程才有机会重新抢锁。

```csharp
lock (_lock)
{
    // 修改共享状态
    _queue.Enqueue(item);
    
    Monitor.Pulse(_lock); // 通知等待者
    // 注意：此时锁还没释放，被Pulse的线程还进不来
    
} // 离开了lock块，锁才真正释放
```

### `Monitor.IsEntered` —— 检查当前线程是否持有锁
```csharp
if (Monitor.IsEntered(_lock))
{
    Console.WriteLine("当前线程已持有锁");
}
```

## 四、Wait 和 Pulse——生产者-消费者完整示例

```csharp
public class BoundedBuffer
{
    private readonly object _lock = new object();
    private readonly Queue<int> _queue = new Queue<int>();
    private readonly int _capacity;
    
    public BoundedBuffer(int capacity)
    {
        _capacity = capacity;
    }
    
    // 生产者：队列满就等着
    public void Produce(int item)
    {
        lock (_lock)
        {
            while (_queue.Count >= _capacity)
            {
                Console.WriteLine($"仓库满 ({_queue.Count}/{_capacity})，生产者等待");
                Monitor.Wait(_lock);
            }
            
            _queue.Enqueue(item);
            Console.WriteLine($"生产: {item}, 当前: {_queue.Count}/{_capacity}");
            
            // 生产完，叫醒消费者
            Monitor.Pulse(_lock);
        }
    }
    
    // 消费者：队列空就等着
    public int Consume()
    {
        lock (_lock)
        {
            while (_queue.Count == 0)
            {
                Console.WriteLine("仓库空，消费者等待");
                Monitor.Wait(_lock);
            }
            
            int item = _queue.Dequeue();
            Console.WriteLine($"消费: {item}, 剩余: {_queue.Count}/{_capacity}");
            
            // 消费完，叫醒生产者
            Monitor.Pulse(_lock);
            return item;
        }
    }
}

// 使用
static void Main()
{
    var buffer = new BoundedBuffer(capacity: 3);
    
    // 两个生产者
    new Thread(() => {
        for (int i = 1; i <= 5; i++)
        {
            buffer.Produce(i);
            Thread.Sleep(500);
        }
    }).Start();
    
    new Thread(() => {
        for (int i = 6; i <= 10; i++)
        {
            buffer.Produce(i);
            Thread.Sleep(700);
        }
    }).Start();
    
    // 三个消费者
    for (int i = 0; i < 3; i++)
    {
        new Thread(() => {
            for (int j = 0; j < 3; j++)
            {
                buffer.Consume();
                Thread.Sleep(800);
            }
        }).Start();
    }
}
```

## 五、Monitor 的陷阱与注意事项

### 陷阱1：在锁外调用 Pulse/Wait
```csharp
// 错误！
Monitor.Pulse(_lock); // 没持有锁，抛 SynchronizationLockException

// 正确
lock (_lock)
{
    Monitor.Pulse(_lock);
}
```

### 陷阱2：Wait 后必须重新检查条件
```csharp
// 错误示范
lock (_lock)
{
    if (_queue.Count == 0) // 应该用 while
    {
        Monitor.Wait(_lock);
    }
    int item = _queue.Dequeue(); // 可能队列又空了，抛异常
}
```

### 陷阱3：Pulse 了但没线程在等待
```csharp
lock (_lock)
{
    _queue.Enqueue(item);
    Monitor.Pulse(_lock); // 如果没人等待，Pulse 直接无效，不会报错
}
```

### 陷阱4：忘记 Exit 导致死锁
```csharp
Monitor.Enter(_lock);
_counter++; // 这里抛异常，下面的 Exit 执行不到
Monitor.Exit(_lock); // 锁永远没释放
```

### 陷阱5：Wait 的虚假唤醒
某些操作系统可能会**无缘无故唤醒**等待的线程，`while` 循环能确保条件真的满足才继续。

## 六、Monitor vs lock：什么时候用 Monitor？

| 需求 | lock | Monitor |
|------|------|---------|
| 简单互斥 | ✅ 简洁 | ❌ 啰嗦 |
| 超时等待 | ❌ 做不到 | ✅ Monitor.TryEnter |
| 等待/通知模式 | ❌ 做不到 | ✅ Wait/Pulse |
| 检查是否已锁 | ❌ 做不到 | ✅ IsEntered |
| 可读性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |

**结论**：
- **默认用 lock**：代码少，不容易出错，99%场景够用
- **必须用 Monitor**：需要超时或 Wait/Pulse 时

---

## 七、性能考量

- **无竞争时**：Monitor 很快（约50-100ns）
- **有竞争时**：线程阻塞、上下文切换，变慢1000倍
- **Wait/Pulse**：比 Sleep/轮询高效，因为不浪费CPU

**性能陷阱**：
```csharp
// 错误：频繁 Wait/Pulse 做轮询
lock (_lock)
{
    while (条件不满足)
    {
        Monitor.Wait(_lock, 10); // 等10ms，本质是轮询
        // 应该：用事件或信号量
    }
}
```

---

## 八、总结

Monitor 是 .NET 同步机制的**基石**：
- `Enter/Exit` 提供互斥，是 lock 的底层
- `TryEnter` 提供超时能力
- `Wait/Pulse` 提供线程间协作能力
