# 共享资源与线程同步问题

## 一、什么是共享资源？为什么它是个麻烦？

**大白话理解**：共享资源就是**多个线程都能摸到的东西**。比如全班同学共用的一块黑板，如果两个人同时写，字就叠在一起谁也看不懂。程序里就是**多个线程都能访问的变量、对象、文件、数据库**等。

**典型共享资源**：
- 静态变量或全局变量
- 堆上创建的对象（多个线程持有同一对象的引用）
- 文件、数据库连接
- 集合（List、Dictionary等）

**代码示例：最简单的共享资源**
```csharp
class BankAccount
{
    public int Balance = 1000; // 共享资源：账户余额
}

class Program
{
    static BankAccount account = new BankAccount();
    
    static void Main()
    {
        // 两个线程同时操作同一个 account 对象
        new Thread(() => Withdraw(800)).Start();
        new Thread(() => Withdraw(800)).Start();
    }
    
    static void Withdraw(int amount)
    {
        if (account.Balance >= amount)
        {
            Console.WriteLine($"线程{Thread.CurrentThread.ManagedThreadId}：余额足够，准备取款");
            Thread.Sleep(100); // 模拟处理时间
            account.Balance -= amount;
            Console.WriteLine($"线程{Thread.CurrentThread.ManagedThreadId}：取款成功，新余额: {account.Balance}");
        }
        else
        {
            Console.WriteLine($"线程{Thread.CurrentThread.ManagedThreadId}：余额不足");
        }
    }
}
```

**可能的结果（每次运行都不同，这才是最可怕的）：**
```
线程9：余额足够，准备取款
线程10：余额足够，准备取款
线程9：取款成功，新余额: 200
线程10：取款成功，新余额: -600  // 透支了！
```

## 二、没有同步机制的三大核心问题

### 问题1：竞态条件——谁跑得快谁说了算

**定义**：多个线程的执行顺序**不可预测**，导致结果取决于"谁先抢到"，而不是逻辑正确性。

**经典案例：累加器**
```csharp
static int counter = 0;

static void Main()
{
    // 1000个线程，每个对 counter 加1
    for (int i = 0; i < 1000; i++)
    {
        new Thread(() => {
            int temp = counter;  // ① 读取
            temp = temp + 1;     // ② 计算
            counter = temp;      // ③ 写回
        }).Start();
    }
    
    Thread.Sleep(2000); // 等所有线程跑完
    Console.WriteLine($"最终 counter 值: {counter}"); // 不是1000！
}
```

**问题分析**（假设 counter 初始为0）：
```
线程A：读取 counter = 0
线程B：读取 counter = 0
线程A：计算 temp = 0 + 1 = 1
线程B：计算 temp = 0 + 1 = 1
线程A：写回 counter = 1
线程B：写回 counter = 1  // 覆盖了A的结果，两次加法只加了一次
```

**结果**：最终 `counter` 大概率小于1000，可能是998、995，甚至900多。**每次运行结果都不同**。

**根本原因**：`counter++` 看似一行代码，实际是分三步（读-改-写），**这三步不是原子操作**（atomic），中间可能被其他线程打断。

### 问题2：数据不一致（脏读/脏写）

**脏读**：读到别人改到一半的数据。

```csharp
class SharedData
{
    public int A = 0;
    public int B = 0;
}

static void Main()
{
    var data = new SharedData();
    
    // 写线程：要保证 A 和 B 同时更新
    new Thread(() => {
        for (int i = 0; i < 1000; i++)
        {
            data.A = i;
            Thread.Sleep(1); // 模拟处理时间
            data.B = i;
        }
    }).Start();
    
    // 读线程：希望看到 A 和 B 一致的值
    new Thread(() => {
        for (int i = 0; i < 10; i++)
        {
            int a = data.A;
            int b = data.B;
            
            if (a != b)
            {
                Console.WriteLine($"脏读！A={a}, B={b}"); // 经常看到
            }
            Thread.Sleep(10);
        }
    }).Start();
}
```

**输出**：
```
脏读！A=5, B=4
脏读！A=100, B=99
...
```

**原因**：写线程更新 A 后、更新 B 前，读线程正好进来读了，导致 A 是新值，B 是旧值，**数据处于不一致的中间状态**。

### 问题3：逻辑错误——判断失效

**案例：用 flag 控制线程停止**
```csharp
static bool _isRunning = true;
static int _count = 0;

static void Main()
{
    // 工作线程：一直累加，直到 _isRunning 为 false
    new Thread(() => {
        while (_isRunning)
        {
            _count++;
        }
        Console.WriteLine($"线程停止，最终 count: {_count}");
    }).Start();
    
    Thread.Sleep(1000);
    Console.WriteLine("准备停止线程...");
    _isRunning = false; // 主线程修改标志
    
    Thread.Sleep(100); // 等等看
    Console.WriteLine($"主线程看到的 count: {_count}");
}
```

**问题**：**工作线程可能永远不会停止！**

**原因**：由于**CPU缓存优化**，工作线程可能把 `_isRunning` 缓存到寄存器中，一直读缓存值（true），即使主线程把它改成 false，工作线程也看不到。这就是**内存可见性问题**。

---

## 三、问题的本质：三个根源

1. **原子性破坏**：多步操作被拆开，中间被插足
2. **可见性失败**：一个线程的修改，另一个线程看不到
3. **有序性错乱**：代码执行顺序被编译器/CPU优化打乱

这三点合起来就是 **并发编程的三大恶魔**。

## 四、为什么这些问题不可预测？

**关键**：线程调度由操作系统决定，**完全随机**。

```csharp
static void UnpredictableExample()
{
    for (int test = 0; test < 5; test++)
    {
        int value = 0;
        bool done = false;
        
        // 写线程
        new Thread(() => {
            value = 42;
            done = true; // 标记完成
        }).Start();
        
        // 读线程：理论上应该看到 done=true 时 value=42
        new Thread(() => {
            int localValue = 0;
            bool localDone = false;
            
            while (!localDone)
            {
                localValue = value;
                localDone = done;
            }
            
            // 期望: localValue=42, 但实际可能是 0！
            Console.WriteLine($"第{test}次: value={localValue}, done={localDone}");
        }).Start();
        
        Thread.Sleep(100);
    }
}
```

**输出（可能）：**
```
第0次: value=42, done=True
第1次: value=0, done=True   // 看到 done=true，但 value 还是0！
第2次: value=42, done=True
第3次: value=0, done=True   // 又出现
...
```

**原因**：`done = true` 可能在 `value = 42` 之前执行（指令重排序），或者 value 的修改对读线程不可见。

## 五、这些问题带来的后果

1. **数据损坏**：账户余额负数、库存数量为负、订单重复提交
2. **程序崩溃**：集合遍历时被修改、数组越界
3. **死锁**（虽然本篇不讲，但它是同步机制不当引起的）：线程互相等待，程序卡死
4. **活锁**：线程不断重试但永远失败
5. **调试噩梦**：问题无法复现，本地调试好好的，到服务器就崩

## 六、经典案例：队列竞争

```csharp
static Queue<int> taskQueue = new Queue<int>();

static void Main()
{
    // 生产者：不断加任务
    new Thread(() => {
        for (int i = 0; i < 100; i++)
        {
            taskQueue.Enqueue(i);
            Console.WriteLine($"加入任务: {i}");
        }
    }).Start();
    
    // 消费者：不断取任务
    new Thread(() => {
        while (true)
        {
            if (taskQueue.Count > 0)
            {
                int task = taskQueue.Dequeue(); // 可能抛异常！
                Console.WriteLine($"处理任务: {task}");
            }
        }
    }).Start();
}
```

**结果**：几乎一定会抛出 `InvalidOperationException`："队列为空"。

**原因**：`Count > 0` 为 true 的瞬间，另一个线程可能已经把最后一个元素取走，`Dequeue` 时队列已空。

## 七、总结：没有同步的世界是地狱

**记住三个核心问题**：
1. **竞态条件**：结果取决于运气，不是逻辑
2. **数据不一致**：读到中间态，写覆盖丢失
3. **不可见性**：一个线程的修改，另一个看不见

**关键结论**：
- **多线程操作共享资源，不加同步，100%会出问题**
- **问题不是"会不会发生"，而是"什么时候发生"**
- **本地调试可能正常，生产环境必然崩溃**
- **问题无法复现，因为线程调度是随机的**
