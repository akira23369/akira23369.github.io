# C#线程同步机制简单介绍

## 一、为什么需要同步机制？

承上篇，共享资源不加保护会出大乱子。同步机制就是**给共享资源加"锁"**，确保同一时间只有一个线程能进去"摸"它。就像公共厕所，进去先锁门，用完再解锁，后面的人排队等着。

**核心目标**：
- **原子性**：保证操作要么全做完，要么全不做，中间不能被打断
- **可见性**：一个线程的修改，其他线程立刻能看到
- **有序性**：防止代码执行顺序被乱优化

---

## 二、同步机制的分类

.NET的同步机制大致分三类，越往后越高级：

**1. 用户模式锁（轻量级，不经过操作系统，快）**
- 纯CPU指令实现，线程等待时不让出CPU（自旋）
- 适合锁持有时间极短的场景

**2. 内核模式锁（重量级，经过操作系统，慢但功能强）**
- 线程等待时进入内核休眠，不消耗CPU
- 适合锁持有时间较长的场景，支持跨进程

**3. 混合锁（前两者的结合，自动切换）**
- 先自旋一会儿，拿不到再进内核休眠
- .NET的默认选择，兼顾性能和功能

## 三、同步机制概览表

| 机制                 | 类型  | 作用             | 大白话类比           | 适用场景                  |
| ------------------ | --- | -------------- | --------------- | --------------------- |
| **lock关键字**        | 混合锁 | 互斥访问代码块        | 单人间厕所，一把钥匙      | 保护小段代码，最常见            |
| **Monitor类**       | 混合锁 | lock的底层实现，功能更细 | 同上，但能中途开门叫人     | 需要TryEnter、Pulse等高级控制 |
| **Mutex**          | 内核锁 | 互斥，可跨进程        | 公共厕所钥匙，能跨楼用     | 跨进程同步，比如单实例程序         |
| **Semaphore**      | 内核锁 | 限制并发数N         | 停车场，最多停N辆车      | 限流，控制最多N个线程访问         |
| **ReadWriteLock**  | 混合锁 | 多读单写           | 阅览室：多人同时看，写时全清场 | 读多写少场景，如配置读取          |
| **Interlocked**    | 用户锁 | 原子操作           | 原子笔，一笔写完不可打断    | 简单计数器，++、--操作         |
| **SpinWait**       | 用户锁 | 纯自旋等待          | 死等，不罢休          | 锁持有时间极短（纳秒级）          |
| **Barrier**        | 混合锁 | 多个线程在某个点汇合     | 跟团游，人到齐才出发      | 分阶段并行任务               |
| **CountdownEvent** | 混合锁 | 等N个信号量都到位      | 倒计时，到0就触发       | 等待多个线程完成              |

## 四、选择哪个？简单指南

**无脑选**：
```csharp
// 99%的场景用 lock 就够了
private static object _lock = new object();

lock (_lock)
{
    // 保护你的共享资源
    _counter++;
}
```

**特殊情况才考虑别的**：
- 需要**超时**等锁：`Monitor.TryEnter`
- 要**跨进程**同步：`Mutex`
- 要**限流**（最多N个线程）：`Semaphore`
- 只是**计数器++/--**：`Interlocked.Increment`
- 读多写少：`ReaderWriterLock`

## 五、通用使用原则

1. **锁对象必须是引用类型**：`object`、`lockObj`，不能是值类型（int、struct）
2. **锁对象要私有**：别用 `this` 或 `typeof(类)`，容易死锁
3. **锁范围要最小**：只包必要的代码，别把整个方法锁了
4. **不要锁字符串**：字符串会被缓存，可能意外共享
5. **避免嵌套锁**：锁中锁容易导致死锁
6. **持有锁时间要短**：长时间持锁会堵死其他线程

**错误示范**：
```csharp
// 1. 锁 this（外部也可能锁 this，死锁风险）
lock (this) { ... }

// 2. 锁字符串
lock ("myLock") { ... } // 所有锁"myLock"的地方都会互相阻塞

// 3. 锁范围太大
lock (_lock)
{
    // 包含耗时操作
    Thread.Sleep(1000); // 其他线程干等1秒
}
```

## 六、同步机制的性能代价

**锁的开销**：
- 无竞争时（单个线程）：几十纳秒
- 有竞争时：线程阻塞、上下文切换，几毫秒到几十毫秒
- 自旋太久：浪费CPU

**性能建议**：
- 能不用锁就不用（用不可变对象、线程本地存储）
- 尽量用用户模式锁（Interlocked）
- 锁内代码要极简

---

## 七、总结

理解这些机制后，记住 **"锁是最后的手段"** ：
- 优先用 `ConcurrentQueue` 等并发集合（内部已加锁）
- 优先用 `Task` 和 `async/await`（自动管理同步）
- 必须用锁时，从 `lock` 开始
