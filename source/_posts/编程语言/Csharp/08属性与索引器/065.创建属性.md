# C# 属性 (Properties) 核心解析

## 属性的本质与核心目标
在面向对象编程中，直接暴露类的字段（Field）会严重破坏类的封装性，外部代码可能会赋予无效或不安全的值。属性（Property）作为字段的“保护屏障”，在提供类似字段访问语法的同时，允许开发者在赋值和取值时加入逻辑控制。

*   **本质**：属性本身并不是存储数据的内存单元，而是包含了一对访问器（`get` 和 `set`）的复合类成员。在编译时，C# 编译器会将属性转换为特定的方法（通常被命名为 `get_PropertyName` 和 `set_PropertyName`）。因此，属性在运行时并不额外占用对象的内存，真正分配内存的依然是底层的私有字段（Backing Field）。
*   **目标**：接收外部输入的值，对其进行合法性校验，只有在校验通过时，才将值赋给对应的私有字段。

## set 和 get 访问器详解
属性通过 `get` 和 `set` 访问器来控制对基础数据的读写操作。

### set 访问器 (写入与校验)
当外部尝试给属性赋值时，会自动触发 `set` 访问器。
*   **隐式参数 `value`**：`set` 访问器内部包含一个名为 `value` 的隐式参数，它代表了外部传入的新值。该参数的数据类型与属性声明的数据类型完全一致。
*   **附加逻辑**：可以在 `set` 中编写自定义的校验规则（如字符串长度限制、数值范围检查等）。若校验失败，可以选择忽略本次赋值、抛出异常或赋予默认值。
*   **限制**：除了隐式参数 `value` 外，`set` 不能定义其他参数，也不允许有返回值。

### get 访问器 (读取数据)
当外部尝试读取属性的值时，会自动触发 `get` 访问器。
*   **核心职责**：返回底层私有字段的值，或者返回经过计算后的数据。
*   **限制**：不能有任何参数，且必须返回与属性数据类型一致的值。

## 语法规范与代码实现

按照 C# 的编码规范，私有字段通常使用驼峰命名法（camelCase），并且强烈建议加上下划线前缀（如 `_empId`）以标识其为私有成员；而属性名称则必须使用帕斯卡命名法（PascalCase）（如 `EmpId`）。需要注意的是，属性名后不能加小括号，否则会被编译器解析为方法。

```csharp
public class Employee
{
    // 1. 定义私有字段 (Backing Field)
    private int _empId;
    private static string _companyName; // 静态私有字段

    // 2. 实例属性
    public int EmpId
    {
        get { return _empId; }
        set 
        { 
            // 校验逻辑：ID必须大于等于100才允许赋值
            if (value >= 100)
            {
                _empId = value;
            }
            // 补充提示：在严谨的实际开发中，如果传入无效值，
            // 更推荐抛出 ArgumentOutOfRangeException，而不是静默失败。
        }
    }

    // 3. 静态属性
    public static string CompanyName
    {
        get { return _companyName; }
        set 
        {
            // 校验逻辑：公司名称长度不能超过20个字符
            if (value != null && value.Length <= 20)
            {
                _companyName = value;
            }
        }
    }
}
```

### 访问修饰符的独立控制
默认情况下，`get` 和 `set` 访问器的访问级别与属性本身的访问修饰符相同。但 C# 允许为访问器单独指定更加严格的修饰符（Restrictive Access Modifier）。
*   **规则约束**：为访问器单独指定的修饰符必须比属性级别的修饰符更严格。例如，如果属性是 `public` 的，那么 `set` 可以被标记为 `private` 或 `protected`；但如果属性本身是 `internal`，则访问器绝不能是 `public`。

```csharp
public class Car
{
    private string _carBrand;

    // 创建只读属性的常见做法：外部可读，但仅限类内部可以修改
    public string CarBrand
    {
        get { return _carBrand; }
        private set { _carBrand = value; }
    }
}
```

## 自动实现属性
如果一个属性不需要任何自定义的校验逻辑，仅仅是用来读取和写入数据，可以使用 C# 提供的自动实现属性。编译器会在后台自动生成一个隐藏的私有字段，并自动生成基础的 get/set 逻辑。

```csharp
public class Employee
{
    // 自动实现属性，无需手动声明对应的私有字段
    public string Job { get; set; } 
}
```

## 属性与构造函数的作用域区分
对象初始化器（Object Initializer）和类的构造函数在与属性的交互上存在明显区别：

*   **对象初始化器**：本质上是在调用属性的 `set` 访问器，因此一定会触发并执行属性内部的校验逻辑。
    ```csharp
    // 赋值时会触发 EmpId 的 set 验证
    Employee emp = new Employee { EmpId = 101, Job = "Developer" }; 
    ```
*   **构造函数直接赋值**：如果在带参构造函数中直接给**私有字段**赋值，将会绕过属性，导致校验逻辑完全失效。
    ```csharp
    public Employee(int empId)
    {
        _empId = empId; // 危险：直接操作字段，绕过了属性验证！
    }
    ```
    **最佳实践建议**：为了保证单一的数据校验入口，即使在类的内部（如构造函数或普通方法中），也应该优先通过属性来为数据赋值，即 `this.EmpId = empId;`，以复用封装好的验证逻辑。

## 经典名著进阶阅读要点

*   **保持二进制兼容性**（摘自《Effective C#》条款1：始终优先使用属性而非公共数据成员）：
    除了封装和校验，使用属性还能保持程序集的二进制兼容性（Binary Compatibility）。如果早期版本暴露了 `public` 字段，后期为了增加校验将其改为属性，那么所有引用了该字段的外部项目都必须重新编译。因为在底层的 IL (中间语言) 代码中，访问字段和调用方法（属性）的指令是完全不同的。从一开始就使用属性可以彻底避免这种灾难。此外，.NET 中的各种框架特性（如 WPF 的数据绑定、各类序列化机制等）通常也只支持属性。
*   **关于性能损耗的迷思**（摘自《CLR via C#》）：
    虽然属性本质上是方法的调用，但这并不会带来性能负担。现代 .NET 的 JIT（即时编译器）非常智能，对于那些只进行简单赋值和读取的属性（包括自动实现属性），JIT 编译器会将其**内联（Inlining）**。这意味着在运行时的机器码层面，调用这些属性的性能与直接操作底层的公共字段是完全一样的。
