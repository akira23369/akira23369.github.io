# Where (条件筛选)

## 方法名与分类
*   **方法名**：`Where`
*   **分类**：筛选/过滤操作符 (Filtering)

## 签名
`Where` 方法有两个极其常用的重载版本：

*   **标准版本：根据条件过滤元素**
```csharp
public static IEnumerable<TSource> Where<TSource>(
    this IEnumerable<TSource> source, 
    Func<TSource, bool> predicate // 传入一个返回 bool 的条件表达式
);
```
*   **参数**：`predicate` 是测试每个元素是否满足条件的委托。
*   **返回**：`IEnumerable<TSource>`。返回一个**包含所有满足条件元素**的新序列（迭代器）。

*   **带索引版本：不仅知道元素本身，还知道它是第几个（从 0 开始计数）**
```csharp
public static IEnumerable<TSource> Where<TSource>(
    this IEnumerable<TSource> source, 
    Func<TSource, int, bool> predicate // 参数1是元素，参数2是它的索引
);
```
*   **应用场景**：当你需要隔行变色、剔除前 N 个特定元素，或者过滤逻辑强依赖于元素所在的位置时使用。

## 核心逻辑
*   **执行方式：延迟执行 (Deferred Execution)**。（**极度重要！**）当你调用 `Where` 时，它**根本没有开始遍历数据**，也不会执行你的 `predicate`。它仅仅是创建了一个包含了过滤规则的“状态机（查询计划）”。只有当你真正开始消费数据（比如 `foreach`、`.ToList()`、`.Count()`）时，过滤才会真正发生。每一次消费就产生一次过滤
*   **是否流式处理：是 (Streaming)**。它不需要把原集合全部加载到内存中再过滤。它是“按需供给”的，下游要一个，它就从上游找一个符合条件的给过去。非常适合处理无限序列或超大数据流。

## 实战代码
**场景 1：基础用法（过滤出所有有效且未过期的数据）**
```csharp
class Ticket { public string Name; public bool IsActive; public int Price; }

var tickets = new List<Ticket>
{
    new Ticket { Name = "早鸟票", IsActive = false, Price = 100 },
    new Ticket { Name = "普通票", IsActive = true, Price = 150 },
    new Ticket { Name = "VIP票", IsActive = true, Price = 300 }
};

// 筛选出所有处于激活状态，且价格大于 100 的票
var validTickets = tickets.Where(t => t.IsActive && t.Price > 100);

foreach (var t in validTickets)
{
    Console.WriteLine(t.Name); // 输出: 普通票, VIP票
}
```

**场景 2：带索引用法（获取集合中所有奇数位置的元素）**
```csharp
string[] lines = { "Row0", "Row1", "Row2", "Row3", "Row4" };

// index % 2 != 0 表示只要索引为奇数的元素（即第 2、4 行...）
var oddRows = lines.Where((line, index) => index % 2 != 0);

Console.WriteLine(string.Join(", ", oddRows)); 
// 输出: Row1, Row3
```

## 避坑/性能指南
**致命避坑 1：无谓的 `Where` 导致性能下降和 GC 压力**
*   **现象**：新手非常喜欢把 `Where` 当作所有 LINQ 操作的前置条件，写出如下代码：
    *   `list.Where(x => x > 10).Any()`
    *   `list.Where(x => x > 10).First()`
    *   `list.Where(x => x > 10).Count()`
*   **危害**：这会在内存中额外创建一个 `WhereListIterator` 对象。虽然是延迟执行，但平白无故增加了一层包装，浪费了 CPU 周期和垃圾回收 (GC) 资源。
*   **正确做法**：**永远直接使用目标方法的带参重载！**
    *   `list.Any(x => x > 10)`
    *   `list.First(x => x > 10)`
    *   `list.Count(x => x > 10)`

**致命避坑 2：延迟执行引发的“多次重复查询”灾难 (Multiple Enumeration)**
*   **现象**：
    ```csharp
    // 假设这是一个耗时的数据库查询或复杂的计算
    var query = dbContext.Users.Where(u => u.Age > 18);
    
    // 灾难开始：
    if (query.Any()) // 第 1 次触发 SQL 查询：SELECT CASE WHEN EXISTS...
    {
        int count = query.Count(); // 第 2 次触发 SQL 查询：SELECT COUNT(*) ...
        foreach (var u in query)   // 第 3 次触发 SQL 查询：SELECT * ...
        {
            Console.WriteLine(u.Name);
        }
    }
    ```
*   **危害**：由于 `Where` 只是一个“查询计划”，你每对它进行一次求值（Any, Count, foreach），它就会**重新执行一遍**全套的过滤逻辑。如果是查数据库，就是重复发了 3 次网络请求！
*   **正确做法（物化查询结果）**：如果你需要多次使用查询结果，**请立刻在 `Where` 后面加上 `.ToList()` 或 `.ToArray()`**，将结果拉取到内存中固化下来。
    ```csharp
    // 直接查回内存（只查1次）
    var activeUsers = dbContext.Users.Where(u => u.Age > 18).ToList(); 
    // 后续随便怎么用，都是直接读内存，极快
    if (activeUsers.Any()) { ... } 
    ```

**性能指南：过滤条件中可能抛出的 `NullReferenceException`**
*   `Where` 内部的 Lambda 表达式会对每一个元素执行。如果集合中混入了 `null` 元素，或者元素的某个属性为 `null`，很容易在遍历到该元素时引发空引用异常导致程序崩溃。
*   **防雷写法**：使用空条件运算符 `?.`。
    ```csharp
    // 危险：如果有一个 u 是 null，或者 u.Address 是 null，直接崩溃
    // var result = users.Where(u => u.Address.City == "Beijing");
    
    // 安全：优雅地过滤掉那些为 null 的异常数据
    var safeResult = users.Where(u => u?.Address?.City == "Beijing");
    ```
