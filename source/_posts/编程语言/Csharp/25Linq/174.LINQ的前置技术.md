# LINQ的前置技术
很多开发者在使用 LINQ（Language Integrated Query，语言集成查询）时，觉得它像魔法一样神奇：不仅能以极其优雅的链式语法操作集合，还能直接翻译成 SQL 语句操作数据库。

但**LINQ 绝不是凭空出现的魔法**。它是 C# 语言从 1.0 到 3.0 版本中，一系列看似独立、实则环环相扣的底层特性演进而来的“究极融合体”。

## 序言：LINQ 的诞生背景

在 LINQ 出现之前，我们在 C# 中处理数据（比如找出一个数组中所有大于 10 的偶数）通常是这样的：

```csharp
List<int> numbers = new List<int> { 1, 5, 12, 18, 7, 20 };
List<int> result = new List<int>();

foreach (int num in numbers)
{
    if (num > 10 && num % 2 == 0)
    {
        result.Add(num);
    }
}
```
这种代码被称为**命令式编程（Imperative Programming）**，告诉计算机“怎么做”。
而 LINQ 引入了**声明式编程（Declarative Programming）**，告诉计算机“做什么”：

```csharp
var result = numbers.Where(n => n > 10 && n % 2 == 0);
```

为了实现这一句优雅的代码，微软足足铺垫了三个大版本。下面我们开始拆解。

## 第一块基石：迭代器与 `IEnumerable<T>` (C# 1.0 - 2.0)
### `IEnumerable<T>` 接口

要理解 LINQ 的工作原理，首先必须了解 `IEnumerable<T>` 接口。

LINQ 的本质是对**集合**的操作。因此，必须要有一个统一的接口来表示“可遍历的集合”。
- **通用性**：C# 中的绝大多数集合（如 Array 数组, List, HashSet, Dictionary 等）都实现了 `IEnumerable<T>` 接口。
- **核心功能**：该接口的主要作用是**允许使用 foreach 循环遍历集合**。如果一个类型没有实现它，就无法被 foreach 遍历。
- **LINQ 的扩展目标**：绝大部分 LINQ 方法都是针对 `IEnumerable<T>` 编写的扩展方法。这意味着，**无论你使用的是数组、List 还是队列，LINQ 的操作方式完全一致**。
- **只读特性**：`IEnumerable<T>` 接口本身**不包含**任何修改集合的方法（没有 Add、Remove 等）。

### 不修改原集合
因为 `IEnumerable<T>` 没有提供修改集合的方法，所以 **LINQ 绝不会（也无法）修改传入的原始集合**。

即使是像 Append（追加元素）这样的方法，它也不会在原数组上添加元素，而是**创建一个包含新元素的全新型 `IEnumerable<T>` 集合**并返回。
```cs
using System;
using System.Collections.Generic;
using System.Linq;

public class Program
{
    public static void Main()
    {
        int[] numbers = { 1, 2, 3, 4, 5 };

        // 尝试在末尾追加数字 10
        // 注意：Append 返回的是一个新的 IEnumerable<int>
        IEnumerable<int> numbersWith10 = numbers.Append(10);

        Console.WriteLine("--- 原始集合 ---");
        foreach (var n in numbers)
        {
            Console.Write(n + " "); // 输出: 1 2 3 4 5
        }
        Console.WriteLine(); // 换行

        Console.WriteLine("--- 新集合 ---");
        foreach (var n in numbersWith10)
        {
            Console.Write(n + " "); // 输出: 1 2 3 4 5 10
        }
    }
}
```

### 方法链

LINQ 方法有两个极其重要的特征：
1. **输入参数**是 `IEnumerable<T>`。
2. **返回值**也是 `IEnumerable<T>`。

因为输入和输出的类型是一样的，我们就可以把一个 LINQ 方法的结果，直接作为下一个 LINQ 方法的输入。这就是所谓的**方法链（Method Chaining）**。

**阶段一：使用中间变量（非方法链做法）**
假设我们要对一个数字集合进行两步操作：
1. 过滤出所有的**奇数** (Where)
2. 将结果**升序排序** (OrderBy)
```cs
int[] numbers = { 5, 2, 8, 3, 7, 1, 9, 4 };

// 1. 过滤出奇数，保存到中间变量
IEnumerable<int> oddNumbers = numbers.Where(n => n % 2 != 0);

// 2. 对中间变量进行排序，保存到最终变量
IEnumerable<int> orderedOddNumbers = oddNumbers.OrderBy(n => n);

// 输出结果: 1 3 5 7 9
```

**阶段二：使用方法链（优雅的 LINQ 做法）**
我们可以省略中间变量 oddNumbers，直接将方法调用连接起来。这使得代码既紧凑又极具可读性。
```cs
int[] numbers = { 5, 2, 8, 3, 7, 1, 9, 4 };

// 使用方法链 (Method Chaining)
// 通常每个方法单独写一行，增加代码的可读性
var orderedOddNumbers = numbers
    .Where(n => n % 2 != 0)  // 先过滤奇数
    .OrderBy(n => n);        // 再排序

Console.WriteLine("排序后的奇数：");
foreach (var n in orderedOddNumbers)
{
    Console.Write(n + " "); // 输出: 1 3 5 7 9
}
```



### `yield return`语法糖
为了简化迭代器的编写，C# 2.0 引入了**迭代器块（Iterator Block）** 和 `yield return` 关键字。

```csharp
public IEnumerable<int> GetNumbers()
{
    yield return 1;
    yield return 2;
    yield return 3;
}
```
**底层原理：** `yield return` 是一个语法糖。编译器在背后会生成一个**状态机（State Machine）** 类，它实现了 `IEnumerator<T>`，帮你记住了代码执行到哪一步。每次调用 `MoveNext()`，它才会执行到下一个 `yield return`。

**与 LINQ 的联系：** 
这就是 LINQ **延迟执行（Deferred Execution）** 的核心秘密！当你写下 `numbers.Where(...)` 时，由于内部使用了 `yield return`，真正的遍历并不会立即发生，只有当你 `foreach` 或者 `ToList()` 时，数据才会像流水线一样流过。

### 延迟执行
#### 概念
- **什么是延迟执行？**  
    当我们声明一个 LINQ 查询（如 Where, Select）时，**代码并不会立即执行计算**。查询的执行会被推迟（Delayed），直到我们**真正需要这些数据时**（例如在使用 foreach 循环遍历它时）才会发生。
- **什么是物化？**  
    将 LINQ 查询真正执行并把结果提取到内存中的过程称为“物化”。触发物化的常见操作包括：foreach 循环、调用 .ToList(), .ToArray(), .Count() 等。
- **查询只是“指令”而不是“数据”**：  
    我们应该把 LINQ 变量看作是“获取数据的方法/SQL语句”，而不是数据本身。

#### 延迟执行的优势与场景演示
1. **好处 1（数据同步）**：总是基于执行那一刻的最新数据源进行操作。
2. **好处 2（组合拼接）**：可以在最终执行前，像搭积木一样不断追加条件（如 .Take(10)），避免无意义的运算。
3. **好处 3（按需加载）**：流式处理（一边检查一边输出），节省内存和 CPU 资源。

**场景一：始终获取最新数据**
由于查询是在被遍历时才执行的，所以如果在声明查询后、执行查询前，原始数据源发生了改变，LINQ 查询会基于最新的数据进行计算。
```cs
using System;
using System.Collections.Generic;
using System.Linq;

public class Program
{
    public static void Main()
    {
        var words = new List<string> { "a", "bb", "ccc", "dddd" };

        // 1. 声明查询：此时并没有执行过滤操作！它只是一个查询指令。
        IEnumerable<string> shortWords = words.Where(w => w.Length < 3);

        Console.WriteLine("第一次遍历:");
        // 2. 第一次触发延迟执行（物化）
        foreach (var word in shortWords)
        {
            Console.WriteLine(word); // 输出: a, bb
        }

        // 3. 修改原始数据源
        words.Add("e");

        Console.WriteLine("\n第二次遍历:");
        // 4. 第二次触发执行：会重新扫描 words 集合，包含新加入的 "e"
        foreach (var word in shortWords)
        {
            Console.WriteLine(word); // 输出: a, bb, e
        }
    }
}
```

**场景二：强制立即执行 (使用 ToList)**
如果我们想把当前的查询结果“定格”下来，不受后续数据源变化的影响，可以使用 .ToList() 或 .ToArray() 强制立即执行并保存结果。
```cs
var words = new List<string> { "a", "bb", "ccc" };

// 添加 .ToList() 会立即执行查询，并将结果放入一个全新的 List 中
List<string> shortWordsList = words.Where(w => w.Length < 3).ToList();

// 修改原集合
words.Add("e");

// 此时遍历 shortWordsList，不会输出 "e"，因为它已经是固定的数据了。
foreach (var word in shortWordsList)
{
    Console.WriteLine(word); // 仅输出: a, bb
}
```


**场景三：提升性能与“查询进化”**
延迟执行使得我们可以在真正请求数据之前，不断地向查询中追加条件。这在操作庞大数据库时极其重要。
```cs
// 假设这是一个包含 3 亿条记录的庞大数据库源
IEnumerable<Person> people = GetMillionsOfPeopleFromDatabase();

// 步骤 1：创建一个查询（并没有真正去查 3 亿条数据）
var americans = people.Where(p => p.Country == "USA");

// 步骤 2：网页只需要显示前 100 条记录，我们对查询进行“进化/追加”
var pageOne = americans.Take(100);

// 步骤 3：真正执行查询！
// 由于延迟执行，底层引擎只会从数据库中拉取 100 条符合条件的记录，而不是先拉取全部美国人再截取。
foreach (var person in pageOne)
{
    Console.WriteLine(person.Name); 
}
```

**场景四：交织执行  - 底层运行机制**
很多人以为 LINQ 是“先默默把所有数据过滤完，然后再交给 foreach 打印”。实际上并非如此。LINQ 是一边过滤，一边把符合条件的元素直接交给循环（按需执行）。
```cs
using System;
using System.Collections.Generic;
using System.Linq;

public class Program
{
    public static void Main()
    {
        string[] animals = { "Cat", "Dog", "Donkey", "Elephant" };

        // 使用自定义方法进行过滤，方便我们观察执行顺序
        var dAnimals = animals.Where(CheckAnimal);

        Console.WriteLine("开始执行 foreach 循环：");
        foreach (var animal in dAnimals)
        {
            Console.WriteLine($"-> 找到并打印: {animal}\n");
        }
    }

    // 自定义过滤条件的方法
    public static bool CheckAnimal(string name)
    {
        Console.WriteLine($"[底层运行] 正在检查动物: {name}");
        return name.StartsWith("D");
    }
}

/* 
=========== 控制台输出 ===========
开始执行 foreach 循环：
[底层运行] 正在检查动物: Cat
[底层运行] 正在检查动物: Dog
-> 找到并打印: Dog

[底层运行] 正在检查动物: Donkey
-> 找到并打印: Donkey

[底层运行] 正在检查动物: Elephant
=================================
*/
```
核心现象：控制台的输出是交织在一起的。LINQ 检查到 "Dog" 符合条件后，立刻暂停后续检查，把 "Dog" 返回给 foreach 打印；打印完后，再回头继续检查 "Donkey"……这进一步证明了它是“按需推迟执行”的。

## 第二块基石：行为参数化——从委托到 Lambda (C# 1.0 - 3.0)

LINQ 需要能够接收自定义的逻辑（比如 `n > 10` 这种条件）。如何把一段**逻辑（方法）** 当作参数传递呢？

### C# 1.0：委托
委托本质上是类型安全的函数指针。
```csharp
public delegate bool FilterDelegate(int num);

public bool IsGreaterThanTen(int num) { return num > 10; }

// 使用
FilterDelegate filter = new FilterDelegate(IsGreaterThanTen);
```
太啰嗦了！为了传一个简单的逻辑，还得在外面专门写一个具名方法。

### C# 2.0：匿名方法
为了省去写具名方法的麻烦，C# 2.0 允许我们直接在原地写逻辑：
```csharp
FilterDelegate filter = delegate(int num) { return num > 10; };
```

### C# 3.0：Lambda 表达式
C# 3.0 决定将简洁进行到底，去掉了 `delegate` 关键字，引入了 `=>`（Goes to）符号。
```csharp
FilterDelegate filter = (num) => { return num > 10; };
// 甚至可以进一步简写（单行语句省略大括号和 return）
FilterDelegate filter = num => num > 10;
```

同时，.NET 预定义了三大泛型委托：
*   `Action<T>`：无返回值（只做事）。
*   `Func<T, TResult>`：有返回值（常用于数据转换：`Select`）。
*   `Predicate<T>` / `Func<T, bool>`：返回布尔值（常用于条件判断：`Where`）。

我们在 LINQ 中写的 `Where(x => x > 10)`，本质上就是向 `Where` 方法传递了一个 `Func<int, bool>` 的 Lambda 表达式。


### eg
假设没有 LINQ，我们需要自己手写一个类似 Any 的方法来检查集合中是否包含符合特定条件的元素。
**硬编码（代码重复度高）**
如果我们需要检查“是否有大于100的数”和“是否有偶数”，通常会写出两个几乎一样的方法，唯一的区别在于 if 里面的判断条件：
```cs
// 检查是否有大于100的数
public bool IsAnyLargerThan100(int[] numbers)
{
    foreach (var number in numbers)
    {
        if (number > 100) // 唯一不同的地方
        {
            return true;
        }
    }
    return false;
}

// 检查是否有偶数
public bool IsAnyEven(int[] numbers)
{
    foreach (var number in numbers)
    {
        if (number % 2 == 0) // 唯一不同的地方
        {
            return true;
        }
    }
    return false;
}
```

**将函数作为参数传递 (使用 Func)**
为了消除重复代码，我们可以提取一个通用的 IsAny 方法，把“判断条件”作为一个函数传递进去。
在 C# 中，表示具有返回值函数的委托类型是 Func<TInput, TOutput>。
Func<int, bool> 表示：接收一个 int 类型的参数，并返回一个 bool 类型的结果。
```cs
// 通用的检查方法
public bool IsAny(int[] numbers, Func<int, bool> predicate)
{
    foreach (var number in numbers)
    {
        if (predicate(number)) // 执行传入的函数
        {
            return true;
        }
    }
    return false;
}

// 单独定义的判断逻辑方法
public bool IsLargerThan100(int number) { return number > 100; }
public bool IsEven(int number) { return number % 2 == 0; }

// 调用方式：
int[] numbers = { 1, 5, 102, 8 };
bool hasLarge = IsAny(numbers, IsLargerThan100); 
bool hasEven = IsAny(numbers, IsEven);
```


**引入 Lambda 表达式 (终极方案)**
虽然上面解决了通用性问题，但每次为了一个小小的判断去单独定义一个方法（如 IsEven）显得非常累赘。Lambda 表达式允许我们直接在调用的地方写出这段逻辑（匿名函数）。

```cs
// 使用 Lambda 表达式，无需额外定义方法！
int[] numbers = { 1, 5, 102, 8 };

bool hasLarge = IsAny(numbers, number => number > 100);
bool hasEven = IsAny(numbers, number => number % 2 == 0);
```

## 第三块基石：类型系统的进化——泛型与匿名类型 (C# 2.0 - 3.0)

### C# 2.0：泛型
如果没有泛型，我们的集合都是 `ArrayList`，里面全是 `object`。每次操作都需要拆箱、装箱和类型转换，既慢又容易报 `InvalidCastException`。
C# 2.0 引入了 `<T>`，使得我们的 `IEnumerable<T>` 和 `Func<T, bool>` 成为可能。LINQ 从此变得**强类型且高性能**。

### C# 3.0：匿名类型
在 LINQ 的 `Select` 投影操作中，我们经常需要从大对象中提取几个字段，组合成一个新对象：
```csharp
// 选出用户的名字和年龄
var query = users.Select(u => new { u.Name, u.Age });
```
这个 `new { u.Name, u.Age }` 就是**匿名类型**。
**底层原理：** 编译器在编译时，会在背后默默生成一个包含 `Name` 和 `Age` 属性的只读类，重写了 `Equals` 和 `GetHashCode`。这让我们无需专门为查询结果去声明成百上千个 DTO（数据传输对象）类。

## 第四块基石：连接一切的胶水——扩展方法 (C# 3.0)

这是让 LINQ 语法变得“神仙”的关键。

试想一下，如果我们要给 `IEnumerable<T>` 添加 `Where`、`Select` 等方法，传统的面向对象做法是：
1. 修改 `IEnumerable<T>` 的源码（不可能，那是微软的基础库）。
2. 写一个工具类 `EnumerableUtil.Where(list, x => x > 10)`（非常难看，无法实现链式调用）。



### 传统的工具类实现 (EnumerableUtil)

如果没有 LINQ，按照传统的面向对象（比如早期的 Java 风格），我们需要写一个像下面这样的静态工具类：
```cs
using System;
using System.Collections.Generic;

public static class EnumerableUtil
{
    // 自己实现 Where（过滤）
    public static IEnumerable<T> Where<T>(IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (var item in source)
        {
            if (predicate(item))
            {
                yield return item;
            }
        }
    }

    // 自己实现 Select（映射/转换）
    public static IEnumerable<TResult> Select<TSource, TResult>(IEnumerable<TSource> source, Func<TSource, TResult> selector)
    {
        foreach (var item in source)
        {
            yield return selector(item);
        }
    }
}
```

### 调用这个工具类感受痛苦

现在我们要使用上面的工具类来处理数据，通常有两种写法，**但每一种都很让人崩溃**：

#### 写法 A：声明一堆中间变量（啰嗦）

为了避免代码嵌套，你只能每一步都存一个临时变量：
```cs
int[] numbers = { 1, 2, 3, 4, 5, 6, 7, 8 };

// 第1步：过滤出偶数
IEnumerable<int> evens = EnumerableUtil.Where(numbers, n => n % 2 == 0);

// 第2步：将偶数乘以 10
IEnumerable<int> results = EnumerableUtil.Select(evens, n => n * 10);

foreach (var n in results)
{
    Console.WriteLine(n); // 输出 20, 40, 60, 80
}
```
缺点：打断了思维连贯性，产生了一堆像 evens 这样毫无意义的中间变量。如果步骤有 5、6 步，代码简直没法看。

#### 写法 B：洋葱式嵌套调用（反人类的阅读顺序）

如果你不想写中间变量，你想把代码合并在一起，就会变成这样：
```cs
int[] numbers = { 1, 2, 3, 4, 5, 6, 7, 8 };

// 噩梦般的洋葱嵌套代码
IEnumerable<int> results = EnumerableUtil.Select(
    EnumerableUtil.Where(numbers, n => n % 2 == 0), 
    n => n * 10
);
```
**缺点：**
**从内向外读：** 人类正常的阅读习惯是“从左到右”（先 Where，后 Select）。但在嵌套语法中，最外层是 Select，最里层才是 Where。你必须从最内层的括号往外层读，这非常违背直觉。
如果再加上排序（OrderBy）和取前三个（Take），代码会变成可怕的：
Take(OrderBy(Select(Where(numbers, ...), ...), ...), 3)
括号层级多到根本看不清参数属于哪个方法！



### C# 3.0 的破局：扩展方法
它允许你在不修改原有类的情况下，给原有类“挂载”新方法。
语法规则：在静态类中编写静态方法，第一个参数前加上 `this` 关键字。

```csharp
public static class MyExtensions
{
    public static void Print(this string str)
    {
        Console.WriteLine(str);
    }
}
// 使用：
"Hello".Print(); // 编译器会翻译成 MyExtensions.Print("Hello")
```

**与 LINQ 的联系：**
LINQ 的所有 API（`Where`, `Select`, `OrderBy`）全都是定义在 `System.Linq.Enumerable` 这个静态类里的**扩展方法**！

```cs
namespace System.Linq
{
    public static class Enumerable
    {
        // 这是一个扩展方法，扩展了 IEnumerable<T>
        public static IEnumerable<TSource> Where<TSource>(
            this IEnumerable<TSource> source, 
            Func<TSource, bool> predicate)
        {
            // 底层实现细节...
        }
    }
}
```

正因如此，我们才能写出像水流一样丝滑的链式代码：
```csharp
collection
    .Where(x => x > 10)
    .Select(x => x.Name)
    .OrderBy(name => name);
```
*(如果没有扩展方法，上面的代码会变成嵌套地狱：`OrderBy(Select(Where(collection, ...), ...), ...)`)*

## 第五块基石：类型推断与隐式类型 `var` (C# 3.0)

当我们使用匿名类型时，遇到了一个死结：
```csharp
??? result = users.Select(u => new { u.Name, u.Age });
```
等号左边的类型该怎么写？由于等号右边是编译器在编译时生成的匿名类，我们在写代码时根本不知道它叫什么名字（编译器可能会叫它 `<>f__AnonymousType0`）。

### 引入 `var` 关键字
为了解决这个问题，C# 3.0 引入了 `var`。
**注意：`var` 绝不是 JavaScript 中的弱类型/动态类型！**
它是**强类型**的。它只是告诉编译器：“哥们，你看一下等号右边返回的是什么类型，帮我在编译时把 `var` 替换成那个具体的类型。”

因此，结合泛型、匿名类型和扩展方法，完整的语句得以成立：
```csharp
var result = users.Select(u => new { u.Name, u.Age }); 
// 编译器推断 result 为 IEnumerable<<>f__AnonymousType0>
```

## 第六块基石：代码即数据——表达式树 Expression Tree (C# 3.0)

如果 LINQ 只能操作内存里的 `List` 集合（LINQ to Objects），那它顶多算个好用的语法糖。
但 LINQ 的伟大之处在于 **LINQ to SQL / Entity Framework**。它能把 C# 代码转换成 SQL 语句发给数据库！

**思考一个问题：**
```csharp
db.Users.Where(u => u.Age > 18)
```
如果这个 Lambda 编译成了 IL 代码（二进制指令），数据库程序怎么可能看得懂 `u.Age > 18` 的 IL 代码？
为了把 C# 逻辑翻译成 SQL 字符串 `SELECT * FROM Users WHERE Age > 18`，我们需要一种能“拆解、分析”代码逻辑的数据结构。

### 引入 Expression Tree
在 C# 3.0 中，如果你的 Lambda 表达式分配给的是一个 `Expression<Func<T, bool>>` 委托，编译器**不会**把它编译成可执行的机器码，而是把它编译成一棵**描述代码结构的树（抽象语法树 AST）**。

```csharp
Expression<Func<User, bool>> expr = u => u.Age > 18;
```
在运行时，ORM 框架（如 EF Core）会遍历这棵树：
*   左节点：找出了对象 `u` 的属性 `Age`。
*   操作符节点：发现了 `>`（GreaterThan）。
*   右节点：发现了常量 `18`。
*   **翻译引擎：** 拼出字符串 `"WHERE Age > 18"`。

这就是为什么针对数据库的接口是 `IQueryable<T>`，而针对内存集合的接口是 `IEnumerable<T>`。前者接收的是表达式树（Expression），后者接收的是普通委托（Func）。

## 终章：万剑归宗——亲手实现我们自己的 LINQ

经过前面 7 节的铺垫，我们已经掌握了实现 LINQ 的全部武功秘籍。
现在，忘掉 `using System.Linq;`，我们亲手写一个基础版的 LINQ 引擎！

新建一个控制台项目，删除对 `System.Linq` 的引用。

### 实现 MyWhere
基于 **扩展方法** + **迭代器(`yield return`)** + **Func委托**：

```csharp
public static class MyLinqExtensions
{
    // this IEnumerable<T> 实现了扩展方法，所有集合都能点出来
    // Func<T, bool> 接收 Lambda 表达式作为判断逻辑
    public static IEnumerable<T> MyWhere<T>(this IEnumerable<T> source, Func<T, bool> predicate)
    {
        // 防御性编程
        if (source == null) throw new ArgumentNullException(nameof(source));
        if (predicate == null) throw new ArgumentNullException(nameof(predicate));

        // 遍历源数据
        foreach (T item in source)
        {
            // 调用传入的委托逻辑进行判断
            if (predicate(item))
            {
                // yield return 实现延迟执行
                yield return item;
            }
        }
    }
}
```

### 实现 MySelect
基于相同原理，但使用 `Func<TSource, TResult>` 进行类型转换：

```csharp
    public static IEnumerable<TResult> MySelect<TSource, TResult>(
        this IEnumerable<TSource> source, 
        Func<TSource, TResult> selector)
    {
        if (source == null) throw new ArgumentNullException(nameof(source));
        if (selector == null) throw new ArgumentNullException(nameof(selector));

        foreach (TSource item in source)
        {
            // 将数据传入转换逻辑，并 yield 出转换后的结果
            yield return selector(item);
        }
    }
```

### 实现 MyToList
由于 `yield return` 是延迟执行的，我们需要一个方法来触发立即执行：

```csharp
    public static List<T> MyToList<T>(this IEnumerable<T> source)
    {
        if (source == null) throw new ArgumentNullException(nameof(source));

        List<T> list = new List<T>();
        // foreach 会调用 IEnumerator 的 MoveNext()，触发迭代器块的执行
        foreach (T item in source)
        {
            list.Add(item);
        }
        return list;
    }
}
```

### 验收成果

现在，让我们用上 **类型推断(var)**、**匿名类型** 和 **Lambda表达式**，调用我们自己的 LINQ：

```csharp
using System;
using System.Collections.Generic;
// 注意：没有 using System.Linq!

class Program
{
    static void Main()
    {
        // 准备测试数据
        List<User> users = new List<User>
        {
            new User { Id = 1, Name = "Alice", Age = 25 },
            new User { Id = 2, Name = "Bob", Age = 17 },
            new User { Id = 3, Name = "Charlie", Age = 30 }
        };

        // 见证奇迹的时刻
        var query = users
            .MyWhere(u => u.Age >= 18)                      // Lambda + 泛型 Func
            .MySelect(u => new { u.Name, IsAdult = true })  // 匿名类型 + 泛型 Func
            .MyToList();                                    // 触发执行

        // 输出结果
        foreach (var item in query)
        {
            Console.WriteLine($"Name: {item.Name}, Adult: {item.IsAdult}");
        }
    }
}

class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public int Age { get; set; }
}
```

**运行结果：**
```text
Name: Alice, Adult: True
Name: Charlie, Adult: True
```

## 总结：编程语言的进化美学

现在回过头来看，LINQ 绝不是拍脑袋想出来的特性，它是一场长达多年的蓄谋已久：

1. 为了解决遍历麻烦，引入了 **`yield return` (迭代器)**。
2. 为了传递代码逻辑，引入了 **委托**，再简化为 **匿名方法**，最终进化为 **Lambda 表达式**。
3. 为了保证类型安全且通用，引入了 **泛型**。
4. 为了不改动原类还能链式调用，引入了 **扩展方法**。
5. 为了解决新对象定义的繁琐，引入了 **匿名类型**，并用 **`var`** 解决类型命名的死结。
6. 为了让逻辑能翻译给数据库，引入了 **表达式树 (Expression Tree)**。

当这 6 块拼图在 C# 3.0 中完美结合时，**LINQ** 就诞生了。
