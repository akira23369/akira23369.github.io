# where (查询语法中的条件筛选)

## 语法格式与映射
*   **关键字**：`where`
*   **表达式要求**：后面必须紧跟一个返回 `bool` 类型结果的表达式。
*   **底层映射**：编译器会将其 100% 翻译为方法语法中的 `.Where(x => ...)`。
*   **支持多重条件**：可以直接使用 C# 的逻辑运算符 `&&` (与)、`||` (或)、`!` (非)。
*   **支持多次叠加**：在一个查询中，你可以写**任意多个** `where` 子句，它们会被翻译成链式调用的多个 `.Where().Where()`。

## 核心逻辑
*   **执行方式**：**延迟执行 (Deferred Execution)**。
*   **是否流式处理：是 (Streaming)**。按需获取，逐个判断。条件返回 `true` 的元素放行到下一环节，返回 `false` 的元素直接丢弃。

## 实战代码
**场景 1：单条件与多条件组合**
```csharp
class Product { public string Name; public decimal Price; public bool IsInStock; }

var products = new List<Product>
{
    new Product { Name = "Laptop", Price = 8000m, IsInStock = true },
    new Product { Name = "Mouse", Price = 150m, IsInStock = true },
    new Product { Name = "Keyboard", Price = 300m, IsInStock = false }
};

// 需求：找出有库存，且价格在 100 到 500 之间的商品
var affordableQuery = 
    from p in products
    // 直接使用 C# 的 && 组合多个条件
    where p.IsInStock && p.Price >= 100m && p.Price <= 500m 
    select p.Name;

// 输出: Mouse
```

**场景 2：多个 `where` 子句的叠加**
有时候为了让代码逻辑分层（比如先排除废数据，再进行业务筛选），可以写多个 `where`，效果等同于用 `&&` 连接。
```csharp
var multiWhereQuery = 
    from p in products
    where p.IsInStock      // 步骤 1：先砍掉没库存的
    where p.Name.StartsWith("L") // 步骤 2：在有库存的基础上，找 L 开头的
    select p;
// 底层会被翻译为：products.Where(p => p.IsInStock).Where(p => p.Name.StartsWith("L"));
```

**场景 3：结合 `let` 过滤计算结果 (查询语法的神级应用)**
如果你要根据某个**动态计算出来的值**进行过滤，在方法语法中需要嵌套，在查询语法中配合 `let` 简直像呼吸一样自然。
```csharp
// 需求：打 8 折后，价格仍然大于 5000 的商品
var discountQuery = 
    from p in products
    let finalPrice = p.Price * 0.8m // 1. 先计算出折后价，存入临时变量
    where finalPrice > 5000m        // 2. 直接拿临时变量做过滤！
    select new { p.Name, FinalPrice = finalPrice };
```

## 避坑/进阶指南
**致命避坑 1：`where` 与 `orderby` / `let` 的顺序决定了生死 (性能核弹)**
*   **现象**：与严谨的 SQL 不同（SQL 强制 WHERE 必须在 ORDER BY 前面），LINQ 查询语法极其自由，**它允许你把 `where` 写在任何地方**。
*   **错误写法（性能灾难）**：
    ```csharp
    var badQuery = 
        from p in products
        orderby p.Price descending // 💣 灾难：先把 100 万条数据全部查出来并在内存里进行耗时的全局排序！
        where p.Price > 1000m      // 然后才过滤出符合条件的 10 条数据...
        select p;
    ```
*   **错误写法 2（无谓的计算）**：
    ```csharp
    var badQuery2 = 
        from p in products
        let complexHash = ComputeHeavyHash(p) // 💣 灾难：给 100 万条废数据也执行了极度耗时的计算！
        where p.IsInStock
        select new { p.Name, Hash = complexHash };
    ```
*   **黄金法则：尽早过滤！永远把 `where` 写在 `from` 的紧跟后面，尽最大可能把数据量降到最低，然后再执行 `let` 计算或 `orderby` 排序！**
    ```csharp
    // ✅ 性能最优的顺序
    var goodQuery = 
        from p in products
        where p.IsInStock      // 1. 最先过滤，100万条变 10条
        let hash = Compute(p)  // 2. 只算 10 次
        orderby p.Price        // 3. 只排 10 条数据
        select p;
    ```

**致命避坑 2：`where` 内部的 `NullReferenceException` 崩溃**
*   这在方法语法的 `Where` 中提到过，在查询语法中同样适用。如果条件链条中某个属性可能是 `null`，必须使用空条件运算符 `?.` 或显式判空。
    ```csharp
    // 危险：如果 user.Address 是 null，直接崩溃
    // where user.Address.City == "Beijing" 
    
    // 安全：优雅防空
    where user.Address?.City == "Beijing"
    ```

**进阶对比：多个 `where` 连写 vs 一个 `where` 配合 `&&`**
*   `where A where B` 会被翻译成 `.Where(A).Where(B)`。
*   `where A && B` 会被翻译成 `.Where(A && B)`。
*   **性能差异**：在 LINQ to Objects (内存集合) 中，`A && B` 的性能**略好于** `where A where B`，因为它少创建了一个底层的状态机迭代器。但在 EF Core 等数据库查询中，两者最终都会被翻译成同一句 SQL (`WHERE A AND B`)，性能没有任何区别。
*   **建议**：如果是同一层面的逻辑，用 `&&` 连起来更紧凑；如果是不同层面的宏观过滤（比如先排除软删除数据，再做业务判定），可以分多行书写以提高可读性。
