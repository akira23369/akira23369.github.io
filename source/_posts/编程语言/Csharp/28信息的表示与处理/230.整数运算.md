# 整数运算

## 无符号加法：溢出后的回绕

### 汽车里程表效应
想象一辆老式汽车的机械里程表，它最多只能显示 4 位数（`0000` 到 `9999`）。
当你开到 `9999` 公里时，再往前开 1 公里，里程表会发生什么？它不会显示 `10000`，而是“咔哒”一声，全部清零，变成了 `0000`。

在计算机中，这就是**无符号加法的溢出（Overflow）**，或者叫**回绕（Wrap-around）**。
因为寄存器的宽度是固定的（比如 32 位），它装不下第 33 位。**计算机的处理方式极其粗暴：直接把多出来的最高位像剪指甲一样剪掉扔进垃圾桶！**

### 数学本质：模运算
对于字长为 $w$ 的无符号数，加法的本质是计算：
$$(x + y) \pmod{2^w}$$
这解释了为什么 $255 + 1 = 0$ （在 8 位系统下，$2^8 = 256$，所以 $(255+1) \pmod{256} = 0$）。

### 如何判定无符号溢出？
在写底层 C 代码时，你怎么知道刚才的加法溢出了？
很简单：**如果你把两个正数加起来，结果居然比其中任何一个数都小，那就是溢出了！**

### C# 代码演示：无符号的回绕
```csharp
using System;

public class UnsignedAdditionDemo
{
    public static void Run()
    {
        Console.WriteLine("=== 1. 无符号加法：回绕 (Wrap-around) ===");
        
        // 我们使用 byte (8位无符号整数)，最大值是 255
        byte x = 250;
        byte y = 10;
        
        Console.WriteLine($"x = {x}, y = {y}");
        
        // 在 C# 中，byte 的加法默认会转换为 int 计算以防溢出。
        // 为了逼真模拟 CSAPP 中 8位 CPU 的行为，我们强转回 byte 并用 unchecked 关掉保护
        unchecked 
        {
            byte result = (byte)(x + y);
            Console.WriteLine($"CPU 计算 x + y 的结果: {result}");
            
            // 为什么是 4？
            // 250 + 10 = 260。
            // 260 的二进制是 1 0000 0100 (9位)。
            // 强行塞进 8位的 byte 中，最高位的 1 被无情剪掉。
            // 剩下 0000 0100，十进制就是 4！
            
            // 溢出检测逻辑
            if (result < x) 
            {
                Console.WriteLine("警告：检测到无符号加法溢出！(结果比加数还要小)");
            }
        }
    }
}
```

## 补码加法：正溢出与负溢出

这是 CSAPP 中最震撼的场景。还记得上一节的“债务与资产”吗？最高位（符号位）是超级债务。

### 什么是正溢出？
想象一个 32 位的系统，你能表示的最大正数是 `2147483647`（也就是 `0111 1111 ... 1111`，没有债务，全是资产）。
如果你在这个数上再加 `1` 呢？
二进制进位像多米诺骨牌一样，一路推到了最高位。结果变成了 `1000 0000 ... 0000`。
还记得吗？**最高位一旦变成 1，它就变成了巨大的债务！**
所以，$2147483647 + 1 = -2147483648$。

**这叫正溢出：两个巨大的正数相加，结果突变成了一个巨大的负数。**（你赚了太多的钱，系统突然判定你欠了银行二十亿）。

### 什么是负溢出？
反过来，如果你有两个巨大的负数（债务）相加，比如 `-2147483648 + (-1)`。
两个最高位的 `1` 相加，产生进位。进位被无情地剪掉扔出了寄存器！
留在寄存器里的最高位变成了 `0`（债务被抹除了！）。
结果变成了 `2147483647`。

**这叫负溢出：两个巨大的负数相加，结果突变成了一个巨大的正数。**（你欠了太多钱，系统突然判定你是世界首富）。

### 溢出判定黄金法则
*   **正 + 正 = 负** $\rightarrow$ 发生了正溢出！
*   **负 + 负 = 正** $\rightarrow$ 发生了负溢出！
*   **正 + 负** $\rightarrow$ **绝对不可能溢出！** （一正一负相加，结果一定会向 0 靠拢，绝对不会突破最大或最小边界）。

### C# 代码演示：天堂与地狱的瞬间翻转

```csharp
using System;

public class TwoComplementAdditionDemo
{
    public static void Run()
    {
        Console.WriteLine("\n=== 2. 补码加法：正溢出与负溢出 ===");
        
        int maxPos = int.MaxValue; // 2147483647
        int minNeg = int.MinValue; // -2147483648
        
        unchecked 
        {
            // 1. 演示正溢出
            int positiveOverflow = maxPos + 1;
            Console.WriteLine($"最大正数: {maxPos}");
            Console.WriteLine($"最大正数 + 1 = {positiveOverflow} (正溢出，变成了最小负数！)");
            
            // 2. 演示负溢出
            int negativeOverflow = minNeg + (-1);
            Console.WriteLine($"\n最小负数: {minNeg}");
            Console.WriteLine($"最小负数 + (-1) = {negativeOverflow} (负溢出，变成了最大正数！)");
            
            // 黑客级的 C 语言溢出检测写法：
            int a = 1500000000;
            int b = 1500000000;
            int sum = a + b;
            
            // 如果 a > 0 且 b > 0，但 sum < 0，则判定为正溢出
            bool isPosOverflow = (a > 0) && (b > 0) && (sum < 0);
            Console.WriteLine($"\n计算 {a} + {b}:");
            Console.WriteLine($"结果是 {sum}。是否发生正溢出？ {isPosOverflow}");
        }
    }
}
```

## 补码的非：一个打破常理的数学异常

在数学中，任何数都有相反数，且 $-(-x) = x$。比如 $5$ 的相反数是 $-5$。
但在计算机的补码系统中，有一个极其恐怖的**异常值（Anomaly）**。

### 怎么求相反数？
计算机怎么算一个数的相反数（比如 `5` 变成 `-5`）？
CSAPP 给出了一个极其优雅的公式：**按位取反，再加一 (`~x + 1`)**。
*   `5` 是 `0000 0101`
*   取反 `~`：`1111 1010`
*   加 `1`：`1111 1011` （这就是 `-5` 在补码中的表示）

### 最小负数 (`TMin`) 的诅咒
在 32 位系统中，最小负数 `TMin` 是 `-2147483648`，它的二进制是 `1000 ... 0000`。
它的相反数应该是谁？是正的 `2147483648` 吗？
**错！32 位系统最大只能表示正的 `2147483647`（因为 0 占了一个名额）。补码系统根本无法表示 `+2147483648`！**

那计算机算 `-TMin` 会得到什么？让我们用公式算一下：
*   原数字 `TMin`: `1000 ... 0000`
*   取反 `~`：`0111 ... 1111`
*   加 `1`：`1000 ... 0000`

**天哪！兜兜转转，它又变回了自己！**
在补码系统中，**最小负数的相反数，依然是最小负数它自己！**

### C# 代码演示：见证 TMin 的诅咒

```csharp
using System;

public class NegationDemo
{
    public static void Run()
    {
        Console.WriteLine("\n=== 3. 补码的非：最小负数的诅咒 ===");
        
        int normalNumber = 5;
        int tMin = int.MinValue; // -2147483648
        
        unchecked
        {
            // 普通数字的相反数
            int negNormal = -normalNumber;
            Console.WriteLine($"数字 {normalNumber} 的相反数是: {negNormal}");
            
            // 揭示底层公式：~x + 1
            int bitwiseNegNormal = ~normalNumber + 1;
            Console.WriteLine($"使用 ~x+1 计算 {normalNumber} 的相反数: {bitwiseNegNormal}");

            // TMin 的诅咒
            Console.WriteLine($"\nTMin (最小负数) 是: {tMin}");
            int negTMin = -tMin;
            Console.WriteLine($"对 TMin 求相反数 (-TMin) 的结果是: {negTMin}");
            
            if (tMin == -tMin)
            {
                Console.WriteLine("震惊！-x 居然等于 x！(仅在 x 为最小负数 或 0 时成立)");
            }
        }
    }
}
```
**忠告：** 如果你写一个 `abs(x)`（求绝对值）的函数，如果传入 `TMin`，它返回的绝对值**依然是负数**！这曾经导致过无数的金融和游戏系统的崩溃。

## 乘法与除法：编译器的“降维打击”性能黑客

在老式的 CPU 中，加法只需要一个时钟周期，但乘法可能需要 10 个周期，而**除法（世界上最慢的整数运算）可能需要 30 个周期！**

高级程序员追求的是算法的时间复杂度（$O(N)$），但编译器（黑客）追求的是每一条汇编指令的榨干。CSAPP 用大篇幅告诉我们：**永远尝试用位移（Shift）和加减法，去替代乘除法。**

### 乘以 $2$ 的幂：左移 `<<`
这个很简单。
$x * 2^k$ 等价于 `x << k`。
比如 $x * 14$。$14 = 8 + 4 + 2 = 2^3 + 2^2 + 2^1$。
编译器会把 `x * 14` 优化成：`(x << 3) + (x << 2) + (x << 1)`。
虽然看起来变长了，但 CPU 执行位移加法的速度，远远秒杀笨重的乘法器。

### 除以 $2$ 的幂：右移 `>>`（与偏置 Biasing 的抢救）
除法比乘法难搞得多。
对于**无符号数**，除以 $2^k$ 很简单，直接**逻辑右移 `>>>`**（左边补 0）即可。

但是对于**有符号的负数**，问题来了！除法是有**舍入（Rounding）** 的。
在 C/C# 中，整数除法 `-3 / 2`，结果必须是 `-1`。（这叫**向 0 舍入**）。

但是，如果我们在 CPU 底层直接对 `-3` 执行算术右移（`>> 1`）会怎样？
*   `-3` 的二进制是 `1111 ... 1101`。
*   算术右移一位： `1111 ... 1110`。
*   查一下补码表，`1111 ... 1110` 是 **`-2`**！
*   `-3 / 2` 变成了 `-2`！计算机向负无穷方向舍入了！这就和标准的除法规则违背了。

### 天才的偏置技术 (Biasing)
为了解决负数右移时舍入方向错误的问题，科学家发明了**偏置（Biasing）** 技术。
规则是：**如果是负数除以 $2^k$，在右移之前，先在原数字上加上 $(2^k - 1)$ 的偏移量。**

用上面的例子：`-3 / 2`（$k=1$）
*   先加偏置：$2^1 - 1 = 1$。
*   `-3 + 1 = -2`。
*   对 `-2` 进行右移 `1` 位：`-2` (`1111 ... 1110`) $\rightarrow$ `1111 ... 1111` (`-1`)。
*   结果奇迹般地变成了正确的 **`-1`**！

偏置的本质是：给负数加上一点点“垫脚石”，如果它恰好不能整除，这个垫脚石就能把它“托”过整数边界，使得除法的截断效果恰好等于“向0舍入”。

拿正数来类比就是，`10 / 3 = 3`, 如果想往大的方向取整就是`10 / 3 = 4`的话，就得加
`10 + (3 - 1) / 3 = 4`

### C# 代码演示：右移除法与偏置技术

```csharp
using System;

public class MultiplicationDivisionDemo
{
    public static void Run()
    {
        Console.WriteLine("\n=== 4. 乘法与除法：位移黑客优化 ===");
        
        int x = 50;
        
        // 1. 乘法优化
        Console.WriteLine("--- 乘法优化 ---");
        int mul = x * 12; // 12 = 8 + 4 = 2^3 + 2^2
        int optimizedMul = (x << 3) + (x << 2);
        Console.WriteLine($"{x} * 12 = {mul}");
        Console.WriteLine($"等价优化 (x << 3) + (x << 2) = {optimizedMul}");

        // 2. 除法：正数右移
        Console.WriteLine("\n--- 正数除法 ---");
        int pos = 11;
        Console.WriteLine($"普通除法: 11 / 4 = {pos / 4}");
        Console.WriteLine($"直接右移: 11 >> 2 = {pos >> 2}"); // 正确，向0舍入

        // 3. 除法：负数右移与偏置技术
        Console.WriteLine("\n--- 负数除法 (解决向下舍入问题) ---");
        int neg = -11;
        Console.WriteLine($"普通除法要求向0舍入: -11 / 4 = {neg / 4}"); // 结果应为 -2
        
        int wrongShift = neg >> 2; 
        Console.WriteLine($"直接算术右移: -11 >> 2 = {wrongShift} (错误！向负无穷舍入变成了 -3)");
        
        // 使用偏置技术修复 (k = 2, 偏置量 = 2^2 - 1 = 3)
        int k = 2;
        int bias = (1 << k) - 1; // 生成偏置量 3
        int fixedShift = (neg + bias) >> k;
        Console.WriteLine($"使用偏置修复后: (-11 + 3) >> 2 = {fixedShift} (完美修复！)");
        
        // 现代编译器底层的除以 2^k 汇编逻辑：
        // 如果 x < 0，加偏置；否则不加偏置。然后再算术右移。
    }
}
```

## 终极总结与执行入口

这章 CSAPP 的核心在告诉你一个极其重要的工程真理：**“永远不要盲目相信算术运算的安全”。**

在高级语言的安乐窝里，我们常常以为 `a + b` 是真理。但今天你看到了：
1. **加法会变成减法**（溢出回绕）。
2. **正数会变成负数**（正溢出）。
3. **负数会变成正数**（负溢出）。
4. **求绝对值后竟然还是负数**（`TMin` 的诅咒）。
5. **除法居然不等于右移**（负数除法引发的偏置技术）。

这一切看似是 Bug，实则都是**二进制补码与有限字长结合后的必然数学规律。** 优秀的程序员（比如写内核、写游戏物理引擎、写加密算法的人），必须精通这种“表盘上的数学”，利用位移榨干性能，并设下层层检测防止溢出的灾难。
