如果说前面的整数（补码）是在教你如何用极度精确、一成不变的砖块搭建金字塔，那么现在的浮点数，就是在教你**如何用有限的画笔，去描绘广袤无垠、且可以无限细分的真实宇宙。**

在现实世界里，从原子的直径（极小）到星系的距离（极大），我们需要表示的数值跨度是恐怖的。更糟糕的是，实数是无限连续的（比如 1 和 2 之间有无数个小数）。**但我们的寄存器只有可怜的 32 位或 64 位。**

IEEE 754 浮点数标准，是计算机科学史上最精妙的妥协，也是一次天才的黑客行为。它成功用极其有限的比特，完美模拟了连续宇宙的错觉。但这套机制极其复杂，且充满了违背常理的数学陷阱。

# 浮点数

## 基础预热：二进制小数

在认识浮点数之前，我们先得搞懂：二进制怎么表示小数？
在十进制里，小数点右边的权重是 $10^{-1}$ (0.1), $10^{-2}$ (0.01)...
在二进制里，完全一样！小数点右边的权重是 **$2^{-1}$ (0.5), $2^{-2}$ (0.25), $2^{-3}$ (0.125)...**

*   `10.1` (二进制) = $2^1 + 0 + 2^{-1}$ = $2 + 0.5$ = **`2.5`** (十进制)
*   `0.11` (二进制) = $2^{-1} + 2^{-2}$ = $0.5 + 0.25$ = **`0.75`** (十进制)

**第一个致命缺陷出现了：**
二进制小数只能极其精确地表示那些能够拆分成 $\frac{1}{2}, \frac{1}{4}, \frac{1}{8}$ 等分数之和的数字。
像十进制的 **`0.1`** 或者是 **`0.2`**，在二进制世界里是**无限循环小数**！这就注定了浮点数从诞生起，就带有**先天性的精度丢失**。

---

## IEEE 754 标准：计算机里的“科学计数法”

把小数全塞进固定位置是行不通的（那叫定点数）。为了应对宇宙级的跨度，IEEE 制定了类似科学计数法的终极公式：

$$V = (-1)^s \times M \times 2^E$$

这三个字母代表了浮点数的灵魂：
1.  **符号位 ($s$, Sign)**：决定是正数 ($s=0$) 还是负数 ($s=1$)。
2.  **尾数 ($M$, Significand/Mantissa)**：一个大于等于 1、小于 2 的纯小数（比如 1.234）。它决定了数字的**精度**。
3.  **阶码/指数 ($E$, Exponent)**：2 的几次方。它决定了数字的**大小范围**。

### 内存布局（这 32 个抽屉怎么分配？）
在 C# 的 `float` (单精度 32位) 中，内存被死死切成了 3 段：
*   **$s$ (1 位)**：第 31 位。
*   **$exp$ (8 位)**：第 23~30 位。用于计算阶码 $E$。
*   **$frac$ (23 位)**：第 0~22 位。用于计算尾数 $M$。

对于 `double` (双精度 64位)：$s$(1位), $exp$(11位), $frac$(52位)。

## 根据 $exp$ 划分的四个世界

浮点数不是一套规则走到底的，根据中间那 8 位的 $exp$（指数位）的不同，浮点数被分为了四个完全不同的“门派”。**这正是 IEEE 754 最天才的地方。**

### 规格化的值 —— 绝大部分日常数值
**条件：** $exp$ 既不是全 0 (`00000000`)，也不是全 1 (`11111111`)。

这里有两个极其骚气的黑客级设计：

1.  **指数的偏置 (Biasing)**：
    $exp$ 有 8 位，当成无符号数看是 1 到 254。但是我们要表示负指数（极小的数）和正指数（极大的数）怎么办？
    IEEE 规定：$E = exp - Bias$ (偏置量)。
    对于 32 位 float，$Bias = 127$。
    所以，如果 $exp$ 是 `128`，那么真实指数 $E = 128 - 127 = 1$。
    如果 $exp$ 是 `100`，那么真实指数 $E = 100 - 127 = -27$。

2.  **隐藏的 1 (Implied leading 1)**：
    既然是科学计数法，尾数 $M$ 永远是 $1.xxxxx$。既然永远是以 1 开头，**那我为什么还要浪费 1 个比特把它存进内存呢？**
    天才！IEEE 规定，$M = 1 + f$（$f$ 就是内存里的 $frac$ 位）。
    这就等于 **“花 23 位的钱，买到了 24 位的精度！”** 

### 非规格化的值
**条件：** $exp$ 是全 0 (`00000000`)。

当我们想表示极其接近 0 的数字，甚至就是真实的 `0.0` 时，第一门派失效了（因为它永远自带一个隐藏的 1，永远不能表示绝对的 0）。
此时系统自动切换到“显微镜模式”：
1.  **真实的 0**：如果 $exp$ 为 0，且 $frac$ 也全为 0，这才是真正的 `0.0`！（而且因为符号位的存在，浮点数有 `+0.0` 和 `-0.0` 两个零）。
2.  **没有隐藏的 1**：$M = f$ （不再加 1 了）。
3.  **平滑过渡（逐渐下溢）**：此时指数固定为 $E = 1 - Bias = -126$。这保证了非规格化数字能够平滑地衔接到规格化数字的最小边界，不会产生突然断裂的鸿沟。

### 特殊值
**条件：** $exp$ 是全 1 (`11111111`)。

1.  **无穷大 (Infinity)**：当 $frac$ 全为 0 时。表示这个数字大到寄存器爆炸了。
    比如，`1.0 / 0.0` 在浮点运算中**不会崩溃**，它会得到正无穷（`+Infinity`）。
2.  **不是一个数 (NaN, Not a Number)**：当 $frac$ 不全为 0 时。
    比如，你试图计算 $\sqrt{-1}$，或者 `Infinity - Infinity`，计算机会返回 `NaN`，意思是：“算不出来了，毁坏了，别管我”。

## C# 代码实战：查看Float

文字太抽象，让我们写一段极其硬核的 C# 代码。我们将输入一个 `float`，扒开它 32 位的皮囊，将它底层的 $s$、$exp$ 和 $frac$ 抽丝剥茧地展示出来！

```csharp
using System;

public class FloatAnatomyDemo
{
    public static void Run()
    {
        Console.WriteLine("=== 1. 像外科医生一样解剖 Float ===");
        
        // 尝试不同的数字，看看它们的底层表现
        // float target = 15.25f; // 可以试着改这些数字: 0.15625f, 0.0f, -0.0f, float.PositiveInfinity
        float target = 0.15625f; // 1/8 + 1/32
        
        // C# 高级技巧：通过 BitConverter 将浮点数的内存原封不动转为整数，方便按位操作
        int bits = BitConverter.SingleToInt32Bits(target);

        // 使用掩码提取三大部分
        int s = (bits >> 31) & 1;                   // 提取最高位
        int exp = (bits >> 23) & 0xFF;              // 提取中间8位
        int frac = bits & 0x7FFFFF;                 // 提取尾部23位

        Console.WriteLine($"观察目标数值: {target}");
        Console.WriteLine($"32位二进制: {Convert.ToString(bits, 2).PadLeft(32, '0')}");
        Console.WriteLine($"符号位 (s): {s}");
        Console.WriteLine($"阶码   (exp): {exp} (二进制: {Convert.ToString(exp, 2).PadLeft(8, '0')})");
        Console.WriteLine($"尾数   (frac): {frac} (二进制: {Convert.ToString(frac, 2).PadLeft(23, '0')})");

        // 解释含义 (假设它是规格化数)
        if (exp > 0 && exp < 255)
        {
            int E = exp - 127;
            double M = 1.0 + (frac / Math.Pow(2, 23));
            Console.WriteLine("\n此为【规格化的值】：");
            Console.WriteLine($"真实指数 E = {exp} - 127 = {E}");
            Console.WriteLine($"真实尾数 M = 1.0 + (frac / 2^23) = {M}");
            double realValue = Math.Pow(-1, s) * M * Math.Pow(2, E);
            Console.WriteLine($"验算公式: (-1)^{s} * {M} * 2^{E} = {realValue}");
        }
        else if (exp == 255)
        {
            Console.WriteLine("\n此为【特殊值】(Infinity 或 NaN)");
        }
        else if (exp == 0)
        {
            Console.WriteLine("\n此为【非规格化的值】(极小值或0)");
        }
    }
}
```

## 舍入规则：为什么计算机“向偶数舍入”？

浮点数的尾数是有限的（23位），就像你试图在一个小盒子里装下整个太平洋，大部分水只能被溢出舍弃（Rounding）。

我们小学学的是“四舍五入”（逢 5 进 1）。
**但 IEEE 754 默认使用的是：“向偶数舍入 (Round-to-even)”。**
意思是：如果要舍弃的部分刚好是正中间（比如 `1.5`, `2.5`），那就向最靠近的**偶数**靠拢。
*   `1.5` $\rightarrow$ `2.0`
*   `2.5` $\rightarrow$ `2.0` （注意，没有变成 3.0！）

**为什么要这么奇葩？**
这是因为统计学偏差！如果我们在海量数据运算中，遇到 `0.5` 总是无脑向上舍入（四舍五入），那么所有中间值的舍入误差全是正数。经过几千万次累加后，结果会比真实值大得多！
“向偶数舍入”非常聪明地让 50% 的几率向上舍入，50% 的几率向下舍入，从而在统计学上把误差完美地**抵消**了！

### C# 代码演示：舍入的真相
在 C# 中，原生的 `Math.Round` 完美继承了 IEEE 标准，默认就是向偶数舍入（即 Bank's Rounding 银行家舍入法）。

```csharp
using System;

public class RoundingDemo
{
    public static void Run()
    {
        Console.WriteLine("\n=== 2. 舍入：奇葩但科学的“向偶数舍入” ===");
        
        double num1 = 1.5;
        double num2 = 2.5;

        Console.WriteLine($"Math.Round({num1}) = {Math.Round(num1)}");
        Console.WriteLine($"Math.Round({num2}) = {Math.Round(num2)}  <-- 看看！它向下变成了偶数 2！");
        
        // 如果你强迫症，非要小学教的四舍五入，你需要额外传参：
        Console.WriteLine($"Math.Round({num2}, MidpointRounding.AwayFromZero) = {Math.Round(num2, MidpointRounding.AwayFromZero)} (小学算法)");
    }
}
```

## 浮点运算的陷阱：被粉碎的结合律

**这是无数新手程序员掉入的无底深渊，也是 CSAPP 给我们的最沉重警告。**

在数学中，加法结合律永远成立：$(a + b) + c = a + (b + c)$。
但在计算机的浮点数中，**结合律被彻底粉碎！**

想象一下，你有一个天文级的巨大数字（比如宇宙的直径），然后你给它加上一粒沙子的大小，然后再减去这个宇宙的直径。按理说，结果应该等于一粒沙子，对吧？

错！当你把沙子加给宇宙时，由于浮点数的尾数容量有限，为了能够把指数“对齐”，沙子的那一点点微末数据会被**无情地推出尾数范围，直接丢弃（被大海吞噬了）**。

### C# 代码演示：浮点黑洞效应

```csharp
using System;

public class FloatAssociativityDemo
{
    public static void Run()
    {
        Console.WriteLine("\n=== 3. 浮点陷阱：结合律的崩塌与精度黑洞 ===");
        
        float a = 3.14f;
        float huge = 1e20f;   // 10 的 20 次方，极其巨大的数
        float minusHuge = -1e20f;

        // 场景 1：先算大数加减 (huge + minusHuge 互相抵消为 0)
        float result1 = a + (huge + minusHuge);
        Console.WriteLine($"场景1: 3.14 + (1e20 - 1e20) = {result1}");

        // 场景 2：按照从左到右执行 (3.14 先加上 1e20)
        float result2 = (a + huge) + minusHuge;
        Console.WriteLine($"场景2: (3.14 + 1e20) - 1e20 = {result2}");
        
        if (result1 != result2)
        {
            Console.WriteLine("\n震惊！加法结合律失效！");
            Console.WriteLine("原因：在计算 (3.14 + 1e20) 时，3.14 相对于 1e20 太小了，");
            Console.WriteLine("它的有效位直接被【截断/舍弃】了！等价于 1e20 + 0。");
            Console.WriteLine("所以随后减去 1e20 时，结果变成了 0！");
        }

        Console.WriteLine("\n这也解释了为什么金融系统算钱【绝对不能用 float/double】，必须用 decimal！");
        Console.WriteLine($"试试 0.1 + 0.2 == 0.3？结果是：{(0.1 + 0.2 == 0.3)} (因为 0.1 和 0.2 在二进制里是无限循环，产生了误差)");
    }
}
```

**CSAPP 工程原则：**
1. 判断两个浮点数是否相等，**永远、永远不要使用 `==`**。必须计算它们的差的绝对值是否小于一个极小值 `epsilon`（如 `Math.Abs(x - y) < 1e-6`）。
2. 把大数字和小数字相加时，要万分小心。如果有大量数字求和，应该**先把所有小数字加起来，最后再去加那个极大的数字**，这样能将精度丢失降到最低。
