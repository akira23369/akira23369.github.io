# NullableTypes可空类型

在C#的类型系统中，理解值类型（Value Types）与引用类型（Reference Types）的区别是掌握可空类型的基础。

## 值类型与引用类型的默认行为

C# 中的所有数据类型均可归为两大类：
*   **值类型（Value Types）：** 包含所有的结构体（`struct`，如 `int`, `double`, `DateTime`）和枚举（`enum`）。值类型直接包含其数据，默认情况下它们是**不可空（Non-nullable）** 的。
*   **引用类型（Reference Types）：** 包含类（`class`）、接口（`interface`）、委托（`delegate`）和数组。引用类型存储的是对数据的内存地址引用，默认情况下它们是**可空（Nullable）** 的，其默认值就是 `null`。

## 为什么需要可空的值类型？

在实际业务场景中，很多时候我们需要表示“数据不存在”、“未知”或“不适用”的状态。

**场景示例：**
定义一个 `Person` 类，其中包含一个表示“孩子数量”的字段。
如果一个员工没有孩子，赋值为 `0` 是合理的。但如果一个员工尚未结婚，或者我们根本不知道他有没有孩子，此时赋值为 `0` 在业务逻辑上是错误的。我们需要一种方式来表示“空白”或“未知”。对于引用类型，我们可以直接用 `null`；但对于像 `int` 这样的值类型，直接赋值 `null` 编译器会报错。

## 声明和使用可空值类型

为了解决上述问题，C# 允许将非空的值类型转换为可空类型。

### 语法定义
有两种方式来定义可空值类型（两者在底层完全等价）：
1.  使用泛型结构体：`Nullable<T>`
2.  使用语法糖（推荐）：在类型后面加问号 `T?`

### 代码示例
```csharp
public class Person
{
    // 非可空类型：必须包含一个具体的整数，默认为 0
    public int Age; 
    
    // 可空类型：可以包含整数，也可以为 null
    public int? NumberOfChildren; 
    // 等同于：public Nullable<int> NumberOfChildren;
}

public class Program
{
    public static void Main()
    {
        Person p1 = new Person();
        p1.NumberOfChildren = 2; // 正常赋值

        Person p2 = new Person();
        p2.NumberOfChildren = null; // 允许赋值为 null，表示数据未知或不适用
    }
}
```

## 核心属性：HasValue 与 Value

当我们把值类型包装成可空类型后，该变量就不再是一个单纯的底层数据类型了，它拥有了两个非常重要的只读属性：

*   **`HasValue` (bool)：** 如果变量包含有效的值，则返回 `true`；如果变量的值为 `null`，则返回 `false`。
*   **`Value` (T)：** 返回底层的值。**注意：** 如果在 `HasValue` 为 `false`（即值为 `null`）时强行访问 `Value` 属性，会抛出 `InvalidOperationException` 异常。

### 安全读取可空类型的代码模式

```csharp
int? numberOfChildren = null;

// 方式一：直接与 null 比较（编译器底层会将其转化为调用 HasValue）
if (numberOfChildren != null)
{
    Console.WriteLine(numberOfChildren);
}

// 方式二：使用 HasValue 和 Value 属性
if (numberOfChildren.HasValue)
{
    // 必须通过 .Value 提取内部的实际整数值
    int actualCount = numberOfChildren.Value;
    Console.WriteLine(actualCount);
}
```

## 类型转换与赋值规则

可空类型 `T?` 和底层基础类型 `T` 是两种不同的类型。例如 `int?` 和 `int` 不能随意直接混用。

*   **隐式转换（向上兼容）：** 可以将 `int` 隐式转换为 `int?`，因为这是绝对安全的。
*   **显式转换（向下提取）：** 不能将 `int?` 直接赋值给 `int` 变量。必须显式强制转换，或者使用 `.Value` 属性。

```csharp
int? nullInt = 5;
int normalInt;

// normalInt = nullInt; // 编译错误：无法将 int? 隐式转换为 int

// 正确的做法1：使用 .Value (存在抛出异常的风险)
normalInt = nullInt.Value;

// 正确的做法2：显式转换 (同样存在抛出异常的风险)
normalInt = (int)nullInt;
```

## 进阶拓展
参考《CLR via C#》与《C# in Depth》

### 底层实现原理
在 CLR (公共语言运行时) 层面，`int?` 实际上是一个标准的结构体（Struct）。`System.Nullable<T>` 的定义大致如下，它要求泛型参数 `T` 必须也是一个值类型（`where T : struct`）：

```csharp
public struct Nullable<T> where T : struct
{
    private bool hasValue;
    private T value;

    public bool HasValue => hasValue;
    public T Value 
    {
        get 
        {
            if (!hasValue) throw new InvalidOperationException();
            return value;
        }
    }
    // ... 其他构造函数和操作符重载
}
```
这意味着**可空值类型本身仍然分配在栈（Stack）上**（或者内联在对象中），它并没有引发堆分配（Heap Allocation）或装箱（Boxing），性能非常高。它只是多用了一个 `bool` 字段来标记是否有值。

### 优雅地处理 null 提取
在实际开发中，直接使用 `.Value` 不够安全。C# 提供了更好的方式来提取可能为 null 的值：

1.  **`GetValueOrDefault()` 方法：** 如果有值则返回该值，如果是 `null` 则返回该基础类型的默认值（比如 int 返回 0）。
2.  **`??` 空合并运算符：** 允许你指定一个自定义的默认值（《Effective C#》推荐做法）。

```csharp
int? unknownChildren = null;

// 如果 unknownChildren 为 null，则赋值为 0
int count1 = unknownChildren.GetValueOrDefault(); 

// 使用 ?? 运算符，如果 unknownChildren 为 null，则赋值为 -1
int count2 = unknownChildren ?? -1; 
```

# 补充：可空引用类型

## 核心概念与“范式转变”
在 C# 8.0 之前，所有的引用类型（如 `string`, `class`, `interface`）天生就是可空的，这导致了臭名昭著的“十亿美元错误”——`NullReferenceException`。
**NullReferenceException 确实是运行时最常见的异常之一**。你可能会遇到：
```cs
string name = null;
int length = name.Length; // NullReferenceException!
```
C# 的设计者 Tony Hoare 后来甚至称 null 为他的“十亿美元错误”。它在1965年被引入 ALGOL W 语言，初衷是“简单”，但后来证明这个简单的决定带来了几十年的麻烦。

C# 继承了这一设计，因为：
需要与 .NET 平台和现有代码兼容
需要与数据库交互（数据库中有 NULL）
引用类型的默认值只能是 null（不可能让所有引用类型默认都有有效值）


可空引用类型的引入改变了这一默认语义：**当启用该特性后，引用类型默认被视为“不可空” (Non-nullable)**。如果你希望一个引用类型可以为 null，必须显式使用 `?` 进行声明。

## 值类型可空 vs 引用类型可空（重要！）
《C# in Depth》中特别强调了两者在底层实现上的根本差异，这是理解该特性的关键：
*   **可空值类型（如 `int?`）：** 这是 **CLR 运行时级别**的改变。`int?` 实际上被编译为泛型结构体 `Nullable<int>`。它在内存中的布局和普通 `int` 是完全不同的。
*   **可空引用类型（如 `string?`）：** 这是 **C# 编译器级别**的“幻觉”。`string?` 在 CLR 运行时层面依然仅仅是普通的 `String`。编译器只是通过插入特性（Attributes）并在编译期进行严格的**静态流分析 (Static Flow Analysis)** 来发出警告，并没有改变类型的运行时本质。

## 启用特性
由于该特性会改变旧代码的语义并产生大量警告，C# 默认只在新项目中启用。可以分为两个级别控制：
*   **项目级别（推荐）：** 在 `.csproj` 文件中添加 `<Nullable>enable</Nullable>`。
*   **文件/代码块级别：** 使用预处理指令 `#nullable enable` 和 `#nullable disable` 局部开启或关闭。

## 语法与编译器流分析代码示例
编译器会像代码检查器一样，追踪变量的状态（Maybe null 还是 Not null）。

```csharp
#nullable enable // 开启可空引用类型特性

public class UserProfile
{
    // 1. 不可空引用类型：必须在声明时或构造函数中初始化，否则编译器警告！
    public string Username { get; set; } 

    // 2. 可空引用类型：允许未初始化（默认为 null），允许赋值为 null
    public string? Nickname { get; set; }

    public UserProfile(string username)
    {
        Username = username; // 初始化了不可空属性，警告消除
    }

    public void PrintNameLength()
    {
        // 正常编译，Username 保证不为 null
        Console.WriteLine(Username.Length); 

        // 编译器警告：Dereference of a possibly null reference.
        // Console.WriteLine(Nickname.Length); 

        // 3. 编译器的静态流分析 (Flow Analysis)
        if (Nickname != null)
        {
            // 编译器很聪明，知道在 if 块内 Nickname 绝不为 null
            // 此时调用 .Length 不会产生警告
            Console.WriteLine(Nickname.Length); 
        }
    }
}
```

## 容忍操作符: `!`
有时候，开发者的业务逻辑能百分之百确定某个可空变量在某处绝对不为 null，但编译器受限于静态分析无法推断出来。这时可以使用后缀 `!`。

**作用：** 告诉编译器“闭嘴，我知道它不可能为空，停止在这个地方报警告”。

```csharp
public string? GetOptionalData() => "Data";

public void Process()
{
    string? data = GetOptionalData();
    
    // 如果直接写 data.Length 会警告。
    // 使用 ! 压制警告。如果运行时 data 真的是 null，这里依然会抛出 NullReferenceException！
    int length = data!.Length; 
}
```
*注：《Effective C#》建议：谨慎使用 `!` 操作符。它通常意味着你的代码设计存在瑕疵，或者你正在与尚未支持可空特性的老旧代码库进行交互。优先考虑修改逻辑让编译器自然推断。*

## 属性标签的高级辅助
当普通的方法签名无法表达复杂的 null 逻辑时（例如：当方法返回 true 时，`out` 参数才不为 null），C# 提供了一系列特性标记（位于 `System.Diagnostics.CodeAnalysis` 命名空间）来辅助编译器推断。

*   `[NotNullWhen(true)]`：经典应用在 `Dictionary.TryGetValue` 中。
*   `[AllowNull]` / `[DisallowNull]`：用于属性，表示获取和设置时的可空期望不同。

```csharp
// 示例：TryParse 模式下的不可空保证
public bool TryGetUserName([NotNullWhen(true)] out string? name)
{
    name = "JohnDoe";
    return true; // 当返回 true 时，编译器会认为传入的 name 不再是 null
}
```

## 最佳实践总结
1.  **区分警告与错误：** 违反 NRT 规则默认只会产生**警告 (Warning)** 而非错误，不会阻止代码编译（除非你开启了 WarnAsError）。这主要是为了向后兼容。
2.  **默认不可空：** 养成将所有对象视为不可空的习惯（即不加 `?`）。只有当业务逻辑明确表示“这里可以没有值”时，才使用可空引用类型。
3.  **防卫性编程不能省：** 既然 `string?` 在运行时还是 `string`，这就意味着外部（如反射、或者未开启此特性的第三方代码）依然可能传一个 null 给你的 `string`（不可空）参数。因此，在暴露给外部的公开 API （Public API）中，传统的 `ArgumentNullException.ThrowIfNull(param);` 依然是必要的。
