# 不可变性与 With 表达式：构建数据的安全防线

## 从“修改状态”到“生成新状态”

在文章 01 中，我们了解了 `record` 的基本语法和值相等性。但 `record` 真正的威力不仅仅在于“比较”，更在于“状态管理”。

在传统面向对象编程（OOP）中，对象通常是**可变（Mutable）** 的。我们通过调用 setter 方法或直接修改属性来改变对象的状态。这种模式在简单的业务逻辑中很直观，但在复杂系统、高并发场景或函数式编程风格中，它带来了巨大的挑战：
*   **竞态条件（Race Conditions）**：多线程同时修改同一对象可能导致数据不一致。
*   **副作用（Side Effects）**：修改一个对象可能会意外影响引用该对象的其他逻辑。
*   **调试困难**：难以追踪对象状态是在何时、何地被修改的。

C# `record` 通过**不可变性（Immutability）** 和 **`with` 表达式**，提供了一种更安全的模式：**不要修改对象，而是创建一个新的对象来代表新的状态。**

本文将深入探讨如何利用 `record` 构建不可变数据模型，掌握 `with` 表达式的精髓，并警惕浅拷贝陷阱。

---

## 一、不可变性：安全的基石

不可变性是指对象一旦创建，其状态就不能被修改。在 C# 中，实现不可变性通常需要组合使用 `readonly` 字段、`init` 访问器和 `record`。

### `init` 访问器：只写一次
C# 9.0 引入了 `init` 访问器。与传统的 `set` 访问器不同，`init` 允许属性在对象初始化期间（构造函数或对象初始化器）赋值，但在初始化完成后变为只读。

```csharp
public class Person
{
    public string Name { get; init; } // 初始化后可读，不可写
    public int Age { get; init; }
}

var p = new Person { Name = "Alice", Age = 30 };
// p.Name = "Bob"; // 编译错误：无法将属性或索引器 Person.Name 设置值
```

**在 Record 中的应用**：
`record` 的位置属性（Positional Properties）默认就是 `init` 的。这意味着当你定义 `record Person(string Name, int Age);` 时，编译器已经为你生成了 `init` 访问器。

```csharp
public record Person(string Name, int Age);

var p1 = new Person("Alice", 30);
// p1.Name = "Bob"; // 编译错误：Property 'Person.Name' has no setter
```

### 真正的不可变 Record
虽然 `record` 默认生成 `init` 属性，但如果你在 `record` 内部手动添加了 `get; set;` 属性，它们依然是可变的。为了构建真正的不可变模型，你需要确保**所有**属性都是 `init` 或 `get`（只读）。

```csharp
// 推荐：完全不可变 Record
public record Order
{
    public int Id { get; init; }
    public string Status { get; init; }
    public DateTime CreatedAt { get; init; } = DateTime.UtcNow;
    
    // 构造函数确保必填字段
    public Order(int id, string status)
    {
        Id = id;
        Status = status;
    }
}
```

**为什么不可变性重要？**
1.  **线程安全**：不可变对象可以在多线程间自由共享，无需锁（Lock）。
2.  **缓存友好**：因为状态不变，计算出的哈希码（Hash Code）永远有效，适合作为 `Dictionary` 的 Key。
3.  **推理简单**：你不需要担心函数调用是否会改变传入的对象。

## 二、With 表达式：非破坏性修改

既然不可变对象不能修改，那如何更新数据？答案是：**创建副本**。C# 9.0 引入了 `with` 表达式，专门用于生成对象的“新版本”。

### 基本语法
`with` 表达式使用对象初始化器的语法，但基于一个现有对象创建新对象。

```csharp
public record Person(string Name, int Age);

var p1 = new Person("Alice", 30);

// 创建一个新对象，Name 不变，Age 变为 31
var p2 = p1 with { Age = 31 };

Console.WriteLine(p1 == p2); // False
Console.WriteLine(p1.Equals(p2)); // False (内容不同)
Console.WriteLine(p1.Age); // 30 (原对象未变)
Console.WriteLine(p2.Age); // 31 (新对象已变)
```

### 编译器背后的原理
`with` 表达式是语法糖。编译器会将其转换为调用复制构造函数（Copy Constructor）。

```csharp
// 伪代码：编译器生成的逻辑
var p2 = new Person(p1.Name, 31);
```

如果 `record` 有继承关系，`with` 表达式会智能地处理基类属性，确保所有层级都被正确复制。

### 链式更新
`with` 表达式可以链式调用，这在构建复杂配置对象或状态机时非常有用。

```csharp
var config = new Config { Timeout = 100 };
var newConfig = config
    with { Timeout = 200 }
    with { RetryCount = 3 };
```

### 性能考量
`with` 表达式会分配新的内存。对于频繁更新且生命周期极短的对象（如循环内的临时计算），这可能会增加 GC 压力。
*   **适用场景**：DTO 转换、状态流转、配置更新、CQRS 查询参数构建。
*   **不适用场景**：高性能计算循环中的计数器、频繁变动的集合元素。

## 三、浅拷贝陷阱：引用类型的深渊

这是使用 `record` 和 `with` 表达式时**最容易踩的坑**。

### 问题描述
`with` 表达式执行的是**浅拷贝（Shallow Copy）**。这意味着它复制了属性的值，但如果属性是引用类型（如 `List<T>`, `string`, `class`），它只复制了引用地址，而不是对象本身。

```csharp
public record Order
{
    public int Id { get; init; }
    public List<string> Items { get; init; } // 引用类型属性
}

var order1 = new Order { Id = 1, Items = new List<string> { "Item A" } };
var order2 = order1 with { Id = 2 };

// 陷阱：order2.Items 和 order1.Items 指向同一个 List 实例！
order2.Items.Add("Item B");

Console.WriteLine(order1.Items.Count); // 输出 2！原对象被意外修改了
```

### 解决方案
要解决浅拷贝问题，你需要在 `with` 表达式中手动深拷贝引用类型属性，或者使用自定义方法。

**方案 A：在 `with` 中手动复制**
```csharp
var order2 = order1 with 
{ 
    Id = 2, 
    Items = [.. order1.Items] // C# 12 集合表达式，创建新 List
    // 或者 order1.Items.ToList()
};
```

**方案 B：定义自定义更新方法**
对于复杂的业务对象，建议封装更新逻辑，避免直接使用 `with` 暴露浅拷贝风险。

```csharp
public record Order
{
    public int Id { get; init; }
    public List<string> Items { get; init; }

    public Order WithNewItem(string item)
    {
        return this with
        {
            Items = [.. this.Items, item] // 深拷贝列表
        };
    }
}
```

### 最佳实践建议
*   **优先使用值类型**：在 Record 中尽量使用 `string`, `int`, `Guid`, `DateTime` 等值类型。
*   **使用不可变集合**：使用 `ImmutableList<T>`, `ImmutableDictionary<T>` 代替 `List<T>`。不可变集合在添加元素时会自动返回新实例，天然配合 `with`。
    ```csharp
    using System.Collections.Immutable;

    public record Order
    {
        public ImmutableList<string> Items { get; init; }
    }
    // 此时 with 是安全的，因为 Items 本身就是不可变的
    ```

## 四、解构：提取数据的便捷方式

`record` 支持解构，允许将对象拆分为多个变量。这对于简化代码非常有用，特别是在处理返回值时。

### 基本解构
```csharp
public record Point(int X, int Y);

var p = new Point(10, 20);
var (x, y) = p; // 自动调用 Deconstruct 方法

Console.WriteLine(x); // 10
Console.WriteLine(y); // 20
```

### 忽略部分数据
你可以使用 `_` 来忽略不需要的属性。
```csharp
var (x, _) = p; // 只获取 X
```

### 在循环中使用
```csharp
var points = new List<Point> { new(1, 1), new(2, 2) };

foreach (var (x, y) in points)
{
    Console.WriteLine($"X: {x}, Y: {y}");
}
```

### 自定义解构
如果你定义了非位置属性的 `record`，你需要手动实现 `Deconstruct` 方法。
```csharp
public record User(string Name, string Email)
{
    // 自定义解构逻辑，例如只返回敏感信息
    public void Deconstruct(out string name, out string email)
    {
        name = Name;
        email = "Hidden"; // 隐藏真实邮箱
    }
}
```

## 五、实战场景：CQRS 与状态管理

不可变 Record 是 CQRS（命令查询职责分离）和状态管理（如 Redux 模式）的完美搭档。

### CQRS 中的 Query 和 Command
在 MediatR 等库中，通常使用 Record 来定义查询和命令对象。因为它们通常是一次性的，不需要修改，且需要值相等性来匹配处理器。

```csharp
// 查询对象
public record GetUserQuery(int UserId) : IRequest<UserDto>;

// 命令对象
public record CreateUserCommand(string Name, string Email) : IRequest<int>;

// 处理器签名
public class GetUserHandler : IRequestHandler<GetUserQuery, UserDto>
{
    public Task<UserDto> Handle(GetUserQuery query, CancellationToken ct)
    {
        // query.UserId 是只读的，安全
        return Task.FromResult(new UserDto(query.UserId));
    }
}
```

### 状态更新（类似 Redux）
在复杂前端应用的后端逻辑或游戏服务器中，状态通常是一个巨大的 Record。更新状态时，我们生成一个新的状态 Record。

```csharp
public record GameState
{
    public int Score { get; init; }
    public int Level { get; init; }
    public List<Player> Players { get; init; }
}

public record Player(string Name, int Health);

// 玩家得分逻辑
public GameState PlayerScored(GameState state, int points)
{
    return state with
    {
        Score = state.Score + points,
        // 注意：Players 列表如果是可变 List，这里需要深拷贝
        Players = [.. state.Players] 
    };
}
```

这种模式保证了**历史状态不可变**，便于实现“撤销/重做”功能或时间旅行调试。

## 六、线程安全：无锁编程的利器

在多线程环境下，可变对象是万恶之源。`record` 的不可变性消除了大部分并发问题。

### 共享状态
```csharp
public record SharedConfig
{
    public string ApiKey { get; init; }
    public int Timeout { get; init; }
}

// 线程 A
var config = new SharedConfig { ApiKey = "123", Timeout = 5000 };

// 线程 B
// 直接读取 config，无需加锁，因为 config 不会被修改
var apiKey = config.ApiKey; 
```

### 状态流转
如果确实需要更新配置，使用 `with` 生成新配置并原子性地替换引用。

```csharp
// 使用 volatile 或 Interlocked 确保引用更新的原子性
private volatile SharedConfig _currentConfig;

public void UpdateConfig(int newTimeout)
{
    var newConfig = _currentConfig with { Timeout = newTimeout };
    _currentConfig = newConfig; // 原子替换引用
}
```
由于 `SharedConfig` 是不可变的，读取 `_currentConfig` 的线程永远不会看到“半更新”的状态。

## 七、常见误区与避坑

1.  **`with` 不是深拷贝**：再次强调，除非属性本身是不可变集合，否则 `with` 只是浅拷贝。
2.  **`record` 默认不是完全不可变**：如果你手动添加了 `set;` 属性，它就可以变。务必检查所有属性。
3.  **`with` 的性能开销**：不要在不必要的地方使用 `with`。如果对象生命周期很短且不需要保留旧状态，直接 `new` 可能更高效。
4.  **继承与 `with`**：在继承的 `record` 中使用 `with` 时，确保基类属性也被正确包含。编译器通常处理得很好，但自定义构造函数时需小心。

## 八、总结与展望

通过本文，我们掌握了 `record` 的核心价值：**不可变性**与**非破坏性更新**。

*   **`init`** 锁定了对象创建后的状态。
*   **`with`** 提供了生成新状态的安全途径。
*   **解构** 简化了数据提取。
*   **线程安全** 是这些特性带来的天然红利。

**关键思维转变**：
不要试图“修补”旧对象，而是“创建”新对象。这听起来可能浪费内存，但在现代 .NET 和 GC 优化下，这种模式带来的代码清晰度和并发安全性远超其成本。

**课后练习**：
1.  定义一个 `ShoppingCart` record，包含 `Items` (ImmutableList) 和 `Total`。
2.  实现一个 `AddItem` 方法，返回新的 `ShoppingCart` 实例。
3.  验证修改新购物车的 `Items` 不会影响旧购物车。
4.  尝试在多线程环境下共享该 `ShoppingCart`，观察是否出现异常。

```cs
using System;
using System.Collections.Immutable;
using System.Linq;
using System.Threading.Tasks;

// 1. 定义一个 ShoppingCart record，包含 Items (ImmutableList) 和 Total
public record ShoppingCart(ImmutableList<string> Items, decimal Total)
{
    // 提供一个默认的空购物车静态属性，方便初始化
    public static ShoppingCart Empty { get; } = new(ImmutableList<string>.Empty, 0m);

    // 2. 实现 AddItem 方法，返回新的 ShoppingCart 实例（纯函数无副作用）
    public ShoppingCart AddItem(string itemName, decimal price)
    {
        // 使用 with 表达式创建当前 record 的副本，并更新相应属性
        // Items.Add() 不会修改原集合，而是返回一个包含了新元素的新 ImmutableList
        return this with
        {
            Items = this.Items.Add(itemName),
            Total = this.Total + price
        };
    }
}

class Program
{
    static void Main()
    {
        Console.WriteLine("--- 3. 验证不可变性：修改新购物车不影响旧购物车 ---");
        
        // 初始化第一个购物车
        var cart1 = ShoppingCart.Empty.AddItem("苹果", 5.0m);
        
        // 在 cart1 的基础上添加商品，生成 cart2
        var cart2 = cart1.AddItem("香蕉", 3.0m);

        Console.WriteLine($"Cart1 商品: [{string.Join(", ", cart1.Items)}], 总价: {cart1.Total}");
        // 输出: Cart1 商品: [苹果], 总价: 5.0
        
        Console.WriteLine($"Cart2 商品: [{string.Join(", ", cart2.Items)}], 总价: {cart2.Total}");
        // 输出: Cart2 商品: [苹果, 香蕉], 总价: 8.0
        
        Console.WriteLine($"结论：Cart1 的商品数量仍然是 {cart1.Items.Count}，未受 Cart2 影响。\n");


        Console.WriteLine("--- 4. 验证多线程环境下的线程安全性 ---");
        
        // 我们将 cart2 作为一个共享资源暴露给多个线程
        var sharedCart = cart2;
        int taskCount = 1000;

        try
        {
            // 启动 1000 个并行任务，同时读取和“修改”共享购物车
            Parallel.For(0, taskCount, i =>
            {
                // 模拟多线程并发读取
                var currentItemsCount = sharedCart.Items.Count;
                var currentTotal = sharedCart.Total;

                // 模拟并发“添加”数据（注意：这只是基于共享实例创建新实例）
                var tempCart = sharedCart.AddItem($"商品_{i}", 1.0m);
                
                // 如果是普通的 List<T>，在多线程同时读写时早就抛出 InvalidOperationException 了
                // 但这里因为没有任何状态被实际修改，所以绝对安全。
            });

            Console.WriteLine("多线程并发操作完成，没有抛出任何异常！");
        }
        catch (Exception ex)
        {
            Console.WriteLine($"出现异常: {ex.Message}");
        }

        Console.WriteLine($"最终 sharedCart 内部的商品数量: {sharedCart.Items.Count}"); 
        // 依然是 2，因为多线程中创建的 tempCart 并没有覆盖 sharedCart 变量
    }
}
```
