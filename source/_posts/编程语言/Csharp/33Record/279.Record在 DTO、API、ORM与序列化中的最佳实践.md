# Record在 DTO、API、ORM与序列化中的最佳实践


在前四篇文章中，我们深入学习了 `record` 的语法、不可变性、底层原理以及性能特征。现在，是时候将这些知识应用到真实的工业级开发场景中了。

在企业级 .NET 开发中，我们 rarely 只写纯粹的 POCO（Plain Old CLR Objects）。我们需要与 ASP.NET Core Web API 交互，需要序列化为 JSON，需要持久化到数据库（EF Core），还需要在 CQRS 架构中传递消息。

`record` 在这些场景中的表现参差不齐：
*   **DTO 与 API**：完美契合，是最佳实践。
*   **CQRS 消息**：天然匹配，推荐使用。
*   **JSON 序列化**：支持良好，但需注意配置。
*   **ORM 实体**：需谨慎，存在陷阱。

本文将作为实战指南，详细剖析 `record` 在主流框架中的集成方案，提供经过验证的最佳实践，并指出那些可能导致生产事故的“坑”。

---

## 一、API 与 DTO 层：Record 的主战场

数据传输对象（DTO）是 `record` 最理想的应用场景。DTO 的本质就是数据的载体，不需要复杂的行为，且需要清晰的契约。

### 请求模型（Request DTOs）
在 API 中，请求模型通常代表客户端的意图。使用 `record` 可以确保请求数据一旦绑定，就不会在管道处理过程中被意外修改。

**最佳实践**：
*   使用 `required` 关键字（C# 11+）确保必填字段。
*   使用 `init` 属性确保不可变。
*   命名清晰，体现意图（如 `CreateUserRequest` 而非 `UserDto`）。

```csharp
// C# 11/12 风格
public record CreateUserRequest
{
    public required string UserName { get; init; }
    public required string Email { get; init; }
    public string? Bio { get; init; } // 可选
    public List<string> Roles { get; init; } = []; // 默认空集合，避免 null
}
```

**优势**：
*   **安全性**：Controller 接收到对象后，不用担心后续中间件修改了 `UserName`。
*   **验证友好**：配合 `required`，框架层即可拦截无效请求。

### 响应模型（Response DTOs）
响应模型代表服务器返回的数据快照。使用 `record` 可以防止服务器内部逻辑在序列化前意外修改响应内容。

```csharp
public record UserResponse
{
    public Guid Id { get; init; }
    public string UserName { get; init; }
    public string Email { get; init; }
    public DateTime CreatedAt { get; init; }
}

// Controller 中
[HttpGet("{id}")]
public ActionResult<UserResponse> GetUser(Guid id)
{
    var user = _userService.GetById(id);
    // 映射到 Record
    var response = new UserResponse 
    { 
        Id = user.Id, 
        UserName = user.Name, 
        Email = user.Email, 
        CreatedAt = user.CreatedAt 
    };
    return Ok(response);
}
```

### 统一响应包装
许多项目喜欢封装统一 API 响应格式（`ApiResponse<T>`）。`record` 非常适合这种泛型包装。

```csharp
public record ApiResponse<T>(bool Success, T? Data, string? Message = null)
{
    public static ApiResponse<T> Ok(T data) => new(true, data);
    public static ApiResponse<T> Fail(string message) => new(false, default, message);
}

// 使用
return ApiResponse<UserResponse>.Ok(response);
```

## 二、JSON 序列化与record集成指南

在 C# 中，`record`（记录类型）可以说是为 **DTO（数据传输对象）** 和 **JSON 序列化/反序列化** 量身定制的特性。因为在 Web API 或消息队列交互中，我们接收或发送的数据通常只是一组**不可变的纯数据**，这正是 `record` 的核心设计理念。

但在实际配合 `System.Text.Json` (STJ) 或 `Newtonsoft.Json` 使用时，有几个非常重要的细节和“坑”需要特别注意。

以下是 `Record` 与 JSON 序列化结合使用的全景指南：

---

### 最常见的用法：位置型 Record

这是最简洁的写法。编译器会自动为你生成属性、构造函数和解构方法。

```csharp
using System.Text.Json;

// 定义一个位置型 Record
public record UserDto(int Id, string Name);

// 1. 序列化 (C# 对象 -> JSON 字符串)
var user = new UserDto(1, "Alice");
string json = JsonSerializer.Serialize(user);
// 输出: {"Id":1,"Name":"Alice"}

// 2. 反序列化 (JSON 字符串 -> C# 对象)
var deserializedUser = JsonSerializer.Deserialize<UserDto>(json);
```

**底层原理：**
由于 `UserDto(int Id, string Name)` **没有无参构造函数**，`System.Text.Json` 在反序列化时，会自动寻找包含所有参数的构造函数（Primary Constructor），并将 JSON 中的字段与构造函数的参数进行名称匹配，然后实例化对象。

---

### 陷阱：命名约定与大小写问题

前端通常使用 `camelCase`（小驼峰，如 `userName`），而 C# 的 Record 属性通常是大驼峰 `PascalCase`（如 `UserName`）。

**问题重现：**
如果前端传来的 JSON 是小驼峰：`{"id": 1, "name": "Alice"}`
你直接使用默认设置反序列化为 `public record UserDto(int Id, string Name);`，**结果通常是报错或得到默认值**（Id=0, Name=null）。

**完美解决方案：**
必须在 `JsonSerializerOptions` 中明确指定命名策略，或者允许大小写不敏感。

```csharp
string jsonFromFrontend = @"{ ""id"": 1, ""name"": ""Alice"" }";

var options = new JsonSerializerOptions
{
    // 方案 A: 允许大小写不敏感 (推荐用于兼容复杂前端)
    PropertyNameCaseInsensitive = true,
    
    // 方案 B: 严格指定 JSON 使用小驼峰规则 (推荐用于标准化 API)
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase
};

var user = JsonSerializer.Deserialize<UserDto>(jsonFromFrontend, options);
// 此时 user 成功解析: Id=1, Name="Alice"
```

---

### 如何映射不规则的 JSON 字段名？

如果第三方 API 返回的 JSON 字段名是蛇形命名（Snake Case），比如 `first_name`，我们如何映射到 C# 的 `FirstName`？

在 `record` 的主构造函数中，你可以直接使用 `[JsonPropertyName]` 特性：

```csharp
using System.Text.Json.Serialization;

// 直接在参数前加特性
public record EmployeeDto(
    [property: JsonPropertyName("emp_id")] int Id, 
    [property: JsonPropertyName("first_name")] string FirstName
);

string json = @"{ ""emp_id"": 9527, ""first_name"": ""唐伯虎"" }";
var emp = JsonSerializer.Deserialize<EmployeeDto>(json);



public record UserDto
{
    public int Id { get; init; }
    
    [JsonPropertyName("user_name")] // 自定义 JSON 字段名
    public string Name { get; init; }
    
    [JsonIgnore] // 序列化时忽略
    public string InternalToken { get; init; }
}
```
*注意：必须写 `[property: JsonPropertyName(...)]`，这是告诉编译器将这个特性应用到生成的**属性**上，而不仅仅是构造函数参数上。*

---

### 忽略某些属性

如果你不想把某些内部数据序列化出去，同样可以使用特性：

```csharp
public record LoginResponse(
    string Token, 
    [property: JsonIgnore] string InternalSecret
);
```

---

### 处理 `required` 属性
C# 11 的 `required` 关键字与 STJ 原生集成。如果 JSON 中缺失了 `required` 字段，STJ 会在反序列化时抛出 `JsonException`。

```csharp
public record LoginRequest
{
    public required string Username { get; init; }
    public required string Password { get; init; }
}

// 如果 JSON 缺少 Password，直接报错，无需手动验证
var req = JsonSerializer.Deserialize<LoginRequest>(json); 
```

**配置选项**：
如果你希望忽略缺失的 `required` 字段（不推荐），可以配置 `JsonPropertyName` 或使用自定义转换器，但最好让反序列化失败以便快速发现客户端错误。


---


### 常见陷阱：集合属性
如果 `record` 包含集合属性，反序列化时默认会创建新的集合实例。

```csharp
public record OrderDto(List<string> Items);
// JSON: {"Items": ["A", "B"]}
// 反序列化后，Items 是一个新的 List 实例，安全。
```
**警告**：不要使用 `ImmutableList` 直接作为属性类型进行反序列化，除非你配置了特定的转换器，因为 STJ 默认不知道如何构造不可变集合。建议使用 `List<T>` 接收，然后在内部转换为不可变集合。


---

### 基于属性的 Record (带 `init` 的可变长初始化)

位置型 Record 要求在 `new` 的时候必须传入所有参数。如果你的 DTO 有 20 个字段，其中 15 个是可选的，位置型 Record 会让构造函数变得非常臃肿。

这时候，推荐使用包含 **无参构造函数** 和 **`init` 属性** 的 Record：

```csharp
public record CreateOrderRequest
{
    public string OrderId { get; init; } = Guid.NewGuid().ToString();
    public decimal Amount { get; init; }
    public string? OptionalRemark { get; init; } // 可选字段
}

// C# 序列化前的初始化，非常优雅
var request = new CreateOrderRequest 
{ 
    Amount = 99.8m 
};

// 反序列化也完全没问题
string json = @"{ ""Amount"": 100.0, ""OptionalRemark"": ""加急"" }";
var newOrder = JsonSerializer.Deserialize<CreateOrderRequest>(json);
```

**为什么 `init` 配合反序列化这么爽？**
*   `init` 表示属性只能在对象初始化的那一刻被赋值。
*   `System.Text.Json` 在底层是通过反射在初始化阶段赋值的，所以**它可以成功给 `init` 属性赋值**。
*   反序列化完成后，一旦对象交到你的业务逻辑代码手中，这些属性就**变成了只读的**，防止被后续代码意外篡改（绝对的线程安全和数据安全）。

---

### Newtonsoft.Json (Json.NET) 的兼容性

如果你还在维护使用老版本 `Newtonsoft.Json` 的项目，需要注意：

*   **完全兼容**：`Newtonsoft.Json`（从 13.0 版本开始）完美支持 Record 的位置型构造函数和 `init` 属性。
*   **特性写法**：如果要改名，使用的是 `[JsonProperty("first_name")]`。

```csharp
using Newtonsoft.Json;

public record OldSystemDto(
    [property: JsonProperty("user_age")] int Age
);
```

---

### 总结与最佳实践建议

1.  **首选 Record 作为 DTO**：无论是 Controller 层接收前端请求（Request），还是向外返回数据（Response），一律推荐使用 `record class`。它的不可变性能极大减少不可预期的 Bug。
2.  **用属性特性修饰**：在位置参数中加特性时，别忘了加上 `property:` 前缀。
3.  **大 JSON 用 `init`**：如果参数过多（超过 5 个）或包含大量可选参数，放弃 `public record(A, B, C...)` 的写法，改用 `{ public string A { get; init; } }` 的对象初始化器写法，代码可读性更好。
4.  **全局配置大小写**：在 ASP.NET Core 项目中，默认的 JSON 序列化器已经配置为 `camelCase` 并且大小写不敏感，所以直接用 `record` 接收前端 JSON 通常是无缝衔接的，无需额外配置。

## 三、ORM 集成：Entity Framework Core 的爱恨情仇

这是 `record` 最具争议的领域。EF Core 依赖变更追踪（Change Tracking）和代理（Proxies），这与 `record` 的不可变性存在天然冲突。

### entity 实体类：慎用 Record
**建议**：**不要**将聚合根（Aggregate Root）或主要实体定义为 `record`。
**原因**：
*   EF Core 需要修改导航属性（Navigation Properties）来建立关系。
*   EF Core 的变更追踪依赖于属性 setter 被调用。
*   `record` 的 `init` 属性阻止了 EF Core 在跟踪_changes_时修改属性。

虽然 EF Core 5+ 支持 `record`，但配置繁琐且容易遇到“对象已更改”的异常。

```csharp
// 不推荐：作为主要实体
public record UserEntity(int Id, string Name); 
// 当你尝试 user.Name = "New" 时会报错，EF Core 无法追踪变更
```

### 值对象：完美匹配
**建议**：**强烈推荐**将 DDD 中的值对象定义为 `record`。
EF Core 7 引入了 **Complex Types（复杂类型）**，专门用于映射没有主键的对象，这正是 `record` 的强项。

```csharp
// 值对象
public record Address(string Street, string City, string ZipCode);

// 实体（使用 class）
public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; }
    
    // EF Core 7+ 配置为 Complex Type
    public Address ShippingAddress { get; set; }
}

// DbContext 配置
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Customer>(entity =>
    {
        entity.ComplexProperty(e => e.ShippingAddress);
    });
}
```
**优势**：
*   地址是不可变的，符合值对象定义。
*   数据库中将 `Street`, `City`, `ZipCode` 展平为 `Customer` 表的列。
*   替换地址时，只需 `customer.ShippingAddress = new Address(...)`，EF Core 能检测到引用变化。

### 主键与不可变性
如果坚持使用 `record` 作为实体，主键必须是 `init` 的。EF Core 可以在构造函数中设置主键，但后续无法修改。

```csharp
public record ProductRecord
{
    public int Id { get; init; } // EF Core 可以设置
    public string Name { get; set; } // 必须可变以支持追踪
}
```
这种混合模式（部分 `init`，部分 `set`）失去了 `record` 的纯粹性，因此不如直接用 `class`。

## 四、CQRS 与消息传递：MediatR 的最佳搭档

在 CQRS 架构中，命令（Command）、查询（Query）和事件（Event）本质上是数据契约。`record` 是定义它们的黄金标准。

### 命令与查询
命令代表意图，查询代表数据请求。它们都是短暂的、不可变的。

```csharp
// 命令
public record CreateOrderCommand(Guid UserId, List<OrderItem> Items) 
    : IRequest<int>; // MediatR 接口

// 查询
public record GetOrderQuery(int OrderId) : IRequest<OrderDto>;

// 处理器
public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, int>
{
    public Task<int> Handle(CreateOrderCommand request, CancellationToken ct)
    {
        // request.UserId 是只读的，安全
        // 处理逻辑
        return Task.FromResult(123);
    }
}
```

### 领域事件
事件是过去发生的事情的事实记录，**必须不可变**。`record` 确保了事件发布后不会被篡改，这对于事件溯源（Event Sourcing）至关重要。

```csharp
public record OrderCreatedEvent(Guid OrderId, DateTime OccurredAt) : IDomainEvent;
public record OrderShippedEvent(Guid OrderId, string TrackingNumber) : IDomainEvent;

// 发布事件
_domainEvents.Add(new OrderCreatedEvent(order.Id, DateTime.UtcNow));
```

### 映射工具（AutoMapper / Mapster）
在 CQRS 中，我们经常需要在 `Entity` <-> `Command` <-> `DTO` 之间映射。
*   **AutoMapper**：完全支持 `record`。配置方式与 `class` 相同。
*   **Mapster**：对 `record` 支持极好，甚至支持免配置映射（如果属性名一致）。

```csharp
// Mapster 示例
var dto = entity.Adapt<OrderDto>(); 
// 如果 OrderDto 是 record，Mapster 会自动调用构造函数或 init 属性
```

## 五、数据验证：FluentValidation 集成

虽然 C# 11 引入了 `required`，但复杂的业务规则仍需外部验证库。`FluentValidation` 是 .NET 生态的标准。

### 定义验证器
验证器针对 `record` 类型定义，逻辑清晰。

```csharp
public class CreateUserRequestValidator : AbstractValidator<CreateUserRequest>
{
    public CreateUserRequestValidator()
    {
        RuleFor(x => x.UserName).NotEmpty().Length(3, 50);
        RuleFor(x => x.Email).EmailAddress();
        RuleFor(x => x.Roles).Must(roles => roles.Count > 0).WithMessage("至少需要一个角色");
    }
}
```

### ASP.NET Core 自动验证
在 .NET 6+ 中，可以通过过滤器自动触发验证。

```csharp
// Program.cs
builder.Services.AddValidatorsFromAssemblyContaining<CreateUserRequestValidator>();
builder.Services.AddMvc().AddFluentValidationAutoValidation();

// Controller 中无需手动调用 Validate()
// 如果验证失败，自动返回 400 Bad Request
```

### 双重验证策略
*   **技术校验**：使用 `required` 关键字处理 null/缺失（编译时 + 反序列化时）。
*   **业务校验**：使用 FluentValidation 处理长度、格式、逻辑（运行时）。
这种组合提供了最健壮的安全防线。

## 六、常见陷阱与生产事故避坑

### 可变集合的泄露
即使 `record` 本身是不可变的，如果它包含可变集合（`List<T>`），外部仍可修改集合内容。

```csharp
public record Order(List<string> Items);
var order = new Order(new List<string> { "A" });
order.Items.Add("B"); // 外部成功修改了 order 的内部状态！
```
**解决方案**：
*   暴露 `IReadOnlyList<T>` 而非 `List<T>`。
*   在构造函数中复制集合：`Items = items.ToList()`。
*   使用 `ImmutableList<T>`。

### 循环引用序列化
如果 `record` A 引用 `record` B，B 又引用 A，`ToString()` 或 JSON 序列化会导致栈溢出。
**解决方案**：使用 `[JsonIgnore]` 打断循环，或使用 `ReferenceHandler.Preserve` 配置。

### EF Core 跟踪异常
使用 `record` 作为实体更新时，如果直接 `context.Update(newRecord)`，EF Core 可能认为所有字段都变了（因为它是新对象）。
**解决方案**：
*   先查询实体，再修改属性（需要 class）。
*   或者使用 `context.Entry(entity).CurrentValues.SetValues(newRecord)`。
*   **最佳方案**：实体用 `class`，DTO 用 `record`，中间进行映射。

### 依赖注入中的生命周期
不要在 Singleton 服务中注入 Scoped 的 `record` 实例（虽然 `record` 通常是数据，但如果你通过 DI 注入配置对象）。
*   **注意**：`record` 本身无状态，通常直接 `new`，不通过 DI 容器解析实例，除非是配置选项（`IOptions<T>`）。

## 七、总结与展望

通过本文，我们完成了 `record` 在主流技术栈中的集成拼图：

1.  **API/DTO**：`record` 是首选，配合 `required` 和 `init` 提供强契约。
2.  **JSON 序列化**：`System.Text.Json` 支持良好，注意构造函数绑定和命名策略。
3.  **ORM (EF Core)**：**实体用 Class，值对象用 Record**。这是生产环境的黄金法则。
4.  **CQRS**：命令、查询、事件定义为 `record`，确保消息的不可变性。
5.  **验证**：`required` + FluentValidation 双重保障。

**核心决策表**：

| 场景                     | 推荐类型                        | 理由                   |
| :--------------------- | :-------------------------- | :------------------- |
| API Request/Response   | `record`                    | 不可变，契约清晰，序列化友好       |
| CQRS Command/Event     | `record`                    | 消息不可变，值相等性有用         |
| EF Core 实体 (Aggregate) | `class`                     | 需要变更追踪，可变导航属性        |
| EF Core 值对象 (Owned)    | `record`                    | 符合值对象定义，EF Core 7 支持 |
| 高频计算对象                 | `record struct`             | 性能优先，减少 GC           |
| 多态基类                   | `abstract record` 或 `class` | 需要继承体系               |

4.  定义一个 `Address` (record) 作为值对象，并在 EF Core 中配置为 Complex Type。
