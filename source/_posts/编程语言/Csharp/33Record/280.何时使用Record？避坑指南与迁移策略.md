# 何时使用Record？避坑指南与迁移策略


经过前五篇的旅程，我们从 `record` 的基础语法出发， traversed 了不可变性、模式匹配、底层原理，再到实战集成。现在，你已经掌握了 `record` 的所有技术细节。

然而，掌握技术细节并不等于能写出优秀的架构。在真实的软件开发中，**“能做什么”往往比“不能做什么”更容易误导开发者**。许多团队在引入 `record` 后，陷入了“万物皆 Record"的狂热，导致 ORM 映射失败、多态逻辑混乱、性能意外下降。

作为架构师或技术负责人，你的任务不是推广新技术，而是**在合适的场景使用合适的工具**。本文将为你提供一份完整的**决策树**，明确 `record` 的边界，分享从 `class` 迁移到 `record` 的安全策略，并总结整个系列的核心精髓。

这是你掌握 C# `record` 的收官之作，也是你将其安全引入生产环境的行动指南。

## 一、何时使用 Record？

这是本文最重要的部分。请将此决策树保存为你的团队开发规范的一部分。

### 推荐使用 Record 的场景

| 场景 | 推荐类型 | 理由 | 示例 |
| :--- | :--- | :--- | :--- |
| **DTO / ViewModel** | `record` | 数据载体，需值相等性，不可变更安全 | `UserDto`, `OrderResponse` |
| **API 请求/响应** | `record` | 契约明确，配合 `required` 校验 | `CreateUserRequest` |
| **CQRS 消息** | `record` | 命令/查询/事件本质是数据快照 | `SubmitOrderCommand`, `OrderCreatedEvent` |
| **配置选项** | `record` | 启动后不可变，线程安全 | `AppSettings`, `DbOptions` |
| **值对象 (VO)** | `record` | 符合 DDD 值对象定义，无身份标识 | `Money`, `Address`, `Color` |
| **缓存键** | `record` | 依赖值相等性和稳定的 `GetHashCode` | `CacheKey` |
| **高频小对象** | `record struct` | 减少 GC 压力，性能敏感 | `Vector3`, `Coordinate` |

### 谨慎使用 Record 的场景

| 场景         | 推荐类型                        | 理由                    | 注意事项                             |
| :--------- | :-------------------------- | :-------------------- | :------------------------------- |
| **ORM 实体** | `class`                     | EF Core 需要变更追踪和代理     | 若用 `record`，需配置复杂类型，且属性需可变       |
| **多态基类**   | `class` / `abstract record` | 继承体系复杂，相等性逻辑难维护       | 若用 `record`，务必 `sealed` 或严格控制继承链 |
| **需要反射修改** | `class`                     | `init` 属性对反射不友好       | 某些序列化库或 Mapper 可能需要 `set`        |
| **大型对象**   | `class`                     | `record struct` 拷贝开销大 | 超过 16 字节的 struct 建议用 class       |

### 避免使用 Record 的场景

| 场景 | 推荐类型 | 理由 | 风险 |
| :--- | :--- | :--- | :--- |
| **富业务模型** | `class` | 需要封装复杂行为和可变状态 | `record` 鼓励贫血模型 |
| **需要深拷贝** | `class` | `with` 只是浅拷贝 | 容易引发引用共享 bug |
| **公有的 API 契约** | `class` (慎用) | 修改为 `record` 是破坏性变更 | 改变继承链 (`IEquatable`)，影响二进制兼容 |
| **需要 `null` 语义** | `class` | `record struct` 不能为 `null` | 除非使用 `record struct?` (可空值类型) |

## 二、常见反模式与避坑指南

即使是在推荐场景中，错误的用法也会导致严重问题。以下是生产环境中常见的“翻车”现场。

### 贫血的领域模型
**错误用法**：将所有领域实体都改为 `record`，并将业务逻辑剥离到服务层。
```csharp
// 反模式
public record Order(string Status); // 没有任何行为

public class OrderService
{
    public void Ship(Order order) 
    { 
        // 外部修改状态，破坏了封装
        var newOrder = order with { Status = "Shipped" }; 
    }
}
```
**后果**：对象失去了保护不变量的能力，业务逻辑分散，难以维护。
**修正**：领域实体（Aggregate Root）应使用 `class`，封装行为和状态变更。`record` 仅用于实体内部的价值对象（如 `OrderId`, `Money`）。

### 可变 Record 作为字典 Key
**错误用法**：
```csharp
public record MutableKey(string Id, string Value); // 假设 Value 是 set
var dict = new Dictionary<MutableKey, string>();
var key = new MutableKey("1", "A");
dict[key] = "Data";
key.Value = "B"; // 哈希码变了！
var found = dict.ContainsKey(key); // False! 数据丢失
```
**后果**：集合行为异常，数据“消失”，难以调试。
**修正**：作为 Key 的 `record` 必须**完全不可变**（所有属性 `init` 或 `get`）。

### 过度使用 `with` 表达式
**错误用法**：在高频循环中使用 `with` 创建大量临时对象。
```csharp
// 反模式：性能杀手
for (int i = 0; i < 1_000_000; i++)
{
    config = config with { Counter = i }; // 每次分配新内存
}
```
**后果**：GC 压力激增，性能下降。
**修正**：对于可变状态累积，使用 `class` 或 `struct` 配合可变字段。`with` 仅用于状态流转（如 CQRS）。

### 继承链过深
**错误用法**：
```csharp
public record Base(...);
public record Level1(...) : Base(...);
public record Level2(...) : Level1(...);
public record Level3(...) : Level2(...);
```
**后果**：`Equals` 和 `GetHashCode` 递归调用层数过多，性能下降；位置参数顺序难以维护。
**修正**：优先使用**组合（Composition）**而非继承。如果必须继承，限制在 2 层以内。

### 忽略集合属性的深拷贝
**错误用法**：
```csharp
public record User(List<string> Tags);
var u1 = new User(new List { "A" });
var u2 = u1 with { Tags = u1.Tags }; // 浅拷贝引用
u2.Tags.Add("B"); 
// u1.Tags 也变成了 "A", "B"
```
**修正**：在 `with` 中显式复制集合：`Tags = [.. u1.Tags]` 或使用 `ImmutableList`。

## 三、迁移策略：从 Class 到 Record 的安全演进

如果你有一个现有的大型项目，想要引入 `record`，请遵循以下**渐进式迁移策略**。切勿一次性重构所有代码。

### 阶段 1：DTO 层试点（低风险）
*   **目标**：API 的 Request/Response 对象。
*   **理由**：DTO 通常无行为，浅层结构，不影响核心业务逻辑。
*   **操作**：
    1.  选择一个新的 API 模块。
    2.  将 DTO 定义为 `record`。
    3.  启用 C# 11 `required` 关键字。
    4.  验证 JSON 序列化和 Swagger 文档是否正常。
*   **风险**：极低。即使出现问题，回滚成本低。

### 阶段 2：消息与事件（中风险）
*   **目标**：CQRS 命令、查询、领域事件。
*   **理由**：消息本身应该是不可变的，`record` 能强化这一约束。
*   **操作**：
    1.  将 MediatR 的 Command/Query 改为 `record`。
    2.  检查事件处理器是否依赖消息的可变性。
    3.  利用模式匹配简化事件分发逻辑。
*   **风险**：中等。需确保消息总线序列化兼容。

### 阶段 3：值对象与配置（中高风险）
*   **目标**：DDD 值对象，`IOptions` 配置类。
*   **理由**：值对象天然是不可变的。
*   **操作**：
    1.  识别领域模型中的值对象（如 `Address`, `Money`）。
    2.  重构为 `record`。
    3.  更新 EF Core 配置（使用 Complex Types）。
*   **风险**：高。涉及数据库映射和领域逻辑，需充分测试。

### 阶段 4：核心实体（极高风险，通常不建议）
*   **目标**：聚合根，EF Core 实体。
*   **建议**：**通常不建议迁移**。除非你完全理解 EF Core 的追踪机制且愿意承担维护成本。
*   **理由**：`class` 的可变性对于 ORM 追踪和业务状态机更友好。
*   **例外**：如果你使用 Dapper 或只读投影，可以将投影对象改为 `record`。

### 迁移工具支持
*   **ReSharper / Rider**：提供 "Convert Class to Record" 的重构功能，能自动处理属性迁移。
*   **Roslynator**：免费的 Visual Studio 扩展，提供类似的重构支持。
*   **手动检查清单**：
    *   [ ] 是否破坏了二进制兼容性（公共 API）？
    *   [ ] 是否影响了 JSON 序列化（构造函数参数名匹配）？
    *   [ ] 是否影响了 ORM 映射？
    *   [ ] 是否引入了浅拷贝风险？

## 四、调试与工具链技巧

`record` 的调试体验通常优于 `class`，但也有一些特殊技巧。

### 自定义调试显示
默认情况下，`record` 会打印所有属性。如果属性过多或包含敏感信息，使用 `[DebuggerDisplay]`。
```csharp
[DebuggerDisplay("User {Name} ({Id})")]
public record User(string Id, string Name, string Password);
// 调试时只显示 Name 和 Id，隐藏 Password
```

### 查看生成的代码
想知道 `record` 到底生成了什么？
*   **Visual Studio**：右键 -> "Go to Implementation" 有时不够，建议使用 **ILSpy** 或 **dotPeek** 查看编译后的 IL 代码。
*   **SharpLab.io**：在线工具，粘贴 `record` 代码，查看反编译后的 C# 代码，直观理解编译器魔法。

### 性能分析
使用 **BenchmarkDotNet** 对比 `class` 和 `record` 的性能。
```csharp
// 简单示例
[Benchmark]
public voidTestClass() { new MyClass(1, 2); }
[Benchmark]
public voidTestRecord() { new MyRecord(1, 2); }
```
在生产环境遇到性能瓶颈时，这是排查是否为 `record` 分配开销的金标准。

## 六、未来展望：C# 未来的 Record

C# 语言仍在进化，`record` 的特性也在不断完善。展望未来（C# 13/14+）：

1.  **更好的 ORM 支持**：预计 EF Core 将进一步优化对不可变实体和 `record` 的支持，减少配置负担。
2.  **集合类型改进**：更多不可变集合类型可能会原生集成到语言特性中，配合 `with` 使用。
3.  **性能优化**：JIT 编译器可能会针对 `record` 的 `Equals` 和 `GetHashCode` 进行更高效的内联优化。
4.  **模式匹配增强**：更强大的列表模式（List Patterns）将与 `record` 结合得更紧密。

## 七、最终挑战：综合实战

为了巩固本系列所学，请尝试完成以下**综合挑战**：

**任务**：构建一个简化的电商订单系统核心模块。
1.  **定义值对象**：使用 `record` 定义 `Money`（含货币符号）、`Address`。确保不可变。
2.  **定义实体**：使用 `class` 定义 `Order` 实体（包含 ID，可变状态 `Status`）。
3.  **定义 DTO**：使用 `record` 定义 `CreateOrderRequest` 和 `OrderResponse`。使用 `required`。
4.  **定义事件**：使用 `record` 定义 `OrderCreatedEvent`。
5.  **API 集成**：创建一个 Minimal API 端点，接收 Request，验证，创建实体，发布事件，返回 Response。
6.  **序列化**：确保 JSON 输出符合 camelCase 规范。
7.  **测试**：编写单元测试，验证 `Money` 的值相等性，验证 `with` 表达式修改事件数据不影响原事件。

**完成标准**：
*   代码中无显式 `Equals` 或 `GetHashCode` 实现（利用编译器生成）。
*   无 mutable 集合直接暴露在 `record` 公共属性中。
*   DTO 与 Entity 分离清晰。
