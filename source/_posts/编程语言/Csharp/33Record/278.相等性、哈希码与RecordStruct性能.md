# 相等性、哈希码与Record Struct性能剖析


在前三篇文章中，我们学习了 `record` 的语法、不可变性、继承以及模式匹配。我们学会了如何“优雅地”使用它。然而，作为专业开发者，仅仅知道“怎么用”是不够的。我们需要理解“为什么这么设计”以及“底层是如何运行的”。

理解 `record` 的底层原理，对于以下场景至关重要：
1.  **性能优化**：在高频调用的循环中，选择 `record class` 还是 `record struct`？
2.  **集合行为**：为什么我的 `record` 放入 `Dictionary` 后找不到了？
3.  **调试问题**：为什么两个看起来一样的对象 `Equals` 返回 `false`？
4.  **内存管理**：如何减少 GC 压力？

本文将深入 `record` 的底层实现，剖析 `Equals` 和 `GetHashCode` 的生成逻辑，重点介绍 C# 10 引入的 `record struct`，并通过性能对比分析，帮助你在不同场景下做出最优的技术选型。

---

## 一、相等性原理：编译器生成的魔法

`record` 最核心的特性是**值相等性（Value Equality）**。这是通过编译器自动生成的代码实现的，而不是运行时魔法。

### `IEquatable<T>` 接口
当你定义一个 `record` 时，编译器会自动让它实现 `IEquatable<T>` 接口。这是实现值相等性的标准方式。

```csharp
public record Point(int X, int Y);

// 编译器生成的伪代码
public record Point : IEquatable<Point>
{
    // ... 构造函数和属性

    public bool Equals(Point? other)
    {
        if (ReferenceEquals(null, other)) return false;
        if (ReferenceEquals(this, other)) return true;
        // 递归比较所有公共属性
        return this.X == other.X && this.Y == other.Y;
    }

    public override bool Equals(object? obj)
    {
        // 类型检查
        return obj is Point other && this.Equals(other);
    }
}
```

**关键点**：
*   **递归比较**：如果属性本身也是 `record`，`Equals` 方法会递归调用该属性的 `Equals`。这意味着比较是深度优先的。
*   **类型检查**：`record` 的 `Equals` 通常要求类型完全匹配。`Point(1, 2)` 不会等于 `DerivedPoint(1, 2, "extra")`，即使基类部分相同。这是为了保持值语义的严谨性。
*   **Null 处理**：编译器生成的代码会自动处理 `null` 引用，避免 `NullReferenceException`。

### `PrintMembers` 与 `ToString`
我们之前提到 `ToString` 会自动打印属性。这背后调用了 `PrintMembers` 方法。

```csharp
protected virtual void PrintMembers(System.Text.StringBuilder builder)
{
    builder.Append($"X = {this.X}, ");
    builder.Append($"Y = {this.Y}");
}
```
**扩展性**：如果你需要自定义 `ToString` 的输出（例如隐藏密码字段），只需重写 `PrintMembers` 即可，无需重写整个 `ToString` 逻辑。

## 二、哈希码（HashCode）：集合操作的基石

在 .NET 中，`Equals` 和 `GetHashCode` 是一对孪生兄弟。如果你重写了 `Equals`，**必须**重写 `GetHashCode`，否则 `HashSet` 和 `Dictionary` 将无法正常工作。

### `record` 的哈希码生成
编译器会自动生成 `GetHashCode` 方法，使用 `HashCode.Combine` 来组合所有属性的哈希值。

```csharp
public override int GetHashCode()
{
    // 伪代码
    var hc = new HashCode();
    hc.Add(this.X);
    hc.Add(this.Y);
    return hc.ToHashCode();
}
```

**哈希码契约**：
1.  如果 `a.Equals(b)` 为 `true`，则 `a.GetHashCode()` 必须等于 `b.GetHashCode()`。
2.  如果 `a.GetHashCode()` 不等于 `b.GetHashCode()`，则 `a.Equals(b)` 必须为 `false`。
3.  哈希码在对象生命周期内应保持不变（除非对象状态改变）。

### 致命陷阱：可变 Record 作为字典 Key
这是使用 `record` 时**最常见且严重**的错误。

**场景**：你定义了一个 `record` 并把它用作 `Dictionary` 的 Key。
**问题**：如果该 `record` 是可变的（即有 `set;` 属性），你在放入字典后修改了属性值，哈希码就会改变。

```csharp
var dict = new Dictionary<Person, string>();
var p1 = new Person("Alice", 30); // record class, 默认 init 但可配合 set 修改
dict[p1] = "Key1";

// 假设 Person 有一个 set 属性（虽然 record 默认 init，但人为添加 set 是可能的）
// p1.Age = 31; // 如果 Age 是可写的

// 此时 p1 的 HashCode 变了，但字典内部存储的位置没变
// 查找时会失败，或者导致数据损坏
```

**解决方案**：
1.  **首选**：确保用作 Key 的 `record` 是**完全不可变**的（所有属性 `init` 或 `get`）。
2.  **次选**：使用 `record struct`（值类型，哈希码基于值）。
3.  **避免**：永远不要将可变对象用作字典 Key。

### 自定义哈希码
在某些场景下，你可能只关心部分属性。例如，`Person` 的相等性只看 `Id`，但 `GetHashCode` 需要包含 `Name` 以优化分布。

```csharp
public record User(int Id, string Name)
{
    // 仅基于 Id 计算哈希码
    public override int GetHashCode()
    {
        return Id.GetHashCode();
    }
    
    // 注意：必须同时重写 Equals 以保持一致性
    public override bool Equals(object? obj)
    {
        return obj is User other && this.Id == other.Id;
    }
}
```
**警告**：手动重写 `Equals` 和 `GetHashCode` 会破坏 `record` 的自动值相等性逻辑，通常不建议这样做，除非有非常明确的性能或业务需求。

## 三、Record Struct：值类型的性能革命

C# 10 引入了 `record struct`。这是 `record` 家族中的新成员，它结合了 `record` 的语法糖和 `struct` 的性能优势。

### 什么是 `record struct`？
*   **类型分类**：值类型（Value Type）。
*   **内存分配**：通常分配在栈上（Stack），或内联在对象中（Inline），避免堆分配（Heap Allocation）。
*   **继承**：**不支持继承**（struct 不能继承其他 class 或 record）。
*   **相等性**：默认值相等性（基于字段内容）。

```csharp
// 定义
public record struct Point(int X, int Y);

// 使用
var p1 = new Point(1, 2);
var p2 = new Point(1, 2);
Console.WriteLine(p1 == p2); // True
```

### 为什么需要 `record struct`？
传统的 `record`（即 `record class`）是引用类型。每次 `new` 都会触发堆分配，增加 GC 压力。
*   **场景**：高频创建的小对象（如坐标点、颜色、货币金额）。
*   **优势**：
    1.  **零 GC 压力**：栈分配对象在方法结束时自动释放，无需垃圾回收。
    2.  **缓存友好**：值类型连续内存布局，CPU 缓存命中率更高。
    3.  **复制开销低**：传递 `record struct` 是值拷贝，但如果是小结构体，比引用拷贝（指针）更快。

### `record struct` 的限制
*   **不可继承**：不能用于多态场景（如事件基类）。
*   **可变性风险**：值类型是值拷贝。如果你在方法内修改 `record struct` 的参数，不会影响调用方。但如果你将其放入集合，修改集合中的元素可能不会反映到原变量（取决于引用）。
*   **默认构造函数**：struct 必须有一个隐式的无参构造函数（所有字段为默认值），这可能导致 `required` 属性校验在默认构造函数上失效（需小心处理）。

### 与 `record class` 的对比

| 特性 | `record class` (默认) | `record struct` |
| :--- | :--- | :--- |
| **类型** | 引用类型 (Reference) | 值类型 (Value) |
| **内存** | 堆 (Heap) | 栈 (Stack) / 内联 |
| **GC** | 受 GC 管理 | 自动释放，无 GC 压力 |
| **继承** | 支持 | 不支持 |
| **相等性** | 值相等 (递归) | 值相等 (逐字段) |
| **适用场景** | DTO, 消息, 复杂对象 | 坐标, 金额, 高频小对象 |
| **默认值** | null | 0 / 空值 |

## 四、性能深度剖析：Benchmark 实战

为了直观展示差异，我们进行一个简单的性能测试。

```csharp
using System;
using System.Diagnostics;

// 1. 明确声明 record class 和 record struct
public record class ClassPoint(int X, int Y);
public record struct StructPoint(int X, int Y);

class Program
{
    static void Main()
    {
        Console.WriteLine("预热中...");
        TestPerformance(10); // 预热，消除 JIT 编译时间的影响

        Console.WriteLine("\n正式测试开始...");
        TestPerformance(10_000_000); // 增加到 1000 万次，让差距更明显

        Console.ReadLine();
    }

    public static void TestPerformance(int iterations)
    {
        Stopwatch sw = new Stopwatch();

        // ==========================================
        // 1. Class 测试 (引用类型)
        // ==========================================
        GC.Collect(); // 清理内存，保证测试公平
        long classMemoryBefore = GC.GetAllocatedBytesForCurrentThread();

        sw.Restart();
        var classPoints = new ClassPoint[iterations];
        for (int i = 0; i < iterations; i++)
        {
            classPoints[i] = new ClassPoint(i, i);
        }
        sw.Stop();
        long classAllocTime = sw.ElapsedMilliseconds;

        // 测试 Class 的遍历性能 (求和)
        sw.Restart();
        long classSum = 0;
        for (int i = 0; i < iterations; i++)
        {
            classSum += classPoints[i].X + classPoints[i].Y;
        }
        sw.Stop();
        long classIterTime = sw.ElapsedMilliseconds;
        long classMemoryUsed = GC.GetAllocatedBytesForCurrentThread() - classMemoryBefore;


        // ==========================================
        // 2. Struct 测试 (值类型)
        // ==========================================
        GC.Collect();
        long structMemoryBefore = GC.GetAllocatedBytesForCurrentThread();

        sw.Restart();
        var structPoints = new StructPoint[iterations];
        for (int i = 0; i < iterations; i++)
        {
            structPoints[i] = new StructPoint(i, i);
        }
        sw.Stop();
        long structAllocTime = sw.ElapsedMilliseconds;

        // 测试 Struct 的遍历性能 (求和)
        sw.Restart();
        long structSum = 0;
        for (int i = 0; i < iterations; i++)
        {
            structSum += structPoints[i].X + structPoints[i].Y;
        }
        sw.Stop();
        long structIterTime = sw.ElapsedMilliseconds;
        long structMemoryUsed = GC.GetAllocatedBytesForCurrentThread() - structMemoryBefore;

        // ==========================================
        // 3. 输出报告
        // ==========================================
        Console.WriteLine($"\n迭代次数: {iterations:N0}");
        Console.WriteLine("--------------------------------------------------");
        Console.WriteLine($"{"测试项",-15} | {"Class (引用类型)",-20} | {"Struct (值类型)",-20}");
        Console.WriteLine("--------------------------------------------------");
        Console.WriteLine($"{"初始化耗时",-15} | {classAllocTime + " ms",-20} | {structAllocTime + " ms",-20}");
        Console.WriteLine($"{"遍历求和耗时",-15} | {classIterTime + " ms",-20} | {structIterTime + " ms",-20}");
        // 将 Bytes 转换为 MB 显示
        Console.WriteLine($"{"堆内存分配",-15} | {classMemoryUsed / 1024.0 / 1024.0:F2} MB{"",-14} | {structMemoryUsed / 1024.0 / 1024.0:F2} MB");
        Console.WriteLine("--------------------------------------------------");
    }
}
```



```txt

--------------------------------------------------

--------------------------------------------------
初始化耗时           | 0 ms                 | 4 ms
遍历求和耗时          | 0 ms                 | 0 ms
堆内存分配           | 0.00 MB               | 0.00 MB
--------------------------------------------------

迭代次数: 10,000,000
--------------------------------------------------
测试项             | Class (引用类型)         | Struct (值类型)
--------------------------------------------------
初始化耗时           | 1778 ms              | 157 ms
遍历求和耗时          | 107 ms               | 82 ms
堆内存分配           | 305.18 MB               | 76.29 MB
--------------------------------------------------
```

1. **堆内存分配 (Heap Allocation)**：
    - `new ClassPoint[N]` 只是在堆上创建了一个包含 N 个**指针（引用）** 的数组。接着在 for 循环中，每次 new ClassPoint(i, i) 都会在堆上进行一次独立的内存分配（产生 1000 万个小对象），这会带来巨大的内存开销和 GC（垃圾回收）压力。
    - `new StructPoint[N]` 会直接在堆上分配一块**连续的内存**，大小正好容纳 1000 万个完整的结构体数据。for 循环中只是简单的内存覆写，没有产生任何额外的堆分配。
2. **遍历性能 (CPU Cache 命中率)**：
    - **Struct** 数组在内存中是连续排列的。当 CPU 读取第一个 Struct 时，会顺便把后面的几个也加载到 CPU L1/L2 缓存中（空间局部性），因此遍历速度极快。
    - **Class** 数组中的元素只是指针，它们指向堆中随机散落的实际对象。CPU 遍历时会遭遇大量的 Cache Miss（缓存未命中），必须去内存中寻址，导致速度较慢。


**决策树：何时选择 `record struct`？**
1.  **对象大小**：小于 16 字节（2 个 int 或 1 个 long + 1 个 int）。如果太大，值拷贝开销会超过引用拷贝。
2.  **生命周期**：对象生命周期短，用完即弃。
3.  **行为**：不需要继承，不需要多态。
4.  **场景**：数学计算、游戏循环、高频交易数据。

## 五、常见陷阱与调试技巧

### 调试时的性能问题
当你在 Visual Studio 中调试 `record` 时，`ToString()` 会被调用。如果 `record` 包含巨大的集合或深层嵌套，调试器可能会卡死。
*   **技巧**：重写 `PrintMembers` 限制输出长度，或使用 `[DebuggerDisplay]` 属性。
    ```csharp
    [DebuggerDisplay("User: {Name}")]
    public record User(string Name, string Email);
    ```

### 序列化与相等性
`System.Text.Json` 反序列化 `record` 时，默认使用公共构造函数。如果你手动重写了 `Equals`，JSON 序列化器不会自动感知，它只关心属性值。
*   **注意**：如果 `record` 包含循环引用（A 包含 B，B 包含 A），序列化会栈溢出。确保对象图是树状的。

### `record struct` 的 `with` 表达式
`record struct` 支持 `with`，但由于它是值类型，`with` 会返回一个新的值类型实例。
```csharp
public record struct Point(int X, int Y);
var p = new Point(1, 1);
var p2 = p with { X = 2 }; // 创建新副本
// p.X 仍然是 1
```
这与 `class` 的行为一致，但底层是栈拷贝。

### 数据库主键
**不要**将 `record` 直接映射为数据库实体（Entity Framework Core 支持有限）。
*   **原因**：数据库通常基于 ID（引用/身份）来管理实体，而 `record` 基于值。
*   **建议**：使用 `class` 作为 EF Core 实体，使用 `record` 作为 DTO 或 View Model。

## 六、总结与展望

通过本文，我们深入到了 `record` 的“心脏”：

1.  **相等性**：`record` 通过编译器生成的 `IEquatable<T>` 和递归比较实现值相等性。
2.  **哈希码**：`GetHashCode` 自动组合属性哈希，但**不可变**是将其用作字典 Key 的前提。
3.  **Record Struct**：C# 10 引入的值类型记录，提供了极高的性能，适用于高频小对象，但牺牲了继承能力。
4.  **性能选择**：
    *   通用业务逻辑、DTO、消息 -> `record class`
    *   高频计算、坐标、金额 -> `record struct`
    *   复杂状态、实体 -> `class`

**核心思维**：
选择 `record` 还是 `struct`，本质上是在权衡**灵活性**（继承、堆分配）与**性能**（栈分配、值拷贝）。理解底层原理能让你在架构设计时做出更精准的决策。
