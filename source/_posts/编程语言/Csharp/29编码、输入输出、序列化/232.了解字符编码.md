# 字符编码基础
计算机中储存的信息都是用二进制数表示的；而我们在屏幕上看到的英文、汉字等字符是二进制数转换之后的结果。通俗的说，按照何种规则将字符存储在计算机中，如'a'用什么表示，称为"编码"；反之，将存储在计算机中的二进制数解析显示出来，称为"解码"，如同密码学中的加密和解密。在解码过程中，如果使用了错误的解码规则，则导致'a'解析成'b'或者乱码。


## 核心概念的铁三角关系

不要把“字符集”和“字符编码”混为一谈！我们用**“新华字典”**来做个比喻：

*   **字符集（Character Set）：字库里有哪些字。**
    *   *比喻*：国家出版了一本《新华字典》，里面收录了10000个汉字。这本字典本身就是“字符集”。
    *   *举例*：ASCII（只收录英文字母和符号）、GB2312（收录常用汉字）、Unicode（野心极大，收录地球上所有语言的字符，甚至包括 Emoji 表情😀）。
*   **码位（Code Point）：字符在字典里的“页码”。**
    *   *比喻*：“中”字在《新华字典》的第 1500 页。这个“1500”就是码位。
    *   *举例*：在 Unicode 这本大字典里，“中”字的码位被规定为 `U+4E2D`（4E2D 是十六进制，转换成十进制是 20013）。**注意：码位只是一个数学概念，还不是计算机里的0和1。**
*   **字符编码（Character Encoding）：把页码变成计算机字节的“规则”。**
    *   *比喻*：我现在要把“1500”这个页码存到硬盘上，我是用 2 个字节存，还是 4 个字节存？我是顺着存，还是倒着存？
    *   *举例*：UTF-8、UTF-16、GBK 都是编码规则。同样是存“中”字（码位 U+4E2D），**UTF-8 规则**说：“我要用3个字节存（`E4 B8 AD`）”；**UTF-16 规则**说：“我用2个字节就够了（`4E 2D`）”。

> **C# 新手避坑：**
> C# 中的 `string` 本质上是一串 `char` 数组。
> `char` 在 C# 中占用 **2个字节**，它代表的其实是一个 UTF-16 的代码单元（我们后面会讲）。

## 编码的演进

*   **ASCII：一切的起点（美国人的傲慢）**
    *   7位编码（最高位补0，凑成1个字节），总共只能表示 128 个字符。
    *   包含：英文字母（a-z, A-Z）、数字（0-9）、标点符号和一些控制字符（回车、换行）。
    *   *现状*：所有现代编码（除了UTF-16/32）都**完全兼容 ASCII**。
*   **ANSI / MBCS（多字节字符集）：诸侯割据的“地方方言”**
    *   *背景*：计算机普及到欧洲、亚洲，128个字符根本不够用。于是各国开始自己造字典。
    *   中国造了 **GB2312**（后来扩充为 **GBK**，再后来是 **GB18030**），用 2 个字节表示一个汉字。
    *   台湾造了 **Big5**（繁体字）。
    *   日本造了 **Shift_JIS**。
    *   *灾难*：在 Windows 系统中，微软把这些本地编码统称为 **ANSI**，并引入了“代码页（Code Page）”的概念（中文大陆系统默认代码页是 936，代表 GBK）。如果你把一个日本程序员用 Shift_JIS 写的文本，发给中国程序员用 GBK 的电脑打开，就会出现经典的 **“锟斤拷”、“烫烫烫”等乱码**。
*   **Unicode：宇宙大一统的字符集**
    *   *使命*：把全世界所有字符放进一本字典里，彻底终结 ANSI 时代的乱码战争。
    *   *记住*：Unicode 只是规定了所有字符的“码位”（ID号），它**没有**规定在硬盘上怎么存（0和1怎么排），怎么存是 UTF 家族的事。

## UTF-8 vs UTF-16 vs UTF-32：谁才是最优解？

它们都是把 Unicode 码位翻译成字节的“编码规则”。

*   **UTF-8：Web 和现代系统的绝对霸主（变长：1~4字节）**
    *   *规则*：英文字母占 1 个字节（和ASCII一模一样，完美兼容），常用汉字占 3 个字节，Emoji表情占 4 个字节。
    *   *优点*：极度节省英文文本的空间；没有“字节序（大小端）”问题；互联网传输的绝对标准（HTTP、JSON、HTML 默认全用它）。
    *   *C# 现状*：.NET Core 和 .NET 5+ 以后，整个微软生态全面拥抱 UTF-8。
*   **UTF-16：Windows 和 C# 内存中的“内室总管”（定长/变长：2或4字节）**
    *   *规则*：绝大多数常用字符（包括汉字）占 2 个字节，极少数生僻字和 Emoji 占 4 个字节。
    *   *优点*：处理字符串速度快（在内存中找字符比 UTF-8 容易计算）。
    *   *C# 必考知识点*：**C# 程序运行在内存中时，所有的 `string` 和 `char` 都是 UTF-16 编码的！**
    *   *坑*：既然 C# 中一个 `char` 是 2 个字节，那如果你在字符串里写一个 Emoji `😀`（占4个字节），C# 会认为这个 Emoji 长度是 2！
        `"😀".Length == 2` （新手往往会因为这个在截取字符串时报错）。
    *   *命名槽点*：在 C# 代码里，如果你调用 `System.Text.Encoding.Unicode`，它**实际上指的是 UTF-16**，而不是宏观意义上的 Unicode！（这是微软早期留下的历史遗留命名问题）。
*   **UTF-32：极其浪费空间的土豪（严格定长：4字节）**
    *   *规则*：管你是字母 'A' 还是汉字 '中'，统统用 4 个字节存。
    *   *缺点*：文本体积直接膨胀几倍。几乎没有人会在存文件或网络传输时用它。

## BOM是什么？

这绝对是每一个初级程序员都会掉进去的大坑！

*   **它的初衷是好的**：
    BOM 叫“字节序标记”。在文件的最开头，偷偷塞进几个隐藏的字节。
    比如，Windows 记事本在保存 UTF-8 文件时，会在文件最开头加上 `EF BB BF` 三个字节。
    这样一来，任何软件打开这个文件，只要看到开头有这三个字节，就知道：“哦！这是一个 UTF-8 编码的文件”，直接按 UTF-8 解析，绝不乱码。
*   **为什么它是“万恶之源”？**
    *   Linux、Mac OS 和现代开源软件**极度讨厌 BOM**。它们认为 UTF-8 根本不需要什么标记。
    *   **现象 1**：如果你用带 BOM 的 UTF-8 保存了一段 C# / Java / Python 代码，跑到 Linux 服务器上编译，编译器会报错：“识别不了第一行的非法字符”。
    *   **现象 2**：写 Web API 返回一个带 BOM 的 JSON 给前端，前端解析直接崩溃，因为 JSON 字符串开头多了三个看不见的空字符。
*   **C# 新手避坑指南**：
    在 C# 中，尽量永远使用 **不带 BOM 的 UTF-8**。
    如果你在 C# 里实例化 UTF8：
    ```csharp
    // 带有 BOM 的 UTF8 (不要用这个来写文件发给别的系统！)
    Encoding utf8WithBom = Encoding.UTF8; 
    
    // 不带 BOM 的纯净 UTF8 (推荐做法！❤️)
    Encoding utf8NoBom = new UTF8Encoding(false); 
    ```

## 实战演示代码

作为新手，你可以把这段代码复制到控制台程序（Console App）里跑一下，直观感受一下编码的魔力：

```csharp
using System;
using System.Text;

class Program
{
    static void Main()
    {
        // 注册提供程序，否则现代 .NET 可能不支持 GBK (如果是老 .NET Framework 则不需要这行)
        Encoding.RegisterProvider(CodePagesEncodingProvider.Instance);

        string text = "C#汉字😀"; // 包含英文(1) + 符号(1) + 汉字(2) + Emoji(1)

        Console.WriteLine($"原始字符串: {text}");
        Console.WriteLine($"C#中的长度 (string.Length): {text.Length}"); // 结果是 6！因为 Emoji 占了 2 个 char

        Console.WriteLine("\n--- 开始按不同规则编码成字节 (存入硬盘的形态) ---");

        // 1. UTF-8 规则
        byte[] utf8Bytes = Encoding.UTF8.GetBytes(text);
        Console.WriteLine($"UTF-8  字节数: {utf8Bytes.Length}"); 
        // 算一算: C(1) + #(1) + 汉(3) + 字(3) + 😀(4) = 12字节
        PrintBytes(utf8Bytes);

        // 2. GBK 规则
        Encoding gbk = Encoding.GetEncoding("GBK");
        byte[] gbkBytes = gbk.GetBytes(text);
        Console.WriteLine($"\nGBK    字节数: {gbkBytes.Length}");
        // 算一算: C(1) + #(1) + 汉(2) + 字(2) + 😀(GBK字典里没有Emoji，会变成一个?号，占1字节) = 7字节
        PrintBytes(gbkBytes);

        // 3. 经典乱码重现：用错误的方式打开！
        Console.WriteLine("\n--- 灾难现场：用 UTF-8 的规则去读取 GBK 存的字节 ---");
        string badString = Encoding.UTF8.GetString(gbkBytes);
        Console.WriteLine(badString); // 打印结果：C#? (这就是经典的菱形问号乱码)
    }

    // 辅助方法：把字节数组打印成十六进制
    static void PrintBytes(byte[] bytes)
    {
        Console.Write("十六进制内容: ");
        foreach (byte b in bytes)
        {
            Console.Write($"{b:X2} "); // X2 表示以两位的十六进制大写打印
        }
        Console.WriteLine();
    }
}
```

**总结一下：**
1. 内存中操作字符串（如 `Substring`, `Replace`），C# 默默用的是 **UTF-16**。
2. 存入数据库、写入本地文件、通过 Web API 发送给前端，一定要主动转换成 **无 BOM 的 UTF-8**。
3. 遇到老旧国企系统对接、古董级设备通信，才可能需要请出 **GBK (GB2312)**。

保持这个世界观，你以后处理所有的文本文件和网络数据传输，都能一眼看穿乱码的本质！
