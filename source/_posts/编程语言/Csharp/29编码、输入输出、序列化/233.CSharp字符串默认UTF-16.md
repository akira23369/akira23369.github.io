# 字符与字符串的本质

## `System.String` 与 `char` 的底层真相

很多新手认为：“`char` 就是一个字，`string` 就是一串字”。这个观念在英语国家勉强行得通，但在现代 C# 编程中是**绝对错误**的。

*   **C# 的 `char` 到底是什么？**
    *   在底层，`char` 本质上是一个 **16位（2个字节）的无符号整数**（相当于 `UInt16`）。
    *   它里面装的，不是“字”，而是 **UTF-16 的一个“代码单元（Code Unit）”**。
*   **C# 内存中的字符串默认采用 UTF-16 编码**
    *   *历史原因*：90年代 C#（和 Java）诞生时，Unicode 组织天真地以为世界上所有的字符 65536 个（2个字节）就足够装下了。于是微软决定用 UTF-16 作为内存默认编码，既省空间又好计算。
    *   *打脸时刻*：后来加入了大量的生僻字、古代文字，特别是 **Emoji 表情** 加入后，65536 个位置瞬间爆满，Unicode 被迫扩容。
    *   *现状*：C# 只能硬着头皮继续用 UTF-16。面对超过 2 个字节的字符，就采用了一种“拼乐高”的黑科技——**代理项（Surrogate Pairs）**。

## “字”与“码”的陷阱：代理项

这是每个 C# 程序员都必须跨过的一道坎！

*   **所有的字符在 C# 里都是 1 个 `char` 吗？**
    *   **绝对不是！**
    *   普通的英文、数字、常用汉字（如“中”）：占 **1 个** `char`（2字节）。
    *   生僻字（如“𪚥”，四个龙）、所有的 Emoji（如“😀”）：占 **2 个** `char`（4字节）。
*   **什么是代理项？**
    *   当遇到 4 字节的字符时，C# 会用**两个相邻的 `char`** 来共同表示这一个字。
    *   前面那个叫“高代理项（High Surrogate）”，后面那个叫“低代理项（Low Surrogate）”。它们必须成对出现，单独拎出来任何一个，都是乱码。
*   **陷阱：为什么 `string.Length` 拿到的不是真正的“字符数”？**
    *   `string.Length` 的底层逻辑是：**“统计这个字符串里包含了多少个 `char`”**，而不是人眼看到的“多少个字”。
    *   如果你写 `"😀".Length`，返回结果是 **2**！
    *   *灾难现场*：假设有一个字符串 `string s = "你好😀";`，你想截取前 3 个字，你用了 `s.Substring(0, 3)`。结果程序会把“😀”拦腰截断，只拿到了“高代理项”，打印出来就是一个无法显示的乱码（通常是一个方块或者 `?`）。
*   **终极解法：如何正确计算肉眼可见的“字符数”？**
    *   使用 `System.Globalization.StringInfo`！它能正确识别“代理项”，把它们当成一个“文本元素（Text Element）”来处理。

```csharp
// 演示代码：字符长度的陷阱
string text = "A中😀𪚥"; // 英文 + 常用汉字 + Emoji + 生僻字

// 1. 错误的长度统计
Console.WriteLine($"常规 Length: {text.Length}"); // 结果是 6！ (1 + 1 + 2 + 2)

// 2. 正确的长度统计（按人类肉眼理解的字数）
var stringInfo = new System.Globalization.StringInfo(text);
Console.WriteLine($"实际文字数: {stringInfo.LengthInTextElements}"); // 结果是 4！

// 3. 正确的截取方式（不会截断半个 Emoji）
string safeSubstring = stringInfo.SubstringByTextElements(0, 3);
Console.WriteLine($"安全截取前3个字: {safeSubstring}"); // 输出 "A中😀"
```

## 字符串的不可变性与编码开销

了解了字符在内存中是怎么存的，接下来要了解字符串是如何在内存中“生灭”的。

*   **什么是字符串的不可变性？**
    *   在 C# 中，一旦你在内存中创建了一个 `string`（比如 `string s = "Hello";`），这块内存就**永远不能被修改**了。
    *   如果你执行 `s = s + " World";`，C# 并不是在原来的内存后面追加字母。而是**重新开辟一块新内存**，存入 "Hello World"，然后把 `s` 指向新内存。旧的 "Hello" 就会变成内存垃圾。
*   **频繁进行编码转换或字符串拼接，为什么会导致性能灾难？**
    *   **内存暴涨**：假设你在一个 10000 次的 `for` 循环里做字符串拼接（`s += i.ToString()`），C# 会在内存里创建 10000 个毫无用处的中间字符串，疯狂挤占内存。
    *   **GC（垃圾回收）卡顿**：C# 的垃圾回收器（Garbage Collector）看到这么多没用的死字符串，就会跑出来打扫卫生。GC 工作的时候，会导致你的程序出现短暂的“冻结（Stop The World）”。如果在做游戏（Unity）或高频交易系统，这种卡顿是致命的。
    *   **编码转换的开销**：像 `Encoding.UTF8.GetBytes(str)` 这样的操作，每次都会在堆内存中 `new` 一个全新的 `byte[]` 数组。如果在网络通信中高频调用，同样会制造大量垃圾。

*   **性能优化避坑指南：**

    1.  **多用 `StringBuilder`**：如果你需要循环拼接大量字符串，**绝对不要用 `+` 或 `+=`**。
        ```csharp
        // ❌ 灾难写法
        string result = "";
        for (int i = 0; i < 1000; i++) { result += "A"; } // 产生 1000 个内存垃圾

        // ✅ 高手写法
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < 1000; i++) { sb.Append("A"); } // 只在一块内存上高效修改
        string result = sb.ToString();
        ```
    2.  **(现代 C# 进阶) 了解 `Span<T>` 和 `Memory<T>`**：
        如果你使用的是较新的 .NET (如 .NET 6/8)，在进行字符编码转换时，可以利用 `Span` 技术，直接在现有的内存上操作，实现 **“零内存分配（Zero Allocation）”**，完全不触发 GC。
        *(新手目前只需知道有这个名词即可，等基础扎实了再去学)*
