# `System.Text.Encoding`

## 编码（String->Bytes）与解码（Bytes->String）

这是整个文本处理中最核心的两个动作。**请死死记住方向，千万别搞反！**

*   **编码（Encode）：`GetBytes()` —— 把人类认知的字符串，打包成机器传输的字节流。**
    *   *场景*：你要把一句话存入硬盘、发送到网络另一端的服务器。
    *   *比喻*：把“中文”这两个字，按照 UTF-8 的规则，翻译成 0 和 1 的包裹发出去。
*   **解码（Decode）：`GetString()` —— 拆开机器收到的字节流，还原成人类认识的字符串。**
    *   *场景*：你用 `File.ReadAllBytes()` 从硬盘读了一堆字节，或者通过 HttpClient 收到了一串字节流，需要把它们变成 C# 里的 `string`。

**标准用法演示：**
```csharp
string originalStr = "C#编码高手";

// 1. 编码 (String -> Bytes)
// 潜台词：请用纯净的 UTF-8 规则，把这串文字转成字节。
byte[] utf8Bytes = Encoding.UTF8.GetBytes(originalStr); 
Console.WriteLine($"打包完成，共计 {utf8Bytes.Length} 个字节。");

// 2. 解码 (Bytes -> String)
// 潜台词：我这里有一包按 UTF-8 规则装的字节，请帮我还原成字符串。
string decodedStr = Encoding.UTF8.GetString(utf8Bytes);
Console.WriteLine($"还原结果: {decodedStr}");
```

## 如何获取指定的第三方编码？（新手必踩的 GBK 大坑）

在旧时代的 `.NET Framework`（比如 4.5/4.7）中，如果你想处理老旧国企系统的 GB2312/GBK 数据，你可以直接这样写：
`Encoding gbk = Encoding.GetEncoding("GBK");` // 顺利运行

**但是！在现代的 `.NET Core` 或 `.NET 5/6/7/8` 中，这么写会直接抛出大红错：`NotSupportedException`！**

*   **为什么微软要这么搞？**
    为了让现代 .NET 运行得足够轻量级，微软把那些乱七八糟的各个国家的本地编码（代码页）全都从核心库里踢出去了。默认只自带 UTF-8、UTF-16、ASCII 等几个核心编码。
*   **如何找回 GBK？**
    你必须在程序启动的最早期（比如 `Program.cs` 的第一行），手动把这些老旧编码“注册”回系统里。

```csharp
// 【极其重要】注册代码页提供程序，这行代码只需在程序启动时执行一次！
System.Text.Encoding.RegisterProvider(System.Text.CodePagesEncodingProvider.Instance);

// 注册完成后，再调用 GBK 就不会报错了！
Encoding gbk = Encoding.GetEncoding("GBK"); // 或者用它的代码页数字 936
Encoding shiftJIS = Encoding.GetEncoding("Shift_JIS"); // 日文编码
```
*(注：如果你的项目是极其精简的形态，可能还需要通过 NuGet 安装 `System.Text.Encoding.CodePages` 包，但一般的 Web/桌面项目已经内置了)*

## 编码回退策略：当遇到“坏数据”该怎么办？

想象一下：你正在按 UTF-8 的规则解码一包字节，但是由于网络波动，其中有 1 个字节损坏了，不符合 UTF-8 的语法。C# 会怎么处理？

C# 提供了两种应对“坏数据”的策略：

*   **策略一：替换策略（Replacement）—— 系统的默认行为**
    *   *做法*：C# 非常宽容。碰到不认识的字节，它不会报错，而是塞一个**替换字符**进去凑数。
    *   如果是解码失败，你会看到经典的 **``**（Unicode 替换字符，码位 U+FFFD）。在一些不支持该字符的环境下，会显示为 `?`。
    *   *缺点*：掩盖了错误。数据已经被悄悄破坏了，你却不知道。
*   **策略二：异常策略（Exception）—— 严谨高手的选择**
    *   *做法*：零容忍！只要碰到哪怕一个不认识的字节，立刻抛出 `DecoderFallbackException` 异常，程序崩溃报错。
    *   *场景*：金融系统、医疗数据、严谨的 API 接口。你宁愿报错，也绝对不能让错误的数据混入数据库！

**高级实战：如何开启异常策略？**
```csharp
// 制造一个损坏的 UTF-8 字节（255 不是合法的 UTF-8 起始字节）
byte[] badBytes = new byte[] { 255, 65, 66 }; 

// 1. 默认的宽容模式（你会得到 "?AB" 或 "AB"，不会报错）
string tolerantResult = Encoding.UTF8.GetString(badBytes);
Console.WriteLine($"宽容模式结果: {tolerantResult}");

// 2. 严谨的异常模式（重新定制一个 UTF-8 武器）
// 参数说明：(不带BOM, 开启抛出异常机制)
Encoding strictUtf8 = new UTF8Encoding(false, true); 

try
{
    // 这行代码会直接触发大红报错！
    string strictResult = strictUtf8.GetString(badBytes);
}
catch (DecoderFallbackException ex)
{
    Console.WriteLine($"拦截到非法数据，拒绝解析！错误详情: {ex.Message}");
}
```

## 乱码的本质与自愈

你一定在网上见过诸如“锟斤拷”、“烫烫烫”、“屯屯屯”、“??”这样的乱码。现在我们用兵器库来解剖它们。

*   **乱码产生的唯一原因：打包（Encode）和拆包（Decode）用的规则不一致！**
    *   *比喻*：发件人用“摩斯密码”写了封信，收件人却用“拼音”去读，读出来的绝对是天书。

*   **“手误”导致乱码后，数据还能救回来吗？**
    很多新手发现乱码的第一反应是去 `Replace` 或者写各种奇葩的转换代码。我们要分情况讨论：

    **🟢 抢救成功的情况（逻辑错乱，但数据没丢）**
    假设对方用 GBK 发送了字节（含中文），但你用默认的 ISO-8859-1（西欧字符集）解析了它。因为西欧字符集是单字节硬解，它没有丢弃任何字节，只是全显示成了奇怪的西欧符号（比如 `ÃºÅí`）。
    *   *急救方案*：把它按西欧字符集**重新编码回原来的字节**，再用 GBK **正确解码**。
    ```csharp
    // 假设 badString 是你拿到的乱码字符串
    // 1. 把错误的字符串退回成原始的字节流 (解铃还须系铃人)
    byte[] originalBytes = Encoding.GetEncoding("ISO-8859-1").GetBytes(badString);
    // 2. 用正确的规则重新拆包
    string goodString = Encoding.GetEncoding("GBK").GetString(originalBytes);
    ```

    **彻底凉凉的情况（被“替换策略”污染，神仙难救）**
    这是最常见也是最悲剧的情况。对方用 GBK 发送中文，你却用 UTF-8 去解码。
    由于 GBK 的字节序列完全不符合 UTF-8 的语法，C# 触发了**替换策略（Fallback）**，把无法识别的字节统统变成了 `` 或 `?`。
    *   *诊断*：一旦原始字节被替换成 `?`，原始信息就**永久丢失**了！这就像把一份文件放进了碎纸机，拿出来的碎纸是无法还原的。经典的“锟斤拷”就是这种破坏性替换产生的衍生乱码。
    *   *结论*：不要试图用代码去修复已经被污染成 `?` 的字符串。**唯一的解决办法是：找到读取数据的第一现场（流读入的地方），在源头将解码规则改为正确的！**

## 总结与进阶

当你掌握了这套 `Encoding` 兵器库的使用方法后，你的 C# 技能树已经点亮了非常关键的一个枝桠：

1.  遇到字符串转字节，条件反射般地想到 `Encoding.UTF8.GetBytes`。
2.  遇到老系统对接抛出不支持的异常，立刻想起 `RegisterProvider` 这个救命口诀。
3.  在核心业务中，遇到来路不明的字节流，懂得使用 `new UTF8Encoding(false, true)` 来进行严格防守。
4.  再遇到乱码，不再瞎猜，而是分析：**“发送方用了什么规则？我这边的流读取时用了什么规则？”**

**进阶小建议：**
以后在阅读或调用 C# 库文件时（比如 `File.ReadAllText`, `StreamReader`, `HttpClient`），你会发现它们往往都有一个重载方法允许你传入 `Encoding` 参数。**作为一个高手，哪怕它默认是 UTF-8，也要养成显式传入 `Encoding.UTF8` 的好习惯**，这样代码的意图会无比清晰，绝不留下隐患！
