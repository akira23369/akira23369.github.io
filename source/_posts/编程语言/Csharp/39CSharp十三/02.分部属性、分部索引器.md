在 C# 13 中，**分部属性（Partial Properties）** 和 **分部索引器（Partial Indexers）** 的引入，补全了 C# “分部成员”家族的最后一块拼图。

要理解这个特性的价值，我们必须先明白一个核心驱动力：**源生成器（Source Generators）**。虽然你可以手动编写分部属性，但这 99% 是为现代 .NET 的自动生成代码技术铺路的。

下面为您详细拆解这两个特性，对比过去与现在的写法，并提供实际的应用场景。

---

### 分部属性

分部属性允许你将一个属性的 **“声明”** 和 **“实现”** 拆分到不同的文件中（必须在同一个 `partial` 类/结构体中）。

#### 痛点：为什么我们需要分部属性？（以 MVVM 为例）
在 C# 13 之前，如果我们使用类似 MVVM Toolkit 这样的源生成器库来实现数据绑定（INotifyPropertyChanged），我们面临一个很别扭的语法。

**C# 13 之前的写法（痛点）：**
开发者只能在一个**私有字段（Field）** 上打特性，让源生成器去生成公开的属性。
```csharp
// 开发者手写的代码：
public partial class UserViewModel
{
    // 痛点 1: 我们明明想要一个公开的 Name 属性，却被迫写一个私有字段
    // 痛点 2: 如果要给生成的属性加 XML 注释或特性，语法极其丑陋（如 [property: JsonIgnore]）
    [ObservableProperty]
    private string _name; 
}
```
*源生成器在后台生成的代码：* `public string Name { get... set... }`。
这导致代码可读性差，IDE 的智能提示在代码生成前也无法识别 `Name` 属性。

#### C# 13 的救赎：自然的属性声明
有了分部属性，你终于可以直接声明你**真正想要的属性**了！源生成器只需要负责把内部的 `get` 和 `set` 逻辑填满即可。

**C# 13 的写法（优雅）：**
```csharp
// 文件1：开发者手写的代码 (UserViewModel.cs)
public partial class UserViewModel
{
    // 直接写出属性的签名，加上 partial 关键字
    [ObservableProperty]
    public partial string Name { get; set; } 
}
```

```csharp
// 文件2：源生成器自动生成的代码 (UserViewModel.g.cs)
public partial class UserViewModel
{
    private string _name; // 生成器自动补全后台字段

    // 补全 get 和 set 的具体逻辑
    public partial string Name 
    { 
        get => _name; 
        set
        {
            if (_name != value)
            {
                _name = value;
                OnPropertyChanged(nameof(Name)); // 触发 UI 更新
            }
        }
    }
}
```
**带来的好处：**
1. **所见即所得**：你写的是属性，API 暴露的也是属性。
2. **注释和特性完美工作**：你可以直接在 `public partial string Name` 上写 `/// <summary>` 和 `[Required]` 特性，它们会无缝应用到最终的属性上。

### 分部索引器

索引器本质上就是**带有参数的属性**（通常表现为 `this[int index]`）。既然属性支持了 `partial`，索引器自然也顺理成章地支持了。

#### 应用场景：强类型包装器与互操作
假设你在写一个包装底层 JSON 数据、字典或与 WebAssembly/C++ 互操作的代码。你需要暴露一个索引器供外部使用，但具体从底层读取数据的脏活累活希望交给源生成器。

**例子：自动生成字典的包装逻辑**

```csharp
// 文件1：开发者手写的代码 (ConfigManager.cs)
public partial class ConfigManager
{
    // 我只定义我要一个可以通过 string 键访问 string 值的索引器
    [GenerateDictionaryWrapper] // 假设这是一个自定义的源生成器特性
    public partial string this[string key] { get; set; }
}
```

```csharp
// 文件2：源生成器自动生成的代码 (ConfigManager.g.cs)
public partial class ConfigManager
{
    // 生成器提供了底层数据结构
    private readonly Dictionary<string, string> _internalStore = new();

    // 生成器实现了索引器的具体逻辑
    public partial string this[string key] 
    { 
        get 
        {
            return _internalStore.TryGetValue(key, out var val) ? val : "Default";
        }
        set 
        {
            _internalStore[key] = value;
            Console.WriteLine($"配置已更新: {key} = {value}");
        }
    }
}
```
就像分部属性一样，分部索引器让你可以定义 API 契约（签名），并将繁琐的存取逻辑外包给自动化工具。

---

### 必须遵守的严格规则

C# 编译器对分部属性/索引器有非常严格的匹配规则，声明部分（Defining）和实现部分（Implementing）必须高度一致：

1. **宿主必须是 Partial**：包含它们的类或结构体必须被标记为 `partial`。
2. **签名必须完全一致**：
   * 属性类型必须完全相同（包括可空引用类型注解，如 `string?`）。
   * 索引器的参数类型、顺序、名称必须完全相同。
3. **访问修饰符必须一致**：如果声明是 `public`，实现也必须是 `public`。
4. **访问器 (get/set) 必须匹配**：
   * 如果声明部分写了 `{ get; set; }`，实现部分必须同时实现 `get` 和 `set`。
   * 如果声明部分只有 `{ get; }`（只读），实现部分也只能实现 `get`。
5. **不支持自动属性语法**：
   当你写 `public partial string Name { get; set; }` 时，编译器不会把它当成自动属性（不会在底层生成隐藏字段），它只代表一个**等待被实现的签名契约**。实现部分必须显式提供 `get` 和 `set` 的代码主体（通常配合一个手动声明的或生成的后台字段）。

### 总结

C# 13 的分部属性和索引器表面上只是加了一个关键字，实际上它是 **.NET 现代化开发体验（特别是依赖 AOT 编译和源生成器的场景）的一块重要基石**。它消除了为了代码生成而不得不编写反人类语法的痛点，让代码回归了最自然、面向对象的本来面目。
