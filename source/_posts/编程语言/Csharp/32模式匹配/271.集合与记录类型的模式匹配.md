# 集合与记录类型的模式匹配

> 本文目标：  
> - 掌握 **列表模式（List Pattern）** 的系统用法  
> - 学会对 `record` / 元组 等“值对象”进行模式匹配  
> - 理解 `Deconstruct` 与“位置模式”的协作  
> - 在实际业务（DTO、命令、事件流）中使用这些特性

---

## 一、List Pattern 与“结构化集合匹配”

**列表模式（List Pattern）** 是 C# 11 引入的，用于匹配：

- 数组：`int[]` / `string[]` / `T[]`
- 一些实现了 `IEnumerable` 特定形状的集合（如 `List<T>` 等）

可以直观地判断：

- 集合是不是空的；
- 长度是多少；
- 第几个位置是什么；
- 头尾元素是什么；
- 中间的一段要不要忽略。

### 最基础的几种形态

```csharp
int[] nums = { 1, 2, 3, 4 };

// 精确匹配：长度为 4 且内容是 1,2,3,4
if (nums is [1, 2, 3, 4])
{
    Console.WriteLine("完全匹配");
}

// 匹配长度为 0（空数组）
if (nums is [])
{
    Console.WriteLine("空数组");
}

// 匹配长度为 1
if (nums is [var only])
{
    Console.WriteLine($"只有一个元素：{only}");
}
```

说明：

- `[]`：空；
- `[a]`：一个元素；
- `[a, b]`：两个元素；
- 模式中的元素本身也可以是**任意模式**（类型、常量、关系等）。

---

## 二、使用 `..`：忽略中间或剩余的元素

`..` 是“切片占位符”：表示“剩余的所有元素”（可以是 0 个）。

### 匹配前缀

```csharp
int[] nums = { 1, 2, 3, 4 };

if (nums is [1, 2, ..])
{
    Console.WriteLine("以 1,2 开头");
}
```

- `[1, 2, ..]`：前两个元素是 1、2，后面随便。

### 匹配后缀

```csharp
if (nums is [.., 3, 4])
{
    Console.WriteLine("以 3,4 结尾");
}
```

- `[.., 3, 4]`：尾部两个元素是 3、4。

### 匹配“首尾”，忽略中间

```csharp
if (nums is [1, .., 4])
{
    Console.WriteLine("首位是 1，末位是 4");
}
```

---

## 三、捕获首尾和中间元素

列表模式可以配合 `var` 来捕获元素值，而 `.. var rest` 捕获“剩余的一段”。

### 捕获首尾

```csharp
if (nums is [var first, .., var last])
{
    Console.WriteLine($"首位：{first}, 末位：{last}");
}
```

### 捕获中间子数组

```csharp
if (nums is [1, .. var middle, 4])
{
    Console.WriteLine($"中间有 {middle.Length} 个元素");
}
```

`middle` 的类型通常是与原数组类型一致的切片类型（编译器会生成合适的代码）。

## 四、列表模式 + switch：解析命令/消息格式

列表模式非常适合下面这种场景：

- 命令行参数；
- 字符串消息分片（`Split` 后的数组）；
- 简单的“命令 + 参数”协议。

### 示例：命令解析（升级版）

```csharp
string HandleCommand(string[] args) => args switch
{
    [] => "Usage: app <add|sub|mul|div> <a> <b>",

    ["help"] => "Help: add/sub/mul/div a b",

    ["add", var a, var b] when int.TryParse(a, out var x)
                             && int.TryParse(b, out var y)
        => (x + y).ToString(),

    ["sub", var a, var b] when int.TryParse(a, out var x)
                             && int.TryParse(b, out var y)
        => (x - y).ToString(),

    ["mul", var a, var b] when int.TryParse(a, out var x)
                             && int.TryParse(b, out var y)
        => (x * y).ToString(),

    ["div", var a, var b] when int.TryParse(a, out var x)
                             && int.TryParse(b, out var y)
                             && y != 0
        => (x / y).ToString(),

    _ => "Invalid command"
};
```

组合点：

- 每一种命令都是一个列表模式：`["add", var a, var b]`；
- `when` 守卫负责**语义校验**（能不能转换为数字、除数是否为 0）；
- 整个方法就是一个“命令路由 + 参数解析 + 业务执行”的模式匹配表达式。

## 五、列表模式 + 属性模式：复杂 DTO 中的集合字段

假设有一个购物车对象：

```csharp
record CartItem(string Sku, int Quantity);

record Cart(CartItem[] Items);
```

我们想做一些判断：

- 购物车为空；  
- 只有一件商品；  
- 第一件是某个特定 SKU；  
- 同时用数量控制。

### 示例：Cart 规则匹配

```csharp
string DescribeCart(Cart cart) => cart switch
{
    { Items: [] } => "购物车为空",

    { Items: [var single] } => $"只有一个商品：{single.Sku}, 数量 {single.Quantity}",

    { Items: [ { Sku: "VIP-001", Quantity: >= 1 }, .. ] } 
        => "包含 VIP 专属商品",

    { Items: [.., { Quantity: <= 0 }] } 
        => "存在数量非法的商品",

    _ => "普通购物车"
};
```

这里出现了多层嵌套：

- `cart` 用**属性模式**：`{ Items: [...] }`；
- `Items` 是数组，用**列表模式**：`[]` / `[var single]` / `[ {...}, .. ]`；
- 内部的 `{ Sku: "VIP-001", Quantity: >= 1 }` 又是属性模式 + 关系模式。

这种写法非常适合做“规则引擎”风格的判定。

## 六、record 类型：模式匹配的天然好伙伴

**record** 是 C# 9 引入的“记录类型”，非常适合作为：

- DTO/消息对象；
- 值对象（DDD）；
- 配置/选项载体。

特点：

- 值相等语义（内容相等）：`record` 比较字段，而不是引用；
- 可以自动生成 `Deconstruct`，支持位置模式；
- 简洁声明：一行写完字段。

### 基本 record 示例

```csharp
public record Person(string Name, int Age);
```

使用：

```csharp
var p = new Person("Alice", 30);
Console.WriteLine(p.Name); // Alice
Console.WriteLine(p.Age);  // 30
```

默认会生成：

```csharp
public void Deconstruct(out string name, out int age)
{
    name = this.Name;
    age = this.Age;
}
```

因此，**位置模式 (Positional Pattern)** 可以直接用于 `Person`。

---

## 七、record + 位置模式：模式匹配更简写

### 在 switch 中使用 record 的位置模式

```csharp
string DescribePerson(Person p) => p switch
{
    ("Alice", _) => "这是 Alice",
    (_, < 18)    => "未成年人",
    (_, >= 60)   => "老年人",
    _            => "普通人"
};
```

这里 `(Name, Age)` 以位置来匹配：

- `("Alice", _)`：名字是 Alice，年龄随意；
- `(_, < 18)`：不管名字，只看年龄；
- `_`：兜底。

### record + 属性模式 vs 位置模式

同样逻辑可以写成属性模式：

```csharp
string DescribePerson(Person p) => p switch
{
    { Name: "Alice" }      => "这是 Alice",
    { Age: < 18 }          => "未成年人",
    { Age: >= 60 }         => "老年人",
    _                      => "普通人"
};
```

两种方式都行，选择建议：

- 字段数量少、顺序合理时：位置模式简洁；
- 字段多或只关注少数字段时：属性模式更清晰。

## 八、record + List Pattern：事件流 / 命令流处理

在 C# 的模式匹配中，**`record`（记录类型） + 列表模式（List Pattern）** 的组合，是近年来 C# 向函数式编程迈进的一大杀器。这种组合特别适合用来处理**事件流（Event Stream）** 或**命令流（Command Stream）**。

简单来说：
*   **`record`** 负责完美地定义**单个事件/命令**（不可变、带有数据、支持继承）。
*   **列表模式 `[...]`** 负责优雅地匹配**多个事件/命令的时间序列**（谁先谁后、发生了什么组合）。

这两个特性的结合，让你能用极度声明式（Declarative）的代码，替代过去极其复杂的 `if-else` 嵌套或状态机（State Machine）逻辑。

---

### 基础回顾：为什么是 Record 和 列表模式？

#### **Record 的优势（C# 9+）**
在事件驱动（Event-Driven）或 CQRS 架构中，事件（Event）和命令（Command）必须是**不可变的（Immutable）**。因为已经发生的事情不能被修改。`record` 天生提供了基于值的相等性、不可变性以及极其简洁的语法。

```csharp
// 定义一个命令/事件的基类
public abstract record UserAction;

// 定义具体的行为
public record Login(string UserId, string IpAddress) : UserAction;
public record AddToCart(string ProductId, int Quantity) : UserAction;
public record Checkout() : UserAction;
public record Payment(decimal Amount) : UserAction;
public record Logout() : UserAction;
```

#### **列表模式的优势（C# 11+）**
列表模式允许你对数组、`Span<T>` 或 `List<T>` 等序列的内容进行模式匹配。你可以匹配特定长度、特定元素，甚至使用 `..`（切片模式）来匹配任意数量的元素。

---

### 核心玩法：处理事件流/命令流

想象一下，你有一个用户的操作历史记录（一个 `UserAction[]` 数组）。你需要根据用户的**行为轨迹**来触发不同的业务逻辑（比如：发放勋章、识别欺诈、推荐商品）。

过去，你可能要写循环、设标志位（Flag）来判断。现在，结合这两者，你可以直接“看着序列说话”：

#### 场景 A：识别特定的行为序列（例如：秒杀作弊检测）

```csharp
public string AnalyzeUserBehavior(UserAction[] actions)
{
    return actions switch
    {
        // 模式1：刚登录就直接支付，且金额大于10000（可疑行为：跳过了购物车和结算）
        [Login(_, var ip), Payment(> 10000)] 
            => $"警告：IP {ip} 存在高危跳步支付行为！",

        // 模式2：登录 -> 加购物车 -> 结算 -> 支付（标准的完美购物流）
        [Login(var uid, _), AddToCart, Checkout, Payment] 
            => $"用户 {uid} 完成了标准购物流程。",

        // 模式3：空序列
        [] => "用户没有任何操作。",

        // 其他任何情况
        _ => "普通操作序列"
    };
}
```

#### 场景 B：使用切片模式 `..`（忽略中间过程，只关注首尾或局部特征）

在实际的事件流中，用户可能会点很多次无关的按钮，所以你经常需要用到 `..` （匹配 0 个或多个元素）和 `_`（丢弃任意单个元素）。

```csharp
public string DetectPatterns(UserAction[] stream)
{
    return stream switch
    {
        // 只要流的结尾是【支付】然后紧接着【登出】，不管前面干了啥
        [.., Payment(var amount), Logout] 
            => $"用户支付了 {amount} 后安全退出。",

        // 提取流的第一个和最后一个事件，不管中间有多长
        [var firstEvent, .., var lastEvent] 
            => $"该用户的起手动作是 {firstEvent.GetType().Name}，最后动作是 {lastEvent.GetType().Name}。",

        // 连续两次加购物车操作（中间没有别的操作），切片可以放在两头
        [.., AddToCart(var p1, _), AddToCart(var p2, _), ..] 
            => $"用户连续对比/添加了商品 {p1} 和 {p2}。",

        _ => "未命中特殊规则"
    };
}
```

---

### 为什么这个模式如此强大？

#### 取代复杂的状态机
在游戏开发或复杂业务中，传统做法是维护一个 `CurrentState`，每来一个事件就写一堆 `if (CurrentState == xxx && Event == yyy)`。
使用 `Record + List Pattern`，你不再需要维护“当前状态”，你只需要提取最近的 $N$ 个事件组成一个数组，直接进行模式匹配。这被称为**事件溯源（Event Sourcing）** 风格的处理。

#### 代码即文档
当你写出 `[Login, .., Checkout, Payment]` 时，连非技术人员（产品经理）都能大致猜出这段代码在拦截什么场景。它的意图表达得非常直接。

#### 极强的防错性
`Record` 支持解构（Deconstruct）。在列表模式中，你可以直接把 `Record` 里面的属性解构出来参与逻辑判断（比如上面例子中的 `> 10000`）。这比 `action.Amount > 10000` 更加内聚。

---

### 进阶技巧：配合 `Span<T>` 提升性能

在处理大量的连续事件流时（比如高频交易、IoT设备日志流），频繁创建数组会造成垃圾回收（GC）压力。列表模式**完美支持 `Span<T>` 和 `ReadOnlySpan<T>`**。

你可以结合滑动窗口（Sliding Window）来处理无限延伸的事件流：

```csharp
// 假设这是不断流进来的大量日志
ReadOnlySpan<UserAction> window = GetRecentActions(); 

// 零分配（Zero-Allocation）的模式匹配
if (window is [.., Payment, Payment, Payment])
{
    Console.WriteLine("警告：检测到连续三次支付请求，可能是系统重试Bug！");
}
```

### 总结

`Record` + 列表模式（List Pattern）是 C# 走向现代化的标志之一。
*   **Record** 把数据打包成了整齐的“积木”。
*   **List Pattern** 提供了一个“模具”，用来检验这些积木拼接出的形状。

在你以后写**状态追踪、日志分析、前端用户行为埋点分析、撤销/重做（Undo/Redo）队列**时，一定要想起这个模式，它会帮你的代码瘦身 50% 以上！

## 九、Deconstruct 与自定义位置模式

不只是 record，普通 class/struct 也可以通过 `Deconstruct` 支持位置模式。

### 自定义 Deconstruct

```csharp
class Point
{
    public int X { get; }
    public int Y { get; }

    public Point(int x, int y) => (X, Y) = (x, y);

    public void Deconstruct(out int x, out int y) => (x, y) = (X, Y);
}
```

### 使用位置模式匹配 Point

```csharp
string DescribePoint(Point p) => p switch
{
    (0, 0)         => "原点",
    (var x, 0)     => $"在 X 轴上，X = {x}",
    (0, var y)     => $"在 Y 轴上，Y = {y}",
    (var x, var y) => $"普通点 ({x}, {y})"
};
```

这里 `(x, y)` 实际调用的是 `Deconstruct(out x, out y)`。

### Deconstruct + List Pattern：二维点集合解析

```csharp
Point[] points = GetPoints();

string Analyze(Point[] ps) => ps switch
{
    [] => "没有点",

    [(0, 0)] => "只有一个原点",

    [(0, 0), ..] => "包含原点",

    [(_, > 0), ..] => "第一个点在上半平面",

    _ => "其他情况"
};
```

- `(0, 0)`：位置模式匹配一个点；
- 与列表模式 `[ ... ]` 结合后，就像“列表中包含点的模式”。

## 十、在 Web / DDD 中的实战思路

### Web API 的请求 DTO

```csharp
public abstract record ApiRequest;
public record CreateUser(string Name, string Email) : ApiRequest;
public record ChangeEmail(int UserId, string NewEmail) : ApiRequest;
public record DeleteUser(int UserId) : ApiRequest;
```

控制器里：

```csharp
Task<IResult> Handle(ApiRequest req) => req switch
{
    CreateUser(var name, var email)       => HandleCreate(name, email),
    ChangeEmail(var id, var newEmail)     => HandleChangeEmail(id, newEmail),
    DeleteUser(var id)                    => HandleDelete(id),
    _                                     => Task.FromResult(Results.BadRequest())
};
```

- 类型模式 + 位置模式；
- record 非常适合表示“封闭集合”的几种请求。

### DDD 中命令 / 事件

- Command：record 表示；
- Event：record 表示；
- Inbound 消息解析后用 switch pattern 做分发；

整体会得到一个“很函数式”的风格：  
> 数据类型 + 模式匹配 + 纯函数处理。

## 十一、常见坑 & 注意事项

1. **List Pattern 对集合类型有要求**  
   - 理论上要满足一定的形状（带索引/Count 等），数组和 `List<T>` 等常见类型都 OK；  
   - 对某些自定义集合可能不直接支持，这时要么用数组中转，要么自己实现适配。

2. **不要用 List Pattern 做重度性能敏感的动态解析**  
   - 编译器会生成遍历逻辑，多次模式匹配可能多次遍历；  
   - 大部分业务场景足够快；  
   - 在热路径的高频循环中，如上万次调用，建议做性能测试或使用更加手动的逻辑。

3. **record 默认是引用类型**  
   - 如果要值类型 semantics + record 功能，可以用 `record struct`；  
   - `record` 默认实现 `Equals/GetHashCode` 以字段为依据。

4. **位置模式字段顺序受 Deconstruct 决定**  
   - 顺序与构造顺序一致（对 record 来说）；  
   - 如果对顺序不确定，优先使用属性模式 `{ Name: ..., Age: ... }`，可读性更好。

## 十二、小结与下一篇预告

本篇你掌握了：

- 列表模式（List Pattern）：
  - `[ ]` / `[a]` / `[a, b]` / `[a, ..]` / `[.., b]` / `[a, .., b]`
  - 捕获首尾、中间数组，配合 `var` 使用
- record 与模式匹配：
  - record 的自动 Deconstruct、位置模式、属性模式；
  - 与 List Pattern、类型模式共同用于事件流/命令流解析；

  - 普通 class/struct 也可参与位置模式；
- 在 Web API / DDD 中使用 record + pattern 构建“数据驱动分发”。
