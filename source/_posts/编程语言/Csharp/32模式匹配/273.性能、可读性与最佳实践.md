# 性能、可读性与最佳实践

> 本文目标：  
> - 搞清楚：模式匹配在性能上大致什么水平、有什么坑需要避免  
> - 总结：怎样写模式匹配代码才“团队可读、容易维护”  
> - 给出：一些“什么时候该用 / 不该用”的经验判断  

---

## 一、性能：模式匹配会不会很慢？

简短结论：

- 对绝大部分业务代码来说，  
  **只要不是在超高频内层循环里疯狂匹配，性能完全不用担心**；
- 编译器会把 `switch + pattern` 编译成高效的分支结构，  
  很多时候和你手写的 if/else 性能差不多，甚至更好。

### 常见几种模式下的编译行为（概念级理解）

1. **枚举 / 常量 switch**  
   - 编译器会尽量用“跳转表（jump table）”或二分树进行优化；
   - 性能非常好，可以认为是 O(1) 或 O(log N) 的跳转。

2. **类型模式（`case X x`）**  
   - 本质是 `isinst`（类型检查）+ 类型转换；
   - 和你手写 `if (x is X)` 差不多。

3. **属性模式 / 列表模式**  
   - 会生成对属性/索引的访问代码，逐步检查；
   - 只要你访问的属性本身不是特别昂贵，就可以认为开销小。

4. **带 `when` 守卫的模式**  
   - 匹配到该分支后，还要执行一个 `bool` 条件表达式；
   - 逻辑越复杂，越可能成为性能瓶颈；
   - 但这和你在 if/else 里写相同逻辑是一样的成本。

### 什么时候需要对性能特别敏感？

- 高并发 + 热路径（例如：每个请求都要执行几万次模式匹配）；
- 需要处理百万级数据集合，并在循环中频繁用复杂嵌套模式；
- 使用了大量 `when` 且守卫条件内部有昂贵操作（IO、数据库、复杂计算）。

此时建议：

- 用 profiler（性能分析器）实际测一测，而不是想象；
- 把昂贵逻辑抽出来缓存或提前计算；
- 必要时，用更“机械”的写法（手写索引访问、Dictionary 查表等）。

## 二、可读性：模式匹配写多了，会不会变成另一种屎山？

会，如果不注意。  
所以我们需要一些**约束和规范**，让模式匹配保持可读。

### 原则 1：一条模式只表达“一种情形”

反例（难读）：

```csharp
order switch
{
    { Customer.IsVip: true, Amount: > 1000, Items: [_, ..], Channel: "Online" }
        when SomeComplexCheck(order) && DateTime.Now.DayOfWeek is not DayOfWeek.Sunday
        => "VIP_BIG_ONLINE_SPECIAL",
    _ => "NORMAL"
};
```

推荐拆分：

- 把“复杂判断”（例如 `SomeComplexCheck`、日期判断）移到 `when` 或辅助方法；
- 每条 pattern 尽量描述“结构 + 简单条件”。

改写示例：

```csharp
bool IsSpecialDay() => DateTime.Now.DayOfWeek is not DayOfWeek.Sunday;

bool IsOrderQualified(Order o) => SomeComplexCheck(o);

string GetTag(Order o) => o switch
{
    { Customer.IsVip: true, Amount: > 1000, Items: [_, ..], Channel: "Online" }
        when IsSpecialDay() && IsOrderQualified(o)
        => "VIP_BIG_ONLINE_SPECIAL",

    _ => "NORMAL"
};
```

阅读成本明显降低。

### 原则 2：适当“布局”和“分块”

推荐：

- 按业务分类加注释；
- 将相关模式写在一起，不相关的分开。

示例：

```csharp
string GetDiscountTag(Order o) => o switch
{
    // ===== 新人优惠 =====
    { Customer.IsNew: true, Amount: >= 100 } => "NEW_100",
    { Customer.IsNew: true, Amount: >= 50  } => "NEW_50",

    // ===== VIP 优惠 =====
    { Customer.IsVip: true, Amount: >= 200 } => "VIP_200",
    { Customer.IsVip: true, Amount: >= 100 } => "VIP_100",

    // ===== 通用优惠 =====
    { Amount: >= 500 } => "COMMON_500",

    _ => "NONE"
};
```

让人一眼就看出：这是按“新人 / VIP / 通用”分块的规则。

### 原则 3：模式中的常量和字段名，要语义清晰

避免魔法数字：

```csharp
{ Amount: >= 1000 } => "VIP",
```

改为：

```csharp
const decimal VipThreshold = 1000m;

{ Amount: >= VipThreshold } => "VIP",
```

再配合命名良好的 record/属性，模式就像“规则文档”。

## 三、团队协作：怎样让别人也看得懂、也愿意用？

### 渐进式引入，而不是“一夜重写”

建议步骤：

1. 先在**新代码**里使用模式匹配（不会破坏旧逻辑）；
2. 找一段典型的“复杂 if/else”老代码，  
   用模式匹配重构一版做对比，让团队成员看到收益；
3. 形成统一的“模式写法规范”（例如上面的原则 1~3），写到代码规范中。

### 统一几种常用写法模板

例如：

- **DTO/状态分类**：统一采用 `switch 表达式 + 属性模式`；
- **状态机**：统一采用 `(状态, 事件) switch`；
- **错误分类**：统一采用 `Error` 的类型 + 属性模式。

给团队一个“推荐模板”，大家用起来风格会趋同，不会乱。

### 配合代码评审

在 CR 中重点关注：

- pattern 是否过于复杂、难读；
- `_` 是否过早出现，遮挡了后面的分支；
- 是否把“业务重要规则”集中在一处，还是散落在多个 if/else 里。

## 四、常见陷阱与避免方式

### 陷阱 1：忘记处理 null

例如：

```csharp
string GetName(Person p) => p switch
{
    { Age: < 18 } => "Child",
    _ => "Adult"
};
```

如果 `p` 可能为 null，这个匹配会直接跳到 `_` 分支，而不会抛异常。  
有时候你期望这种行为，有时候你不是。

建议：

- 对外部输入（比如 Controller 参数）：显式处理 null：

```csharp
string GetName(Person? p) => p switch
{
    null => "Unknown",
    { Age: < 18 } => "Child",
    _ => "Adult"
};
```

- 对显然不应为 null 的内部对象，可以直接不写 null 分支，出了问题让异常暴露设计缺陷。

### 陷阱 2：兜底分支 `_` 写太早

```csharp
var text = value switch
{
    _ => "Other",
    1 => "One",
    2 => "Two"
};
```

后面的分支永远不会匹配，编译器会警告，但仍要养成“兜底在最后”的习惯：

```csharp
var text = value switch
{
    1 => "One",
    2 => "Two",
    _ => "Other"
};
```

### 陷阱 3：`when` 中有副作用 / 昂贵操作

```csharp
result switch
{
    { Error: NetworkError } when LogAndReturnFalse(result) => ...,
    ...
};
```

一旦你在 `when` 里做了副作用（写日志、改状态等），  
要注意：守卫条件**只有在该模式匹配成功时才会执行**；  
若模式很模糊，可能根本不会执行到 `when`。

建议：

- 把副作用放在分支内部（switch 语句里）；
- 或者在外层做副作用，pattern 只负责**判断**。

## 五、什么时候“应该用模式匹配”？

可以用几条简单经验来判断：

### 有一个“主变量”，根据它的不同形态走不同逻辑

例如：

- 一个 DTO 的不同组合字段；
- 一个状态枚举 + 事件；
- 一个错误类型。

这种时候，**非常适合**用 `switch + pattern` 把逻辑集中起来。

### 逻辑主要是“分类”、“映射”而不是“大量副作用”

例如：

- 输入 → 输出（标签计算、状态转换、文本描述）；
- 错误 → HTTP 状态码；
- DTO → ViewModel。

这种纯函数逻辑，用 `switch 表达式` 非常合适。

### 需要问自己：代码读起来像“业务规则表”吗？

如果你的逻辑本质上就是一堆规则：

> “如果满足条件 A，就做 X；满足条件 B，就做 Y；否则 Z”

那用模式匹配写出的代码看起来就会像一张表，是好事。

## 六、什么时候“先别急着用模式匹配”？

### 只判断一两个简单条件

```csharp
if (age < 18)
    return "Child";
else
    return "Adult";
```

这种不需要强行改成：

```csharp
return age switch
{
    < 18 => "Child",
    _    => "Adult"
};
```

二者皆可，看团队风格；  
对简单场景，if/else 更容易被新人接受。

### 逻辑主要是“过程式操作”，不是分类

例如：

```csharp
if (!File.Exists(path))
{
    Directory.CreateDirectory(Path.GetDirectoryName(path)!);
    File.WriteAllText(path, "...");
    Log(...);
}
else
{
    // ...
}
```

这里主要是操作 IO 和副作用，不是对数据进行分类；  
继续用 if/else 很自然。

### 团队尚未熟悉 pattern，且项目已经比较稳定

- 在这种项目中，可以在**新功能**中使用模式匹配，而不是大规模重构旧代码；
- 等大家熟悉之后，再逐步重构关键逻辑，避免大面积“不必要的改动”。

## 七、与其他语言对比：你已经在用“高阶语法了”

多说一句，模式匹配在很多现代语言中都是核心特性：

- F# / Scala / Haskell / Rust：早就有很强的 pattern matching；
- Kotlin / Swift：也有更“表达式化”的 `when`；
- C# 这几年是在向这些方向靠拢，让你能在 C# 中写出更“声明式”的代码。

你现在学会的 C# 模式匹配，  
已经是向这些语言靠拢的关键一步，用好了，整个代码风格都会升级一大截。
