# 复杂模式组合与嵌套

> 本文目标：  
> - 学会在真实业务中**组合和嵌套各种模式**  
> - 掌握从“屎山 if/else”重构到“清爽 pattern + switch”的套路  
> - 兼顾：可读性、可维护性、性能与团队风格  

---

## 一、复杂模式组合的核心思路

现代 C# 模式匹配可以做三件事：

1. **按类型分发**：不同类型走不同逻辑  
2. **按结构/属性分发**：同一类型，不同字段组合走不同逻辑  
3. **按值范围/状态分发**：不同输入值区间走不同逻辑  

复杂模式，就是这三类组合在一起：  
> 类型 + 属性 + 列表 + 关系 + 逻辑(and/or/not) + when 守卫

核心规则只有两条：

- **把“判条件”变成“描述形态”**（pattern 就是数据的形态）  
- **从“最具体”写到“最通用”**（优先级高的分支写前面）

下面进入实操。

## 二、案例 1：从多层 if/else 重构为模式匹配

### 原始代码（典型业务判断）

假设有一个订单优惠逻辑：

```csharp
decimal CalcDiscountRate(Order order)
{
    if (order == null) return 1.0m;

    if (order.Customer != null && order.Customer.IsVip)
    {
        if (order.Amount >= 1000)
        {
            return 0.8m;
        }
        else if (order.Amount >= 500)
        {
            return 0.85m;
        }
        else
        {
            return 0.9m;
        }
    }
    else
    {
        if (order.Amount >= 2000)
        {
            return 0.85m;
        }
        else if (order.Amount >= 1000)
        {
            return 0.9m;
        }
        else
        {
            return 1.0m;
        }
    }
}
```

问题：
- 嵌套多层，很难一眼看全逻辑；
- 新人加规则容易改坏。

### 分析逻辑维度

我们有三个条件维度：
- `order == null`
- `order.Customer.IsVip`（VIP vs 非 VIP）
- `order.Amount` 区间（>= 2000、>=1000、>= 500、其他）

### 重构为 switch 表达式 + 属性模式 + 关系模式

```csharp
decimal CalcDiscountRate(Order? order) => order switch
{
    null => 1.0m,

    // VIP 客户
    { Customer.IsVip: true, Amount: >= 1000 } => 0.8m,
    { Customer.IsVip: true, Amount: >= 500  } => 0.85m,
    { Customer.IsVip: true }                 => 0.9m,

    // 非 VIP
    { Amount: >= 2000 } => 0.85m,
    { Amount: >= 1000 } => 0.9m,

    _ => 1.0m
};
```

特点：
- 所有分支平铺，无嵌套；
- VIP 逻辑与普通逻辑分块，肉眼阅读非常清晰；
- 新增逻辑（比如“黑金 VIP”）只要在顶部插入分支。

## 三、属性模式嵌套：深层对象结构判断

### 场景：复杂 DTO 条件

有这样的对象：

```csharp
class PaymentRequest
{
    public string Channel { get; set; } = ""; // "Wechat", "Alipay", "Bank"
    public decimal Amount { get; set; }
    public CustomerInfo? Customer { get; set; }
    public Address? BillingAddress { get; set; }
}

class CustomerInfo
{
    public bool IsVip { get; set; }
    public int Level { get; set; } // 1~5
}

class Address
{
    public string Country { get; set; } = "";
}
```

### 传统写法片段（很多人会这么写）

```csharp
if (request.Channel == "Wechat")
{
    if (request.Amount > 0 && request.Amount <= 2000)
    {
        if (request.Customer != null && request.Customer.IsVip)
        {
            // ...
        }
        else
        {
            // ...
        }
    }
    else if (request.Amount > 2000)
    {
        // ...
    }
}
else if (request.Channel == "Alipay")
{
    // ...
}
else
{
    // ...
}
```

### 模式匹配重构：属性 + 关系 + 逻辑组合

```csharp
string CalcPaymentRoute(PaymentRequest req) => req switch
{
    // 微信 + VIP + 0 < 金额 <= 2000
    { Channel: "Wechat",
      Amount: > 0 and <= 2000,
      Customer.IsVip: true } => "Wechat_VIP_Normal",

    // 微信 + 非VIP + 0 < 金额 <= 2000
    { Channel: "Wechat",
      Amount: > 0 and <= 2000 } => "Wechat_Normal",

    // 微信 + 大额
    { Channel: "Wechat",
      Amount: > 2000 } => "Wechat_HighValue_RiskCheck",

    // 支付宝 + 海外用户
    { Channel: "Alipay",
      BillingAddress.Country: not "CN" } => "Alipay_Oversea",

    // 支付宝 + 国内
    { Channel: "Alipay",
      BillingAddress.Country: "CN" } => "Alipay_CN",

    // 银行渠道
    { Channel: "Bank" } => "Bank_Transfer",

    // 兜底
    _ => "Unknown"
};
```

亮点：
- 利用嵌套属性：`Customer.IsVip`, `BillingAddress.Country`;
- `not "CN"` 体现逻辑模式；
- 将原来嵌套的 if 层级“摊平”。

## 四、列表模式 + 属性模式：处理复杂集合输入

### 场景：命令行/消息参数解析

假设一个简单的命令定义：字符串数组 `args`：

- `["add", "1", "2"]` → 加法  
- `["sub", "x", "y"]` → 减法  
- `["help"]` → 帮助  
- 空数组 → 打印帮助  

### 列表模式重构

```csharp
string HandleArgs(string[] args) => args switch
{
    [] => "Usage: calc <add|sub> <a> <b>",

    ["help"] => "Help: add a b / sub a b",

    ["add", var a, var b] when int.TryParse(a, out _) && int.TryParse(b, out _) 
        => (int.Parse(a) + int.Parse(b)).ToString(),

    ["sub", var a, var b] when int.TryParse(a, out _) && int.TryParse(b, out _) 
        => (int.Parse(a) - int.Parse(b)).ToString(),

    _ => "Invalid command"
};
```

组合点：
- 列表模式 `[ ... ]` 匹配参数结构；
- `var a, var b` 捕获参数；
- `when` 守卫做数据合法性检查；
- 把“命令路由 + 参数解析”合在一处，逻辑清晰。

## 五、嵌套模式 + when：复杂业务规则分发

### 场景：风控规则

某平台对订单进行风控打标签：

- 大额（>5000）+ 新用户（注册 <30 天） → 高危  
- 大额 + 老用户 + 海外 → 中危  
- 金额正常 + IP/地址异常 → 中危  
- 其他 → 低危  

假设有：

```csharp
record RiskContext(
    Order Order,
    User User,
    LocationInfo Location
);

record Order(decimal Amount);
record User(DateTime RegisterTime);
record Location(string Country, bool IsIpSuspicious);
```

### 重构为 switch 表达式

```csharp
string CalcRiskLevel(RiskContext ctx) => ctx switch
{
    // 大额 + 新用户
    { Order.Amount: > 5000m,
      User.RegisterTime: var t } when (DateTime.UtcNow - t).TotalDays < 30
        => "High",

    // 大额 + 老用户 + 海外
    { Order.Amount: > 5000m,
      Location.Country: not "CN" }
        => "Medium",

    // 金额正常 + IP 或 地址异常
    { Order.Amount: <= 5000m,
      Location: { IsIpSuspicious: true } }
        => "Medium",

    // 其他
    _ => "Low"
};
```

要点：
- 结构信息（订单金额、注册时间、地理信息）用**属性模式**描述；
- “是否新用户”是时间差逻辑，适合放在 `when` 守卫中；
- 规则按照风险优先级由高到低排列（避免被低级规则遮挡）。

## 六、可读性与可维护性：防止“pattern 版本屎山”的原则

模式匹配可以写得很优雅，也可以写得非常难懂。  
推荐几个实践原则：

### 原则 1：每条分支尽量“短”和“单一目的”

不推荐：

```csharp
{ A: > 0 and < 10, B: > 5 and < 15, C: null, D: { X: > 0 and < 5, Y: not 0 } } => ...
```

推荐：
- 拆成多个规则；
- 把特别复杂的判断逻辑提出来用**命名方法**或**布尔属性**。

```csharp
bool IsSmallValidRange(Context c) =>
    c.A is > 0 and < 10 &&
    c.B is > 5 and < 15;

string Handle(Context c) => c switch
{
    { C: null, D: { X: > 0 and < 5, Y: not 0 } } when IsSmallValidRange(c)
        => "OK",
    _   => "Fail"
};
```

### 原则 2：适当加注释或“按业务分块”

```csharp
string GetDiscountTag(Order o) => o switch
{
    // ===== VIP 客户 =====
    { Customer.IsVip: true, Amount: >= 2000 } => "VIP_2000",
    { Customer.IsVip: true, Amount: >= 1000 } => "VIP_1000",

    // ===== 普通大客户 =====
    { Amount: >= 5000 } => "BIG_5000",
    { Amount: >= 2000 } => "BIG_2000",

    // ===== 其他 =====
    _ => "NONE"
};
```

让阅读者立刻知道哪些规则是同一业务块。

### 原则 3：尽量用模式表达“结构”，用 `when` 表达“复杂逻辑”

- 结构性的条件：字段值、类型、区间 → 用 pattern；
- 计算性的条件：时间差、调用其他方法等 → 用 `when`。

## 七、性能与编译器行为（简单了解一下就够）

- 编译器会对 `switch` + 模式做优化，  
  对枚举、常量等会生成**跳转表**或**高效的分支树**；
- 对于几十个分支的复杂模式，手写 if/else 通常不会比编译器更聪明；
- 真正可能有影响的是：  
  - 在每个分支里做了昂贵操作（数据库/IO），那是业务设计问题；  
  - 或者使用了大量 `when` 并重复计算，可以用局部变量/方法减少重复计算。

简单原则：
- 不要过早为模式匹配担心性能；
- 如果确实在一个高频循环中使用了巨量分支，  
  再用 profiler 测一下，考虑是否用字典映射、缓存表等替代。

## 八、小练习：自己动手重构 if/else

试着把下面代码重构为 switch + pattern（可以当做练习）：

```csharp
string GetLevel(User u)
{
    if (u == null) return "Unknown";

    if (u.IsAdmin) return "Admin";

    if (u.IsVip)
    {
        if (u.Score > 1000) return "VIP-Diamond";
        if (u.Score > 500)  return "VIP-Gold";
        return "VIP";
    }
    else
    {
        if (u.Score > 800) return "User-Plus";
        return "User";
    }
}

```

目标：
- 使用属性模式、关系模式；
- 逻辑按“管理员 > VIP > 普通”优先级排列；
- 保持可读性。

```cs
string GetLevel2(User u) => u switch
{
    null => "Unknown",
    { IsAdmin: true } => "Admin",
    
    // 如果逻辑变复杂，你也可以配合使用 logical patterns (and)
    { IsVip: true, Score: > 1000 } => "VIP-Diamond",
    { IsVip: true, Score: > 500 } => "VIP-Gold",
    { IsVip: true } => "VIP",
    
    { Score: > 800 } => "User-Plus",
    _ => "User"
};
```
