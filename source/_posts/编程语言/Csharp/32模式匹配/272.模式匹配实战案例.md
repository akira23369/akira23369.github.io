## 一、输入验证与 DTO 规则校验

场景：Web API 接收一个“创建订单”的请求 DTO，需要做一系列校验：

- 用户 Id 必填且 > 0  
- 商品列表不能为空  
- 每个商品数量 > 0  
- 支付方式为特定集合之一  
- 如果是“线下支付”，必须有门店 Id  

### DTO 定义（示例）

```csharp
public record CreateOrderRequest(
    int UserId,
    List<OrderItem> Items,
    string PaymentMethod, // "Online", "Offline"
    int? StoreId          // 线下支付才需要
);

public record OrderItem(
    int ProductId,
    int Quantity
);
```

### 传统写法（典型 if/else）

```csharp
List<string> Validate(CreateOrderRequest req)
{
    var errors = new List<string>();

    if (req == null)
    {
        errors.Add("请求不能为空");
        return errors;
    }

    if (req.UserId <= 0)
        errors.Add("用户 Id 非法");

    if (req.Items == null || req.Items.Count == 0)
        errors.Add("商品列表不能为空");
    else
    {
        foreach (var item in req.Items)
        {
            if (item.ProductId <= 0)
                errors.Add("商品 Id 非法");
            if (item.Quantity <= 0)
                errors.Add("商品数量必须大于 0");
        }
    }

    if (req.PaymentMethod != "Online" && req.PaymentMethod != "Offline")
        errors.Add("支付方式非法");

    if (req.PaymentMethod == "Offline" && req.StoreId is null)
        errors.Add("线下支付必须指定门店");

    return errors;
}
```

可以工作，但非常“命令式”，逻辑散落。

### 用模式匹配重构“单项规则”

核心思路：  
> 把每条规则写成一个“模式 + 错误描述”的小表，然后统一应用。

先写几个辅助函数：

```csharp
bool HasInvalidItem(CreateOrderRequest req) =>
    req.Items is null or [] ||
    req.Items.Any(i => i.ProductId <= 0 || i.Quantity <= 0);
```

用 switch + pattern 写多个规则：

```csharp
IEnumerable<string> Validate(CreateOrderRequest? req) => req switch
{
    null => new[] { "请求不能为空" },

    { UserId: <= 0 } => new[] { "用户 Id 非法" },

    { Items: null or [] } => new[] { "商品列表不能为空" },

    { Items: var items } when items.Any(i => i.ProductId <= 0)
        => new[] { "存在商品 Id 非法的条目" },

    { Items: var items } when items.Any(i => i.Quantity <= 0)
        => new[] { "存在数量 <= 0 的商品条目" },

    { PaymentMethod: not ("Online" or "Offline") }
        => new[] { "支付方式非法" },

    { PaymentMethod: "Offline", StoreId: null }
        => new[] { "线下支付必须指定门店" },

    _ => Array.Empty<string>()
};
```

特点：

- 每个分支只负责“一条规则”；
- 规则整体像配置表，很适合后期维护；
- 条件多时，可以把复杂逻辑提到 `when` 或辅助方法中。

进一步，你可以把多条错误合并（例如：从“第一次匹配的错误”升级为“收集所有错误”），那就需要稍复杂的写法（遍历规则表），这里就不展开了。

## 二、命令路由

场景：你有一个“内部命令总线”，所有命令都实现同一个接口或基类，由一个 Handler 统一分发。

### 命令定义

```csharp
public abstract record Command;

public record CreateUser(string Name, string Email) : Command;
public record ChangeEmail(int UserId, string NewEmail) : Command;
public record DisableUser(int UserId) : Command;
```

### 传统分发方式

```csharp
async Task HandleCommandAsync(Command command)
{
    switch (command)
    {
        case CreateUser c:
            await HandleCreateUser(c);
            break;
        case ChangeEmail c:
            await HandleChangeEmail(c);
            break;
        case DisableUser c:
            await HandleDisableUser(c);
            break;
        default:
            throw new InvalidOperationException("未知命令类型");
    }
}
```

这已经算比较现代的写法了，但我们可以用 **switch 表达式** 让它更“函数式”。

### 使用 switch 表达式进行分派

```csharp
Task HandleCommandAsync(Command command) => command switch
{
    CreateUser c  => HandleCreateUser(c),
    ChangeEmail c => HandleChangeEmail(c),
    DisableUser c => HandleDisableUser(c),
    _             => throw new InvalidOperationException("未知命令类型")
};
```

再进一步：你可以结合 **记录+位置模式** 简化参数传递：

```csharp
Task HandleCommandAsync(Command command) => command switch
{
    CreateUser(var name, var email)
        => HandleCreateUser(name, email),

    ChangeEmail(var id, var newEmail)
        => HandleChangeEmail(id, newEmail),

    DisableUser(var id)
        => HandleDisableUser(id),

    _ => throw new InvalidOperationException("未知命令类型")
};
```

优势：

- 所有命令路由写在一个地方，非常直观；
- 新增命令时，只需增加一个 `record` + 一个分支。

## 三、状态机实现

场景：订单状态流转（简化版）：

- `Created` → 可变为 `Paid` 或 `Cancelled`  
- `Paid` → 可变为 `Shipped` 或 `Refunded`  
- `Shipped` → 可变为 `Completed`  
- 其余组合为非法状态流转  

### 定义状态和事件

```csharp
public enum OrderStatus
{
    Created,
    Paid,
    Shipped,
    Completed,
    Cancelled,
    Refunded
}

public enum OrderEvent
{
    Pay,
    Cancel,
    Ship,
    Complete,
    Refund
}
```

### 传统写法：嵌套 if / switch

```csharp
OrderStatus Transit(OrderStatus current, OrderEvent ev)
{
    switch (current)
    {
        case OrderStatus.Created:
            if (ev == OrderEvent.Pay) return OrderStatus.Paid;
            if (ev == OrderEvent.Cancel) return OrderStatus.Cancelled;
            break;

        case OrderStatus.Paid:
            if (ev == OrderEvent.Ship) return OrderStatus.Shipped;
            if (ev == OrderEvent.Refund) return OrderStatus.Refunded;
            break;

        case OrderStatus.Shipped:
            if (ev == OrderEvent.Complete) return OrderStatus.Completed;
            break;
    }

    throw new InvalidOperationException($"非法状态流转：{current} -> {ev}");
}
```

逻辑正确，但看起来很琐碎。

### 用元组 + switch 表达式重构

```csharp
OrderStatus Transit(OrderStatus current, OrderEvent ev) => (current, ev) switch
{
    (OrderStatus.Created, OrderEvent.Pay)    => OrderStatus.Paid,
    (OrderStatus.Created, OrderEvent.Cancel) => OrderStatus.Cancelled,

    (OrderStatus.Paid, OrderEvent.Ship)      => OrderStatus.Shipped,
    (OrderStatus.Paid, OrderEvent.Refund)    => OrderStatus.Refunded,

    (OrderStatus.Shipped, OrderEvent.Complete) => OrderStatus.Completed,

    _ => throw new InvalidOperationException($"非法状态流转：{current} -> {ev}")
};
```

进一步用位置模式解构也可以，但简单枚举时直接 tuple 更自然。

优点：

- 清晰呈现“状态 × 事件”的映射；
- 很像一张“转移表”，业务同学也容易读懂；
- 所有非法组合统一落到 `_` 分支抛错。

## 四、错误与异常分类处理

场景：你有一个服务调用结果，要根据错误类型做不同处理：

- 网络错误：记录日志 + 重试  
- 身份认证失败：返回 401  
- 业务校验失败：400 + 错误信息  
- 其他未预料错误：500  

### 定义错误模型（示例）

```csharp
public abstract record Error;

public record NetworkError(string Message, bool IsTimeout) : Error;
public record AuthError(string Reason) : Error;
public record ValidationError(string Field, string Message) : Error;
public record UnknownError(Exception Exception) : Error;
```

假设你的服务返回：

```csharp
public record ServiceResult<T>(bool IsSuccess, T? Data, Error? Error);
```

### 模式匹配进行分类处理

```csharp
IResult ToHttpResult<T>(ServiceResult<T> result) => result switch
{
    { IsSuccess: true, Data: var data } 
        => Results.Ok(data),

    { Error: NetworkError { IsTimeout: true, Message: var msg } }
        => Results.StatusCode(StatusCodes.Status504GatewayTimeout), // 或者重试处理

    { Error: NetworkError { IsTimeout: false, Message: var msg } }
        => Results.StatusCode(StatusCodes.Status503ServiceUnavailable),

    { Error: AuthError { Reason: var reason } }
        => Results.Unauthorized(),

    { Error: ValidationError { Field: var field, Message: var msg } }
        => Results.BadRequest(new { Field = field, Message = msg }),

    { Error: UnknownError { Exception: var ex } }
        => Results.StatusCode(StatusCodes.Status500InternalServerError),

    _ => Results.StatusCode(StatusCodes.Status500InternalServerError)
};
```

关键点：

- `ServiceResult<T>` 使用属性模式；  
- `Error` 使用 **类型模式 + 属性模式**；  
- 逻辑分类集中，避免在业务代码处处 `if (error is NetworkError)`。

## 五、业务配置与规则表：用模式写“规则引擎雏形”

场景：营销优惠规则（简化版）：

- 新用户 + 首单金额 ≥ 100 → 首单券 20  
- VIP 用户 + 金额 ≥ 200 → 立减 30  
- 大额订单（金额 ≥ 500） → 免运费  
- 其他无优惠  

### 模型定义

```csharp
public record UserInfo(bool IsNewUser, bool IsVip);

public record OrderContext(UserInfo User, decimal Amount);
```

### 用 switch 表达式写“规则表”

```csharp
string? CalcPromotionTag(OrderContext ctx) => ctx switch
{
    // 新用户首单优惠
    { User.IsNewUser: true, Amount: >= 100 } => "NEW_USER_20",

    // VIP 大额
    { User.IsVip: true, Amount: >= 200 } => "VIP_30",

    // 大额免运费
    { Amount: >= 500 } => "FREE_SHIPPING",

    // 无优惠
    _ => null
};
```

规则说明：

- 业务规则按优先级排序：新用户 > VIP > 大额；  
- 新增规则非常自然：只需要在前面/中间插入一个分支；  
- 更复杂时，可以引入 `when` 承载一些计算型条件。

## 六、综合小项目草图：REST API + Pattern Matching

假设你有一个 Minimal API 项目，框架代码如下：

```csharp
app.MapPost("/orders", async (CreateOrderRequest req, IOrderService service) =>
{
    // 1. 校验
    var errors = Validate(req).ToArray();
    if (errors.Length > 0)
        return Results.BadRequest(new { Errors = errors });

    // 2. 执行业务命令
    var cmd = new CreateOrderCommand(req.UserId, req.Items, req.PaymentMethod, req.StoreId);
    ServiceResult<OrderDto> result = await service.ExecuteAsync(cmd);

    // 3. 按错误类型转成 HTTP 应答
    return ToHttpResult(result);
});
```

其中：

- `Validate(req)` 一节可以用第一节中的模式匹配校验写法；  
- `ExecuteAsync` 内部可以用“命令路由 + 状态机 + 模式匹配”做分发；  
- `ToHttpResult(result)` 可以用“错误分类处理”的模式匹配写法。

整套下来，你的项目会呈现出一种风格：

- 所有“根据数据形态分支”的地方，都写成 pattern + switch；  
- 逻辑清晰、靠前、集中，减少深层嵌套；  
- 新增规则时不改 if/else 树，而是在 pattern 表中插入一行。

## 七、模式匹配实战时的几个习惯建议

1. 从“局部”开始，而不是一次性重写整个项目  
   - 找一段长 if/else，先重构一小块成 pattern，感受一下再扩展。

2. 优先用 `switch 表达式` 处理“输入 → 输出”的函数  
   - 特别适合 DTO 映射、状态转移、分类标签计算等。

3. 复杂逻辑分三层：
   - 结构/类型判断 → pattern  
   - 简单数值条件 → 关系模式 + 逻辑模式  
   - 复杂计算型条件 → `when` + 辅助方法

4. 不要强行追求“全项目无 if/else”  
   - 模式匹配是工具，不是宗教；  
   - 简单一两个条件，用 if/else 更直观，就继续用即可。
