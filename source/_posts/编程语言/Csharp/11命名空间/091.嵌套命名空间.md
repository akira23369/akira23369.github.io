# 嵌套命名空间

## 什么是嵌套命名空间？
当一个命名空间内部包含另一个命名空间时，内部的命名空间被称为**嵌套命名空间**。

在大型应用程序中，随着代码库的增长，单一的主命名空间中可能会堆积过多的类和接口。嵌套命名空间的核心目的就是**建立子分组 (Sub-grouping)**，将庞大且职责繁杂的类型进一步细分。例如，在人力资源（`HR`）模块中，可能存在众多类型的员工，通过建立管理层（`Mgr` 或 `Management`）子命名空间，可以将与经理相关的类型（如 `Manager`、`AssistantManager`）独立出来，提高代码的可读性和组织性。

## 嵌套命名空间的声明方式

在 C# 中，有多种方式可以声明嵌套命名空间。

### 传统的块级作用域嵌套
最基础的方式是通过大括号的嵌套来实现：

```csharp
namespace HR
{
    // 在 HR 内部声明嵌套的 Mgr 命名空间
    namespace Mgr
    {
        public interface IManager 
        { 
            void ManageTeam();
        }

        public class Manager : IManager 
        {
            public void ManageTeam() { /* 业务逻辑 */ }
        }

        public class AssistantManager 
        { 
            // 业务逻辑
        }
    }
}
```

### 使用点语法声明 (更推荐的现代写法)
结合《C# 核心技术指南》(C# in a Nutshell) 以及现代 C# 的编程风格，为了避免多层大括号带来的缩进地狱，通常建议直接使用**点语法 (Dot Notation)** 来声明嵌套命名空间。如果配合 C# 10 引入的文件级命名空间，代码会极其简洁：

```csharp
// 现代 C# 推荐写法：文件级命名空间 + 点语法
namespace HR.Mgr;

public interface IManager 
{ 
    void ManageTeam();
}

public class Manager : IManager 
{
    public void ManageTeam() { /* 业务逻辑 */ }
}
```

## 访问嵌套命名空间中的成员

无论是使用传统嵌套还是点语法声明，CLR 看到的最终类型全名（完全限定名）都是一样的。访问嵌套命名空间中的类型时，必须提供完整的路径：`外部命名空间.内部命名空间.类型名`。

### 显式使用完全限定名
如果不引入命名空间，直接在代码中实例化对象，需要写出全路径：

```csharp
public class Program
{
    public static void Main()
    {
        // 编译器不会自动在任何命名空间中寻找类，必须明确指定路径
        HR.Mgr.Manager manager = new HR.Mgr.Manager();
        HR.Mgr.IManager imanager = new HR.Mgr.Manager();
    }
}
```

### 使用 `using` 指令引入
在实际开发中，每次都书写完全限定名会导致代码冗长。通常会在文件顶部使用 `using` 引入到最深层的嵌套命名空间：

```csharp
using HR.Mgr; // 引入嵌套命名空间

public class Program
{
    public static void Main()
    {
        // 引入后即可直接使用短类名
        Manager manager = new Manager();
    }
}
```

## 命名规范与架构避坑指南

结合《Framework Design Guidelines》(框架设计准则)，在使用嵌套命名空间时需要注意以下几点：

### 严禁命名空间与类同名
如果内部存在一个名为 `Manager` 的类，**绝不要**将命名空间也命名为 `Manager`。
例如，避免出现 `HR.Manager.Manager` 这样的结构。这会导致严重的**编译器名称解析歧义 (Ambiguity)**。当在代码中输入 `Manager.` 时，编译器无法确定开发者是要访问 `Manager` 命名空间下的成员，还是要访问 `Manager` 类的静态成员。
*   **解决方案**：命名空间应倾向于使用复数形式或表示概念的词汇。例如，使用 `HR.Management`，或者使用缩写 `HR.Mgr`。

### 控制嵌套的深度
如果嵌套命名空间的层级过多（例如 `A.B.C.D.E`），会显著增加调用方访问类的代码长度和理解成本。
*   业界标准建议遵循 `公司名.产品名.模块名.子模块名` 的层级结构，尽量将嵌套深度控制在 3 到 4 层以内（例如 `Microsoft.Extensions.DependencyInjection`）。

### 成员类型的丰富性
与外层命名空间一样，嵌套命名空间不仅仅用于存放**类 (Classes) 和接口 (Interfaces)**，同样可以用来分组**结构体 (Structures)、枚举 (Enumerations) 和委托 (Delegates)**。合理地将这些类型划分到子命名空间中，有助于构建高内聚、低耦合的代码库。
