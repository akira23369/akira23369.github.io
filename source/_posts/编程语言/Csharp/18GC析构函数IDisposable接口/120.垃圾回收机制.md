# 垃圾回收机制


在 C# 中，内存管理由 CLR（公共语言运行时）的垃圾回收器（GC）自动负责。开发者不需要像在 C/C++ 中那样手动分配和释放内存（`malloc`/`free`）。极大地降低了内存泄漏和悬空指针的风险。
- **工作区域：** GC **仅**负责清理**托管堆 (Managed Heap)** 上的内存。它不负责栈内存（值类型随作用域自动弹出），也不负责非托管资源（如文件句柄、数据库连接、操作系统内核对象）。
- **触发时机：** GC 运行是不确定的。它通常在托管堆分配量达到特定阈值、系统内存不足或操作系统发出内存压力信号时触发

## 核心概念与内存分配

在 C# 中，内存主要分为栈（Stack）和堆（Heap）。值类型通常分配在栈上，而引用类型（类的实例）始终分配在堆上。

*   **托管堆 (Managed Heap)：** 当 CLR（公共语言运行时）启动时，会为应用程序预留一块连续的虚拟内存区域，这被称为托管堆。
*   **分配机制：** 所有的类对象都会在这个托管堆上按顺序连续分配。堆中维护着一个指针（NextObjPtr），指向下一个对象即将分配的地址。
*   **角色分工：** CLR 的**内存管理器 (Memory Manager)** 负责分配内存；**垃圾回收器 (Garbage Collector)** 负责释放不再被使用的内存。

## 垃圾回收底层算法：标记与压缩

参考《CLR via C#》中对 GC 机制的深度剖析，GC 并不是简单地“记录引用的数量”（引用计数法），而是采用 **“标记-压缩” (Mark and Compact)** 算法。这比传统的引用计数（Reference Counting，存在循环引用问题）更高级。

1. **挂起线程：** GC 开始时，首先挂起所有执行托管代码的线程。
2. **标记阶段：** GC 从**根 (Roots)** 开始遍历。根包括**全局/静态变量、线程栈上的局部变量和 CPU 寄存器**。GC 沿着根的引用顺藤摸瓜，构建一个对象图。所有能被访问到的对象标记为“存活”，访问不到的视为“垃圾”。
3. **压缩阶段 ：** GC 将所有存活的对象在内存中向下移动，使它们紧凑地排列在一起。
4. **重定向引用：** 由于对象在内存中的物理地址发生了移动，GC 会自动更新所有指向这些对象的引用变量。
5. **恢复线程：** 内存整理完毕，恢复线程执行。通过压缩，解决了内存碎片化问题。

## 分代假设与代龄机制

为了提高性能，避免每次 GC 都扫描整个几十上百兆的堆内存，CLR 将对象划分为三个“代 (Generations)”：**Gen 0, Gen 1, Gen 2**。

这一设计的理论依据是**分代假设 (Generational Hypothesis)**：
1. 越新的对象，生命周期越短（局部变量刚用完就没用了）。
2. 越老的对象，生命周期越长（全局配置、缓存等）。
3. 回收一部分内存总是比回收全部内存要快。

**各代龄的作用与晋升机制：**
*   **第 0 代 (Gen 0) - 短命代：** 包含新分配的对象。由于生命周期短（如方法内部的局部变量），Gen 0 的垃圾回收发生得最频繁，且速度极快（通常在毫秒级）。
*   **第 1 代 (Gen 1) - 缓冲区：** 在 Gen 0 的回收中**存活下来**的对象，会被**晋升 (Promoted)** 到 Gen 1。它作为一个缓冲区，介于短命和长命对象之间。
*   **第 2 代 (Gen 2) - 长命代：**  包含长生命周期的对象（如静态变量、单例对象、缓存）。在 Gen 1 的回收中存活下来的对象会被晋升到 Gen 2。Gen 2 的回收成本最高，通常只在系统内存紧张时触发（称为 Full GC）。

*(补充：《CLR via C#》指出，大于 85,000 字节的大对象会直接分配在特殊的“大对象堆 (LOH)”，并且默认被视为 Gen 2，因为在内存中移动大对象的成本极高。)*

## 大对象堆LOH
对于大于或等于 **85,000 字节**的对象（如大型数组或大字符串），CLR 认为移动它们耗费的 CPU 成本太高。

- 大对象不会被分配在 Gen 0，而是直接分配在专门的大对象堆 (LOH) 中。
- LOH 属于 Gen 2 的一部分。这意味着只有在执行代价高昂的 Gen 2 回收时，大对象才会被清理。
- **碎片化问题：** 传统上，LOH 在回收后**不进行压缩**，因此极易产生内存碎片。（注：在较新的 .NET 版本中，可以通过 `GCSettings.LargeObjectHeapCompactionMode` 手动指示 GC 在下次回收时压缩 LOH，但仍非常耗时）。

## 垃圾回收的触发时机与手动控制

**GC 何时发生？**
1.  Gen 0 的分配空间达到阈值（即堆中没有足够的连续可用空间来创建新对象时）。
2.  操作系统报告物理内存不足。
3.  应用程序正常退出时。

**关于 `GC.Collect()`：**
开发者可以通过调用 `System.GC.Collect()` 强制触发垃圾回收。
但在《Effective C#》等经典著作中，极其**不推荐**在常规业务代码中调用此方法。因为 CLR 的垃圾回收器是高度自调优的，手动触发会打乱 GC 的执行频率和代龄预算机制，反而可能导致性能下降。通常只有在应用程序刚刚经历了一次极大规模的缓存清空后，才考虑手动调用。

## GC 管理内存，但不管理“资源”

这是一个初学者极易混淆的概念。**GC 只负责清理托管内存**。
如果你的对象打开了数据库连接、文件句柄、网络套接字或操作系统的 GDI 句柄（这些被称为**非托管资源**），GC 并不知道如何关闭它们。

如果依赖 GC 来清理这些资源，会导致严重的资源泄漏。针对非托管资源，必须实现 `IDisposable` 接口，并使用 `using` 语句块来确保资源被及时且确定性地释放（Dispose 模式）。这是编写健壮 C# 代码的关键基石。
## **标准Dispose模式（代码演示）：**  
为了提供确定性的释放机制并兼顾安全性，业界有一套标准模板（微软官方推荐）：
```cs
using System;
using System.IO;

public class ResourceHolder : IDisposable
{
    // 非托管资源
    private IntPtr _unmanagedHandle; 
    // 托管资源
    private FileStream _managedStream; 
    // 标记是否已释放
    private bool _disposed = false;

    public ResourceHolder()
    {
        // 初始化资源...
    }

    // 1. 实现 IDisposable 接口的公开方法（供开发者主动调用或 using 语句调用）
    public void Dispose()
    {
        Dispose(true);
        // 告诉 GC：我已经手动清理了，不要再去调用终结器了！避免进入 F-Reachable 队列。
        GC.SuppressFinalize(this); 
    }

    // 2. 保护的虚方法：执行实际的清理逻辑
    // disposing = true: 由 Dispose() 调用，可安全清理托管和非托管资源。
    // disposing = false: 由终结器调用，说明对象正在被 GC 销毁，此时绝对不能访问其他托管对象（因为它们可能已经被回收了），只能清理非托管资源。
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 清理托管资源
            _managedStream?.Dispose();
        }

        // 清理非托管资源
        if (_unmanagedHandle != IntPtr.Zero)
        {
            // 例如：CloseHandle(_unmanagedHandle);
            _unmanagedHandle = IntPtr.Zero;
        }

        _disposed = true;
    }

    // 3. 终结器（作为最后的安全网：防止开发者忘了调用 Dispose）
    ~ResourceHolder()
    {
        Dispose(false);
    }
}

// 使用方式：利用 using 语法糖，确保即使发生异常也能调用 Dispose()
/*
using (var holder = new ResourceHolder())
{
    // 使用资源...
} // 离开作用域时自动调用 holder.Dispose()
*/

```
## 代码示例：验证对象代龄的晋升

我们可以使用 C# 代码来直观地观察对象是如何在不同代龄之间晋升的。

```csharp
using System;

public class Program
{
    public static void Main()
    {
        // 1. 创建一个新对象，它会被分配在 Gen 0
        object myObject = new object();
        Console.WriteLine($"初始代龄: {GC.GetGeneration(myObject)}"); // 输出 0

        // 2. 强制触发一次针对 Gen 0 的垃圾回收
        // 因为 myObject 被局部变量引用，它是"活着"的，会存活下来
        GC.Collect(0); 
        
        // 3. 存活下来的对象会被晋升到 Gen 1
        Console.WriteLine($"第一次 GC 后的代龄: {GC.GetGeneration(myObject)}"); // 输出 1

        // 4. 再次触发针对所有代的垃圾回收
        GC.Collect();
        
        // 5. 再次存活的对象被晋升到最高代 Gen 2
        Console.WriteLine($"第二次 GC 后的代龄: {GC.GetGeneration(myObject)}"); // 输出 2

        // 6. 即使再发生 GC，最高也只到 Gen 2
        GC.Collect();
        Console.WriteLine($"第三次 GC 后的代龄: {GC.GetGeneration(myObject)}"); // 依然输出 2
    }
}
```

## 最佳实践总结

1. **避免调用 `GC.Collect()`：** 永远不要试图在业务代码中干预 GC 的工作。GC 是高度自适应的，手动调用通常会破坏其动态调整的阈值，导致性能下降（把本该死的 Gen 0 对象硬生生塞进了 Gen 1 或 Gen 2）。
2. **严格使用 `using` 语句：** 任何实现了 `IDisposable` 的对象，都必须包裹在 `using` 块中，或在 `finally` 块中调用 `Dispose()`。
3. **警惕事件泄漏 (Event Leaks)：** 在长生命周期对象（如主窗口）中订阅了短生命周期对象（如临时对话框）的事件，如果退出时不取消订阅（`-=`），长生命周期对象会一直持有短生命周期对象的引用，导致其永远无法被 GC 回收。
4. **对象池 (Object Pooling)：** 对于频繁创建和销毁的大对象（如大型数组、位图），应使用对象池技术（如 `ArrayPool<T>`），避免给 LOH 和 GC 带来巨大压力。
