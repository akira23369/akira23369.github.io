# 方法重写与多态性

方法重写（Method Overriding）是面向对象编程中实现**多态性（Polymorphism）** 的核心机制。它允许子类为父类中已经定义的方法提供属于自己的特定实现。通过方法重写，系统可以在运行时根据对象的实际类型动态决定调用哪个版本的方法，这为构建高度可扩展和灵活的系统奠定了基础。

## 核心概念与设计意图

在类的继承体系中，父类通常定义了通用的行为模式。然而，不同的子类可能需要对这些行为进行修改或**扩展**。

*   **修改（替换）**：子类完全抛弃父类的业务逻辑，提供一套全新的实现。
*   **扩展（追加）**：子类不仅保留父类的核心逻辑，还在其基础之上追加子类特有的操作。

在 C# 的设计哲学中（参考《Effective C#》），父类的设计者必须显式地“开放”权限，允许特定的方法被重写。如果父类不同意，子类是无法重写该方法的。

## 核心语法规则：`virtual` 与 `override`

C# 对方法重写有着非常严格的语法约束，这被称为“显式重写（Explicit Overriding）”：

1.  **父类的授权 (`virtual`)**：父类的方法必须使用 `virtual`（虚方法）、`abstract`（抽象方法）或本身就是 `override` 的方法来修饰。`virtual` 关键字向编译器宣告：“这个方法在未来可能会被子类重写”。
2.  **子类的声明 (`override`)**：子类如果决定重写该方法，必须使用 `override` 关键字。
3.  **签名绝对一致**：子类重写的方法，其**方法名、参数列表、返回类型**以及**访问修饰符（如 `public`、`protected`）** 必须与父类完全一致。
4.  **可选择性**：重写 `virtual` 方法是完全可选的。如果子类不使用 `override` 重写它，将默认继承并使用父类的实现。

> **纠正与补充**：在某些场景下，我们希望在子类中扩展父类的逻辑，通常会在子类方法中调用 `base.MethodName()`。但请注意，**调用 `base` 并非强制要求，也不必须放在方法的第一行**。开发者完全可以根据业务需求，在方法体的前面、中间、后面调用，甚至完全不调用（彻底覆盖父类逻辑）。

## 代码实战：扩展父类逻辑

以下代码演示了如何在保留父类健康保险计算逻辑的基础上，在子类中追加额外的保险额度计算。

```csharp
using System;

public class Employee
{
    public string Name { get; set; }

    public Employee(string name) { Name = name; }

    // 1. 父类使用 virtual 关键字开放重写权限
    public virtual void CalculateHealthInsurance()
    {
        Console.WriteLine($"[Employee] {Name} 的基础健康保险额度为: $500");
    }
}

public class Manager : Employee
{
    public Manager(string name) : base(name) { }

    // 2. 子类使用 override 关键字重写该方法
    public override void CalculateHealthInsurance()
    {
        // 3. (可选) 使用 base 调用父类的实现，复用基础逻辑
        base.CalculateHealthInsurance();
        
        // 4. 追加 Manager 特有的逻辑
        Console.WriteLine($"[Manager] {Name} 获得额外的管理层保费补贴: $1000");
    }
}

public class Program
{
    public static void Main()
    {
        Manager mgr = new Manager("Alice");
        // 调用时，将依次执行父类逻辑和子类逻辑
        mgr.CalculateHealthInsurance();
    }
}
```

## 深度对比：方法重写 (Override) vs 方法隐藏 (New)

这是 C# 面向对象中最容易混淆的考点。假设有一个 `Manager` 对象，但是我们把它赋值给了一个 `Employee` 类型的引用变量（向上转型）。

```csharp
Employee emp = new Manager("Alice");
emp.CalculateHealthInsurance();
```

*   **如果子类使用的是方法隐藏 (`new`)**：
    由于变量声明类型是 `Employee`，编译器在编译时（静态绑定）就决定了调用 `Employee` 类的方法。子类 `Manager` 的逻辑**不会**被执行。
*   **如果子类使用的是方法重写 (`override`)**：
    即使变量类型是 `Employee`，但在运行时，系统会检查这块内存实际上装的是一个 `Manager` 对象，因此会**动态分配（晚期绑定）** 去执行 `Manager` 类中重写的逻辑。

## 底层机制深入 (CLR 视角：虚方法表)

根据《CLR via C#》的详细剖析，方法重写的魔法来源于 CLR（公共语言运行时）层面的**虚方法调用指令 (`callvirt`)** 和**虚方法表（vtable / Virtual Method Table）**。

1.  当一个类中存在 `virtual` 方法时，CLR 会为该类型在内存中构建一张“虚方法表”，表里记录了所有虚方法的实际内存地址。
2.  当子类使用 `override` 重写了方法后，CLR 会在子类的虚方法表中，将该方法的内存地址替换为 **子类新实现的内存地址**。
3.  当执行 `emp.CalculateHealthInsurance()` 时，由于编译器看到该方法是 `virtual` 的，它会生成 `callvirt` 指令。
4.  在程序运行的瞬间，`callvirt` 指令会首先检查 `emp` 指针指向的实际对象头（Object Header），找到其真实的类型对象指针（Type Handle），然后顺藤摸瓜找到该真实类型（`Manager`）的虚方法表，最终调用表中登记的最新的方法地址。

这就是多态性能在运行时“认清对象真面目”的底层原因。

## 框架设计与最佳实践

在现代企业级开发中，面向对象设计的核心原则之一是**开闭原则（Open/Closed Principle, OCP）**：软件实体应对扩展开放，对修改封闭。

方法重写完美契合了这一原则。在实际的商业框架（如 ASP.NET Core, Entity Framework Core）中，微软提供了大量的基类（如 `Controller`, `DbContext`）。

*   例如在 EF Core 中，开发者需要继承 `DbContext`，并**重写 (`override`)** 其内部的 `OnModelCreating(ModelBuilder modelBuilder)` 方法，以此来注入开发者自定义的数据库表映射关系。
*   基类（框架层面）负责极其复杂的底层生命周期管理和依赖注入，而开发者只需要通过 `override` 暴露出的钩子（Hook）方法，将自己的业务逻辑嵌入到框架的执行流中，而无需触碰或修改框架核心的任何一行源码。
