## 一、继承机制的核心运行法则 (归纳总结)

在实际开发和技术面试中，必须牢记以下关于继承的绝对准则：

### 内存布局与访问权限的本质区别
*   **内存完整性**：当实例化一个子类对象时，内存中会完整分配**父类所有字段**的空间，包括父类中声明为 `private` 的私有字段。
*   **访问隔离**：子类无法在代码中直接访问父类的 `private` 字段。但这仅仅是编译器层面的权限隔离，这些私有数据依然存在于子类对象的内存堆中，并且可以通过父类提供的 `public` 或 `protected` 方法/属性进行间接操作。

### 方法隐藏 vs 方法重写判别
*   **方法隐藏 (`new`)**：**编译时决议**。执行哪个方法完全取决于**引用变量的声明类型**。如果用父类变量引用子类对象，依然会执行父类的方法。参数列表必须一致，但返回类型可以不同。
*   **方法重写 (`virtual` + `override`)**：**运行时决议（动态分发 / Dynamic Dispatch）**。执行哪个方法取决于内存中**对象的实际类型**。这是面向对象多态性的基石。

### `base` 调用的自主权
*   在子类重写的方法体中，**并不强制要求**调用父类的方法（`base.MethodName()`）。
*   是否调用、在哪里调用（方法开头、中间或结尾）完全由子类的业务逻辑决定。如果不调用，父类该方法的逻辑将完全不会执行。

### 单根继承与多重实现
*   C# 严格执行**类的单继承**规则（一个类只能有一个直接父类）。
*   为了弥补单继承的局限性，C# 允许一个类**实现多个接口 (Interfaces)**，以实现行为规约的多重继承。

## 二、 深度拓展：CLR 底层视角的继承 (参考《CLR via C#》)

理解 C# 的继承，不能仅停留在语法层面，必须了解公共语言运行时（CLR）是如何处理类型的。

### 万物之祖：`System.Object`
在 C# 中，如果定义一个类时没有显式指定父类，编译器会自动让它继承自 `System.Object`。这意味着任何 C# 对象（无论是类、结构体还是委托）最终都继承了 `Object` 的基本行为，例如 `ToString()`, `Equals()`, `GetHashCode()`, 和 `GetType()`。

### 类型的安全转换 (`is` 与 `as` 运算符)
由于继承关系的存在（Is-a），C# 允许隐式的向上转型（子类赋值给父类变量）。但向下转型（父类引用转换为子类变量）是不安全的。
*   CLR 在运行时会检查对象的**类型句柄 (Type Handle)**。如果强转类型不匹配，会抛出 `InvalidCastException`。
*   **最佳实践**：永远使用 `is` 模式匹配或 `as` 运算符来进行安全的类型转换，避免昂贵的异常捕获开销。
    ```csharp
    Employee emp = new Manager();
    // C# 7.0+ 模式匹配写法 (推荐)
    if (emp is Manager mgr) {
        mgr.ApproveLeave(); 
    }
    ```

### 虚方法表 (vtable) 的开销
虽然多态（`virtual`/`override`）极其强大，但它并非没有代价。虚方法调用在底层需要经过多一次的指针间接寻址（查找方法表）。在极其苛刻的性能敏感场景（如游戏引擎的每帧更新、高频交易系统）中，过深的继承树和大量虚方法调用会导致 CPU 缓存未命中（Cache Miss）。这也解释了为什么 `sealed` 关键字在性能优化中具有重要地位。

## 三、 面向对象设计准则：继承的最佳实践
(参考《Effective C#》与《代码大全》)

在架构设计中，继承是一把双刃剑。滥用继承会导致代码结构僵化、难以维护。

### 组合优于继承
继承代表了极其强烈的**紧耦合**关系。子类的实现严重依赖于父类的内部细节。
*   如果类 A 只是想**借用**类 B 的某些功能，而不是在逻辑上“是一个”类 B，就不应该使用继承。
*   替代方案是将类 B 的实例作为类 A 的一个私有字段存放，这种关系称为**组合 (Composition / Has-a 关系)**。组合在运行时更加灵活，且不破坏封装性。

### 里氏替换原则
SOLID 原则中的 "L" 是判断继承关系是否合理的金标准：
**“程序中的父类实例都应该能够被替换为子类的实例，而不会影响程序的正确性。”**
*   如果子类重写父类方法时，抛出了父类未曾声明的异常，或者改变了父类方法的核心语义，就违反了 LSP，这种继承就是失败的设计。

### 警惕“脆弱的基类”问题
当一个系统发展到一定规模，基类会被大量的子类继承。此时，如果在基类中添加一个新的虚方法，或者修改了基类某个受保护字段的行为，可能会在不知不觉中破坏了某个子类的逻辑。
**应对策略**：
*   默认将不应被继承的类设为 `sealed`。
*   优先使用接口（Interface）来定义契约，使用抽象类（Abstract Class）来提供部分实现。

## 四、 现代 C# 语法对继承的演进

随着 C# 版本的更迭，继承机制也加入了一些现代化的特性：

### 协变返回类型(C# 9.0+)
在重写方法时，子类现在可以返回比父类方法更具体的派生类型，这消除了过去常见的强制类型转换代码。
```csharp
public virtual Employee GetTopPerformer() { ... }
// 子类重写时，直接返回更具体的 Manager 类型
public override Manager GetTopPerformer() { ... } 
```

### 记录类型 (Records) 的继承 (C# 9.0+)
C# 引入了基于值相等的 `record` 类型。`record` 也可以继承，但规定**记录只能继承自记录，类只能继承自类**，两者不能交叉继承。这保证了值相等性语义在继承链中的一致性。
