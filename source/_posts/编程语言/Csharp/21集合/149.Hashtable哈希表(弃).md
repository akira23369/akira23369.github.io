# `Hashtable` 哈希表

## 一、 核心概念与底层逻辑(为什么它被时代抛弃？)

`Hashtable` 位于非泛型命名空间 `System.Collections` 下。

*   **本质**：它是一个基于键的哈希代码组织起来的**非泛型**键值对集合。
*   **万物皆 Object**：它的 Key 和 Value 类型都是 `object`。这意味着你可以把任何类型（数字、字符串、自定义类）混杂着塞进同一个 `Hashtable` 里。
*   **底层冲突解决机制（面试核弹 ）**：
    当两个不同的 Key 计算出相同的哈希值（哈希冲突）时：
    *   `Dictionary<TKey, TValue>` 使用的是**拉链法 (Chaining)**（在冲突位置挂一个链表）。
    *   `Hashtable` 使用的是**双重哈希法 (Double Hashing)**。当发生冲突时，它会使用另一个哈希函数再次计算步长，去数组里寻找下一个空槽位。
*   **致命弱点：装箱与拆箱 (Boxing & Unboxing)**：
    因为它的参数是 `object`，当你存入值类型（如 `int`, `struct`）时，CLR 必须在堆（Heap）上分配内存，把值类型包装成引用类型（装箱）；当你读取时，又要把它拆成值类型（拆箱）。这会导致**极其严重的 CPU 性能损耗和垃圾回收（GC）压力**。这就是它被彻底淘汰的核心原因。

Hashtable 的极速检索能力源于其特殊的内存映射和数学计算方式。

**哈希码生成 (GetHashCode)**
每个添加到 Hashtable 的键都会首先被提取其哈希码（Hash Code）。
- **数字类型**：数字本身通常直接作为哈希码（例如键为 10，哈希码就是 10）。
- **字符串类型**：System.String 类内部实现了特定的散列算法，通过遍历字符串的所有字符来计算出一个随机且尽量均匀分布的整数作为哈希码。
- **自定义对象**：如果将自定义类（如 Employee）的实例作为键，开发者**必须**重写 System.Object 的 GetHashCode() 方法，并结合业务上的唯一标识（如 EmployeeId）来返回哈希码。同时，为了处理哈希冲突，还应当一并重写 Equals() 方法。

**索引计算与存储位置**
Hashtable 不像数组那样顺序存储数据，而是通过特定公式计算出存储的索引：  
**计算公式： Index = HashCode % HashTable_Capacity**
- **容量设定**：Hashtable 的初始容量通常是一个**素数**（默认初始通常为 17）。使用素数取模可以极大地减少哈希冲突。
- **动态扩容 (Rehashing)**：当元素增加，导致装载因子（Load Factor）过高时，Hashtable 会自动扩容。新的容量会是当前容量两倍之后的下一个素数（例如从 17 扩容到 37，再到等更大的素数）。**扩容是一个极其消耗性能的操作**，因为所有的索引都必须根据新的容量重新计算并分配。

**冲突处理 (Collision Resolution)**
当两个不同的键计算出相同的索引时，就会发生哈希冲突。在底层数据结构上，传统的散列表通常采用**链地址法（Chaining）** 或**开放寻址法（Open Addressing）**。在出现冲突的索引位置，元素会以链表等形式被关联起来。检索时，会先通过计算到达指定索引，如果发现多个元素，则遍历该链表并调用 Equals() 方法比对出精确匹配的键。

## 二、 核心属性

### `Count` (实际包含的元素数)
*   **说明**：获取 `Hashtable` 中当前的键值对数量。时间复杂度 O(1)。

### `Keys` (键集合) 与 `Values` (值集合)
*   **说明**：获取包含所有键/值的 `ICollection`。
*   **注意**：返回的是非泛型的集合，遍历出来依然全是 `object`。

### `IsSynchronized` 与 `SyncRoot` (时代遗物：线程安全)
*   **说明**：在早期的 .NET 中，为了实现线程安全，集合都自带这两个属性。
*   `IsSynchronized`：判断当前哈希表是否是线程安全的（默认是 `false`）。
*   `SyncRoot`：获取一个可用于同步访问 `Hashtable` 的对象。
*   **示例 (老派加锁法)**：
```csharp
Hashtable ht = new Hashtable();
// 使用 SyncRoot 加锁，确保多线程下绝对安全
lock (ht.SyncRoot) {
    ht.Add("Key1", "Value1");
}
```

## 三、 索引器 - 最大的坑点

### `this[object key]` (通过方括号 `[]` 访问)
*   **读数据（Get）**：**（与 Dictionary 最大的区别！）**
    *   在 `Dictionary` 中，如果 Key 不存在，用 `[]` 读取会抛出 `KeyNotFoundException`。
    *   在 `Hashtable` 中，如果 Key 不存在，**它不会报错，而是静默返回 `null`！**
*   **写数据（Set）**：Key 存在则覆盖，不存在则新增。
*   **代码示例**：
```csharp
Hashtable config = new Hashtable();
config["Theme"] = "Dark"; // 写入字符串 (object)
config["Timeout"] = 30;   // 写入整数 (触发隐式装箱！将 30 包装成了 object)

// 读取
object theme = config["Theme"]; // 返回 "Dark"

// 最大的陷阱：
object lang = config["Language"]; // Key不存在，不会报错！lang 变成了 null。

// 因为拿出来的是 object，你必须手动强制类型转换 (拆箱)
int timeout = (int)config["Timeout"]; 
```

## 四、 添加元素

### `Add(object key, object value)`
*   **说明**：将指定的键和值添加到 `Hashtable`。
*   **时间复杂度**：平均 O(1)。
*   **异常**：如果 Key 已存在，抛出 `ArgumentException`。如果 Key 为 `null`，抛出 `ArgumentNullException`。
*   **示例**：
```csharp
Hashtable user = new Hashtable();
user.Add("ID", 1001);
user.Add("Name", "Alice");
// user.Add("ID", 1002); // 报错：已添加了具有相同键的项
```
*   *(注：`Hashtable` 没有 `TryAdd` 这种现代方法。)*

---

## 五、 移除元素

### `Remove(object key)`
*   **说明**：移除带有指定键的元素。
*   **返回值**：**没有返回值 (void)！** （`Dictionary` 的 Remove 会返回 `bool` 告诉你是否移除成功）。如果 Key 不存在，它什么也不做，也不会报错。
*   **时间复杂度**：O(1)。
*   **示例**：
```csharp
Hashtable cache = new Hashtable();
cache.Add("Session", "abc123xyz");

cache.Remove("Session"); // 成功移除
cache.Remove("GhostKey"); // Key不存在，无事发生，也不报错
```

### `Clear()`
*   **说明**：清空所有元素。时间复杂度 O(n)。

## 六、 查找与验证

### `Contains(object key)` 与 `ContainsKey(object key)`
*   **说明**：这两个方法在 `Hashtable` 中**完全等价**！底层源码里 `Contains` 直接调用了 `ContainsKey`。判断是否包含指定键。
*   **时间复杂度**：O(1)。

### `ContainsValue(object value)`
*   **说明**：判断是否包含特定值。
*   **时间复杂度**：O(n)。（必须遍历整个哈希表的所有桶，极其缓慢，坚决避免使用）。

*   *(注：`Hashtable` 没有 `TryGetValue` 方法。传统的安全读取方式是：)*
```csharp
Hashtable ht = new Hashtable();
// 安全读取的老套路：
if (ht.ContainsKey("Key1")) {
    int val = (int)ht["Key1"]; 
}
// 或者利用它返回 null 的特性 (仅限引用类型)：
object result = ht["Key2"];
if (result != null) {
    // 找到了
}
```

## 七、 遍历哈希表

这也是面试常考的细节。`Dictionary` 遍历出来是 `KeyValuePair<K,V>`，而 `Hashtable` 遍历出来是什么？

答案是：**`DictionaryEntry` 结构体**。

```csharp
Hashtable mixedData = new Hashtable();
mixedData.Add("StringKey", "Hello");
mixedData.Add(123, 456.78); // 极其混乱的类型混合，Hashtable 允许这么做

// 必须使用 DictionaryEntry 接收
foreach (DictionaryEntry entry in mixedData) {
    Console.WriteLine($"键: {entry.Key} (类型: {entry.Key.GetType()}), " +
                      $"值: {entry.Value} (类型: {entry.Value.GetType()})");
}
```

## 八、 高级特性

“既然有了 Dictionary，Hashtable 是不是一无是处？”

### 终极对比：`Hashtable` vs `Dictionary<TKey, TValue>`

| 核心特性            | `Hashtable` (旧时代)         | `Dictionary<K, V>` (新时代)      |
| :-------------- | :------------------------ | :---------------------------- |
| **泛型支持**        | ❌ 否 (全都是 `object`)        | ✅ 是 (类型绝对安全)                  |
| **性能 (值类型)**    | ❌ 极差 (频繁装箱拆箱分配堆内存)        | ✅ 极高 (无额外内存开销)                |
| **找不到 Key 的行为** | **返回 `null` (不报错)**       | **抛出 `KeyNotFoundException`** |
| **遍历时的实体类型**    | `DictionaryEntry`         | `KeyValuePair<TKey, TValue>`  |
| **哈希冲突解决算法**    | **双重哈希 (Double Hashing)** | **拉链法 (Chaining)**            |
| **数据读取顺序**      | 绝对无序                      | 通常是插入顺序 (但不保证绝对)              |

### 线程安全性 - Hashtable 的唯一“闪光点”
虽然 `Dictionary` 完全不具备线程安全，但 `Hashtable` 提供了一个内置的线程安全包装器：

```csharp
Hashtable normalHt = new Hashtable();

// 返回一个线程安全的 Hashtable 包装器！
Hashtable safeHt = Hashtable.Synchronized(normalHt); 

// 现在，多线程同时对 safeHt 进行 Add/Remove 操作是安全的
// (但遍历 foreach 依然不安全，需要手动 lock)
```
**架构师点评**：虽然它能这么做，但在现代 C# 中，我们有性能高出几个数量级的无锁并发字典 `ConcurrentDictionary<TKey, TValue>`。所以 `Hashtable.Synchronized` 也已被彻底淘汰。

### 为什么面试官喜欢问装箱/拆箱？
因为这是 C# 性能优化的核心基石。
```csharp
Hashtable ht = new Hashtable();
for(int i = 0; i < 100000; i++) {
    ht.Add(i, i); 
    // 灾难发生：i 是 int(值类型)。
    // Add(object, object) 要求引用类型。
    // CLR 会在堆上 new 出 200,000 个 object 对象来包裹这些 int。
    // GC (垃圾回收器) 瞬间压力山大，导致程序卡顿。
}
```
相反，`Dictionary<int, int>` 直接在底层数组中存储 `int`，0 堆内存分配，0 GC 压力。

## 九、 总结提炼

请将这段总结作为你笔记的灵魂：

1.  **历史地位**：它是 C# 1.0 时代的产物，是 `Dictionary` 的祖先。**新项目坚决不用，老项目看懂即可。**
2.  **核心痛点**：非泛型设计导致“万物皆 object”，引发**装箱拆箱**的性能灾难，且丧失了编译期的类型安全检查。
3.  **避坑口诀**：读不到 Key 悄悄返回 `null`；遍历要用 `DictionaryEntry`；冲突采用双哈希。
4.  **高频面试话术**：“我会优先使用 `Dictionary<TKey, TValue>`，因为泛型避免了装箱拆箱，如果是多线程场景，我会用 `ConcurrentDictionary` 替代 `Hashtable.Synchronized`。”
