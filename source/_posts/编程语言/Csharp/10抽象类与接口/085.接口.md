# 接口

接口（Interface）是 C# 中实现多态性和解耦的最强大工具。如果说抽象类（Abstract Class）是一个半成品，那么接口就是一份**纯粹的契约（Contract）**。它定义了类型“能够做什么”，而完全不涉及“如何去做”。

## 核心概念与本质

在传统的 C# 设计中（C# 8.0 之前），接口可以被看作是一个**纯抽象类**。它只包含成员的声明，不包含任何实现逻辑。

*   **命名规范**：在 .NET 生态中，接口的名称始终以大写字母 **`I`** 开头（例如 `IVehicle`, `IDisposable`, `IEnumerable`）。
*   **契约精神**：当一个类声明实现某个接口时，它就在向编译器和调用方郑重承诺：“我一定会提供这个接口中定义的所有属性、方法、事件的完整实现。”
*   **解耦的威力**：调用方只需要针对接口进行编程，完全不需要知道底层是哪个具体的类在执行代码。这是依赖注入（DI）和控制反转（IoC）的理论基础。

## 接口的核心语法与严格约束

定义和实现接口时，需要遵循 C# 编译器设定的一系列严格规则：

1.  **成员隐式公开与抽象**：接口内部的方法、属性声明不需要（在旧版 C# 中也是不允许）书写 `public` 和 `abstract` 访问修饰符。它们**默认且只能是公开的和抽象的**。
2.  **绝对禁止状态（字段）**：接口中**绝对不能包含字段（Fields）**，无论是普通字段还是静态字段。接口只能定义行为，不能持有数据状态。
3.  **禁止构造函数**：因为接口不能被实例化，也没有字段需要初始化，所以接口不能包含构造函数。
4.  **无 `override` 关键字**：类在实现接口方法时，不需要也不能使用 `override` 关键字（这与继承抽象类不同）。实现的方法必须被标记为 `public`。
5.  **多重继承机制**：C# 严禁类的多重继承，但**允许一个类同时实现任意多个接口**。同时，接口也可以继承自其他接口（接口继承）。

## 深度对比：抽象类 vs 接口 

这是架构设计时最常面临的选择，也是极高频的面试题。

| 对比维度            | 抽象类 (Abstract Class)                    | 接口 (Interface)                        |
| :-------------- | :-------------------------------------- | :------------------------------------ |
| **继承关系**        | 单继承（一个类只能有一个基类）。                        | 多实现（一个类可以实现多个接口）。                     |
| **状态 (Fields)** | 可以包含实例字段和静态字段，维护核心状态。                   | **严格禁止**包含任何字段。                       |
| **构造函数**        | 可以有构造函数（供子类通过 `base()` 调用）。             | 不能有构造函数。                              |
| **访问修饰符**       | 可以有 `public`, `protected`, `private` 等。 | 成员默认全局公开 (`public`)。                  |
| **设计语义**        | **"Is-A" (是一个)** 关系。定义同一类事物的核心血脉。       | **"Can-Do" (能做某事)** 关系。定义跨越不同物种的通用能力。 |

## 代码实战：将抽象类重构为接口

以下代码展示了如何将一个基于抽象类的系统重构为基于接口的系统。注意字段的下放和属性的具体实现。

```csharp
using System;

// 1. 定义纯粹的契约 (接口)
public interface IEmployee
{
    // 接口中的属性（本质上是抽象的 get/set 方法声明）
    int EmployeeId { get; set; }
    string EmployeeName { get; set; }
    string Location { get; set; }

    // 接口中的方法声明（没有大括号方法体）
    double GetInsuranceAmount();
}

// 2. 子类实现接口
// 语法：类名 : 接口名
public class Manager : IEmployee
{
    // 子类必须自己维护状态（字段）
    private int _employeeId;
    
    // 实现接口属性
    public int EmployeeId 
    { 
        get { return _employeeId; }
        set 
        { 
            // 子类可以自由加入自己的业务校验规则
            if(value >= 1000 && value <= 2000)
                _employeeId = value; 
        }
    }

    // 使用自动属性快速实现接口属性
    public string EmployeeName { get; set; }
    public string Location { get; set; }

    // 实现接口方法 (必须是 public，不需要 override)
    public double GetInsuranceAmount()
    {
        return 1000.00; // Manager 的特定实现
    }
}

public class Salesman : IEmployee
{
    public int EmployeeId { get; set; }
    public string EmployeeName { get; set; }
    public string Location { get; set; }

    public double GetInsuranceAmount()
    {
        return 500.00; // Salesman 的特定实现
    }
}

public class Program
{
    public static void Main()
    {
        // 多态性：使用接口作为引用类型变量
        // 调用方根本不在乎实际的对象是 Manager 还是 Salesman
        // 只要它实现了 IEmployee，就一定有 GetInsuranceAmount 方法
        IEmployee emp1 = new Manager();
        IEmployee emp2 = new Salesman();

        Console.WriteLine($"Manager Insurance: {emp1.GetInsuranceAmount()}");
        Console.WriteLine($"Salesman Insurance: {emp2.GetInsuranceAmount()}");
    }
}
```

## 架构级思考与底层演进 (扩展阅读)

### 什么时候用接口？什么时候用抽象类？
(参考《Effective C#》)
*   **首选接口**：在现代 C# 开发中，设计模式强烈推荐 **“面向接口编程”** 。接口提供了最大的灵活性。当你需要定义一组行为，并且这些行为可能被毫无关系的类（比如 `Car` 和 `Person` 都实现了 `IMovable`）所实现时，必须使用接口。
*   **慎用/结合使用抽象类**：如果你发现多个子类中存在大量**完全重复的模板代码和共享状态**，应当使用抽象类来消除重复。在大型框架中，常见的最佳实践是**混合使用**：定义一个接口（如 `IList`），然后提供一个实现了该接口的基础抽象类（如 `CollectionBase`），子类既可以选择继承抽象类以复用代码，也可以选择直接实现接口以保持极端的灵活性。

### CLR 底层视角
在公共语言运行时（CLR）中，由于类可以实现多个接口，因此不能像单继承那样只维护一张简单的虚方法表（vtable）。当一个类实现了接口时，CLR 会为该接口在类型的内存结构中生成一张**附加的接口分发映射表（Interface Dispatch Map）**。这意味着通过接口调用方法，在底层需要进行两次指针寻址，其性能开销会**极微弱地**略高于直接调用类的虚方法，但在 99.9% 的业务开发中，这种纳秒级的性能损耗是完全可以忽略不计的。

### 现代 C# 的颠覆：默认接口方法 (C# 8.0+)
需要特别补充的是，从 C# 8.0 开始，微软为了解决接口的**版本控制问题**，引入了**默认接口方法（Default Interface Methods, DIM）**。
现在，接口中**允许**编写包含具体实现逻辑的方法了。但这并不意味着接口变成了抽象类——接口依然绝对禁止包含实例字段。DIM 的引入主要是为了让 API 库的作者能够在不破坏数百万老用户现有代码的前提下，向现有接口中平滑地追加新方法。
