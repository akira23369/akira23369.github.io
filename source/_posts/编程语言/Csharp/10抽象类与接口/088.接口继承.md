# 接口继承

在面向对象架构设计中，不仅类可以继承类，**接口也可以继承接口**。接口继承主要用于建立契约之间的层级关系和依赖关系。通过接口继承，可以将多个细粒度的接口组合成一个更宏大的契约体系。

## 核心概念与语法逻辑

**接口继承**是指一个子接口（Child Interface）派生自一个或多个父接口（Parent Interface）。
*   **语义表达**：它表达了一种“契约的累加”。例如，“飞行器”（`IFlyingVehicle`）本质上也是一种“交通工具”（`IVehicle`）。
*   **强制实现约束**：当一个具体类声明实现某个子接口时，C# 编译器会**强制要求该类必须实现子接口本身定义的所有成员，以及其所有层级的父接口中定义的全部成员。**

## 接口引用变量的“视角边界”

接口的继承关系直接决定了引用变量在调用时的“可见性（Visibility）”：
*   **通过父接口类型的引用变量**：只能访问父接口中声明的方法和属性。
*   **通过子接口类型的引用变量**：不仅可以访问子接口自己声明的成员，**还可以直接访问父接口中声明的成员**。这是因为子接口在逻辑上已经包含了父接口的全部定义。

## 代码实战：构建契约层级

以下代码演示了如何通过接口继承，将“自然人”的属性强制绑定到“员工”的契约中。

```csharp
using System;

// 1. 定义父接口 (基础契约)
public interface IPerson
{
    DateTime DateOfBirth { get; set; }
    int GetAge();
}

// 2. 定义子接口 (派生契约)
// 语法：子接口 : 父接口
// 语义：任何想成为 IEmployee 的类型，必须首先满足 IPerson 的条件
public interface IEmployee : IPerson
{
    int EmployeeId { get; set; }
    void DoWork();
}

// 3. 具体实现类
// 只需要声明实现 IEmployee，但实际上被强制要求实现 IEmployee 和 IPerson 的所有成员
public class Manager : IEmployee
{
    // --- 实现 IEmployee 的成员 ---
    public int EmployeeId { get; set; }
    public void DoWork()
    {
        Console.WriteLine("Manager is reviewing reports.");
    }

    // --- 强制实现 IPerson 的成员 (由 IEmployee 继承而来) ---
    public DateTime DateOfBirth { get; set; }
    public int GetAge()
    {
        // 简化的年龄计算逻辑
        return (int)((DateTime.Now - DateOfBirth).TotalDays / 365.25);
    }
}

public class Program
{
    public static void Main()
    {
        Manager realManager = new Manager()
        {
            EmployeeId = 1001,
            DateOfBirth = new DateTime(1985, 5, 20)
        };

        // 视角 1：子接口引用 (拥有最广的视野)
        IEmployee empRef = realManager;
        empRef.DoWork();           // 访问自身契约
        int age = empRef.GetAge(); // 直接访问父契约成员，合法！
        Console.WriteLine($"Employee Age: {age}");

        // 视角 2：父接口引用 (视野受限)
        IPerson personRef = realManager;
        personRef.GetAge();        // 合法
        // personRef.DoWork();     // 编译错误：IPerson 契约中不存在 DoWork
    }
}
```

## 架构设计探讨与底层分析 (扩展阅读)

理解接口继承的真正威力，需要结合软件设计的经典原则。

### 接口隔离原则与契约组合
根据 SOLID 原则中的**接口隔离原则（Interface Segregation Principle）**，我们不应该设计庞大臃肿的接口（Fat Interfaces）。
在实际工程中，《代码大全》推荐的做法是：
1.  首先定义职责极度单一的小接口（例如 `IReadable`, `IWritable`）。
2.  利用接口的多重继承特性，将小接口**组合**成复合接口（例如 `public interface IReadWrite : IReadable, IWritable { }`）。
3.  这样，底层实现类可以根据实际情况选择只实现部分功能（只实现 `IReadable`），而高层业务逻辑可以要求一个完整的复合能力（要求传入 `IReadWrite`）。

### 避免契约的逃避
《Effective C#》中指出，接口继承的一个重要用途是**设定前置条件**。
如果在你的业务逻辑中，一个对象要成为“员工（`IEmployee`）”，它在物理逻辑上**绝对不能绕过**“必须是一个人（`IPerson`）”这个事实。
如果你采用类同时实现两个不相关的接口（即上一节中的多重实现 `class Manager : IEmployee, IPerson`），那么别的开发者完全可以写出一个 `class Robot : IEmployee`（只实现员工接口，不实现自然人接口）。
通过 `public interface IEmployee : IPerson`，你在架构层面上彻底锁死了这种可能，强制建立了业务上的绝对依赖关系。

### CLR 底层的分发映射
在《CLR via C#》对类型系统的解析中，当 CLR 加载 `Manager` 类时，它会扫描该类实现的所有接口。由于 `Manager` 实现了 `IEmployee`，而 `IEmployee` 又继承自 `IPerson`，CLR 会在 `Manager` 类型的内部方法表中，**分别为 `IEmployee` 和 `IPerson` 构建独立的接口分发映射（Interface Dispatch Map）**。
这意味着，在运行时，将 `Manager` 对象转换为 `IEmployee` 或 `IPerson` 进行方法调用时，其底层指针跳转的效率是完全一致且高度优化的。
