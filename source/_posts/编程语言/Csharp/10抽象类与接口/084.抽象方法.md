# 抽象方法

抽象方法是面向对象设计中实现强制多态的核心机制。它允许基类定义行为的契约（方法签名），而将具体的执行逻辑完全推迟到派生类中去实现。

## 核心概念与设计意图

当基类确知某个行为是所有子类都必须具备的，但不同子类实现该行为的具体过程又截然不同以至于基类无法提供一个“合理的默认实现”时，就应当使用抽象方法。

**业务场景示例**：
在一个银行系统中，存在父类 `BankAccount`（银行账户）以及子类 `SavingsAccount`（储蓄账户）和 `CurrentAccount`（活期/对公账户）。
所有账户都需要计算利息（`CalculateInterest`），但个人储蓄账户和企业对公账户的利率和计算公式完全不同。此时，父类无法提供一个通用的利息计算逻辑，只能将其声明为抽象方法，强制各个具体的账户子类自行实现。

## 严格的语法与编译期约束

C# 编译器对抽象方法施加了极其严格的规则限制，以保证契约的绝对执行：

1.  **无方法体**：抽象方法只包含方法声明（签名），以分号 `;` 结尾，绝不能包含大括号 `{ }`。
2.  **宿主限制**：抽象方法**只能**声明在抽象类（`abstract class`）内部。普通类不能包含抽象方法。
3.  **强制重写**：任何继承自该抽象类的非抽象子类，**必须**实现所有的抽象方法。如果不实现，子类也会报错，导致编译失败。
4.  **签名绝对一致**：子类在实现时，必须使用 `override` 关键字，并且其访问修饰符（如 `public`）、返回类型、方法名和参数列表必须与父类中的抽象方法完全一致。

## 核心对比：`abstract` vs `virtual`

在实际开发中，正确区分何时使用虚方法（Virtual），何时使用抽象方法（Abstract）是架构设计的基石。

| 特性                  | `virtual` (虚方法)              | `abstract` (抽象方法)        |
| :------------------ | :--------------------------- | :----------------------- |
| **方法体 (Body)**      | 必须提供默认的方法实现。                 | 绝对不能提供方法实现。              |
| **子类重写 (Override)** | **可选**。子类如果不重写，将自动沿用父类的默认逻辑。 | **强制**。子类必须重写，否则无法通过编译。  |
| **设计语义**            | “这是一个通用行为，但你可以根据需要修改它。”      | “这是一个必须具备的行为，且你必须自己实现它。” |
| **宿主类**             | 可以存在于普通类或抽象类中。               | 只能存在于抽象类中。               |

## 代码实战：强制契约实现

以下代码展示了如何利用抽象类和抽象方法来规范不同员工类型的健康保险计算逻辑。

```csharp
using System;

// 1. 定义抽象父类
public abstract class Employee
{
    public string Name { get; set; }

    public Employee(string name)
    {
        Name = name;
    }

    // 2. 声明抽象方法：没有方法体，强制子类实现
    public abstract void CalculateHealthInsurance();
}

// 3. 子类 1：Manager
public class Manager : Employee
{
    public Manager(string name) : base(name) { }

    // 必须使用 override，且签名必须完全匹配
    public override void CalculateHealthInsurance()
    {
        // Manager 特有的复杂计算逻辑
        Console.WriteLine($"[Manager] {Name} 的健康保险额度计算完成：$1000");
    }
}

// 4. 子类 2：Salesman
public class Salesman : Employee
{
    public Salesman(string name) : base(name) { }

    // 必须实现，否则 Salesman 无法被编译
    public override void CalculateHealthInsurance()
    {
        // Salesman 特有的计算逻辑
        Console.WriteLine($"[Salesman] {Name} 的健康保险额度计算完成：$500");
    }
}

public class Program
{
    public static void Main()
    {
        // 多态调用
        // 注意：无法实例化 Employee (如 new Employee())
        Employee mgr = new Manager("Alice");
        Employee sales = new Salesman("Bob");

        // 运行时根据实际对象类型，调用各自重写后的具体实现
        mgr.CalculateHealthInsurance();
        sales.CalculateHealthInsurance();
    }
}
```

## 架构设计与底层机制剖析

### 模板方法模式
结合 GoF 的《设计模式》，抽象方法最经典的应用场景是**模板方法模式**。
在大型框架设计中，基类（抽象类）通常会定义一个普通的方法作为算法的“骨架”（模板），而在骨架中调用各种抽象方法。这样，基类控制了算法的执行顺序和整体流程，而将某些特定的、可变的具体步骤推迟到子类中去实现。

```csharp
public abstract class DataProcessor
{
    // 模板方法（控制流程），子类无需重写
    public void Process()
    {
        ReadData();     // 具体步骤 1
        FormatData();   // 具体步骤 2 (抽象方法)
        SaveData();     // 具体步骤 3
    }

    private void ReadData() { Console.WriteLine("读取数据..."); }
    private void SaveData() { Console.WriteLine("保存数据..."); }

    // 留给子类实现的具体逻辑
    protected abstract void FormatData(); 
}
```

### CLR 视角的抽象方法
根据《CLR via C#》的解析，在公共语言运行时（CLR）的底层，抽象方法本质上就是一种**特殊的虚方法**（在 C++ 中被称为纯虚函数，Pure Virtual Function）。
*   在生成的 IL（中间语言）代码中，抽象方法会被标记为 `virtual` 和 `abstract`。
*   CLR 会确保任何包含未实现抽象方法的类型，其元数据都会被标记为不可实例化。这是在虚拟机层面保证了抽象契约的安全性，防止在运行时执行到内存中不存在的空方法体。
