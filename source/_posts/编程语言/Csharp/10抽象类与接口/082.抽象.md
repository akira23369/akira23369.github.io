# 抽象 (Abstraction)

抽象（Abstraction）是面向对象编程（OOP）的四大基本支柱之一（封装、继承、多态、抽象）。其核心思想是通过**简化复杂系统的结构和行为**，提取出系统中最重要、最本质的特征，而将复杂的底层实现细节隐藏起来。

## 核心概念：什么是抽象？

在软件工程中，抽象本质上是建立一个**蓝图（Blueprint）** 或**契约（Contract）**。这个契约只包含公开的、重要的属性和方法，用来定义“这个对象能做什么”，而完全不关心“它是怎么做到的”。

**经典类比：书籍的目录（Table of Contents）**
抽象就像是一本书的目录。通过阅读目录，读者可以立即知道这本书包含了哪些章节、涵盖了哪些主题，而不需要通读整本书的具体文字。在代码中，当你查看一个抽象类型时，你看到的就是这组操作的“目录”，而具体的业务逻辑（章节内容）则推迟到具体的子类中去实现。

## 抽象的两种实现方式

在 C# 中，抽象主要通过两种语言机制来实现：**抽象类（Abstract Classes）** 和 **接口（Interfaces）**。它们都充当具体子类的父级约束，强制子类必须实现某些特定的成员。

### 抽象类
抽象类是一种**不完整的类**，它不能被实例化（不能 `new`）。它通常包含两部分：
*   **具体实现**：所有子类共享的通用代码和状态（字段）。
*   **抽象成员**：使用 `abstract` 关键字修饰的方法或属性，只有声明，没有方法体。它强制所有非抽象的派生类必须使用 `override` 关键字来提供具体的实现。

### 接口 (Interface)
接口是一种**极其严格的契约**。传统上（C# 8.0 之前），接口中只能包含方法、属性、事件或索引器的声明，绝对不能包含任何状态（字段）或实现。实现接口的类必须提供接口中定义的所有成员的具体代码。

> **语法提示**：在 C# 命名规范中，接口的名称通常以大写字母 **`I`** 开头（如 `ICar`, `IDatabase`）。

## 代码实战：汽车模型的抽象

以下代码展示了如何利用抽象类和接口来提取汽车（Car）的通用行为。

```csharp
using System;

// 1. 使用接口定义高度抽象的契约
public interface IVehicle
{
    // 接口只定义“能做什么”
    void StartEngine();
    void StopEngine();
}

// 2. 使用抽象类提供部分抽象和共享逻辑
public abstract class Car : IVehicle
{
    // 共享的状态（抽象类可以有字段）
    public string ModelName { get; protected set; }

    public Car(string modelName)
    {
        ModelName = modelName;
    }

    // 实现接口方法（提供通用逻辑）
    public void StartEngine()
    {
        Console.WriteLine($"{ModelName}: 引擎点火...");
        CheckSystem(); // 调用内部通用逻辑
    }

    public void StopEngine()
    {
        Console.WriteLine($"{ModelName}: 引擎熄火...");
    }

    // 内部的受保护逻辑
    protected void CheckSystem()
    {
        Console.WriteLine("系统自检完成，状态正常。");
    }

    // 3. 抽象方法：强制具体的子类必须提供自己的实现
    // 因为不同类型的汽车，其加速机制是完全不同的（如电车 vs 油车）
    public abstract void Accelerate();
}

// 4. 具体的实现类：电车
public class ElectricCar : Car
{
    public ElectricCar(string modelName) : base(modelName) { }

    // 必须使用 override 实现抽象方法
    public override void Accelerate()
    {
        Console.WriteLine($"{ModelName}: 电机输出最大扭矩，瞬间推背感！");
    }
}

// 5. 具体的实现类：油车
public class GasCar : Car
{
    public GasCar(string modelName) : base(modelName) { }

    public override void Accelerate()
    {
        Console.WriteLine($"{ModelName}: 变速箱降档，引擎发出轰鸣声加速！");
    }
}

public class Program
{
    public static void Main()
    {
        // 抽象类本身不能被实例化: Car myCar = new Car(); // 编译错误！
        
        // 针对抽象进行编程 (Program to an abstraction)
        Car tesla = new ElectricCar("Tesla Model 3");
        Car mustang = new GasCar("Ford Mustang");

        tesla.StartEngine();
        tesla.Accelerate();

        Console.WriteLine("-------------------");

        mustang.StartEngine();
        mustang.Accelerate();
    }
}
```

## 架构与设计原则补充 (扩展阅读)

结合《代码大全》(Code Complete) 与 GoF 的《设计模式》(Design Patterns)，抽象在系统架构中扮演着至关重要的角色：

### “面向接口编程，而不是面向实现编程”
这是面向对象设计中最著名的原则之一。
*   当系统中的各个模块依赖于**抽象（接口/抽象类）** 而不是具体的**实现类**时，模块之间的耦合度会大大降低。
*   在上面的例子中，客户端代码（`Main` 方法或者其他业务服务）只需要知道 `IVehicle` 或 `Car` 存在 `StartEngine` 和 `Accelerate` 方法即可。如果未来加入一种“氢动力汽车”，客户端代码完全不需要修改，这就是**开闭原则（OCP）** 的完美体现。

### 依赖倒置原则
SOLID 原则中的 "D" 强调用抽象来解耦高层模块和底层模块：
1.  高层模块不应该依赖底层模块。两者都应该依赖其抽象。
2.  抽象不应该依赖细节。细节应该依赖抽象。
通过定义良好的抽象契约，团队甚至可以实现并行开发（例如：后端定义好 `IRepository` 接口，前端就可以根据接口进行 Mock 测试，而后端可以慢慢实现数据库对接逻辑）。

### 现代 C# 的抽象演进 (C# 8.0 默认接口方法)
根据《C# in a Nutshell》，从 C# 8.0 开始，接口打破了“绝对不能有实现”的铁律，引入了**默认接口方法（Default Interface Methods, DIM）**。这使得开发者可以在不破坏现有实现类的情况下，向现有的接口中安全地添加新的方法。不过，接口依然不允许包含实例字段（状态），这依然是它与抽象类最核心的物理界限。
