# 表达式树(Expression Trees）

在 C# 3.0 中，伴随 LINQ 一起引入的**表达式树（Expression Trees）** 是 C# 语言中最具深度和魔力的特性之一。在日常的业务逻辑开发中，开发者极少需要手动去构建表达式树，但它却是诸如 Entity Framework (EF Core) 等 ORM 框架能够完美运作的绝对基石。

## 核心概念：代码即数据


想象一下你要吃一道菜：
- **普通方法（委托 Delegate / Func）：** 就像是一盘**已经做好的菜**。你可以直接吃（执行它），但如果你想知道里面放了多少盐，或者想把它改成辣的，非常困难，因为它已经成型了。
- **表达式树（Expression Tree）：** 就像是这道菜的**菜谱（文字说明）**。它不是真正的菜，不能直接吃。但你可以**阅读它**（哦，原来第一步是切菜，第二步是放盐），你可以**修改它**（把放糖改成放辣椒），你甚至可以**把它翻译成别的语言**（比如发给一个法国厨师看）。当你觉得没问题了，你随时可以照着菜谱把菜**做出来（编译并执行）**。

**总结一句话：** 表达式树就是把 C# **代码当作“数据”** 来存储的一种结构，而不是直接编译成机器码。

关于表达式树，一个非常常见但也容易引起误解的说法是“它是一个由委托（Delegates）组成的树形结构”。
参考《C# in Depth》（Jon Skeet 著）对表达式树的严谨剖析，更准确的定义应该是：**表达式树是一种将 C# 代码以抽象语法树（AST, Abstract Syntax Tree）的数据结构形式表示在内存中的机制。**

*   **委托 (Delegate)：** 是编译好的、可直接执行的二进制指令序列（**代码即执行**）。
*   **表达式树 (Expression Tree)：** 是尚未编译的数据结构，它记录了逻辑的构成（比如左边是一个参数，右边是一个常量，中间是一个加号）。（**代码即数据**）。

暂时不需要学会如何手写复杂的表达式树，但当你以后看到 `IQueryable` 或者方法的参数里写着 `Expression<>` 时，你要知道：**它要的不是你的执行结果，它要的是你的代码蓝图。**


## 直观对比：Func vs Expression

让我们看一段最简单的代码，过滤出大于 5 的数字。
**情况 A：普通的委托（Func）**
```cs
Func<int, bool> isGreaterThanFive = x => x > 5;
bool result = isGreaterThanFive(10); // 直接运行，结果是 true
```
在这里，`x => x > 5` 被编译成了二进制指令，像一个黑盒子，你只能运行它。


**情况 B：表达式树（Expression）**
```cs
// 注意类型外面包了一层 Expression<>
Expression<Func<int, bool>> expr = x => x > 5; 
```

在这里，虽然代码长得一模一样，但 C# 编译器没有把它变成黑盒子，而是把它拆解成了一棵**树状的数据结构**。

这棵树大概长这样：
- **根节点 (Lambda):** 有一个输入参数，和一个方法体。
    - **左边参数 (Parameter):** 名字叫 `x`，类型是 `int`。
    - **右边方法体 (Binary):** 一个“大于号 (>)”操作。
        - **大于号的左边:** 参数 `x`。
        - **大于号的右边 (Constant):** 常数 `5`。

你可以通过代码直接去“读取”这棵树里的信息！
```cs
Console.WriteLine(expr.Body); // 输出: (x > 5)
Console.WriteLine(expr.Parameters[0].Name); // 输出: x
```


## 表达式树的声明与编译流程

要使用表达式树，需要引入 `System.Linq.Expressions` 命名空间。表达式树的泛型包装类型是 `Expression<TDelegate>`，其中 `TDelegate` 通常是 `Func` 或 `Action` 委托。

表达式树的生命周期分为三个核心阶段：**构建 -> 编译 -> 执行**。

### 场景 1：基础数学运算 (计算平方)

```csharp
using System;
using System.Linq.Expressions;

public class Program
{
    public static void Main()
    {
        // 1. 构建阶段 (代码即数据)：
        // 编译器看到右侧的 Lambda 表达式，并不会将其编译为可执行的 IL 代码，
        // 而是将其解析为一个树状的数据结构（ParameterExpression, BinaryExpression 等）。
        Expression<Func<int, int>> squareExpression = a => a * a;

        // 2. 编译阶段 (数据转换为代码)：
        // 调用 Compile() 方法，CLR 会在运行时遍历这棵语法树，动态生成 IL 代码，
        // 并返回一个真正可执行的强类型委托。
        Func<int, int> squareDelegate = squareExpression.Compile();

        // 3. 执行阶段：
        // 执行委托，得到最终结果
        int result = squareDelegate.Invoke(10); // 或者直接写 squareDelegate(10)
        Console.WriteLine($"10 的平方是: {result}"); // 输出: 100
    }
}
```

### 场景 2：复杂对象条件判断 (判断是否为青少年)

```csharp
using System;
using System.Linq.Expressions;

public class Student
{
    public int StudentId { get; set; }
    public string StudentName { get; set; }
    public int Age { get; set; }
}

public class Program
{
    public static void Main()
    {
        Student student = new Student { StudentId = 1, StudentName = "Alice", Age = 15 };

        // 1. 构建表达式树：表示逻辑 "Age > 12 且 Age < 20"
        Expression<Func<Student, bool>> isTeenagerExpr = s => s.Age > 12 && s.Age < 20;

        // 2. 编译为可执行的委托
        Func<Student, bool> isTeenagerDelegate = isTeenagerExpr.Compile();

        // 3. 执行判断
        bool isTeenager = isTeenagerDelegate(student);
        
        Console.WriteLine($"{student.StudentName} 是青少年吗？ {isTeenager}"); // 输出: True
    }
}
```


### 进阶玩法：手动拼装表达式树（动态构建查询）

有时候，你在写代码的时候根本不知道过滤条件是什么（比如用户在网页上，左边下拉框选了“年龄”，中间选了“小于”，右边填了“25”）。  
这时候没法写死 `x => x < 25`，你可以用代码**动态拼出一棵树**：
```cs
// 我们要手动拼出: x => x < 25

// 1. 创建参数节点: x (类型为 int)
ParameterExpression param = Expression.Parameter(typeof(int), "x");

// 2. 创建常数节点: 25
ConstantExpression constant = Expression.Constant(25, typeof(int));

// 3. 创建比较节点: x < 25 (LessThan)
BinaryExpression body = Expression.LessThan(param, constant);

// 4. 把它们组合成一个 Lambda 表达式树
Expression<Func<int, bool>> dynamicExpr = Expression.Lambda<Func<int, bool>>(body, param);

// 看看拼出来的结果
Console.WriteLine(dynamicExpr); // 输出: x => (x < 25)

// 运行它
var myFunc = dynamicExpr.Compile();
Console.WriteLine(myFunc(20)); // 输出: True

```

## 底层解析：编译器如何解析表达式树？

在上面的例子中，当我们写下 `a => a * a` 时，如果在左边声明的是 `Func<int, int>`，编译器直接生成一个匿名方法；但因为左边声明的是 `Expression<Func<int, int>>`，编译器在后台实际上生成了类似下面这种繁琐的对象构建代码：

```csharp
// 编译器在后台隐式执行了类似如下的节点拼接操作：
ParameterExpression paramA = Expression.Parameter(typeof(int), "a");
BinaryExpression multiplyExpr = Expression.Multiply(paramA, paramA);
Expression<Func<int, int>> squareExpression = Expression.Lambda<Func<int, int>>(multiplyExpr, paramA);
```
这正是表达式树被称为“树”的原因：它由各种 Expression 节点（参数节点、二元操作节点、常量节点等）拼接而成，自底向上（Bottom-up）组合成完整的逻辑。

## 为什么需要表达式树？(核心应用场景)

如果在同一个 C# 程序中，无论如何都要调用 `.Compile()` 转成委托再执行，那为什么不一开始就直接使用委托呢？这样不是白白浪费了编译树的性能吗？

这就涉及到了表达式树最核心的价值：**跨语言/跨系统的查询翻译 (Query Translation)**。

以 Entity Framework (LINQ to SQL / LINQ to Entities) 为例：
假设我们有如下查询代码去数据库查询青少年学生：
`dbContext.Students.Where(s => s.Age > 12 && s.Age < 20).ToList();`

1. 如果 `Where` 接收的是一个**委托（Func）**：
   EF 无法查看委托内部写了什么逻辑（委托已经是黑盒的底层机器码了）。EF 只能把数据库里**所有的**学生数据全部下载到程序的内存中，然后逐个执行委托进行过滤。这对于拥有百万条数据的数据库来说是灾难性的。
   
2. 因为 `Where` 接收的是一个**表达式树（Expression）**：
   EF 可以在不执行代码的情况下，像拆解 JSON 一样拆解这棵树，发现左边是一个名为 `Age` 的属性，中间是大于号，右边是常量 `12`。于是，EF 框架将这棵 C# 的表达式树**翻译**成了原生的 SQL 语句：
   `SELECT * FROM Students WHERE Age > 12 AND Age < 20`
   然后将这句 SQL 发送给数据库去执行。

这就是为什么绝大多数普通开发者无需手动创建表达式树，但整个现代 .NET 数据访问层却须臾离不开它的根本原因。
