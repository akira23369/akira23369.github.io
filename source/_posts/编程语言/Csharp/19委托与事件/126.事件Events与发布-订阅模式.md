# 事件 (Events) 与发布-订阅模式

在 C# 中，事件（Events）是实现组件间松耦合通信的核心机制。它是多播委托（Multicast Delegates）的最高级抽象，构建了软件设计模式中经典的**发布-订阅模式（Publisher-Subscriber Pattern）**。

## 核心概念：发布与订阅体系

事件机制本质上是一个通知系统（Notification System），用于在状态发生改变时，将信息从一个对象广播给其他依赖该对象的对象。

*   **发布者 (Publisher)：** 拥有状态并定义事件的类。当其内部的某些数据发生变化或特定动作被触发时（例如：按钮被点击、银行账户利率修改、员工部门变更），发布者负责**引发（Raise/Invoke）** 事件。
*   **订阅者 (Subscriber)：** 关注发布者状态变化的类。订阅者会向发布者的事件注册自己的方法（称为**事件处理程序 Event Handler**）。当事件被引发时，这些方法会被自动执行。

## 为什么需要事件？(委托的局限性)

既然多播委托已经可以持有一组方法并依次调用，为什么 C# 还要专门引入 `event` 关键字？

参考《CLR via C#》中的深度解析，如果把委托直接声明为类的 `public` 字段，会破坏面向对象的**封装性**，带来严重的安全性问题：
1.  外部类可以直接使用 `=` 赋值，从而恶意或意外地清空掉之前所有其他订阅者注册的方法。
2.  外部类可以随时随地直接调用该委托，伪造事件的触发，这打破了“谁拥有状态，谁才应该发出通知”的逻辑闭环。

**`event` 关键字的作用就是施加极其严格的访问控制约束：**
*   在类的外部，事件只能使用 `+=`（订阅）和 `-=`（取消订阅）操作符。
*   **事件只能在定义它的类（发布者类）内部被触发（Invoke）。** 任何外部类都无权调用。

*(注：可以将事件理解为委托的“属性包装器”，就像 Property 封装 Field 一样，Event 封装了 Delegate。)*

## 事件的完整底层架构与代码实现

在 C# 中，事件的完整声明包含一个底层的私有委托实例，以及类似属性的 `add` 和 `remove` 访问器。当外部类使用 `+=` 时，会执行 `add` 代码块；使用 `-=` 时，会执行 `remove` 代码块。传入的方法引用由关键字 `value` 表示。

### 核心代码演示

```csharp
using System;

// 1. 声明委托类型 (定义事件的签名契约)
public delegate void DataChangedDelegate(int oldValue, int newValue);

// --- 发布者类 ---
public class Publisher
{
    // 隐藏在底层的私大多播委托，负责真正存储方法引用
    private DataChangedDelegate _dataChangedDelegate;

    // 2. 声明事件 (包含明确的 add 和 remove 访问器)
    public event DataChangedDelegate OnDataChanged
    {
        add 
        { 
            // value 代表订阅者传进来的方法引用
            _dataChangedDelegate += value; 
        }
        remove 
        { 
            _dataChangedDelegate -= value; 
        }
    }

    // 3. 触发事件的方法
    public void ChangeData(int oldValue, int newValue)
    {
        Console.WriteLine($"[Publisher] 数据正在从 {oldValue} 变更为 {newValue}...");
        
        // 传统的安全触发方式：先检查是否为空 (是否有订阅者)
        if (_dataChangedDelegate != null)
        {
            _dataChangedDelegate(oldValue, newValue); // 触发通知
        }
        
        // 现代 C# 推荐的线程安全触发方式：
        // _dataChangedDelegate?.Invoke(oldValue, newValue);
    }
}

// --- 订阅者类 ---
public class Subscriber
{
    // 事件处理程序 (方法签名必须与 DataChangedDelegate 委托完全匹配)
    public void HandleDataChange(int oldVal, int newVal)
    {
        Console.WriteLine($"[Subscriber] 收到通知！开始根据新数据 {newVal} 进行重新计算。");
    }
}

// --- 主程序 ---
public class Program
{
    public static void Main()
    {
        Publisher pub = new Publisher();
        Subscriber sub = new Subscriber();

        // 4. 订阅事件 (触发 add 访问器)
        pub.OnDataChanged += sub.HandleDataChange;

        // 发布者内部状态改变，主动引发事件
        pub.ChangeData(100, 200);

        // 5. 取消订阅 (触发 remove 访问器)
        pub.OnDataChanged -= sub.HandleDataChange;
    }
}
```

## 深入剖析与最佳实践

### 空值检查与线程安全 (`?.Invoke`)
在触发事件时，如果当前没有任何对象订阅该事件，底层委托的值就是 `null`。此时直接调用会导致 `NullReferenceException` 崩溃。
在《Effective C#》中强烈建议使用 C# 6.0 引入的空值条件运算符 `?.Invoke()`。它不仅语法简洁，更重要的是它能在内部将委托缓存在一个临时变量中，从而避免多线程环境下的竞态条件（例如在判空后，另一个线程恰好执行了 `-=` 移除了最后被引用的方法）。

### 避免带返回值的事件
事件的委托返回类型应当始终设定为 `void`。
因为事件底层是多播委托，如果定义了返回值，当触发事件并依次执行多个订阅者的方法时，调用方只能接收到**最后一个**订阅者返回的值，前面所有订阅者的返回值都会被丢失，这会导致逻辑上的混乱与不可预期行为。

### 编译器的自动实现 (语法糖)
在实际开发中，我们极少手动编写 `add` 和 `remove` 代码块以及私有的底层委托（就像我们很少手写带有私有字段的完整属性，而是使用自动属性 `public int Age { get; set; }`）。
如果省略访问器直接声明事件，C# 编译器会自动在后台生成一个同名的私有委托字段，以及线程安全的 `add` / `remove` 方法。*(下一阶段的笔记会专门探讨这种“自动实现的事件”。)*

### C# 标准事件模式
虽然可以像上文中那样自定义带有业务参数（如 `int, int`）的委托，但 .NET 框架定义了一套标准的事件设计规范：
要求委托的签名必须包含两个参数：
1.  `object sender`：事件的发送者（通常传入 `this`）。
2.  `EventArgs e`：事件的参数（继承自 `System.EventArgs`，用于封装传递的数据）。
（这通常通过预定义的 `EventHandler` 和 `EventHandler<TEventArgs>` 泛型委托来实现）。
