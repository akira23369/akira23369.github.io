# 预定义泛型委托：Predicate

在介绍了 `Func` 和 `Action` 之后，C# 预定义泛型委托三剑客中的最后一位是 **`Predicate`**。

在计算机科学和逻辑学中，**Predicate（谓词）** 一词指的是一个判断真假的逻辑命题。在 C# 中，`Predicate` 委托的设计初衷正是为了封装那些 **“评估某个对象是否满足特定条件”** 的方法。

## 核心概念：什么是 Predicate？

`Predicate<T>` 是定义在 `System` 命名空间下的一个泛型委托。

**使用 `Predicate` 的硬性条件：**
1. 目标方法**必须且只能接收 1 个输入参数**（类型为泛型 `T`）。
2. 目标方法**必须且只能返回 `bool` 类型**。

### 语法结构解析

`public delegate bool Predicate<in T>(T obj);`

*   `Predicate<T>`：接收一个 `T` 类型的参数，返回 `bool`（`true` 或 `false`）。

## 为什么有了 Func 还需要 Predicate？

从签名上看，`Predicate<T>` 与 `Func<T, bool>` 在逻辑上是**完全等价**的。它们都是接收一个对象并返回一个布尔值。

既然如此，为什么微软还要专门保留 `Predicate` 委托呢？
根据《C# in Depth》的解释，这主要是一个**历史遗留问题和语义表达**的问题：

1.  **历史原因：** `Predicate<T>` 实际上是在 .NET 2.0 时代伴随泛型集合（如 `List<T>`）一起被引入的（主要用于 `Find`、`RemoveAll` 等方法）。而 `Func` 和 `Action` 是在 .NET 3.5 时代伴随 LINQ 一起引入的。
2.  **语义明确：** 当你在 API 中看到 `Predicate<T>` 时，它的业务语义极其明确——这是一个用于“条件判断/过滤”的方法。而看到 `Func<T, bool>` 时，它只表示一个普通的转换逻辑，语义不如 `Predicate` 强烈。

## 代码演进与实战示例

`Predicate` 最典型的应用场景就是作为集合类的过滤条件。

### 场景 1：基础用法 (结合内联 Lambda)

```csharp
using System;

public class Program
{
    public static void Main()
    {
        // 声明一个 Predicate，用于判断数字是否为正数
        Predicate<int> isPositive = n => n >= 0;

        Console.WriteLine(isPositive(10));  // 输出: True
        Console.WriteLine(isPositive(-5));  // 输出: False
        
        // 声明一个 Predicate，用于验证字符串长度
        Predicate<string> isValidPassword = pwd => pwd.Length >= 8;
        Console.WriteLine(isValidPassword("12345")); // 输出: False
    }
}
```

### 场景 2：在框架层面的典型应用 (`List<T>`)

这是我们在日常开发中最常接触到 `Predicate` 的地方。`.NET` 的很多老旧集合类 API 仍然强制要求传入 `Predicate<T>` 而不是 `Func<T, bool>`。

```csharp
using System;
using System.Collections.Generic;

public class Employee
{
    public string Name { get; set; }
    public int Salary { get; set; }
}

public class Program
{
    public static void Main()
    {
        List<Employee> employees = new List<Employee>
        {
            new Employee { Name = "Alice", Salary = 5000 },
            new Employee { Name = "Bob", Salary = 8000 },
            new Employee { Name = "Charlie", Salary = 3000 }
        };

        // List<T>.FindAll 方法要求传入一个 Predicate<T>
        // 我们传入内联 Lambda：emp => emp.Salary >= 5000
        List<Employee> highEarners = employees.FindAll(emp => emp.Salary >= 5000);

        Console.WriteLine("高薪员工列表：");
        foreach (var emp in highEarners)
        {
            Console.WriteLine($"- {emp.Name}: {emp.Salary}");
        }
        // 输出: 
        // - Alice: 5000
        // - Bob: 8000
    }
}
```

## 预定义委托三剑客总结表

为了在实际开发中准确选择，以下是 `Func`、`Action` 和 `Predicate` 的终极对比：

| 特性 | `Action` | `Func` | `Predicate` |
| :--- | :--- | :--- | :--- |
| **返回值类型** | 总是 `void` | 由最后一个泛型参数决定（必不为 `void`） | 总是 `bool` |
| **参数数量** | 0 到 16 个 | 0 到 16 个输入参数 | **仅限 1 个**输入参数 |
| **主要应用场景** | 执行没有返回结果的动作（更新状态、打印日志、回调通知）。 | 数据转换、工厂方法创建对象、LINQ `Select`。 | 条件验证、数据过滤、LINQ `Where`、集合 `FindAll`。 |
| **等价写法** | 无 | `Func<T, bool>` 等价于 `Predicate<T>` | `Predicate<T>` 等价于 `Func<T, bool>` |

**《Effective C#》的最佳实践建议：** 
在你自己设计新的 API 时，除非是为了向后兼容旧的 .NET 2.0 代码，否则建议**优先使用 `Func<T, bool>` 来代替 `Predicate<T>`**。因为在 LINQ 体系中，所有的扩展方法（如 `.Where()`, `.Count()`）使用的都是 `Func<T, bool>`。统一使用 `Func` 可以减少不必要的委托类型转换，让代码生态更加一致。
