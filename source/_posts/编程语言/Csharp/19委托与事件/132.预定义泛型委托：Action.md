# 预定义泛型委托：Action

在学习了 `Func` 委托之后，我们知道 `Func` 强制要求目标方法必须有一个返回值。但在 C# 的实际开发中，我们有大量的方法仅仅是执行某些操作（例如打印日志、保存文件、更新 UI 状态等），它们并不需要返回任何数据，即返回类型为 `void`。

为了填补 `Func` 在 `void` 返回类型上的空白，微软在 .NET 框架中提供了另一个极其重要的预定义泛型委托大家族：**`Action`**。

## 核心概念：什么是 Action？

`Action` 委托的唯一职责就是封装一个**没有返回值（即返回类型为 `void`）** 的方法。

**使用 `Action` 的硬性条件：**
1. 目标方法的返回类型**必须是 `void`**。
2. 目标方法可以包含 **0 到 16 个输入参数**。

### 语法结构解析

与 `Func` 不同，`Action` 的泛型签名中没有代表返回值的参数。它的所有泛型参数全部代表**输入参数类型**。

*   `Action`（非泛型版本）：无输入参数，无返回值。
*   `Action<T>`：接收 1 个 `T` 类型参数，无返回值。
*   `Action<T1, T2>`：接收 2 个参数，无返回值。
*   ...以此类推，最多到 `Action<T1, T2, ... T16>`。

## 代码演进与实战示例

`Action` 极大地简化了无返回值回调方法和事件驱动架构的编写。

### 场景 1：基础用法 (结合 Lambda 表达式)

```csharp
using System;

public class Program
{
    public static void Main()
    {
        // 1. 无参数的 Action
        Action printWelcome = () => Console.WriteLine("欢迎学习 C#!");
        printWelcome(); // 输出: 欢迎学习 C#!

        // 2. 带有参数的 Action
        // 接收两个 string 参数，无返回值
        Action<string, string> printFullName = (firstName, lastName) => 
        {
            Console.WriteLine($"Full Name: {firstName} {lastName}");
        };
        printFullName("John", "Doe"); // 输出: Full Name: John Doe
    }
}
```

### 场景 2：将 Action 作为回调函数传递

这是在异步编程或耗时任务中最常见的模式。我们在执行任务时，将一个 `Action` 委托传递进去，当任务完成时，通过调用该 `Action` 来通知调用方。

```csharp
using System;
using System.Threading;

public class TaskRunner
{
    // 接收任务名称，并在完成时通过 Action 回调通知
    public void ExecuteTask(string taskName, Action<string> onCompleted)
    {
        Console.WriteLine($"[开始] 执行任务: {taskName}...");
        // 模拟耗时操作
        Thread.Sleep(1000); 
        Console.WriteLine($"[结束] 任务: {taskName} 执行完毕。");

        // 触发回调函数
        onCompleted?.Invoke(taskName);
    }
}

public class Program
{
    public static void Main()
    {
        TaskRunner runner = new TaskRunner();

        // 将 Lambda 表达式作为 Action 回调传递
        runner.ExecuteTask("数据备份", taskName => 
        {
            Console.WriteLine($"[回调通知] 收到通知：{taskName} 已经成功完成，可以进行下一步操作。");
        });
    }
}
```

## Action 与 Func 的对比与选择

在架构设计时，选择 `Action` 还是 `Func` 的原则极其简单：**是否需要从委托中获取数据？**

| 特性 | `Action` | `Func` |
| :--- | :--- | :--- |
| **返回值类型** | 必须是 `void` | 必须是指定的类型（非 `void`） |
| **泛型参数含义** | 全部是输入参数 | 前面的是输入参数，最后一个是返回值 |
| **无输入参数的写法** | `Action` | `Func<TResult>` |
| **应用场景** | 执行命令、触发事件、日志打印、无返回数据的回调。 | 提取数据、进行计算、工厂方法、LINQ 投影 (`Select`)。 |

## 框架层面的应用(Bridge模式)

正如视频中所提及，`Action` 和 `Func` 构成了一种天然的“桥梁（Bridge）”。

在 .NET 框架的底层源码中（比如 `List<T>.ForEach(Action<T> action)` 方法），微软的工程师只负责定义方法的执行框架：遍历列表并对每个元素调用传入的 `Action`。
作为应用程序开发者的你，只需要编写符合该 `Action` 签名的业务逻辑（比如打印元素或者修改元素状态）并传递进去即可。

这种设计使得框架代码与业务代码完全解耦，是开闭原则（Open-Closed Principle）在函数式编程思想下的完美体现。
