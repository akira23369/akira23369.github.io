# 标准事件委托：EventHandler

在 C# 中，虽然我们可以使用 `Action`、`Func` 或自定义委托来定义事件，但微软在 .NET 框架中建立了一套**标准事件模式（Standard .NET Event Pattern）**。这套模式的核心正是预定义委托 **`EventHandler`** 以及它的泛型版本 **`EventHandler<TEventArgs>`**。

参考《CLR via C#》中关于事件设计的指导原则，遵循这套标准模式可以保证代码与整个 .NET 生态系统（特别是 WinForms、WPF 等 UI 框架）的高度兼容性和一致性。

## 核心概念与签名解析

无论是标准的 `EventHandler` 还是泛型的 `EventHandler<TEventArgs>`，其底层签名都强制规定了两个核心参数，并且返回类型永远为 `void`。

```csharp
// 非泛型版本签名（用于不需要传递额外数据的事件）
public delegate void EventHandler(object sender, EventArgs e);

// 泛型版本签名（用于需要传递自定义数据的事件）
public delegate void EventHandler<TEventArgs>(object sender, TEventArgs e) where TEventArgs : EventArgs;
```

### 深入解析两大固定参数：

1.  **`object sender` (事件发送者)：**
    *   代表引发该事件的对象引用。
    *   **为什么类型是 `object`？** 因为这套签名被设计为适用于 .NET 框架中的所有类。任何类都可以作为发送者。
    *   在发布者（Publisher）类中触发事件时，通常会传入 `this` 关键字。
    *   在订阅者（Subscriber）的事件处理程序中，如果需要访问发布者的成员，通常需要将 `sender` 强制向下转型（Downcasting）为具体的发布者类型。

2.  **`EventArgs e` (事件参数)：**
    *   代表随事件传递的附加状态或数据（Payload）。
    *   基类 `System.EventArgs` 本身不包含任何数据。如果事件仅仅是作为一个“通知”（例如：按钮被点击了），直接传递 `EventArgs.Empty` 即可。

## 传递自定义数据：自定义 EventArgs

当事件不仅需要通知“发生了某事”，还需要传递“相关的上下文数据”时（例如：温度改变了，新温度是多少？），我们需要创建自定义的事件参数类。

**开发范式：**
1. 创建一个继承自 `System.EventArgs` 的类（按照规范，类名以 `EventArgs` 结尾）。
2. 在该类中定义只读属性来保存传递的数据。
3. 使用 `EventHandler<自定义EventArgs类>` 来声明事件。

## 完整实战代码示例

以下代码展示了如何使用 `EventHandler<T>` 实现一个温度监控报警系统的标准事件驱动模型：

```csharp
using System;

// 1. 定义自定义事件参数类 (继承自 EventArgs)
public class TemperatureChangedEventArgs : EventArgs
{
    public double OldTemperature { get; }
    public double NewTemperature { get; }

    public TemperatureChangedEventArgs(double oldTemp, double newTemp)
    {
        OldTemperature = oldTemp;
        NewTemperature = newTemp;
    }
}

// 2. 发布者类 (Publisher)
public class Thermostat
{
    private double _currentTemperature;

    // 使用预定义的泛型 EventHandler 声明事件
    public event EventHandler<TemperatureChangedEventArgs> TemperatureChanged;

    public void SetTemperature(double newTemp)
    {
        if (_currentTemperature != newTemp)
        {
            double oldTemp = _currentTemperature;
            _currentTemperature = newTemp;

            // 触发事件
            OnTemperatureChanged(oldTemp, newTemp);
        }
    }

    // 标准模式：定义一个受保护的虚拟方法来触发事件
    protected virtual void OnTemperatureChanged(double oldTemp, double newTemp)
    {
        // 实例化自定义 EventArgs
        var e = new TemperatureChangedEventArgs(oldTemp, newTemp);
        
        // 触发事件，sender 传入 this 代表当前恒温器对象实例
        TemperatureChanged?.Invoke(this, e);
    }
}

// 3. 主程序 (充当订阅者的角色)
public class Program
{
    public static void Main()
    {
        Thermostat thermostat = new Thermostat();

        // 订阅事件：使用 Lambda 表达式
        thermostat.TemperatureChanged += (sender, e) =>
        {
            // 如果需要，可以将 sender 转换为实际类型
            var source = sender as Thermostat;
            
            Console.WriteLine($"[警告] 温度已改变！旧温度: {e.OldTemperature}°C, 新温度: {e.NewTemperature}°C");
        };

        // 改变状态，触发事件
        Console.WriteLine("设置温度为 25.5°C...");
        thermostat.SetTemperature(25.5);

        Console.WriteLine("设置温度为 30.0°C...");
        thermostat.SetTemperature(30.0);
    }
}
```

### 为什么必须是 void 返回类型？
正如多播委托所表现出的特性，如果事件底层的委托带有返回值，当有多个订阅者注册时，触发事件的发布者只能接收到**最后一个**订阅者执行后的返回值，这会导致严重的逻辑不可预期性。因此，`EventHandler` 强制规定返回类型为 `void`。如果需要订阅者向发布者反馈数据，应该在 `EventArgs` 中添加可写的属性（虽然一般建议 `EventArgs` 为只读）。

### EventArgs.Empty 的使用
如果事件不需要传递任何额外数据，**千万不要**使用 `new EventArgs()`。每次实例化都会在托管堆上分配内存并增加 GC 负担。标准的做法是使用 `EventArgs.Empty`（它底层是一个静态只读实例），这样可以实现零内存分配。

```csharp
// 声明无数据的事件
public event EventHandler ProcessCompleted;

// 触发
ProcessCompleted?.Invoke(this, EventArgs.Empty);
```

### 适用场景探讨
`EventHandler` 模式是构建桌面级 GUI 应用程序（如 Windows Forms, WPF, UWP）的基石。在这些框架中，所有的 UI 事件（Click、TextChanged、MouseOver）无一例外都采用了这种签名。

但在现代的 ASP.NET Core MVC 或 Web API 开发中，HTTP 请求本质上是无状态的、线性的流转过程，直接使用 C# 事件机制的场景大幅减少（通常会被依赖注入、中间件或基于消息队列的发布/订阅架构所取代）。即便如此，理解并掌握 `EventHandler` 依然是深入理解 .NET 框架底层设计哲学的必经之路。
