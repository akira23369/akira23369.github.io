# catch 块的匹配艺术与执行逻辑

## 引言
在上一篇中，我们认识了庞大的异常家族。当 `try` 块中的代码发生意外时，系统会抛出一个具体的异常对象（比如 `FileNotFoundException`）。接下来，系统会在代码中寻找能够处理这个对象的 `catch` 块。

如果把抛出异常比作“抛绣球”，那么 `catch` 块就是下面接绣球的人。系统会按照怎样的规则把绣球交给正确的人呢？本篇将为你详细揭秘。

---

## 精确匹配：如何通过异常类型筛选

在早期的编程语言中，捕获错误往往是一刀切的。但在 C# 中，你可以为不同类型的异常编写专门的处理逻辑。这叫做**精确匹配**。

### 语法基础
`catch` 关键字后面跟着一对圆括号，里面声明了你想要捕获的**异常类型**和一个**变量名**。
```csharp
catch (FileNotFoundException ex)
{
    // 只有当抛出的异常是 FileNotFoundException（或其子类）时，才会进入这里
}
```

### 为什么要精确匹配？
因为不同的异常需要完全不同的“抢救”方案。

**代码示例：场景 - 读取用户配置**
假设我们要求用户输入一个数字作为配置参数：

```csharp
using System;

public class Program
{
    public static void Main()
    {
        Console.WriteLine("请输入一个整数作为配置值：");
        string input = Console.ReadLine();

        try
        {
            // 可能发生转换错误，也可能发生数字溢出错误
            int configValue = int.Parse(input);
            Console.WriteLine($"配置成功，值为：{configValue}");
        }
        catch (FormatException ex)
        {
            // 应对策略 A：用户输入了字母或乱码
            Console.WriteLine("【格式错误】您输入的不是有效的整数，系统将使用默认配置值 0。");
        }
        catch (OverflowException ex)
        {
            // 应对策略 B：用户输入的数字太大，超过了 int 的最大值
            Console.WriteLine("【溢出错误】您输入的数字太大了，超出了系统承受范围！");
        }
    }
}
```
通过精确匹配，程序能够对症下药，给用户最准确的反馈，而不是含糊地报错。

## 捕获顺序规则：从上到下，从具体到宽泛

当一个 `try` 块后面跟着多个 `catch` 块时，C# 编译器和运行时遵循一套极其严格的匹配规则：**从上到下逐个检查，匹配到第一个合适的就执行，然后忽略后面的所有 catch 块。**

### 继承关系决定了先后顺序
这里必须引入上一篇讲过的**异常类层次结构**。
比如，`FileNotFoundException` 继承自 `IOException`，而 `IOException` 又继承自 `Exception`。

**核心铁律：子类异常必须放在父类异常的前面！** （即：从最具体的异常开始，到最宽泛的异常结束）。

### 如果顺序写反了会怎样？
如果你把父类放在了前面，C# 编译器会非常聪明地拦住你，直接报**编译错误（CS0160）**。

**反面教材（无法通过编译）：**
```csharp
try
{
    string text = System.IO.File.ReadAllText("config.txt");
}
catch (Exception ex) 
{
    // 错误！Exception 是所有异常的基类。
    // 如果把它放在第一位，它会像一张超级大网，把所有异常都拦截下来。
    Console.WriteLine("发生了错误");
}
catch (System.IO.FileNotFoundException ex)
{
    // 编译错误 CS0160：由于前面的 catch (Exception) 已经拦截了一切，
    // 这段代码永远不可能被执行到（Unreachable code）。
    Console.WriteLine("文件找不到");
}
```

**正确的姿势：漏斗式捕获**
```csharp
try
{
    string text = System.IO.File.ReadAllText("config.txt");
}
catch (System.IO.FileNotFoundException ex)
{
    // 第一层过滤：最具体。只有文件真找不到时才进来
    Console.WriteLine("文件丢失，请检查路径。");
}
catch (System.IO.IOException ex)
{
    // 第二层过滤：较宽泛。捕获除了 FileNotFoundException 之外的其他 IO 异常
    // 比如：文件被占用、没有读取权限等
    Console.WriteLine("读取文件时发生 IO 故障：" + ex.Message);
}
catch (Exception ex)
{
    // 第三层过滤：保底。捕获所有未知的奇葩异常（比如内存不足）
    Console.WriteLine("发生了未知的严重系统错误。");
}
```

## 进阶技巧：异常过滤器 (Exception Filters)

*注：这是 C# 6.0 引入的强大特性。*

有时候，光靠“异常类型”来筛选还不够。假设数据库抛出了一个 `SqlException`，但你想针对“主键冲突（错误码 2627）”和“连接超时（错误码 -2）”分别处理，在过去你只能在 catch 块里写 `if-else`。

现在，你可以使用 `when` 关键字进行更细粒度的匹配：

```csharp
try
{
    SaveDataToDatabase();
}
catch (SqlException ex) when (ex.Number == 2627)
{
    // 只有当异常是 SqlException，并且错误号是 2627 时，才匹配这个 catch 块
    Console.WriteLine("用户名已存在，请更换一个。");
}
catch (SqlException ex) when (ex.Number == -2)
{
    Console.WriteLine("数据库连接超时，请检查网络。");
}
catch (SqlException ex)
{
    // 处理其他所有数据库异常
    Console.WriteLine("数据库发生未知异常：" + ex.Message);
}
```
**好处：** 保持了 catch 块的单一职责，代码更加平铺和清晰；更重要的是，如果 `when` 条件不满足，异常会继续往下寻找匹配项，而不会破坏原始的调用堆栈（这在高级调试中非常关键）。

## 捕获所有异常：何时以及如何使用 catch(Exception ex)

`catch (Exception ex)` 是异常处理中的终极安全网，因为它能捕获所有的异常。但也正因如此，它是一把极其危险的双刃剑。

### 危险的反面模式：吞没异常
新手最常犯的错误，就是不管三七二十一，用 `catch(Exception)` 把代码包起来，然后里面什么都不干，或者只写一句 `Console.WriteLine("出错了")`。

```csharp
// 极度恶劣的代码示例（切勿模仿）
public void ProcessPayroll()
{
    try
    {
        // 复杂的发工资逻辑
        CalculateTaxes();
        TransferMoney();
    }
    catch (Exception ex)
    {
        // 异常被吃掉了！
        // 钱没发出去，但程序没有报错，继续默默运行。
        // 老板和员工都不知道发生了什么，直到月底对账才发现大灾难。
    }
}
```
**为什么错？** 你不仅掩盖了常规错误，甚至把可能导致系统崩溃的严重错误（如内存溢出、空指针）也掩盖了。程序带着错误的状态继续运行，往往会造成更严重的数据损坏。

### 正确的使用场景：在系统的“边界”兜底
那么，什么时候该用 `catch (Exception ex)` 呢？
答案是：在程序的**最顶层边界（Top-Level Boundaries）**。

*   **UI 层（如 WinForms/WPF 的全局异常处理事件）：** 防止一个没想到的 Bug 直接弹窗让程序闪退，而是捕获后弹出一个友好的“很抱歉，程序遇到未知问题”，然后优雅退出或重置界面。
*   **Web API 控制器顶层或中间件：** 捕获所有未处理的异常，将其转化为 HTTP 500 状态码返回给前端，同时把堆栈信息记录到服务端的日志中心（如 NLog, Serilog），绝对不能让服务端进程崩溃。
*   **线程或后台任务的入口点：** 保证一个后台线程的崩溃不会导致整个主进程崩溃。

**最佳实践示例：全局请求拦截器（伪代码概念）**
```csharp
public HttpResponse HandleUserRequest(Request req)
{
    try
    {
        // 调用底层的各种业务逻辑
        return BusinessLogic.Process(req);
    }
    catch (ValidationException ex) // 我们预期的业务校验异常
    {
        return new HttpResponse(400, ex.Message); // 告诉前端：你参数传错了
    }
    catch (Exception ex) // 兜底：处理所有预期之外的 Bug
    {
        // 1. 记录详细日志（必须包含 ex.StackTrace）
        Logger.Error("发生未处理的系统异常", ex);
        
        // 2. 返回模糊的错误信息给用户，隐藏技术细节
        return new HttpResponse(500, "服务器开小差了，请稍后再试。");
    }
}
```

### 总结
1.  **永远优先捕获最具体的异常。**
2.  **子类异常在前，父类异常在后。**
3.  **善用 `when` 过滤器简化逻辑。**
4.  **绝不滥用 `catch (Exception)` 去掩盖错误，只在系统边界处用它来记录日志和兜底。**
