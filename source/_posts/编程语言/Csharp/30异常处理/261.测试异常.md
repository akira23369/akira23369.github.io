# 测试异常——保障代码健壮性的最后防线


在软件开发中，我们往往容易将大量精力投入到“正常流程”（Happy Path）的单元测试中，而忽视了对异常情况的测试。然而，一个健壮的系统不仅要在输入正确时表现良好，更要在面对非法输入、依赖服务宕机或资源枯竭时，能够按照预期抛出或处理异常。测试异常，就是验证系统在边界条件和故障场景下行为的正确性。

本节将以 .NET 社区中最主流的 xUnit 测试框架以及 Moq 模拟库为例，深入探讨如何编写高质量的异常测试。

## 单元测试中的异常断言：Assert.Throws 与 Assert.ThrowsAsync

在早期的测试框架（如老版本的 MSTest）中，开发者经常使用 `[ExpectedException]` 特性来标记一个测试方法期望抛出异常。这种方式存在一个致命缺陷：它无法精确定位异常是由测试方法中的哪一行代码抛出的。如果测试的准备阶段（Arrange）意外抛出了同类型的异常，测试也会被判定为通过，这会掩盖真正的 Bug。

现代测试框架推荐使用显式的断言方法来捕获异常。

同步方法的测试：Assert.Throws
对于同步执行的代码，我们使用 `Assert.Throws` 或 `Assert.Throws<TException>`。它接收一个 Action 委托，并在执行该委托时捕获异常。

```csharp
using System;
using Xunit;

public class MathUtilities
{
    public int Divide(int numerator, int denominator)
    {
        if (denominator == 0)
        {
            throw new ArgumentOutOfRangeException(nameof(denominator), "除数不能为零。");
        }
        return numerator / denominator;
    }
}

public class MathUtilitiesTests
{
    [Fact]
    public void Divide_DenominatorIsZero_ThrowsArgumentOutOfRangeException()
    {
        // Arrange
        var math = new MathUtilities();
        int numerator = 10;
        int denominator = 0;

        // Act & Assert
        // Assert.Throws 会拦截委托中抛出的异常。如果委托没有抛出异常，或者抛出的类型不匹配，测试将失败。
        Assert.Throws<ArgumentOutOfRangeException>(() => math.Divide(numerator, denominator));
    }
}
```

异步方法的测试：Assert.ThrowsAsync
在异步编程盛行的今天，很多方法返回 Task。对于异步方法，必须使用 Assert.ThrowsAsync，它接收一个 `Func<Task>` 委托，并且你需要等待（await）这个断言的完成。

```csharp
using System;
using System.Threading.Tasks;
using Xunit;

public class DataService
{
    public async Task LoadDataAsync(string id)
    {
        if (string.IsNullOrEmpty(id))
        {
            throw new ArgumentNullException(nameof(id));
        }
        await Task.Delay(10); // 模拟异步I/O操作
    }
}

public class DataServiceTests
{
    [Fact]
    public async Task LoadDataAsync_NullId_ThrowsArgumentNullException()
    {
        // Arrange
        var service = new DataService();

        // Act & Assert
        // 注意前面的 await，如果不加 await，测试可能会在异步操作抛出异常前就结束，导致测试结果不可靠。
        await Assert.ThrowsAsync<ArgumentNullException>(() => service.LoadDataAsync(null));
    }
}
```

## 异常消息与属性的深度验证：精确 vs 模糊匹配

仅仅断言异常类型往往是不够的。例如，一个方法可能会在不同的业务逻辑分支抛出相同类型的 InvalidOperationException。为了确保代码走到了正确的错误处理分支，我们需要检查异常的具体属性，尤其是异常的 Message 或者自定义属性。

Assert.Throws 和 Assert.ThrowsAsync 会返回被捕获的异常实例，这允许我们对其进行进一步的断言。

精确匹配（Exact Match）
精确匹配要求期望的消息与实际抛出的消息完全一致。

```csharp
[Fact]
public void Divide_DenominatorIsZero_ThrowsWithExactMessage()
{
    // Arrange
    var math = new MathUtilities();

    // Act
    var exception = Assert.Throws<ArgumentOutOfRangeException>(() => math.Divide(10, 0));

    // Assert
    // 验证特定属性
    Assert.Equal("denominator", exception.ParamName);
    
    // 验证精确的错误消息（注意：系统异常的消息通常会附带参数名，所以精确匹配往往比较苛刻）
    Assert.Equal("除数不能为零。 (Parameter 'denominator')", exception.Message);
}
```

模糊匹配（Fuzzy Match）
在实际项目中，异常消息可能会因为多语言（国际化）、.NET 版本的升级或动态拼接的内容而发生微小的变化。因此，使用包含关系（Contains）或正则表达式进行模糊匹配往往是更推荐的最佳实践，它能提升测试的脆弱性。

```csharp
[Fact]
public void Divide_DenominatorIsZero_ThrowsWithFuzzyMessage()
{
    // Arrange
    var math = new MathUtilities();

    // Act
    var exception = Assert.Throws<ArgumentOutOfRangeException>(() => math.Divide(10, 0));

    // Assert
    // 只要消息中包含核心错误信息即可，忽略框架添加的额外格式
    Assert.Contains("除数不能为零", exception.Message);
}
```

验证自定义异常属性
如果你使用了自定义异常，还可以验证你附加的业务上下文数据是否正确传递。

```csharp
// 假设有一个自定义异常：public class UserNotFoundException : Exception { public int UserId { get; } }

[Fact]
public void GetUser_UserDoesNotExist_ThrowsUserNotFoundExceptionWithUserId()
{
    var repository = new UserRepository();
    int invalidUserId = 999;

    var ex = Assert.Throws<UserNotFoundException>(() => repository.GetUser(invalidUserId));

    Assert.Contains("找不到指定的用户", ex.Message);
    Assert.Equal(invalidUserId, ex.UserId); // 验证业务属性
}
```

## Mock 异常：模拟依赖项抛出异常

在分层架构中，上层模块依赖于下层模块（如业务逻辑层依赖数据访问层）。测试业务逻辑层时，我们需要验证：当下层模块发生异常（如数据库连接超时）时，当前层是否能正确地捕获、记录日志并转换为合适的业务异常抛出。

这时，我们需要使用 Mock 框架（如 Moq）来强制下层接口抛出异常。

场景设定：
我们有一个 IUserRepository 接口和一个 UserService。当 IUserRepository 抛出底层的 SqlException 时，UserService 应该捕获它，并抛出一个更友好的 UserServiceException，同时包含原始的内部异常（InnerException）。

```csharp
using System;
using System.Data.SqlClient;
using Moq;
using Xunit;

// --- 业务代码 ---
public interface IUserRepository
{
    string GetUserName(int id);
}

public class UserServiceException : Exception
{
    public UserServiceException(string message, Exception innerException) 
        : base(message, innerException) { }
}

public class UserService
{
    private readonly IUserRepository _repository;

    public UserService(IUserRepository repository)
    {
        _repository = repository;
    }

    public string GetUserName(int id)
    {
        try
        {
            return _repository.GetUserName(id);
        }
        catch (Exception ex) // 现实中应捕获具体异常如 SqlException，这里为演示简化
        {
            // 记录日志...
            throw new UserServiceException("获取用户信息失败，请稍后重试。", ex);
        }
    }
}

// --- 测试代码 ---
public class UserServiceTests
{
    [Fact]
    public void GetUserName_RepositoryThrowsException_WrapsInUserServiceException()
    {
        // Arrange
        var mockRepository = new Mock<IUserRepository>();
        var simulatedDbException = new InvalidOperationException("数据库连接超时"); 
        
        // 配置 Mock 对象：当调用 GetUserName(1) 时，抛出预设的异常
        mockRepository
            .Setup(repo => repo.GetUserName(1))
            .Throws(simulatedDbException);

        var userService = new UserService(mockRepository.Object);

        // Act & Assert
        // 验证是否抛出了包装后的外层业务异常
        var actualException = Assert.Throws<UserServiceException>(() => userService.GetUserName(1));

        // 验证外层消息
        Assert.Equal("获取用户信息失败，请稍后重试。", actualException.Message);
        
        // 验证内部异常（InnerException）是否是我们模拟的底层异常
        Assert.NotNull(actualException.InnerException);
        Assert.Same(simulatedDbException, actualException.InnerException);
        Assert.Equal("数据库连接超时", actualException.InnerException.Message);
    }
}
```

在上面的 Mock 测试中，我们使用了 `Throws` 方法来配置依赖项的行为。这种测试方法被称为“交互测试”或“行为验证”，它对于验证系统的异常处理策略（边界层的异常映射规则）至关重要。

## 测试异常的常见反模式（应避免的做法）

在编写异常测试时，新手常犯以下错误，需要在实践中规避：

反模式 1：手动写 try-catch 进行断言
千万不要在测试方法中写 try-catch 来判断异常，这会让测试代码变得冗长且逻辑脆弱。

```csharp
// 错误示例（不要这样做）
[Fact]
public void BadTestExample()
{
    var math = new MathUtilities();
    try
    {
        math.Divide(10, 0);
        Assert.True(false, "应该抛出异常，但没有抛出"); // 如果没有异常，手动让测试失败
    }
    catch (ArgumentOutOfRangeException)
    {
        // 测试通过
    }
}
```
这种做法不仅可读性差，而且如果抛出了预期之外的异常类型，测试框架会直接中断，无法提供像 Assert.Throws 那样清晰的断言失败信息。

反模式 2：断言过于宽泛的基类
如果你预期方法抛出 ArgumentNullException，就不要去 `Assert.Throws<Exception>`。捕获基类 Exception 意味着如果代码因为其他 Bug（比如代码中隐藏的 NullReferenceException）崩溃，测试也会认为结果符合预期，从而产生假阳性测试（False Positive）。异常测试必须尽可能精确地指定预期的异常类型。

总结：
测试异常是领域驱动设计（DDD）中防御性编程和契约式设计的天然延伸。通过组合使用 Assert.Throws、异常属性的断言以及 Mock 框架的异常模拟能力，我们可以确保系统在最恶劣的环境下依然能够按照既定的降级策略或错误处理逻辑运行，从而大幅提升 C# 程序的可靠性。
