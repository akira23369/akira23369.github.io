# finally 块的奥秘与清理哲学

## 引言
在前面的文章中，我们学会了用 try 圈定危险区域，用 catch 捕获并处理异常。但是，程序的运行不仅仅是处理内存里的数据，往往还会涉及到与外部世界的交互：打开磁盘上的文件、建立与数据库的连接、占用网络端口等。

如果 try 块在执行到一半时发生了异常，程序会直接跳到 catch 块。那么问题来了：刚刚打开的文件还没来得及关闭怎么办？刚刚建立的数据库连接难道就一直干耗着吗？

为了解决这个“资源泄漏”的致命问题，C# 引入了 finally 关键字。

---

## 资源清理保证：无论是否发生异常都会执行

finally 块的唯一也是最重要的使命就是：**提供一个绝对可靠的执行保证。** 

只要程序进入了 try 块，那么无论 try 块中的代码是顺利执行完毕，还是中途抛出了异常，甚至是 catch 块中又抛出了新的异常，finally 块中的代码都**一定会被执行**。

### 为什么我们需要这种保证？
在 .NET 中，存在两种资源：
1. **托管资源（Managed Resources）：** 比如字符串、数组、普通的 C# 对象。这些资源由垃圾回收器（GC）自动管理，你不需要手动去释放。
2. **非托管资源（Unmanaged Resources）：** 比如文件句柄、数据库连接、网络套接字（Socket）、操作系统的窗口句柄等。GC 并不知道如何关闭这些系统级的资源。如果你不显式地写代码去释放它们，它们就会一直占用系统资源，直到程序崩溃。

### 经典反面教材 vs finally 救场

假设我们要往一个文本文件里写入日志。

**反面教材：没有 finally，导致文件被永远锁死**
```csharp
public void WriteLog(string message)
{
    StreamWriter writer = new StreamWriter("system.log");
    
    // 如果 message 为 null，这里会抛出 NullReferenceException
    writer.WriteLine(message.ToUpper()); 
    
    // 如果上面抛出异常，下面这行关闭文件的代码将永远不会被执行！
    writer.Close(); 
}
```
如果在上面的代码中发生了异常，文件流没有被关闭。当其他程序（甚至是我们的程序自己再次调用这个方法时）试图读取或写入 `system.log` 时，就会报出“文件正被另一进程使用”的错误。

**正确的姿势：使用 finally 确保清理**
```csharp
public void WriteLogSafe(string message)
{
    StreamWriter writer = null;
    try
    {
        writer = new StreamWriter("system.log");
        Console.WriteLine("文件已打开，准备写入...");
        
        // 即使这里抛出异常
        writer.WriteLine(message.ToUpper()); 
        
        Console.WriteLine("写入成功。");
    }
    catch (NullReferenceException)
    {
        Console.WriteLine("错误：日志信息不能为空。");
    }
    finally
    {
        // 这里的代码无论如何都会执行
        if (writer != null)
        {
            writer.Close();
            Console.WriteLine("文件已安全关闭。");
        }
    }
}
```
在这个安全的版本中，不管写入操作是否成功，finally 块都会检查 `writer` 是否被实例化，并负责将其关闭。水龙头打开了，无论如何最后都要拧紧，这就是 finally 的哲学。

## return 与 finally：执行顺序详解

如果在 try 块或者 catch 块中遇到了 `return` 语句，程序是要立即返回给调用者，还是先去执行 finally 块？

这是一个非常经典的 C# 陷阱题。
**答案是：先执行 finally 块，再真正将结果返回给调用者。**

### 执行流程拆解
让我们通过一段代码来观察具体的执行顺序：

```csharp
public class Program
{
    public static void Main()
    {
        Console.WriteLine("开始调用方法");
        int result = TestMethod();
        Console.WriteLine($"方法返回结果: {result}");
    }

    public static int TestMethod()
    {
        try
        {
            Console.WriteLine("执行 try 块");
            return 1; // 准备返回 1
        }
        finally
        {
            Console.WriteLine("执行 finally 块");
        }
    }
}
```
**控制台输出结果：**
```text
开始调用方法
执行 try 块
执行 finally 块
方法返回结果: 1
```
**底层逻辑：** 当代码执行到 `return 1;` 时，CLR（.NET 运行时）计算好了返回值（1），把它暂存在一个临时的地方。然后，CLR 发现下面还有一个 finally 块，于是立刻挂起返回操作，转身去执行 finally 块里的代码。等 finally 块执行完毕后，CLR 才把之前暂存的返回值抛给调用者。

### 在 finally 里修改返回值会怎样？
既然 finally 是在 return 之后、真正返回之前执行的，那如果在 finally 块里修改了准备返回的变量，最终的返回值会变吗？

```csharp
public static int TrapMethod()
{
    int number = 10;
    try
    {
        return number; // 步骤一：暂存返回值 10
    }
    finally
    {
        number = 99; // 步骤二：在 finally 中修改变量
        Console.WriteLine($"finally 块中的 number 变成了: {number}");
    }
}
```
很多新手会认为这个方法返回 99。**大错特错！这个方法返回的仍然是 10。**

**原理解析：**
对于值类型（如 int），`return number;` 发生时，系统已经把 `10` 这个值复制到了一块临时的内存（或者寄存器）中作为最终的返回值。之后你在 finally 里修改 `number` 变量，修改的只是原来的局部变量，根本影响不到已经打包好准备发货的那个“返回值副本”。

*(注：如果返回的是引用类型（如一个对象），而在 finally 中修改了该对象的内部属性，那么调用者看到的属性值是会被改变的，因为传递的是引用的地址。但这种写法严重违背了代码的可读性，强烈不建议在 finally 中做与资源清理无关的逻辑。)*

## finally 中的异常：会发生什么？如何避免？

finally 块是用来“救火”的，但如果“消防员”自己也出事了怎么办？

这是一个极其危险的场景：**如果 finally 块内部也抛出了异常，它将直接掩盖掉 try 或 catch 中原本发生的异常。** 这种现象被称为“异常吞噬（Exception Masking）”。

### 灾难现场重现
```csharp
public static void DisasterMethod()
{
    try
    {
        // 这里的业务逻辑发生了严重的除零错误
        int a = 1 / int.Parse("0"); 
    }
    finally
    {
        // 清理代码因为疏忽，引发了空引用异常
        string resource = null;
        int length = resource.Length; 
    }
}
```
如果你在外部调用 `DisasterMethod` 并试图捕获异常，你会收到一个 `NullReferenceException`。
原本真正导致业务失败的元凶 `DivideByZeroException` **被永远地抹去和丢失了**。你排查日志时会完全摸不着头脑，这就是 finally 中发生异常的可怕之处。

### 如何避免 finally 中的异常？
为了防止消防员纵火，我们在编写 finally 块时必须遵守以下铁律：

1. **保持绝对简单（Keep it simple and stupid）：** finally 块里只做一件事——释放资源。绝对不要在 finally 里面写复杂的业务逻辑、数据库查询或网络调用。
2. **永远进行判空（Null Checks）：** 释放对象前，一定要确保该对象已经被成功实例化。
   ```csharp
   finally
   {
       if (connection != null && connection.State != ConnectionState.Closed)
       {
           connection.Close();
       }
   }
   ```
3. **防御性编程：** 如果 finally 里的清理动作确实有风险（比如通知外部服务器关闭连接，网络可能会断），可以再使用一层内部的 try-catch 把清理动作包起来，默默消化掉清理过程中的错误，不要让它抛出到外部。
   ```csharp
   finally
   {
       try
       {
           if (networkStream != null) networkStream.Close();
       }
       catch 
       { 
           // 忽略清理时发生的错误，或者仅仅记录在本地日志中
           // 绝对不向外抛出，以保护原本 try 块中的核心异常不被覆盖
       }
   }
   ```

---
**本篇总结：**
finally 是 C# 中保障程序健壮性的最后一道防线。它无视正常流程的跳转和异常的干扰，坚持完成资源清理工作。理解了 return 与 finally 的执行顺序，并严格防止 finally 内部引发异常，你就能写出滴水不漏的安全代码。
