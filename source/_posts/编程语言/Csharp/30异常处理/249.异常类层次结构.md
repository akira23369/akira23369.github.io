# 异常类层次结构与黑匣子解密

## 引言
在上一篇中，我们学习了使用 `try-catch` 为程序穿上防弹衣。但你可能会疑惑：`catch (DivideByZeroException ex)` 这里的 `DivideByZeroException` 是哪里来的？为什么它能精确捕获除零错误？

在 C# 的世界里，**所有的异常都是类（Class）**。当错误发生时，.NET 运行时（CLR）或你的代码会“实例化”一个异常对象，并把它“抛（throw）”出来。今天，我们就来认识一下这个庞大的异常家族。

---

## `System.Exception`：所有异常的“老祖宗”

在 C# 中，不管是什么类型的异常，它们都必须继承自一个最终的基类：`System.Exception`。
你可以把它理解为航空史上的“黑匣子”。当程序发生空难（崩溃）时，这个基类对象里装满了调查事故原因所需的所有核心数据。

### 核心“黑匣子”属性解析
当我们捕获到一个异常对象 `ex` 时，以下四个属性是我们破案的关键：

#### `Message`（案情简报）
*   **是什么：** 一段人类可读的字符串，简明扼要地描述了发生了什么错误。
*   **举例：** `"未将对象引用设置到对象的实例。"` 或 `"索引超出了数组界限。"`
*   **注意：** 这个属性通常是给**开发者或运维人员**看的，**千万不要直接把 `Message` 展示给最终用户**（用户看不懂，且可能泄露敏感信息，如数据库表名）。

#### `StackTrace`（案发轨迹 / 调用堆栈）
*   **是什么：** 这是一个字符串，记录了异常发生前，程序是一步步经过哪些方法来到“案发现场”的。它精确到**文件名和行号**（如果在 Debug 模式下或有 PDB 文件）。
*   **比喻：** 就像是嫌疑人的 GPS 历史轨迹。
*   **重要性：⭐⭐⭐⭐⭐**（排错的第一依据！）

#### `InnerException`（案中案 / 嵌套异常）
*   **是什么：** 有时候，一个异常会导致另一个异常。为了不丢失最原始的错误原因，我们会把导致当前异常的“元凶”包装在 `InnerException` 中。
*   **比喻：** 俄罗斯套娃。
*   **场景：** 数据库连接失败（底层异常 `SqlException`），导致用户登录失败（上层抛出自定义异常 `LoginFailedException`）。此时 `LoginFailedException.InnerException` 就是那个 `SqlException`。

#### `Data`（随身口袋）
*   **是什么：** 一个键值对字典（`IDictionary`）。允许我们在抛出异常时，往里面塞入一些自定义的上下文数据，方便在捕获时分析。

### 代码演示：解剖异常黑匣子
```csharp
using System;

public class Program
{
    public static void Main()
    {
        try
        {
            MethodA();
        }
        catch (Exception ex)
        {
            Console.WriteLine("=== 异常黑匣子数据 ===");
            Console.WriteLine($"【异常类型】: {ex.GetType().Name}");
            Console.WriteLine($"【简报 (Message)】: {ex.Message}");
            Console.WriteLine($"【发生方法 (TargetSite)】: {ex.TargetSite}");
            Console.WriteLine($"【案发轨迹 (StackTrace)】:\n{ex.StackTrace}");
            
            if (ex.Data.Contains("UserId"))
            {
                Console.WriteLine($"【附加数据 (Data)】: 发生错误的 UserId 是 {ex.Data["UserId"]}");
            }
        }
    }

    static void MethodA() => MethodB();
    
    static void MethodB()
    {
        // 模拟一个带有自定义数据的异常
        var ex = new InvalidOperationException("用户的账户状态异常，无法执行操作。");
        ex.Data.Add("UserId", 10086); // 往口袋里塞点线索
        ex.Data.Add("Time", DateTime.Now);
        
        throw ex; // 抛出！
    }
}
```
*(运行这段代码，你会清晰地看到 `MethodB` 是如何经过 `MethodA` 最终抛到 `Main` 方法的。)*

## 异常的两大分支与历史遗留问题

如果你翻开早期的 .NET 文档，你会发现 `System.Exception` 之下派生了两个主要的子类：

1.  **`System.SystemException`（系统异常）：**
    由 .NET 运行时（CLR）抛出的异常。比如空指针、数组越界、内存溢出等。它们代表底层基础设施或程序基本逻辑出了问题。
2.  **`System.ApplicationException`（应用异常）：**
    设计初衷是让**开发者自定义的业务异常**都继承自这个类，以便和系统异常区分开。

**⚠️ 划重点：这是一个已经被微软官方“废弃”的设计理念！**
在实际开发中，微软发现这种强行分类并没有带来实质性的好处，反而增加了类的层级复杂度。
**现代 C# 最佳实践：** 当你需要自定义异常时，**不要**继承 `ApplicationException`，而是**直接继承 `System.Exception`**（我们在后续章节会详细讲解自定义异常）。

## Fatal（致命错误）：有些错，救不了

虽然 `try-catch` 很强大，但有些异常被称为 **Fatal Exception（致命/严重异常）**。面对它们，程序通常应该选择“原地去世”（Fail Fast），而不是强行抢救。

*   **`OutOfMemoryException`（内存耗尽）：** 当程序申请不到内存时抛出。此时系统的状态极度不稳定，即使你 catch 住了，下一步连弹出一个警告框的内存可能都没了。
*   **`StackOverflowException`（堆栈溢出）：** 通常由无限递归引起（比如方法 A 调用方法 B，方法 B 又调用方法 A）。**在现代 .NET 中，这种异常是无法被 catch 捕获的**，程序会直接被操作系统强行终止。
*   **`ExecutionEngineException`：** .NET CLR 内部引擎发生致命错误。

**处理哲学：** 面对致命错误，不要试图用 `catch (Exception ex)` 去掩盖。让程序崩溃，并确保有外部守护进程（如 Docker、Windows 服务控制器、Supervisor）能够记录崩溃日志并重启程序，这才是最安全的做法。

## 常见内置异常图鉴

.NET 内置了上百种异常，你不需要全部背下来，但必须对以下最常打交道的“常客”了如指掌。我们按场景将它们分类：

### 参数校验家族（开发者没传对参数）
这是你在编写类库或方法时，**最经常主动抛出**的异常。
*   **`ArgumentNullException`：** “你不能给我一个 null！”。最常用，当方法要求参数必须有值却收到 null 时抛出。
*   **`ArgumentOutOfRangeException`：** “你给的数字太离谱了！”。比如要求传入 1-100 的分页页码，调用者传了 -5。
*   **`ArgumentException`：** 参数错误的通用基类。比如要求传入有效的邮箱格式，传来的却是一串乱码。

### 状态错误家族（时机不对）
*   **`InvalidOperationException`：** “现在不能做这个操作！”。比如：试图从一个空的队列中取出数据；或者在数据库连接还没打开时就去查询数据。
*   **`ObjectDisposedException`：** 试图操作一个已经被释放（Dispose）的对象（比如已关闭的文件流）。

### 低级 Bug 家族（纯属代码没写好）
这些异常通常是代码逻辑漏洞导致的，**正常情况下绝不应该在生产环境中抛出**。
*   **`NullReferenceException`（著名的空引用异常）：** 试图调用一个为 `null` 的对象的属性或方法。这是新手最常遇到的噩梦。（C# 8.0 引入的“可空引用类型”就是为了消灭它）。
*   **`IndexOutOfRangeException`：** 数组越界。比如数组长度是 5，你非要访问 `array[10]`。
*   **`InvalidCastException`：** 强行转换失败。比如试图把一个装有 `Dog` 对象的变量硬转成 `Cat` 类型。

### 外部资源环境家族（老天爷不赏饭吃）
这些异常往往不受代码控制，与网络、磁盘、权限等环境有关，**是 `try-catch` 需要重点防范的对象**。
*   **`IOException`及其子类：**
    *   `FileNotFoundException`（文件找不到）
    *   `DirectoryNotFoundException`（目录不存在）
    *   `UnauthorizedAccessException`（文件没有读写权限）
*   **`TimeoutException`：** 请求超时（常见于网络请求、数据库查询）。

### 最佳实践示例：主动防御（防患于未然）
好的代码不会等系统报错，而是在源头掐断。
```csharp
public void ProcessUserOrder(string userId, int orderAmount)
{
    // 1. 主动抛出异常：防御性编程，保护自己的方法不被乱用
    if (userId == null)
        throw new ArgumentNullException(nameof(userId), "用户ID不能为空！");
        
    if (orderAmount <= 0)
        throw new ArgumentOutOfRangeException(nameof(orderAmount), "订单金额必须大于0！");

    // 2. 正常业务逻辑...
    Console.WriteLine($"开始处理用户 {userId} 的订单...");
}
```
