# 全天候防御——全局异常处理策略

## 引言：为什么我们需要“全局”的防御？

在前面的文章中，我们学会了在代码里写 `try-catch`。你可以把它想象成在房间里放置**灭火器**。

如果我们在“读取文件”的代码旁边放了灭火器（写了 `try-catch`），那么读取文件失败时，我们能迅速扑灭火苗，程序安然无恙。

但现实情况是：**程序员是人，不是神。** 
我们不可能预判所有的 Bug，也不可能在每一行代码外面都套上 `try-catch`（那代码就没法看了）。如果某个角落的一行代码（比如计算工资的逻辑）突然抛出了一个我们没想到的“空指针异常”，而旁边又没有灭火器，会发生什么？

*   火苗会迅速蔓延，直接烧毁整个程序。
*   表现给用户的就是：**程序突然卡死，弹出一个看不懂的英文报错框，然后瞬间“闪退”。**
*   对于开发者来说更惨：程序崩溃了，但没有任何日志留下来，你根本不知道用户刚才干了什么，完全无法修复。

**全局异常处理，就是这栋大楼的“中央火灾报警与自动喷水系统”。**
它是程序的**最后一道防线（兜底机制）**。只要发生任何没被 `try-catch` 拦住的异常，在程序彻底死亡之前，这个全局系统都会被触发。

它虽然不能真正“修复”那个 Bug，但它可以做到两件至关重要的事情：
1.  **记录黑匣子：** 把错误信息、发生时间、代码行数写进日志文件。
2.  **优雅地告别：** 给用户弹出一个温和的提示（“很抱歉，程序遇到未知问题，正在安全退出”），而不是直接闪退。

接下来，我们就来看看在 C# 的不同应用场景下，如何配置这套“中央喷水系统”。

## 控制台应用（Console）：最基础的兜底

对于我们最熟悉的控制台黑框框程序，.NET 提供了一个作用域叫做 `AppDomain`（应用程序域）。你可以把它理解为程序运行的整个“地盘”。

只要在这个地盘上，任何一个线程抛出了没人管的异常，都会触发 `AppDomain.CurrentDomain.UnhandledException` 这个事件。

**代码演示：为控制台配置全局兜底**

```csharp
using System;

public class Program
{
    public static void Main()
    {
        // 1. 在程序启动的第一行，立刻注册全局异常处理事件
        AppDomain.CurrentDomain.UnhandledException += GlobalExceptionHandler;

        Console.WriteLine("程序已启动...");

        // 模拟一个极其隐蔽的、我们忘了写 try-catch 的 Bug
        string name = null;
        Console.WriteLine(name.Length); // 这里会引发 NullReferenceException！

        // 下面这行永远不会执行
        Console.WriteLine("程序正常结束。"); 
    }

    // 2. 这是我们的“中央火灾报警器”
    private static void GlobalExceptionHandler(object sender, UnhandledExceptionEventArgs e)
    {
        // 拿到那个没人管的异常对象
        Exception ex = (Exception)e.ExceptionObject;

        // 记录黑匣子日志（实际开发中会写到 txt 文件里）
        Console.WriteLine("\n==================================");
        Console.WriteLine("【警报】捕获到致命的全局异常！");
        Console.WriteLine($"错误原因：{ex.Message}");
        Console.WriteLine($"案发地点：\n{ex.StackTrace}");
        Console.WriteLine("==================================\n");

        // 告诉用户，并优雅退出
        Console.WriteLine("很抱歉，程序遭遇了无法恢复的错误，按任意键退出...");
        Console.ReadLine();
        
        // 强行终止程序，防止带着错误的状态继续运行造成数据损坏
        Environment.Exit(1); 
    }
}
```

当你运行这段代码，程序不会立刻闪退并报出红色的系统错误，而是会工工整整地打印出我们的“警报”信息，然后等待用户按键退出。这就是全局兜底的魅力。

## 桌面端应用（WinForms & WPF）：保护界面不崩溃

*(小白必看概念：在带有界面的桌面软件中，有一个特殊的概念叫“UI 线程”。你可以把它想象成一个专门负责在屏幕上画图、响应鼠标点击的“画师”。如果画师因为 Bug 崩溃了，整个软件界面就消失了，也就是闪退。)*

### WinForms 的全局处理
在老牌的 WinForms 桌面开发中，除了要像控制台那样防范后台线程的崩溃，还要专门防范 UI 线程（画师）的崩溃。

所以它有专属的报警器 `Application.ThreadException`：

```csharp
static void Main()
{
    // 捕获 UI 线程（画师）发生的意外
    Application.ThreadException += new ThreadExceptionEventHandler(UIThreadException);
    
    // 强制所有 Windows 窗体错误都通过上面的事件来处理
    Application.SetUnhandledExceptionMode(UnhandledExceptionMode.CatchException);

    // 捕获非 UI 线程（后台搬砖的）发生的意外
    AppDomain.CurrentDomain.UnhandledException += new UnhandledExceptionEventHandler(CurrentDomain_UnhandledException);

    Application.Run(new Form1());
}

static void UIThreadException(object sender, ThreadExceptionEventArgs t)
{
    // 弹出一个友好的对话框给用户，而不是直接让界面闪退
    MessageBox.Show("抱歉，您刚才的点击操作引发了一个未知错误，但程序还能继续运行。", "系统提示");
    // 记录日志...
}
```

### WPF 的全局处理
WPF 是比 WinForms 更现代的桌面框架，它有着同样的设计思路，只是名字叫法不同。在 WPF 中，负责界面的系统叫 `Dispatcher`（调度员）。

在 WPF 的 `App.xaml.cs` 文件中，你可以重写这个事件：

```csharp
public partial class App : Application
{
    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);
        // 注册全局异常事件
        this.DispatcherUnhandledException += App_DispatcherUnhandledException;
    }

    private void App_DispatcherUnhandledException(object sender, DispatcherUnhandledExceptionEventArgs e)
    {
        MessageBox.Show($"发生了一个错误：{e.Exception.Message}");
        
        // 【核心魔法】
        // 告诉系统：“这个异常我已经处理过了，请当做没发生过，不要让程序闪退！”
        e.Handled = true; 
    }
}
```
**注意：** 这里的 `e.Handled = true` 是一把双刃剑。虽然它能保住程序不闪退，让用户继续操作，但如果之前的 Bug 破坏了核心数据，继续运行可能会导致更严重的错误。通常只建议对无关紧要的界面层异常使用。

## Web 服务端（ASP.NET Core）：不让整个餐厅因为一个顾客而倒闭

*(小白必看概念：开发网站后端（Web API）就像是开一家餐厅。每一台用户的手机/浏览器发来一个请求，就像是进来一个顾客。服务器并发处理成千上万个请求。)*

想象一下，如果服务员在给 4号桌 顾客端菜时，不小心把盘子打碎了（发生了未处理的异常）。
在没有全局兜底的情况下，这会导致整个餐厅停电、关门倒闭（服务器进程崩溃），1号桌到100号桌的客人全被赶出去！这绝对是灾难。

**ASP.NET Core 的异常处理哲学是：打碎了盘子，我们给 4号桌 顾客道歉（返回 HTTP 500 错误码），然后清扫碎片（记录日志），但餐厅继续正常营业，不受影响。**

### 怎么实现？通过“中间件”（Middleware）

你可以把中间件想象成餐厅大门到厨房之间的一个“安检通道”。所有的请求都要进过这个通道。
ASP.NET Core 内置了一个非常强大的通道，叫 `UseExceptionHandler`（异常处理中间件）。

**它的底层逻辑其实极其简单，就是我们在最外层包了一个巨大的 try-catch：**

```csharp
// 这只是帮助你理解原理的伪代码
public void ExceptionMiddleware(Request 请求)
{
    try
    {
        // 放行，让请求去执行具体的业务逻辑（比如查询数据库、登录等）
        执行业务逻辑(请求);
    }
    catch (Exception ex)
    {
        // 只要里面任何一个角落抛出了未处理的异常，都会被这里接住！
        
        // 1. 写日志，通知开发人员修 Bug
        Log.Error(ex, "请求处理失败！");

        // 2. 将响应状态码改成 500 (服务器内部错误)
        请求.Response.StatusCode = 500;

        // 3. 给浏览器或前端 App 返回一段统一的 JSON 格式道歉信
        // 绝对不能把 ex.StackTrace 返回给前端（防止黑客看到数据库结构）
        请求.Response.WriteJson(new { 
            message = "服务器开小差了，请稍后再试", 
            errorCode = "SYSTEM_ERR" 
        });
    }
}
```

在实际的 ASP.NET Core 代码中，你只需要在程序启动文件（`Program.cs`）里写短短一两行代码，就能开启这个强大的防御：

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// 如果是在生产环境（线上正式服）
if (!app.Environment.IsDevelopment())
{
    // 启用全局异常兜底中间件，如果出错，统一跳转到 /Error 页面，或者返回标准化 JSON
    app.UseExceptionHandler("/Error"); 
}

app.MapGet("/", () => "Hello World!");
app.Run();
```

得益于这种设计，哪怕你写的某个网页有极其严重的 Bug，它最多只让访问那个网页的用户报错，你的网站整体依然稳如泰山。

## 总结：小白必须掌握的“全局视野”

虽然上面列举了三种不同的框架，代码看着眼花缭乱，但作为小白，你只需要记住以下三个核心真理：

1. **不可替代性：** 全局异常处理不是用来替代局部的 `try-catch` 的。它不能帮你重试网络请求，不能帮你重新打开文件。它只是个“收尸人”和“黑匣子记录员”。
2. **万物归一：** 无论什么框架，都有自己拦截全局异常的专门接口或事件。在开始一个新项目时，**第一件事就是去百度“xxx框架 全局异常处理 怎么写”**，并把它配置好。
3. **日志是灵魂：** 在全局异常处理器中，如果不把拿到的错误信息（特别是 `StackTrace` 堆栈轨迹）记录到日志文件（或者数据库）里，那么这个兜底毫无意义，因为你第二天上班依然不知道昨晚程序为什么报错。
