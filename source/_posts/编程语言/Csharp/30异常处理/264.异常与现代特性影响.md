# 现代 C# 特性影响：重塑防御性编程的新武器

随着 C# 语言的不断迭代（尤其是从 C# 8.0 到 C# 12+），这门语言的设计哲学正在发生微妙的转变：从“在运行时安全地处理错误”逐渐向“在编译时提前消灭错误”演进。这些现代语言特性虽然并非专门为异常处理而设计，但它们深刻地改变了我们编写防御性代码的方式，大幅降低了某些特定异常发生的概率，并提升了代码的“异常安全性”（Exception Safety）。

本节将探讨可空引用类型、记录类型以及高级模式匹配是如何影响日常异常处理策略的。

## 可空引用类型（NRT）：告别 NullReferenceException 的梦魇

计算机科学史上著名的“价值十亿美元的错误”——空引用异常（`NullReferenceException`，简称 NRE），是 C# 开发者最常见、也最让人头疼的运行时异常。在 C# 8.0 之前，任何引用类型（如 `string`、`class`）都可以被合法地赋值为 `null`，编译器不会给出任何警告，直到运行时崩溃。

为了防御 NRE，传统的代码中充斥着大量的“防御性异常抛出”：
```csharp
// 传统 C# 时代的常见防御性编程
public void ProcessOrder(Order order)
{
    if (order == null)
    {
        throw new ArgumentNullException(nameof(order));
    }
    if (order.Customer == null)
    {
        throw new ArgumentException("订单的客户信息不能为空");
    }
    // 处理逻辑...
}
```

C# 8.0 引入了**可空引用类型（Nullable Reference Types, NRT）**。开启该特性后，引用类型默认是“不可为空”的。如果你想让一个变量可以为 null，必须显式地加上 `?`（如 `string?`、`Order?`）。

NRT 带来的异常处理范式转变：
当开启 NRT 后，编译器充当了极其严格的代码审查员。它通过静态流分析，强制你在可能出现 null 的地方进行检查，从而将运行时的 `NullReferenceException` 转化为了编译时的警告（或错误）。

```csharp
#nullable enable // 开启 NRT

// 现在的契约非常清晰：order 绝不可能是 null
public void ProcessOrder(Order order) 
{
    // 编译器保证调用方如果传入 null 会得到警告
    // 我们不再需要手动写 if (order == null) throw... 这样的样板代码
    
    // 如果某个属性声明为 string? Description;
    // 编译器会强制你处理 null 情况，否则在调用 order.Description.Length 时报错
    int len = order.Description?.Length ?? 0; 
}
```

配套利器：`ArgumentNullException.ThrowIfNull`（C# 10+）
对于面向公共 API 的类库，即便开启了 NRT，为了防止非 C# 语言或未开启 NRT 的调用方传入 null，我们仍需要在边界处抛出异常。C# 10 引入了极简的抛出语法：

```csharp
public void UpdateUser(User user)
{
    // 一行代码替代原先的 if (null) throw...
    // 内部利用了 CallerArgumentExpression 特性，自动捕获参数名 "user"
    ArgumentNullException.ThrowIfNull(user); 
    
    // 业务逻辑...
}
```

## 记录类型（Record）：不可变性与“强异常安全性”

C# 9.0 引入了 `record` 类型，它天生倾向于**不可变性（Immutability）**。不可变对象一旦被创建，其状态就永远无法被修改。

不可变性与异常安全（Exception Safety）有着密不可分的关系。在传统的面向对象编程中，修改一个复杂对象的状态通常需要多步操作。如果在修改到一半时抛出了异常，对象就会处于一种“半修改”的非法状态（脏状态）。其他代码如果读取到这个“损坏”的对象，就会引发难以追踪的业务异常。

传统的脆弱状态：
```csharp
public class BankAccount
{
    public decimal Balance { get; set; }
    public string Status { get; set; }

    public void ApplyPenalty()
    {
        Balance -= 100; // 步骤1
        // 假设这里抛出了数据库异常或网络异常
        Status = "Penalized"; // 步骤2未执行
        
        // 结果：账户被扣了钱，但状态没更新，数据不一致！
    }
}
```

Record 的强异常安全保证：
强异常安全（Strong Exception Guarantee）是指：如果一个操作失败（抛出异常），程序的状态会回滚到操作开始之前的状态，不会有任何副作用。`record` 结合 `with` 表达式，天然实现了这一境界。

```csharp
public record BankAccount(decimal Balance, string Status);

public class AccountService
{
    public BankAccount ApplyPenalty(BankAccount account)
    {
        // with 表达式会创建一个全新的对象（非破坏性突变）
        // 如果在创建新对象的过程中发生异常，旧的 account 对象依然完好无损
        return account with 
        { 
            Balance = account.Balance - 100,
            Status = "Penalized"
        };
    }
}
```
通过使用 `record`，我们消灭了因为“状态突变中途抛出异常”而引发的数据损坏问题。结合构造函数中的一次性状态校验，对象要么无法被创建（直接抛出异常），要么一旦创建就永远有效。

## 模式匹配：优雅取代类型转换异常与条件分支

从 C# 7 到 C# 11，模式匹配（Pattern Matching）经历了巨大的飞跃。在异常处理领域，模式匹配极大地简化了类型检查、安全转换以及多条件异常捕获的语法。

取代类型转换异常（InvalidCastException）
过去，强制类型转换是非常危险的操作，容易引发 `InvalidCastException`。现代 C# 推荐使用 `is` 模式。

```csharp
// 过去容易抛出异常的做法：
// var dog = (Dog)animal; 
// dog.Bark();

// 现代 C# 的模式匹配：安全、优雅、无异常开销
if (animal is Dog dog)
{
    dog.Bark(); // dog 只有在转换成功时才可用
}
```

Switch 表达式与详尽性检查（Exhaustiveness Checking）
在处理不同类型的错误代码或枚举时，过去我们使用冗长的 `switch-case`，如果忘记处理某个枚举值，程序可能会静默失败或在后续执行中抛出异常。现代的 `switch` 表达式具有编译时的**详尽性检查**功能。

```csharp
public enum OperationStatus { Success, NotFound, Unauthorized, Timeout }

public string GetStatusMessage(OperationStatus status) => status switch
{
    OperationStatus.Success => "操作成功",
    OperationStatus.NotFound => "找不到资源",
    OperationStatus.Unauthorized => "无权访问",
    OperationStatus.Timeout => "请求超时",
    // 如果未来在枚举中增加了一个新值（如 InternalError）
    // 编译器会直接给出警告，提示这里没有处理所有可能的情况！
    // 运行时如果遇到未处理的值，会自动抛出安全的 SwitchExpressionException。
    _ => throw new InvalidOperationException("未知的状态") 
};
```

模式匹配与异常过滤器的结合
在系列前面的 2.3 节我们提到过异常过滤器（`when` 关键字）。模式匹配可以在异常过滤器中发挥强大的威力，允许我们根据异常内部结构的特定模式来决定是否捕获。

```csharp
try
{
    await SendHttpRequestAsync();
}
// 使用属性模式（Property Pattern）直接在 catch 块中解构和匹配异常的状态码
catch (HttpRequestException ex) when (ex is { StatusCode: HttpStatusCode.ServiceUnavailable })
{
    // 仅当异常状态码为 503 时才捕获，进行重试逻辑
    Console.WriteLine("服务不可用，准备重试...");
}
// 其他 HTTP 异常不会被上面捕获，会自动向上层冒泡
```


## 结语：异常处理的至高境界是“没有异常”

至此，《C# 异常处理系列笔记》的架构、实践、性能与陷阱篇已全部完结。

回顾这十几篇笔记，我们从最基础的 `try-catch-finally` 语法起步，深入剖析了 `Exception` 的类层次结构，探讨了如何通过自定义异常和日志框架建立企业级的全局异常处理策略；我们还在微观层面上，见识了异步编程中的异常聚合机制、热点路径下的性能灾难，以及多线程与生命周期中的致命陷阱。

然而，正如本节现代 C# 特性所展示的那样：**最高级的异常处理，往往是通过优秀的架构设计和现代语言特性，让异常从根本上失去发生的土壤。**

借助可空引用类型，我们消灭了空指针；借助记录类型，我们保证了状态的一致性；借助 `TryParse` 和结果模式（Result Pattern），我们保障了极致的性能。异常处理不应该被视为代码失败后的“补救措施”，而应该作为防御性编程（Defensive Programming）和契约式设计（Design by Contract）的核心一环，贯穿于软件生命周期的始终。
