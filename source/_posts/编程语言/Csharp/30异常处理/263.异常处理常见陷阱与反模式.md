# 常见陷阱与反模式：避开那些让系统崩溃的暗礁

在掌握了异常的捕获、抛出以及性能考量之后，我们需要将目光转向实际开发中最容易踩坑的灰色地带。异常处理机制如果被误用，不仅无法保护系统，反而会掩盖真正的 Bug，甚至导致难以排查的内存泄漏和进程崩溃。

本节将盘点 C# 异常处理中最常见的反模式（Anti-patterns），并深入探讨对象生命周期与多线程环境下的异常陷阱。

## 吞噬异常：空的 catch 块与沉默的杀手

这是初级开发者最常犯，也是对系统危害最大的错误。所谓“吞噬异常”（Swallowing Exceptions），是指捕获了异常但没有进行任何实质性处理（甚至连日志都没有记录），直接让程序“默默”继续执行。

反模式示例：
```csharp
public void SaveUserData(User user)
{
    try
    {
        // 将用户数据写入本地文件
        string json = JsonSerializer.Serialize(user);
        File.WriteAllText("user_data.json", json);
    }
    catch (Exception)
    {
        // 留空：假装什么都没发生
        // 或者仅仅写了一句无用的注释：// TODO: 处理异常
    }
}
```

危害：
如果磁盘空间满了或者没有文件写入权限，`File.WriteAllText` 会抛出异常。由于异常被吞噬，调用方会误以为数据已经成功保存。这种状态不一致会导致后续的业务逻辑全盘崩溃，且由于没有日志，排查此类 Bug 犹如大海捞针。

修正方案：
永远不要写空的 catch 块。至少应该记录日志。如果当前层级不知道如何处理该异常（例如不知道是否应该重试或中止），则根本不应该捕获它，或者在捕获记录日志后使用 `throw;` 原样重新抛出。

## 异常滥用：用异常控制业务流程

上一节我们讨论了由于性能原因不应在热点路径用异常做控制流，而从架构设计和代码可读性的角度来看，用异常控制常规业务逻辑同样是一种典型的反模式。

反模式示例：
```csharp
public void ProcessUserLogin(string username, string password)
{
    try
    {
        User user = Authenticate(username, password);
        // 正常登录逻辑...
    }
    catch (UserNotFoundException)
    {
        // 流程控制：跳转到注册页面
        RedirectToRegisterPage();
    }
    catch (WrongPasswordException)
    {
        // 流程控制：提示密码错误
        ShowErrorMessage("密码错误");
    }
}
```

危害：
异常应该代表“异常情况”（Exceptional conditions），即破坏了方法契约的情况。用户输入错误密码是常规业务逻辑中可预期的分支，不属于系统故障。使用 try-catch 来替代 if-else，会打破“最少惊讶原则”（Principle of Least Astonishment），让代码的执行流变得像意大利面条一样难以追踪。

修正方案：
返回枚举（Enum）、布尔值或结果对象（Result Pattern）。
```csharp
LoginResult result = Authenticate(username, password);
if (result.Status == LoginStatus.UserNotFound)
{
    RedirectToRegisterPage();
}
// 其他分支处理...
```

## 构造函数中的异常：部分构造的幽灵对象

当在类的构造函数中抛出异常时，会发生什么？这是一个经典的面试题，也是一个危险的陷阱。

如果在构造函数执行中途抛出异常，对象实例化失败，返回值将是 `null`。CLR 的垃圾回收器（GC）最终会回收已经为该对象分配的托管内存，这部分没有问题。但问题在于非托管资源。

陷阱示例：
```csharp
public class NetworkProcessor
{
    private FileStream _logFile;
    private Socket _socket;

    public NetworkProcessor(string logFilePath, string ipAddress)
    {
        // 1. 成功打开文件句柄（非托管资源）
        _logFile = new FileStream(logFilePath, FileMode.OpenOrCreate);
        
        // 2. 假设这里抛出了 UriFormatException 或 SocketException
        _socket = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
        _socket.Connect(ipAddress, 80); 
    }
}
```

危害：
当 `_socket.Connect` 抛出异常时，构造函数被中止。因为对象尚未构造完成，调用方无法拿到该对象的引用，因此也绝对无法调用该对象的 `Dispose` 方法。结果是：第一步打开的 `_logFile` 文件句柄被永远泄漏了，直到整个进程结束。

防护策略：
尽量保持构造函数的简单，避免在其中执行 I/O 操作或容易失败的复杂逻辑。如果不可避免，必须在构造函数内部使用 try-catch，在 catch 块中清理已分配的资源，然后再将异常重新抛出。

## 析构函数中的异常：进程的直接终结者

析构函数（在 C# 中通常称为 Finalizer，语法为 `~ClassName()`）由垃圾回收器（GC）在一个特殊的后台终结器线程上调用。

致命陷阱：
自 .NET Framework 2.0 以来（包括现代的 .NET Core 和 .NET 5+），如果析构函数中抛出未捕获的异常，CLR 的默认行为是：直接终止整个应用程序进程。

```csharp
public class UnsafeResourceCleaner
{
    ~UnsafeResourceCleaner()
    {
        // 如果这里由于文件被占用抛出 IOException
        // 整个应用程序（不论是网站还是桌面端）将瞬间崩溃，且很难捕获和记录
        File.Delete("temp.dat"); 
    }
}
```

绝对规则：
永远不要让任何异常逃逸出析构函数。如果必须在析构函数中执行可能失败的代码，必须将其包裹在万能的 try-catch 块中，并吞噬异常（这是极少数允许使用空 catch 块或仅记录日志的场景，因为在终结器线程上抛出异常没有任何意义，且极其危险）。

## 静态构造函数异常：被永久封印的类型

静态构造函数（`static ClassName()`）在类型第一次被访问前由 CLR 自动调用。它的隐蔽性在于：开发者无法明确控制它的调用时机。

陷阱示例：
```csharp
public class GlobalConfig
{
    public static string ConnectionString;

    static GlobalConfig()
    {
        // 如果配置文件不存在，这里将抛出 FileNotFoundException
        ConnectionString = File.ReadAllText("config.txt");
    }
}
```

危害：
如果静态构造函数内部抛出异常，CLR 会将其包装在一个 `TypeInitializationException` 中。更糟糕的是，在这个应用程序域（AppDomain）或进程的整个生命周期内，这个类型将被标记为不可用。之后代码中任何试图访问 `GlobalConfig` 的地方，哪怕没有触发原来的逻辑，都会直接抛出 `TypeInitializationException`。

最佳实践：
静态构造函数必须是绝对安全的（Exception-safe）。不要在里面读取文件、访问数据库或进行网络请求。复杂的初始化应该使用 `Lazy<T>` 延迟加载，以便在失败时能够处理并在下次重试。

## 线程间异常传递：跨越边界的静默崩溃

在现代并发编程中，异常的作用域是绑定在特定线程（或执行上下文）上的。在后台线程抛出的异常，不会神奇地自动跑到主线程的 try-catch 块中。

老式并发的陷阱：
```csharp
public void StartBackgroundWork()
{
    try
    {
        // 开启一个后台线程
        ThreadPool.QueueUserWorkItem(_ => 
        {
            throw new InvalidOperationException("后台任务爆炸了！");
        });
    }
    catch (Exception ex)
    {
        // 这里的代码【永远不会】执行。
        // 主线程根本捕获不到后台线程的异常。
        Console.WriteLine(ex.Message); 
    }
}
```

后果：
在 Thread 或 ThreadPool 线程中发生的未处理异常，会直接触发 `AppDomain.UnhandledException`，进而导致整个应用程序崩溃退出。

现代解决方案：
始终使用基于任务的异步模式（TAP），即 `Task` 和 `Task<T>`。`Task` 对象会在内部捕获工作线程中抛出的所有异常，将其存储起来，直到你调用 `await`、`Task.Wait()` 或读取 `Task.Result` 时，才将异常抛给调用方线程。这也是为什么系列前面的笔记中强调：绝对要避免使用 `async void`，因为 `async void` 方法内的异常无法被 `Task` 包装，会直接导致进程崩溃。

总结：
精通 C# 的异常处理，很大程度上取决于你能否避开这些常见的反模式。不要用异常控制流程，警惕构造函数与静态构造函数的失败场景，严守析构函数的异常边界，并深刻理解多线程环境下的异常传播机制。绕过这些陷阱，你的代码将变得坚不可摧。
