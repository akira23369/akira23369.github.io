# 自定义异常的设计与最佳实践

## 引言

.NET 框架内置了上百种异常类型，从常见的 `NullReferenceException` 到与底层相关的 `SqlException`，可以说应有尽有。但在复杂的企业级应用中，框架提供的通用异常往往无法精准表达具体的“业务痛点”。

比如，在一个银行系统中，当用户试图取出超过其账户余额的钱时，我们抛出内置的 `InvalidOperationException`（无效操作异常）合适吗？从技术上讲，这确实是个无效操作；但从业务层面上看，它太宽泛了，调用者无法仅通过异常类型就判断出这是“余额不足”，从而在前端弹出一个“去充值”的提示。

这时候，我们就需要量身定制自己的异常——自定义异常（Custom Exceptions）。

---

## 设计原则：何时需要自定义异常

在动手写代码之前，我们要明确一个克制原则：**不要为了自定义而自定义。** 

如果你仅仅是想给调用者传递一条错误信息，直接抛出内置异常并附带清晰的 `Message` 即可（例如 `throw new ArgumentException("用户名不能为空")`）。

只有当满足以下**至少一个条件**时，才应该考虑创建自定义异常：

1. **调用者需要针对特定业务错误执行不同的 catch 逻辑：**
   就像引言中的例子，如果系统抛出专属的 `InsufficientFundsException`（余额不足异常），调用者就可以精确地 `catch (InsufficientFundsException)`，然后引导用户去充值页面，而不是统一显示模糊的“系统内部错误”。
2. **需要携带额外的业务数据：**
   系统内置异常只能携带字符串消息（Message）。如果你需要随异常传递一个特定的业务实体（比如交易流水号、当前实际余额、失败的商品ID列表），你就需要自定义异常来承载这些属性。
3. **为了统一领域模型的语义：**
   在领域驱动设计（DDD）中，将业务逻辑中的错误抽象为领域特定的异常，可以使代码的业务表达力大大增强。

---

## 最佳实践：继承哪个基类？如何命名？

### 命名规范
自定义异常的类名必须严格遵循一个铁律：**以 `Exception` 作为后缀。**
例如：`UserNotFoundException`、`InventoryShortageException`。这能让其他开发者在阅读代码时，一眼认出这是一个异常类。

### 继承的选择
正如在第二篇笔记中提到的，早期的 .NET 文档曾建议业务异常继承自 `System.ApplicationException`。但这已被证明是一个失败的设计，微软官方已明确废弃了这一指导原则。

**现代 C# 开发的唯一标准：**
自定义异常应直接继承自 `System.Exception`。（如果你是在开发特定的类库，且有更基础的基类，比如所有的 I/O 错误继承自 `IOException`，你也可以继承相应的特定内置类）。

## 必备元素：标准的构造函数与自定义属性

一个合格的自定义异常，绝不仅仅是改个名字那么简单。微软官方对自定义异常有一套标准的实现模式，通常要求提供三个核心构造函数，以保证它与 .NET 基础设施的完美兼容。

下面，我们以“余额不足异常”为例，演示一个标准的自定义异常类的完整写法。

### 核心代码演示

```csharp
using System;

// 1. 明确命名，继承自 Exception
public class InsufficientFundsException : Exception
{
    // 自定义业务属性：发生异常时的核心数据
    public decimal CurrentBalance { get; }
    public decimal AttemptedWithdrawal { get; }
    public string TransactionId { get; }

    // 2. 无参构造函数（必备）
    // 提供一个合理的默认 Message
    public InsufficientFundsException() 
        : base("账户余额不足，无法完成交易。") 
    { 
    }

    // 3. 接收 Message 的构造函数（必备）
    // 允许调用者传入更详细的提示语
    public InsufficientFundsException(string message) 
        : base(message) 
    { 
    }

    // 4. 接收 Message 和内部异常 InnerException 的构造函数（必备）
    // 用于异常包装机制
    public InsufficientFundsException(string message, Exception innerException) 
        : base(message, innerException) 
    { 
    }

    // 5. 带有完整业务属性的自定义构造函数（推荐）
    // 这是我们在业务代码中最常调用的构造函数
    public InsufficientFundsException(
        decimal currentBalance, 
        decimal attemptedWithdrawal, 
        string transactionId) 
        : base($"交易失败 [单号:{transactionId}]：试图提取 {attemptedWithdrawal}，但当前余额仅为 {currentBalance}。")
    {
        CurrentBalance = currentBalance;
        AttemptedWithdrawal = attemptedWithdrawal;
        TransactionId = transactionId;
    }
}
```

### 业务场景中的使用

有了这个异常，我们的转账逻辑不仅能防错，还能传递丰富的数据：

```csharp
public void Withdraw(string accountId, decimal amount)
{
    decimal currentBalance = GetBalance(accountId);
    if (currentBalance < amount)
    {
        string transId = Guid.NewGuid().ToString();
        // 抛出携带业务数据的专属异常
        throw new InsufficientFundsException(currentBalance, amount, transId);
    }
    
    // 执行扣款逻辑...
}
```

而在外层捕获时：

```csharp
try
{
    accountService.Withdraw("ACC-123", 5000m);
}
catch (InsufficientFundsException ex)
{
    // 调用者可以精确拿到差额并进行处理
    decimal shortage = ex.AttemptedWithdrawal - ex.CurrentBalance;
    Console.WriteLine($"交易拦截：您还差 {shortage} 元。流水号：{ex.TransactionId}");
}
```

## 序列化支持：`[Serializable]` 属性的历史与现状

在查阅许多老旧的 C# 教程时，你会发现标准的自定义异常除了上面提到的几个构造函数，还会要求加上 `[Serializable]` 特性，并提供一个专用于反序列化的 `protected` 构造函数。

```csharp
using System.Runtime.Serialization;

[Serializable] // 标记为可序列化
public class InsufficientFundsException : Exception
{
    // ... 前面的常规构造函数 ...

    // 反序列化构造函数
    protected InsufficientFundsException(SerializationInfo info, StreamingContext context) 
        : base(info, context) 
    {
        // 如果有自定义属性，需要在这里手动反序列化
        CurrentBalance = info.GetDecimal(nameof(CurrentBalance));
        AttemptedWithdrawal = info.GetDecimal(nameof(AttemptedWithdrawal));
        TransactionId = info.GetString(nameof(TransactionId));
    }

    // 重写 GetObjectData 以支持序列化自定义属性
    public override void GetObjectData(SerializationInfo info, StreamingContext context)
    {
        base.GetObjectData(info, context);
        info.AddValue(nameof(CurrentBalance), CurrentBalance);
        info.AddValue(nameof(AttemptedWithdrawal), AttemptedWithdrawal);
        info.AddValue(nameof(TransactionId), TransactionId);
    }
}
```

### 为什么过去需要它？
在传统的 .NET Framework 时代，存在应用程序域（AppDomain）的概念，以及 Remoting 等跨进程通信技术。当一个异常在一个域抛出，需要传递到另一个域被捕获时，它必须跨越系统边界，这就要求异常对象必须支持底层的**二进制序列化**。

### 现在的必要性（.NET Core / .NET 5+ 时代）
随着跨平台 .NET 的普及，微软出于安全原因（反序列化漏洞），已经**默认禁用甚至逐步废弃了二进制序列化（BinaryFormatter）**。在现代的微服务、Web API 架构中，异常通常会被全局中间件捕获，然后转化为 JSON 格式返回给客户端，不再依赖底层的二进制序列化机制。

**结论建议：**
如果你是在维护老旧的 .NET Framework 项目，或者你的库需要被各种老系统引用，请严格加上上述序列化代码。
如果你是在开发全新的基于 .NET 6/7/8+ 的现代 Web/云原生项目，**可以安全地忽略序列化构造函数和 `[Serializable]` 标签**，这能让你的代码更清爽。

## 特殊场景：业务异常 vs 技术异常的架构设计

在设计企业级系统的全局异常处理方案时，将异常区分为**业务异常（Business / Domain Exception）** 和**技术异常（Technical Exception）** 是极其重要的架构思想。

### 业务异常
* **定义：** 由用户输入不当或业务规则冲突引起的可预期错误。比如：密码错误、商品下架、账户被冻结。
* **特点：** 这**不是代码 Bug**。系统运行正常，只是用户的请求不符合规则。
* **处理策略：** 通常不需要记录为 Error 级别的系统日志（最多记为 Info 或 Warning 以供统计）；在 Web API 中，应捕获并转化为 `HTTP 400 (Bad Request)` 或 `422 (Unprocessable Entity)`，将具体的异常 Message 直接返回给前端展示给用户。

### 技术异常
* **定义：** 由环境、网络、基础设施或代码 Bug 导致的非预期错误。比如：数据库连接断开、空引用、内存溢出。
* **特点：** 真正的**系统故障**，需要开发人员介入排查。
* **处理策略：** 必须记录为 Error 级别的日志，并附带完整的堆栈跟踪（StackTrace），同时可能触发警报邮件。在 Web API 中，返回 `HTTP 500 (Internal Server Error)`，且**绝对不能把底层错误信息（如 SQL 报错）返回给前端**，只返回一句泛泛的“系统繁忙”。

### 最佳实践：定义一个公共的基类

为了在全局捕获时轻松区分它们，通常我们会在项目中定义一个基类：

```csharp
// 所有的业务异常都继承自这个类
public abstract class BusinessException : Exception
{
    public int ErrorCode { get; }

    protected BusinessException(int errorCode, string message) 
        : base(message)
    {
        ErrorCode = errorCode;
    }
}

// 具体的业务异常
public class UserFrozenException : BusinessException
{
    public UserFrozenException() 
        : base(4001, "您的账户已被冻结，无法操作。") { }
}
```

在 ASP.NET Core 的全局异常过滤器中：

```csharp
public void OnException(ExceptionContext context)
{
    if (context.Exception is BusinessException bizEx)
    {
        // 这是业务错误，属于用户操作不当
        Log.Information($"业务拦截: {bizEx.Message}");
        context.Result = new BadRequestObjectResult(new { code = bizEx.ErrorCode, msg = bizEx.Message });
    }
    else
    {
        // 这是技术 Bug，拉响警报！
        Log.Error(context.Exception, "发生严重的系统级异常！");
        context.Result = new StatusCodeResult(500); // 对前端隐藏细节
    }
    context.ExceptionHandled = true;
}
```

---
**本篇总结：**
自定义异常不仅能让代码更具表达力，还能成为传递业务数据的绝佳载体。记住核心准则：继承 `Exception` 类、提供标准的构造函数组合，并在宏观架构上区分好业务异常与技术异常，你的代码质量将会有质的飞跃。
