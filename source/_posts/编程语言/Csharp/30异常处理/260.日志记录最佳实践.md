# 让排错犹如神助——日志记录最佳实践

## 引言

很多新手程序员在写 catch 块时，通常会这么写：

反面教材
```csharp
catch (Exception ex)
{
    Console.WriteLine("发生错误：" + ex.Message);
    // 或者写入文本：File.AppendText("error.log", ex.Message);
}
```

等系统真到了生产环境，出了问题，打开 error.log 一看，满屏全是“未将对象引用设置到对象的实例”、“索引超出了数组界限”。
这时候你会陷入深深的绝望：是谁引发的？在哪个方法里发生的？当时传进来的参数是什么？完全不知道。

高质量的日志不仅要记录“出错了”，还要像一份专业的尸检报告，详细记录当时的时间、地点、人物和死因。

---

## 记录什么：不要放过任何上下文线索

当捕获到一个系统级技术异常时，一条合格的日志必须包含以下三大维度：

### 异常的完整堆栈
永远不要只记录 `ex.Message`！`ex.Message` 通常只是一句干巴巴的废话。
你必须记录整个 `Exception` 对象本身，大多数现代日志框架（如 Microsoft.Extensions.Logging）都提供了专门的重载方法来接收 Exception 对象，这会自动记录包含行号的 `StackTrace`（调用堆栈）和嵌套的 `InnerException`。

### 触发时的上下文信息
代码是静态的，而系统的运行状态是动态的。同样的空指针异常，如果是普通用户触发的，可能只是个小 Bug；如果是超级管理员触发的，可能导致整个系统瘫痪。
必须记录：
*   **操作人：** UserId、TenantId（租户ID）、请求的 IP 地址。
*   **操作源：** 是来自于 HTTP API 请求、消息队列消费，还是后台定时任务？
*   **关联 ID（CorrelationId）：** 在微服务架构中，一个请求会穿梭于多个服务，必须有一个贯穿始终的唯一流水号，否则日志就像一盘散沙，根本串不起来。

### 关键参数
这是排错时最值钱的数据！很多 Bug 是由于特定格式的数据引发的。如果不记录当时的输入参数，你即使看到了堆栈，也无法在本地机器上重现这个 Bug。

最佳实践：完整的日志记录示例
```csharp
public void ProcessOrder(int orderId, string userEmail)
{
    try
    {
        // 复杂的扣款与发货逻辑
        ExecutePayment(orderId); 
    }
    catch (Exception ex)
    {
        // 好的日志记录应该包含：动作、参数、异常对象
        _logger.LogError(ex, 
            "处理订单时发生严重的未知异常。OrderId: {OrderId}, UserEmail: {UserEmail}, 发生时间: {Time}", 
            orderId, userEmail, DateTime.UtcNow);
            
        throw; // 记录完后继续抛出（或进行全局兜底处理）
    }
}
```

## 敏感数据处理：绝不踩踏的安全红线

既然记录参数那么重要，那我把用户传进来的整个 JSON 对象全存进日志里行不行？
**绝对不行！**

在当今的数据合规要求（如欧洲的 GDPR、国内的个人信息保护法）下，日志文件通常会汇聚到中央日志服务器（如 Elasticsearch、阿里云 SLS）。开发人员、运维人员甚至数据分析师都能看到这些日志。

一旦你在日志中记录了 **PII（Personally Identifiable Information，个人可识别信息）**，这就构成了严重的数据泄露。

### 必须坚决拦截（不记录或脱敏）的数据：
*   用户密码、Token、动态验证码。
*   完整的身份证号、护照号。
*   完整的银行卡号、CVV 码。
*   用户的真实姓名结合具体住址。

### 最佳实践：数据脱敏
在记录日志前，编写或使用现成的脱敏工具类，对敏感字段进行打码处理。

代码演示：简单的日志脱敏辅助类
```csharp
public static class LogMasker
{
    // 遮蔽邮箱：abcde@gmail.com -> a***e@gmail.com
    public static string MaskEmail(string email)
    {
        if (string.IsNullOrEmpty(email) || !email.Contains("@")) return email;
        var parts = email.Split('@');
        var name = parts[0];
        if (name.Length <= 2) return "***@" + parts[1];
        return $"{name[0]}***{name[name.Length - 1]}@{parts[1]}";
    }

    // 遮蔽银行卡：只保留后四位
    public static string MaskCreditCard(string cardNo)
    {
        if (string.IsNullOrEmpty(cardNo) || cardNo.Length < 4) return "***";
        return new string('*', cardNo.Length - 4) + cardNo.Substring(cardNo.Length - 4);
    }
}

// 在业务代码中记录：
_logger.LogError(ex, "用户支付失败。Account: {Account}", LogMasker.MaskCreditCard(user.CreditCardNumber));
```

## 日志级别映射：不要乱喊“狼来了”

所有的日志系统都提供级别分类（如 Trace, Debug, Info, Warn, Error, Fatal）。
在异常处理中，如何将不同的异常映射到不同的级别，决定了你们公司的报警邮件是否会变成垃圾邮件。

如果把所有的 catch 全记为 Error，运维人员一天收到一万封报警邮件，最后的结果就是大家都会无视报警。

### 级别的正确映射策略：

*   **Warning（警告）：需要引起关注，但系统自愈了或主流程未受损。**
    比如：调用第三方发短信接口失败（抛出 `TimeoutException`），但代码中配置了重试机制，第二次重试成功了。第一次的异常应该记为 Warning，而不是 Error。
    再比如：捕获到了由用户恶意输入导致的解析异常，拒绝了请求，系统本身安然无恙。

*   **Error（错误）：单一请求或单一操作彻底失败。**
    比如：用户 A 查询他自己的订单详情时，数据库抛出了一个 `SqlException`（死锁）。这个操作失败了，应该给前端返回 500。但这只影响了用户 A，其他用户不受影响，系统还在正常运行。这属于 Error。

*   **Fatal / Critical（致命）：半夜必须叫醒程序员起床修 Bug。**
    比如：程序启动时连不上 Redis 缓存集群；或者系统核心的磁盘写满了抛出 `IOException`。这种异常一旦发生，意味着整个服务处于瘫痪状态，所有进来的请求都会死掉。面对这种异常，不但要记录 Fatal 日志，还应当立即触发电话或短信报警。

## 结构化日志：现代日志框架的降维打击

这是本篇笔记最核心、也是现代 C# 开发中最重要的日志观念转变。

### 传统日志的痛点：字符串拼接
在过去（比如使用早期的 log4net 时），我们往往将变量拼接到字符串里再记录。

传统文本日志
```csharp
// 伪代码
string logMsg = string.Format("用户 {0} 在 {1} 购买了商品 {2} 失败", userId, DateTime.Now, productId);
File.AppendAllText("log.txt", logMsg);
```
写出来的日志长这样：
`[Error] 2023-10-01 10:00:00 用户 10086 在 2023-10-01 购买了商品 999 失败`

**致命问题：无法搜索与统计！**
假设双十一大促，由于 Bug 产生了 50 万条这样的报错日志。老板问你：“帮我查一下商品ID是 999 的受影响用户名单，并且统计一下失败率。”
面对 50 万行纯文本，你只能写极其复杂的正则表达式去提取字符串里的数字，效率极低且容易出错。

### 结构化日志的概念
结构化日志的核心理念是：**不要把日志当成一段长文本，而是把日志当成一条包含多个独立属性的“数据记录”（通常表现为 JSON 格式）。**

在现代 C# 中，**Serilog** 是公认的最强大的结构化日志框架（甚至微软官方的 ILogger 也全面吸纳了结构化日志的语法）。

### Serilog 的消息模板语法

看看使用结构化日志是如何记录上面那段错误的：

结构化日志最佳实践
```csharp
// 注意：不要使用字符串插值 ($"") 拼接变量！
// 要使用日志框架自带的模板占位符，保持大括号内的参数名
_logger.LogError(ex, "用户 {UserId} 购买了商品 {ProductId} 失败", userId, productId);
```

当这行代码执行时，日志框架（如 Serilog）在底层不仅会生成给人看的纯文本字符串，更重要的是，它会提取出 `{UserId}` 和 `{ProductId}` 作为独立的字段，输出成一条 JSON 数据推送到日志中心（如 Elasticsearch）：

底层实际存储格式演示
```json
{
  "Timestamp": "2023-10-01T10:00:00.123Z",
  "Level": "Error",
  "MessageTemplate": "用户 {UserId} 购买了商品 {ProductId} 失败",
  "RenderedMessage": "用户 10086 购买了商品 999 失败",
  "Properties": {
    "UserId": 10086,
    "ProductId": 999
  },
  "Exception": "System.Data.SqlException: Timeout expired..."
}
```

**降维打击的优势：**
现在，当你想排查商品 999 的问题时，你不需要写正则了。你只需要在日志查询系统（如 Kibana 或阿里云控制台）中，直接输入查询语句：
`Properties.ProductId = 999 AND Level = "Error"`
系统瞬间就能为你过滤出所有相关记录，甚至能直接根据 `UserId` 画出柱状图进行统计分析。

### 进阶技巧：使用 @ 符号序列化整个对象
如果你想在日志中记录一整个复杂的请求对象（如一个包含多个属性的订单实体），在传统的日志中，你必须重写该对象的 `ToString()` 方法。
在 Serilog 中，你只需要在变量名前面加上一个 `@` 符号，框架会自动将这个对象深度序列化为 JSON 存入日志中：

```csharp
var orderRequest = new { Item = "Laptop", Price = 5000, Count = 1 };

// 加了 @ 符号，orderRequest 整个对象的结构都会被原样保存到日志系统中
_logger.LogInformation("收到新订单请求：{@OrderRequest}", orderRequest);
```

## 结语

写日志和捕获异常一样，是一门克制的艺术。
*   记少了，出问题时你犹如盲人摸象。
*   记多了（甚至记录了敏感密码），你可能面临法律风险或导致磁盘撑爆。
*   只有按照不同的级别、剥离敏感信息，全面拥抱 **“结构化日志”** 的写法，你捕获到的每一个异常才能转化为最锋利的排错利器。
