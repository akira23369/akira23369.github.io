# throw 的深层用法与堆栈追踪的秘密

## 引言
在编程世界中，抛出异常并不是一件坏事。合理地抛出异常，不仅能及时阻断错误的状态继续蔓延，还能给调用者提供极其重要的调试线索。

然而，哪怕是工作了几年的 C# 程序员，在面临“如何正确抛出异常”时，也常会写出掩盖案发现场的毒瘤代码。今天，我们就来彻底搞懂 `throw` 的正确姿势。

---

## 重新抛出异常：`throw;` vs `throw ex;` 的致命差异

这是 C# 异常处理中最经典、也是在面试中最常被问到的问题。

假设我们在 `catch` 块中捕获了一个异常，记录了日志，但发现当前层级无法真正解决这个问题，需要把它继续往上抛，交给调用者处理。此时，你有两种写法，但它们在底层的行为天差地别。

### `throw ex;`：毁尸灭迹的“假案发现场”
当你使用 `throw ex;` 时，.NET 运行时（CLR）会认为你在这里**重新发起了一个全新的异常**。
这带来的致命后果是：**原始异常的堆栈追踪（StackTrace）被清空了，新的堆栈追踪从当前这一行代码重新开始记录。**

**代码演示：**
```csharp
using System;

public class Program
{
    public static void Main()
    {
        try
        {
            MethodA();
        }
        catch (Exception ex)
        {
            Console.WriteLine("最终捕获到的异常堆栈：");
            Console.WriteLine(ex.StackTrace);
        }
    }

    public static void MethodA()
    {
        try
        {
            MethodB(); // 调用底层方法
        }
        catch (Exception ex)
        {
            // 记录日志...
            throw ex; // 【错误示范】使用 throw ex; 重新抛出
        }
    }

    public static void MethodB()
    {
        // 这里是真正的案发现场：引发了空引用异常
        string text = null;
        int length = text.Length; 
    }
}
```

**输出的堆栈信息（大致如下）：**
```text
在 Program.MethodA() 位置 ...
在 Program.Main() 位置 ...
```
**分析：** 你会发现，堆栈信息里根本没有提到 `MethodB`！对于排查问题的程序员来说，他只能看到错误是从 `MethodA` 抛出的，却永远找不到真正引发空指针的 `MethodB`。这就好比探员到了现场，发现指纹和脚印已经被全扫干净了，根本无从查起。

### `throw;`：原汁原味的“保留现场”
如果你使用 `throw;`（后面什么都不加），CLR 会明白你的意图：**你只是在传递这个异常，而不是制造新异常。** 它会完美保留异常最初发生时的完整堆栈轨迹。

**正确做法：**
```csharp
    public static void MethodA()
    {
        try
        {
            MethodB();
        }
        catch (Exception ex)
        {
            // 记录日志...
            throw; // 【正确示范】直接写 throw;
        }
    }
```

**修改后的堆栈信息：**
```text
在 Program.MethodB() 位置 ...  <-- 真正的案发地点保留下来了！
在 Program.MethodA() 位置 ...
在 Program.Main() 位置 ...
```

**【铁律】：如果在 catch 块中需要将当前捕获的异常原封不动地抛出，永远、永远、永远只写 `throw;`。**

## 抛出新的异常与包装异常（InnerException）

有时候，原封不动地抛出异常（`throw;`）并不是最佳选择。

### 何时需要抛出新异常？
在分层架构（如三层架构、洋葱架构）中，上层通常不应该关心下层的具体技术细节。

假设在 UI 层调用了 `UserService.Login()` 方法，底层因为网络抖动引发了一个 `SqlException`（数据库连接异常）。如果 UI 层直接捕获到 `SqlException`，它会很懵，因为它根本不知道什么是 SQL。
UI 层只关心一件事：**用户登录失败了**。

此时，在服务层（Service层），我们应该捕获底层的技术异常，将其**转化为具有业务含义的新异常**再抛出。

### InnerException 的正确使用方式
在抛出新异常时，为了既让上层看懂业务含义，又不丢失底层的技术排查线索，我们必须使用异常的包装机制——即 `InnerException`。

所有的 `Exception` 类都提供了一个带两个参数的构造函数：
`public Exception(string message, Exception innerException)`

**实战演示：异常包装**
```csharp
public class UserService
{
    public void Login(string username, string password)
    {
        try
        {
            // 模拟底层数据库调用
            ConnectToDatabase();
        }
        catch (SqlException ex) 
        {
            // 捕获到底层异常。
            // 此时我们不仅要抛出一个具有业务意义的异常，还要把元凶 ex 包装进去
            throw new ApplicationException("用户登录服务暂时不可用，请稍后再试。", ex);
        }
    }

    private void ConnectToDatabase()
    {
        // 模拟一个数据库超时异常
        throw new SqlException("Network timeout error code -2"); 
    }
}
```

在最外层（如全局异常处理中间件）捕获时，开发人员可以通过一层层剥开 `InnerException` 属性，最终找到引发系统瘫痪的罪魁祸首 `SqlException`，而前端用户只能看到我们包装在最外层的友好提示 `"用户登录服务暂时不可用"`。各取所需，堪称完美。

## C# 7+ throw 表达式

在 C# 7.0 之前，`throw` 是一个**语句（Statement）**。这意味着它必须单独占据一行代码，不能与其他代码混写。这在做参数校验时，经常会导致代码极其冗长。

从 C# 7.0 开始，微软将 `throw` 升级为了一种**表达式（Expression）**。这意味着你可以把它嵌在其他表达式的执行语句中。这使得代码的紧凑度和可读性有了质的飞跃。

### 结合 null 合并运算符 (`??`)
这是最爽的一个特性，专门用来消灭参数判空的 `if` 语句。

**传统写法（C# 7.0 之前）：**
```csharp
public class Person
{
    private string _name;

    public Person(string name)
    {
        if (name == null)
        {
            throw new ArgumentNullException(nameof(name));
        }
        _name = name;
    }
}
```

**使用 throw 表达式（C# 7.0+）：**
```csharp
public class Person
{
    private string _name;

    public Person(string name)
    {
        // 语义：把 name 赋值给 _name，如果 name 是 null，直接抛出异常
        _name = name ?? throw new ArgumentNullException(nameof(name));
    }
}
```
仅仅一行代码，兼顾了赋值和校验，极其优雅。

### 结合条件运算符 (`?:`)
在三元表达式中，你也可以直接让某个不合法的基础分支抛出异常。

```csharp
public string GetAccessLevel(int roleId)
{
    // 如果角色 ID 大于 0，返回级别；否则直接抛出参数异常
    return roleId > 0 
        ? "Admin" 
        : throw new ArgumentException("角色ID必须大于0", nameof(roleId));
}
```

### 结合表达式主体成员 (`=>`)
对于一些简单的只读属性或单行方法，如果它注定是不支持或未实现的，可以直接用 `=> throw`。

```csharp
public class ReadOnlyConfig
{
    public string ConnectionString { get; } = "Server=myServer...";

    // 任何人试图修改配置，直接抛出不支持异常
    public void UpdateConfig(string newConfig) => throw new NotSupportedException("配置是只读的，不允许修改！");
}
```

---
**本篇总结：**
掌握 `throw` 的深层用法是迈向高级 C# 开发者的必经之路。
1. **重抛异常只用 `throw;`**，保住你的堆栈追踪。
2. **跨层传递异常时，善用 `InnerException`**，既兼顾业务语义，又不丢底层线索。
3. **拥抱 `throw` 表达式**，让你的防御性编程代码变得像诗一样简练。
