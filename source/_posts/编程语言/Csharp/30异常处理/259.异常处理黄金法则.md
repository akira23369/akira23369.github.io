# 异常处理黄金法则与架构哲学

## 何时抛出异常：前置条件与契约式设计

很多新手在写方法时，喜欢抱着一种“得过且过”的心态：只要系统没报错，我就接着往下运行。这往往会导致一个极其隐蔽的 Bug 在代码执行到最深处时才爆发（比如臭名昭著的空引用异常 `NullReferenceException`）。

### 防御性编程与“快速失败（Fail-Fast）”
**黄金法则第一条：在方法的最开头进行拦截，一旦发现输入不合法，立刻抛出异常，绝不让错误的状态进入核心逻辑。**

这在软件工程中被称为**契约式设计（Design by Contract）**。你可以把一个方法看作是与调用者签订的一份“契约”：
*   **前置条件：** 调用者必须保证传给我的参数是有意义的（不能是 null，不能是负数）。
*   **后置条件：** 只要前置条件满足，我保证给你返回正确的结果。

如果调用者违约（传了非法的参数），方法有权利、也必须立刻“撕毁契约”（抛出异常）。

**反面教材：缓慢失败（极难排查）**
```csharp
public void ProcessOrder(Order order)
{
    // 没有前置检查，直接开始漫长的业务逻辑
    DoSomeSetup();
    CalculateDiscount();
    
    // 运行了 2 秒钟后，这里突然因为 order 是 null 而崩溃
    // 排查时，你很难确定到底是因为前面哪一步把数据弄坏了，还是最初传进来的就是坏的。
    string customerName = order.Customer.Name; 
}
```

**资深写法：护城河模式（Guard Clauses）**
```csharp
public void ProcessOrder(Order order)
{
    // 前置检查：快速失败
    if (order == null)
        throw new ArgumentNullException(nameof(order), "订单对象不能为空。");
        
    if (order.Customer == null)
        throw new ArgumentException("订单必须包含客户信息。", nameof(order));

    // 只有经过了严格的安检，才允许执行后续的核心逻辑
    DoSomeSetup();
    CalculateDiscount();
    string customerName = order.Customer.Name; 
}
```

## 何时捕获异常：只在能“真正处理”时捕获

这是全天下所有新手程序员最容易犯的错误：为了防止程序崩溃，到处写 `try-catch(Exception)`。

### 什么是“真正处理”？
**黄金法则第二条：如果你不知道捕获到这个异常后该怎么善后，那就根本不要捕获它！**

捕获异常并不仅仅是为了“不让程序死掉”，而是你要有**备用方案（Plan B）**。以下场景才属于“真正处理了异常”：
1.  **重试机制：** 请求外部接口网络超时了，捕获异常后，休眠 2 秒钟再试一次。
2.  **降级服务/使用默认值：** 试图读取用户自定义的配置文件报错了，捕获异常后，不抛出，而是给系统赋一个默认的安全配置值。
3.  **友好的用户交互：** 在 UI 层的按钮点击事件中，捕获底层的“余额不足异常”，然后弹出一个漂亮的对话框让用户去充值。

### 不要充当“沉默的帮凶”
如果你捕获了异常，既没有重试，也没有给用户反馈，甚至只是在控制台打印了一句 `Console.WriteLine("出错了")`，这就叫**吞没异常（Swallowing Exceptions）**。

这极其可怕，因为程序的运行状态已经被破坏了，但它还在假装一切正常地往下跑。这会导致数据库被写入脏数据，或者在其他地方引发更诡异的 Bug。

**结论：** 除非你有明确的 Plan B，或者你身处全局异常处理的“兜底层”（详见上一篇），否则，放任异常向上抛出（气泡式冒泡）是绝对正确的选择！

## 何时转换异常：层边界处的“隔离艺术”

在现代软件架构中，我们通常会将代码分层。最经典的是三层架构：**表现层（UI / Web API） -> 业务逻辑层（Service） -> 数据访问层（Repository）。**

每一层都应该只说自己的“语言”。

### 抽象泄漏的灾难
假设你的 UI 层调用了 Service 层的一个 `Login` 方法，而 Service 层直接调用了 Repository 层。Repository 层在查询数据库时，因为网络断开发生了 `SqlException`，并且一路抛给了 UI 层。

此时，UI 层的代码被迫写成了这样：
```csharp
// UI 层的代码
try
{
    userService.Login(username, password);
}
catch (SqlException ex) // UI 层被迫认识了底层的技术细节
{
    MessageBox.Show("数据库连接失败！");
}
```
**问题在哪？** 这违背了分层架构的初衷。UI 层不应该知道底层是用 SQL Server、MySQL 还是本地 TXT 文件存储数据的。如果哪天底层换成了 MongoDB（抛出的可能是 `MongoConnectionException`），你的 UI 层代码就得全部重写！这就叫“抽象泄漏”。

### 异常映射
**黄金法则第三条：在层与层的边界处捕获底层的技术异常，并将其转换为上层能够理解的业务异常（领域异常）。**

正确的做法是在 Repository 层或 Service 层进行异常的转换，同时利用 `InnerException` 保留底层的案发现场：

```csharp
// 数据访问层的代码
public User GetUser(string username)
{
    try
    {
        return dbContext.Users.First(u => u.Name == username);
    }
    catch (SqlException ex)
    {
        // 捕获特定技术异常，转换为通用数据异常（包装原始异常）
        throw new DataAccessException("连接数据源时发生故障。", ex);
    }
}

// 业务逻辑层的代码
public void Login(string username, string password)
{
    try
    {
        var user = userRepository.GetUser(username);
        // ... 密码校验逻辑 ...
    }
    catch (DataAccessException ex)
    {
        // 捕获数据异常，转换为业务领域的异常
        throw new LoginFailedException("登录服务暂时不可用，请稍后再试。", ex);
    }
}
```
最终，UI 层只需要 `catch (LoginFailedException)` 就可以了。这种设计使得各层之间的耦合度降到了最低。

## 何时记录异常：集中式日志 vs 分散式日志

有了异常，我们必定要记录日志（写到文件或 Elasticsearch 等集中式日志服务器上）。但日志该在哪里记？

### 满屏日志的噩梦
很多开发者有一个坏习惯：**一边 catch，一边 log，一边 throw**。

```csharp
public void MethodA()
{
    try { MethodB(); }
    catch (Exception ex) 
    { 
        Log.Error(ex, "MethodA 出错了"); // 记一次
        throw; 
    }
}

public void MethodB()
{
    try { MethodC(); }
    catch (Exception ex) 
    { 
        Log.Error(ex, "MethodB 出错了"); // 记两次
        throw; 
    }
}
```
如果 `MethodC` 抛出了一个错误，这个错误会被 `MethodB` 记录一次，然后再被 `MethodA` 记录一次。最终你的日志文件里会出现极其冗余的垃圾数据，查个 Bug 要翻几十页重复的堆栈信息。

### 集中式记录的哲学
**黄金法则第四条：一个异常在其整个生命周期中，只应该被记录（Log）一次。**

最佳的记录地点通常只有两个：
1. **在你真正处理掉（消化掉）这个异常的地方。** 比如你捕获了异常并决定使用默认值，此时这个异常被“吃掉”了，不会再往上抛，你应该在这里记录一条警告（Warning）级别的日志。
2. **在全局异常处理器中（最高层）。** 对于那些无法处理、一路往上抛的严重系统错误，统一交由最顶层的中间件（如 ASP.NET Core 的 `UseExceptionHandler`）进行一次性集中记录。因为异常对象本身（尤其是 `StackTrace` 属性）就已经包含了从底层到顶层的完整调用链路，完全不需要你在每一层都去打印一遍。

## 本篇总结

掌握这四大黄金法则，你对待异常的处理方式将发生质的改变：

1. **该抛就抛，绝不手软：** 用 `ArgumentNullException` 等防御性代码守住方法的入口。
2. **不乱捕获，不当帮凶：** 没有恢复手段（Plan B）的 `catch` 块一律删掉。
3. **层层设卡，适时包装：** 在层级边界使用 `InnerException` 转换异常，防止底层技术细节污染上层业务。
4. **克制记录，统一收集：** 拒绝满屏的 Log 语句，把记录的重任交给全局处理层。
