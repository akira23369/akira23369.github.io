这是本系列的第七篇。在之前的文章中，我们讨论了如何通过“异常类型”（如 `FileNotFoundException`）来决定由哪个 `catch` 块来处理异常。

但在实际开发中，现实世界往往比简单的类型匹配要复杂得多。如果同一个类型的异常，由于内部错误码的不同，需要完全不同的抢救方案，我们该怎么办？

今天，我们将解锁 C# 6.0 引入的一项极具颠覆性的特性——**异常过滤器（Exception Filters）**。

# 异常过滤器的高级魔法

## 引言
假设你正在开发一个访问数据库的方法。当网络波动或者 SQL 语句写错时，系统都会抛出 `SqlException`。
但在业务逻辑上：
*   如果是“主键冲突”（错误码 2627），你想提示用户“该账号已存在”。
*   如果是“连接超时”（错误码 -2），你想悄悄地进行重试。
*   如果是其他严重的 SQL 语法错误，你想直接崩溃并记录日志。

在 C# 6.0 之前，这简直是个噩梦。我们来看看过去的程序员是怎么挣扎的，以及现代 C# 是如何优雅解决这个问题的。

---

## 传统做法的痛点与 when 关键字的诞生

### C# 6.0 之前的“笨办法”
在没有异常过滤器的时代，由于类型都是 `SqlException`，我们只能先把它抓进来，然后在 `catch` 块里面写一堆 `if-else`。如果发现当前的错误码我们处理不了，只能无奈地把它再抛出去。

```csharp
// 【旧时代的写法】：臃肿且破坏了堆栈状态
try
{
    SaveToDatabase();
}
catch (SqlException ex)
{
    if (ex.Number == 2627)
    {
        Console.WriteLine("主键冲突：账号已存在。");
    }
    else if (ex.Number == -2)
    {
        Console.WriteLine("网络超时，准备重试...");
    }
    else
    {
        // 发现处理不了，只能重新抛出
        throw; 
    }
}
```
这种写法有两个致命问题：
1. 代码揉成一团，违反了单一职责原则。
2. **极其致命的底层缺陷：** 只要程序进入了 `catch` 块，**堆栈展开（Stack Unwinding）** 就已经发生了。即使你马上调用了 `throw;`，如果你正在使用高级调试工具（如分析进程的内存转储 Dump 文件），案发现场最原始的内存状态已经被破坏了！

### 救星降临：when 关键字
C# 6.0 引入了 `when` 关键字，允许我们在 `catch` 后面附加一个布尔表达式。只有当异常类型匹配，**且** `when` 后面的条件为 `true` 时，程序才会进入这个 `catch` 块。

```csharp
// 【现代 C# 的写法】：清晰、平铺、高效
try
{
    SaveToDatabase();
}
catch (SqlException ex) when (ex.Number == 2627)
{
    Console.WriteLine("主键冲突：账号已存在。");
}
catch (SqlException ex) when (ex.Number == -2)
{
    Console.WriteLine("网络超时，准备重试...");
}
catch (SqlException ex)
{
    // 兜底处理其他 SQL 异常
    Console.WriteLine($"未知的数据库错误：{ex.Message}");
}
```
代码瞬间变得如丝般顺滑，不同条件的逻辑被完美地隔离开来。

## 性能与底层优势：为什么过滤器比 catch 内判断更高级？

刚才提到，传统 `if-else` 加 `throw;` 的写法会破坏堆栈状态。为什么加上 `when` 就能解决这个问题？这涉及到 CLR（.NET 运行时）处理异常的底层机制。

### 过滤器的执行时机（Two-Pass Exception Handling）
当异常发生时，CLR 处理异常实际上分为“两趟（Two-Pass）”：

*   **第一趟（寻找匹配项）：** CLR 沿着调用堆栈往上找，检查有没有哪个 `catch` 能接住这个异常。
    *   如果你用了 `when` 过滤器，CLR 会在**当前发生异常的上下文中**计算 `when` 里面的表达式。
    *   如果计算结果为 `false`，CLR 会认为这个 `catch` 不匹配，继续往上找。此时，**堆栈原封不动，犹如什么都没发生过**。
*   **第二趟（展开堆栈并执行）：** 一旦找到了匹配的 `catch`（类型匹配且 when 返回 true），CLR 才会开始“堆栈展开（释放沿途的局部变量）”，然后真正跳入 `catch` 块执行代码。

**核心结论：**
异常过滤器（Exception Filters）**绝不仅仅是语法糖**！它是 CLR 底层原生支持的功能（早在 VB.NET 和 F# 中就存在，C# 6 才引入）。使用 `when` 可以保证在不匹配的情况下，异常的原始现场绝对不被破坏，这在排查疑难杂症（尤其是生产环境的崩溃分析）时价值连城。

## 极客玩法：日志记录的“黑魔法”

因为我们知道了“`when` 表达式的计算不会破坏堆栈”这一底层特性，黑客级别的高级 C# 程序员发明了一种极为精妙的玩法：**不捕获异常，只记录日志。**

假设你想在某个方法发生异常时记录一条日志，但你不想真正处理这个异常，你希望它继续往上抛，让顶层的全局异常处理器去接管。

传统的做法是：先 catch 住 -> 记日志 -> throw;（破坏了状态）。
利用过滤器，我们可以这么写：

```csharp
public class LogHelper
{
    // 这个方法永远返回 false，但它的副作用是记录了日志
    public static bool LogException(Exception ex)
    {
        Console.WriteLine($"[日志拦截] 发生异常: {ex.Message}");
        return false; // 核心：坚决返回 false！
    }
}

public class Program
{
    public static void DoSomethingRisky()
    {
        try
        {
            int a = 1 / int.Parse("0"); // 引发除零错误
        }
        // 这里的 when 表达式调用了 LogException 方法。
        // 方法打印了日志，并返回 false。
        // 因此 catch 块被跳过，异常继续完美地向上抛出！
        catch (Exception ex) when (LogHelper.LogException(ex)) 
        {
            // 这里的代码永远、永远不会被执行
        } 
    }
}
```
这种设计模式被称为 **“Log and Pass”（记录并放行）**。它让你在不干扰任何异常处理流程、不破坏堆栈展开机制的前提下，像幽灵一样在代码的任意位置插入诊断探针。

## 高级实践场景：结合环境与业务状态进行筛选

`when` 后面不仅可以判断异常对象本身的属性，它可以写**任何返回 `bool` 值的表达式**。这意味着你可以把应用的运行环境、业务状态等外部因素结合起来。

### 场景一：基于运行环境（开发 vs 生产）的差异化处理
有时我们在开发环境下希望某些错误直接抛出导致崩溃（方便暴露问题），而在生产环境下则希望友好地吞掉它。

```csharp
try
{
    LoadOptionalPlugin(); // 加载非核心插件
}
catch (DllNotFoundException) when (Environment.GetEnvironmentVariable("ASPNETCORE_ENVIRONMENT") == "Production")
{
    // 只有在生产环境，找不到非核心插件时我们才降级处理，不影响主干业务
    Console.WriteLine("警告：某些非核心功能不可用，系统继续运行。");
}
// 如果是开发环境，上面这个 catch 进不去，程序会直接报错，提醒开发者补齐 DLL！
```

### 场景二：结合 HTTP 状态码（如 Polly 库的重试机制原理）
在微服务调用中，我们经常遇到 `HttpRequestException`。我们只想在遇到“503 服务不可用”或“408 请求超时”等临时性故障（Transient Errors）时才进行重试处理，而如果是“401 未授权”，重试一万次也没用，直接报错即可。

```csharp
try
{
    var response = await httpClient.GetAsync("https://api.example.com/data");
    response.EnsureSuccessStatusCode();
}
catch (HttpRequestException ex) when (IsTransient(ex.StatusCode))
{
    Console.WriteLine("检测到瞬时网络故障，等待 2 秒后发起重试...");
    // 执行重试逻辑
}

// 辅助方法：判断是否是瞬时故障
bool IsTransient(HttpStatusCode? statusCode)
{
    return statusCode == HttpStatusCode.RequestTimeout || 
           statusCode == HttpStatusCode.ServiceUnavailable ||
           statusCode == HttpStatusCode.BadGateway;
}
```

---
**本篇总结：**
C# 的异常过滤器（`when` 关键字）是处理复杂异常逻辑的一把尖刀。
1. **平铺代码：** 告别冗长的 `if-else`，让针对特定错误码的处理逻辑更加清晰。
2. **底层安全：** 在不进入 `catch` 块的前提下完成判断，保护了极其珍贵的堆栈现场。
3. **极高上限：** 通过结合外部状态或使用“Log and Pass”模式，解锁无穷的架构设计可能性。
