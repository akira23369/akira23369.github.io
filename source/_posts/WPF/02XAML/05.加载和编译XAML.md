## 加载和编译 XAML

前面讲了 XAML 的语法、命名空间、属性写法、代码隐藏，你已经知道怎么“写” XAML 了。但写完以后，怎么“用”它呢？也就是 XAML 到底怎么变成一个活生生的窗口显示在屏幕上？这就是“加载和编译”这一节要回答的问题。

其实你在日常开发中基本只用一种方式——编译 XAML，然后由 `InitializeComponent` 自动加载 BAML。但 WPF 给了你好几条路，每条路都有自己适合的场景。理解这几种不同的加载策略，能让你对 XAML 和 WPF 的运行模型理解得更透，以后碰上动态界面需求时脑子里也有备用方案。

下面四小节就是四种组合拳：

1. 只使用代码（完全不用 XAML）
2. 代码 + 未编译的 XAML（运行时动态解析 XAML 文本）
3. 代码 + 编译过的 XAML（最标准的做法）
4. 只使用 XAML（完全抛弃 C# 代码隐藏）

我们一个一个来看。

---

### 只使用代码

**什么意思？**

就是不在项目里放任何 `.xaml` 文件，界面里所有的控件、布局、属性，全部用 C# 一行一行写出来。就像以前写 Windows Forms 一样，只不过用 WPF 的类库。

**怎么干？**

比如你想显示一个窗口，里面有一个 StackPanel，里面有一个按钮和一个文本框。用纯代码就是这样：

```csharp
public partial class MainWindow : Window
{
    public MainWindow()
    {
        var panel = new StackPanel();
        var button = new Button { Content = "点我" };
        var textBox = new TextBox { Width = 200 };
        
        button.Click += (s, e) => textBox.Text = "按钮被点了";
        
        panel.Children.Add(button);
        panel.Children.Add(textBox);
        this.Content = panel;
    }
}
```

程序启动时，`MainWindow` 的构造函数里把这些对象构造出来、设好属性、建立父子关系、挂上事件，然后窗口一显示，界面就出来了。

**什么场景下会这么做？**

说实话，纯代码创建界面的方式在实际 WPF 开发中非常少见。因为有了 XAML 声明式语法，你用代码画界面对比一下就知道：代码又臭又长、不直观、布局逻辑和控件属性全搅在一起，后期维护想死。然而它依然有存在价值：

- 当你需要**完全动态创建界面**时，比如说你的控件数量、类型是在运行时才确定的，或者界面结构由用户自定义，这时候 XAML 的静态结构就不够用了，必须写代码动态构建。
- 当你写一些小型工具或测试窗口，实在不想再建一个 XAML 文件的时候，直接代码里搞一个简单的界面也可以接受。
- 当你在学习 WPF 的原理时，用纯代码构建一个简单的界面，你会立刻体会到 WPF 控件树的本质：所有控件都是普通的 .NET 对象，只不过通常用 XAML 来描述它们。这有助于你打破“XAML 是魔法”的迷思。

**缺点很明显：**

- 缺乏声明式结构的清晰性，一眼看不出界面长什么样。
- 放弃了 XAML 带来的设计器支持、热重载、编译期检查等这些便利。
- 没有分离关注点，逻辑和界面混在一个文件里。

所以，纯代码一般只作为对动态需求的一种补充，而不会用来做常规开发。你心里有这根弦就行。

### 使用代码和未经编译的 XAML

**什么意思？**

XAML 文件不参与编译过程，它就以 `.xaml` 文本文件的形式存在（或者从数据库、网络读取的字符串）。在程序运行时，用 `XamlReader.Load`（或 `XamlReader.Parse`）方法，现场把这段 XAML 文本解析成一棵对象树，然后把这对象树显示出来。

**怎么干？**

假设你有一个文本文件 `DynamicWindow.xaml`，内容是：

```xml
<Window xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        Title="动态窗口" Height="200" Width="300">
    <StackPanel>
        <Button Content="确定" />
        <TextBox />
    </StackPanel>
</Window>
```

在 C# 里这么加载：

```csharp
string xamlText = File.ReadAllText("DynamicWindow.xaml");
Window win = (Window)XamlReader.Parse(xamlText);
win.ShowDialog();
```

如果一切没问题，窗口就弹出来了。

**注意几个关键点：**

- **没有代码隐藏类**。因为你没有 `x:Class` 声明，也没有编译，所以这个窗口背后没有一个继承自 `Window` 的 partial 类。你只能用 `Window` 基类的接口去操作它。比如你想拿到那个 `Button`，就得在运行时遍历逻辑树（`LogicalTreeHelper`）或者视觉树，用 `FindName` 方法逐个找。这比直接写 `btnOK.Text` 痛苦多了。
- **不能直接在 XAML 里挂事件**。因为事件处理需要指向某个方法，而你没有代码隐藏类，解析器找不到方法，抛异常。要处理事件，只能在加载完拿到对象后，用代码手动订阅：`button.Click += ...`。
- **没有编译期检查**。XAML 里的拼写错误、类型错误、命名空间缺失全都留到运行时才会暴露，调试起来比较困难。
- **性能差一些**。因为每次加载都要完整解析 XML 文本并生成对象，比预编译的 BAML 慢。不过对于偶尔加载一次的场景，这个性能损失无伤大雅。

**什么场景用？**

- **需要让用户自定义界面**。比如你做一个报表工具，允许用户编写一小段 XAML 定义报表布局，程序运行时加载这些 XAML。
- **从网络或数据库动态拉取界面定义**。比如服务器端发来一段配置，客户端动态构建对应控件。
- **写调试或诊断工具**，临时加载一段 XAML 看看效果，不想重新编译程序。

**安全警告：`XamlReader.Load` 会执行代码吗？**

会的。XAML 解析过程中，如果碰到标记扩展（比如 `{Binding}`）或者 `x:Code` 内嵌代码，它是可以执行托管代码的。所以如果你加载的是不可信的 XAML 文本（例如从网络下载），一定要注意安全问题，否则可能被注入恶意代码。正规处理要么做沙盒，要么避免加载外部不可信 XAML。

**另一种轻度变体：`XamlServices.Load`**

除了 `XamlReader`，你还可以用 `System.Xaml` 命名空间下的 `XamlServices.Load`，它功能相似，也能加载 XAML 文本或流。面对简单的场景选哪个都行，`XamlServices` 是较新的 API，并且支持更多的 XAML 服务（比如保存对象图回 XAML）。初学者暂时用 `XamlReader.Parse` 就够。

### 使用代码和编译过的 XAML

**这就是你最熟悉的标准做法了**——WPF 应用创建的默认模式。百分之九十五以上的 WPF 代码都是这条路。

**具体过程：**

1. 你在项目中有一个 `Window1.xaml` 文件和一个 `Window1.xaml.cs` 文件。
2. 编译项目时，XAML 编译器将 `.xaml` 转换成 BAML（二进制表示），并嵌入到程序集中作为资源。
3. 同时，XAML 编译器自动生成一个 `Window1.g.cs` 文件（在 \) 目录下，一般不直接看），里面包含：
   - `partial class Window1` 声明。
   - `InitializeComponent()` 方法，此方法加载嵌入的 BAML 资源（`Application.LoadComponent` 或类似），并将所有带 `x:Name` 的控件赋值给对应的字段。
   - 按照 XAML 中指定的事件处理器，自动订阅事件。
4. 你在 `Window1.xaml.cs` 中的构造函数里调用 `InitializeComponent()`，所有对象就位，界面显示。

**为什么这条路径是首选？**

- **强类型**：你在代码隐藏里直接用 `this.btnOK` 访问按钮，因为自动生成的字段就是 `Button` 类型，IDE 有智能提示，编译会检查。
- **编译期验证**：XAML 中的错误会在编译时被发现，减少运行时崩溃。
- **分离界面与逻辑**：XAML 拥有卓越的声明能力，代码隐藏只关心逻辑，二者通过 `x:Name` 和事件属性协作，分工清晰。
- **高性能**：BAML 是预解析过的二进制流，加载速度远超动态解析 XML 文本。而且 WPF 会在设计时把 BAML 加载优化得很好。
- **设计器支持**：当你打开一个编译过的 XAML 文件时，Visual Studio 的设计视图能够实时解析 BAML 的元数据，给出可视化的编辑体验。

**运行时加载已编译的 XAML 资源**

你可能不是总在 `MainWindow` 里用 `InitializeComponent`，有时候你希望按需加载某个独立编译的页面或控件。只要那个 XAML 被编译到了程序集中，你就可以这样加载：

```csharp
// 假设你有一个编译好的 UserControl 叫 MyControl.xaml
MyControl control = new MyControl(); // 它的构造函数会调用 InitializeComponent 加载自己的 BAML
```

就这么简单。你只要 `new` 那个部分类，内部自动完成加载。这比动态解析未编译的 XAML 要快且安全。

如果你想要获取未实例化的 BAML 流，可以使用 `Application.LoadComponent(new Uri("/MyAssembly;component/Window1.xaml", UriKind.Relative))` 之类的方法，但通常我们直接用 `new`，不会手动戳 BAML。

**注意文件背后的 g.cs 文件**

初学者可能会好奇为什么在解决方案资源管理器里找不到 `Window1.g.cs`。它的确存在，在 `\obj\Debug` 之类输出目录里。你可以用“转到定义”或者在代码隐藏里对 `InitializeComponent` 按 F12 来查看生成的代码。时不时看一眼生成代码有助于你理解魔术是怎么发生的。

### 只使用 XAML

**这可能是最让人好奇的话题：我能不能完全不写一行 C#，纯用 XAML 写个应用程序？**

答案是可以，但是极其受限制，而且通常不被算作一个完整的可交付程序。有几种程度不同的“只使用 XAML”：

**最弱的形式：静态 UI 展示**

你可以写一个 `.xaml` 文件，没有 `x:Class`，然后作为资源或通过 `XamlServices.Load` 加载，得到一个静态的控件树。用户能看到界面，但不能做任何有意义的交互，因为没有任何事件处理代码。除非你的交互被完全限定在以下几种纯 XAML 机制内：

- 使用 `Trigger`（触发器）或 `DataTrigger` 响应属性变化。
- 使用 `Storyboard` 和动画来改变视觉效果。
- 使用 `EventTrigger` 配合 `SoundPlayerAction` 或 `BeginStoryboard` 等内置动作（但这些动作仍然有限）。

例如，你可以制作一个鼠标移上去会变色的按钮，或者一个会自己旋转的图标，这些纯靠 XAML 可以完成。但要实现“点击按钮从数据库读取数据”，就没有纯 XAML 的方案，必须写代码。

**使用 `x:Code` 内嵌代码**

XAML 里其实允许在 `x:Code` 块中直接写 C# 代码。例如：

```xml
<Window x:Class="NoCodeBehind.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">
    <Window.Resources>
        <x:Code>
            <![CDATA[
                void ButtonClick(object sender, RoutedEventArgs e)
                {
                    txt.Text = "Hello from XAML code";
                }
            ]]>
        </x:Code>
    </Window.Resources>
    <StackPanel>
        <Button Click="ButtonClick" Content="点我"/>
        <TextBlock x:Name="txt"/>
    </StackPanel>
</Window>
```

这样你确实没有单独的 `.cs` 文件，所有的界面和代码都写在 XAML 文件里。但这仍然需要 `x:Class` 指定一个编译生成的类，并且在编译时 `x:Code` 的内容会被提取到自动生成的类中。实际上仍然有编译过程，只是代码隐藏在 XAML 内部。

为什么一般不这么做？因为可维护性极差，没有智能提示，代码和标记混在一起又长又乱，比代码隐藏还糟糕。只有极个别的场景（比如某些代码生成器产出 XAML 时），会这样搞。

**XAML Only 应用程序框架**

有一些框架或者工具号称可以写“纯 XAML 应用”，比如早期一些工作流或原型工具。但最终都要么是背后自动生成了一些代码隐藏，要么就是利用了非常强大的绑定和命令机制把逻辑推到了标记扩展里，但这不能算完全没有代码，只是代码移到了通用库中。

在现实世界里，**零代码的 WPF 应用是不可能的，因为程序的入口点（`Main` 方法）必须是托管代码**。你最少需要一个 `App.xaml.cs` 里的 `Main` 或者 `Application.Run` 来启动消息循环。所以“只使用 XAML”更多是一种思想实验或极度受限的情况。

这节把它列出来，主要是让你看到 XAML 能力的边界：**XAML 是声明式的对象图构建语言，它本身不擅长描述流程和控制逻辑，它的强项是描述静态结构和绑定关系。** 真正的应用程序需要逻辑支撑，代码隐藏或 ViewModel 是不可避免的。

### 四种方式小结

| 方式 | 界面定义 | 逻辑位置 | 编译 | 典型场景 |
|------|----------|----------|------|----------|
| 只使用代码 | C# 代码 | 事件处理也在代码中 | 编译 | 完全动态创建界面，或极简测试 |
| 代码 + 未编译 XAML | XAML 文本 | 代码手动操作对象 | 不编译（运行时解析） | 用户自定义界面、动态加载外部 XAML |
| 代码 + 编译过的 XAML | 编译时转换为 BAML | 代码隐藏类（部分类） | 编译 | 日常标准开发，99% 的情况 |
| 只使用 XAML | XAML 文本 | 基本没有或借助触发器 | 不编译或弱编译 | 无交互静态展示，或内嵌代码的小实验 |

这四种方式不是非此即彼的，你可以在一个项目里混合使用。比如大部分窗体走标准编译路线，但其中某个功能模块允许用户拖拽生成 XAML 实时预览，那就可以用未编译的 XAML 加载。

对于初学者，把精力牢牢放在第三种（代码+编译过的 XAML）上，因为它身上承载了 WPF 几乎全部的生产力工具和最佳实践。但了解其他方式，能帮你回答“如果我偏不用 XAML 行不行？”、“如果 XAML 不编译怎么跑？”这类疑惑，将来碰到动态需求时也知道从哪入手。
