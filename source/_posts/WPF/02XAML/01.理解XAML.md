# 理解XAML

## 印象中的“XML 传数据”？

因为你印象里的 XML 长这样：

```xml
<person>
    <name>张三</name>
    <age>25</age>
</person>
```


这是用 XML 描述“一个人”的数据。

而 WPF 里的 XML 长这样：
```xml
<Button Content="点我" />
```


这是用 XML 描述“一个按钮”的**对象**。

**本质上完全相同**——都在用标签和属性来描述东西。只不过：

- 在“传递数据”的场景里，描述的是**数据**（人名、年龄等）。
- 在 WPF 中，描述的是**界面对象**（窗口、按钮、布局）。

WPF 解析器会把这套 XML 描述的界面元素，**动态创建成内存里的真实 UI 对象**（比如 `Button` 类的一个实例）。


## 理解XAML

这一节主要是让你搞清楚XAML到底是个啥，它在WPF里扮演什么角色。很多人刚接触WPF的时候，看到一堆尖括号和冒号，觉得好像HTML，但又不太一样，心里就犯嘀咕。这节就是把这事儿掰开揉碎讲清楚。

XAML全称是Extensible Application Markup Language，翻译过来就是"可扩展应用程序标记语言"。听着有点绕口，其实核心就是一句话：**XAML是一种用来定义用户界面的声明式语言**。啥叫声明式呢？就是你告诉系统"我想要一个按钮，它是红色的，放在左边"，而不是写代码一步步教系统怎么画这个按钮。你说什么就是什么，系统负责把它变成现实。

这跟传统的做法差别巨大，下面2.1.1就专门讲这个对比。

### WPF之前的图形用户界面

在WPF出现之前，做Windows桌面程序的界面基本就两条路：要么用拖控件的方式，要么完全手写代码。

先说拖控件。比如用Windows Forms开发，你在设计器里拖一个按钮到窗体上，设置它的文字、颜色、位置，然后Visual Studio在背后给你生成一大堆C#代码。这些代码藏在叫`Form1.Designer.cs`的文件里，里面全是`this.button1 = new Button()`、`this.button1.Text = "确定"`、`this.button1.Location = new Point(100, 200)`这种东西。界面长啥样，完全由这些C#代码控制。

这么干的问题在哪儿呢？

第一，**界面和代码混在一起**。设计人员如果想调一下按钮的位置，他就得去改C#代码，但他可能根本不懂编程。反过来，程序员想调一下界面布局，也得在一堆琐碎的属性赋值里翻来翻去。虽然设计器和代码是同步的，但一旦出了设计器搞不定的复杂情况，你就得手动改那些自动生成的代码，手一滑就可能搞崩整个窗体。

第二，**这种代码生成的界面是"一次性"的**。什么意思呢？按钮的位置是写死成`(100, 200)`的，你运行程序后拖动窗口变大，按钮还在老地方呆着，除非你写一堆布局逻辑去手动调整。而在WPF里，布局是自动的、响应式的，这个后面会详细讲。

第三，**传统的界面定义方式跟图形设计师的工具链是割裂的**。设计师用Expression Blend或者Adobe系列工具做出来的漂亮界面，要想变成程序里的真实界面，得靠程序员去"临摹"，不仅效率低，还容易走样。XAML则能做到设计工具和开发工具共用同一份文件，设计师在Blend里拖出来的界面，保存后程序员直接在Visual Studio里打开，看到的就是同一个XAML，各干各的互不干扰。

再说说更早的年代，连拖控件都没有的时候。那会儿写Windows程序（比如用纯C语言和Win32 API），你创建一个窗口要注册窗口类、写消息循环、处理`WM_CREATE`、`WM_PAINT`消息，在`WM_PAINT`里用GDI函数一笔一画地把界面画出来。你想放个按钮？得再创建一个子窗口，给它指定位置和样式。全是用C语言硬写，代码量巨大不说，可维护性极差。后来MFC稍微封装了一下，但本质上还是那套消息驱动的模型，界面定义和业务逻辑深度纠缠。

WPF彻底改变了这个局面。它提出了**XAML+代码隐藏**的分离模式。XAML专门负责定义界面长什么样，代码隐藏（就是那个`.xaml.cs`文件）专门写事件处理的逻辑。比如你定义了一个按钮，XAML里写`<Button Content="点我" Click="Button_Click"/>`，然后在代码隐藏里写`private void Button_Click(object sender, RoutedEventArgs e){...}`，这样界面和逻辑就分开了。设计师改XAML不影响程序员的逻辑代码，程序员改逻辑也不会破坏界面结构。

更进一步，WPF后来还搞出了MVVM模式，数据绑定机制让你连事件处理代码都可以大幅减少，界面通过绑定直接关联到数据对象，按钮的可用状态、列表的内容、文本的显示全都自动同步。这些后面章节会细讲，但根儿都在XAML这套声明式架构上。

### XAML变体

这一段讲的是"XAML"这个词其实不单单指一种格式，它有好几个变种，分别用在不同场景里，但底层解析规则是相通的。

最常用的当然就是**WPF里的XAML**，也是这本书重点讲的。你在WPF项目里看到的`.xaml`文件，里面定义的都是WPF的控件和布局，比如`Window`、`Button`、`StackPanel`这些东西。它的命名空间默认指向WPF相关的程序集。

然后是**Silverlight里的XAML**。Silverlight是微软以前搞的一个浏览器插件，可以理解为"精简版的WPF跑在浏览器里"。它的XAML语法和WPF非常像，但支持的控件和功能少一些，毕竟它要跨平台、要跑在沙盒里，很多底层的Windows特性用不了。虽然后来Silverlight基本被抛弃了，但理解它的存在有助于你明白XAML这套语法的通用性——同一套标记语言的思想可以适配不同的运行时环境。

还有**WF（Workflow Foundation）里的XAML**。WF是微软的工作流引擎，你可以用XAML来定义工作流的步骤、分支、循环。比如`<Sequence>`、`<If>`、`<While>`这些活动节点，写在XAML里，然后引擎去执行。这已经不是界面了，而是用XAML来描述业务逻辑流程。这说明XAML不光能画界面，它本质上是一种用XML来表示对象图的方式，什么对象都能表示。

另外还有**XPS（XML Paper Specification）** 用的XAML。XPS是微软搞的一种固定布局的文档格式，类似PDF。XPS文档内部就是用XAML来描述页面上的文字、图片、路径的。这也说明XAML的应用范围很广。

这些变体的存在说明了一个道理：**XAML的本质是一套基于XML的对象实例化语法**。不管是界面控件、工作流活动、文档元素，还是你自定义的普通CLR对象，理论上都能用XAML来声明。

### XAML编译

这个小节解释了一个关键问题：你写的XAML文件到底是怎么变成程序的一部分的？是程序运行时去读那个文本文件一行行解析吗？还是怎么着？

答案是：**编译时就把XAML处理好了，不是运行时去现场解析**。这样做性能高很多。

具体流程是这样的：

你在Visual Studio里添加一个`Window1.xaml`文件，VS会自动生成一个对应的代码隐藏文件`Window1.xaml.cs`，里面有这个窗体的类定义（用`partial`关键字声明）。当你编译项目时，会发生两件重要的事。

**第一，XAML文件会被转换成BAML**。BAML全称是Binary Application Markup Language，也就是"二进制应用程序标记语言"。说白了，就是把XAML的文本格式变成压缩的二进制格式。为什么要这么干呢？因为文本解析很慢，而且XAML文件可能很大（复杂的界面几百上千行很正常），直接带着文本去运行，每次打开窗口都要解析一遍XML，加载速度就慢。而BAML是预解析过的二进制流，运行时直接加载就行，速度飞快。同时BAML比原始XAML体积小很多，对程序集的大小也有好处。

**第二，VS会自动生成一个g.cs文件（你一般看不到它，在obj目录下）**。这个文件里用C#代码把XAML里定义的所有有名字的控件都声明成类的字段，并在初始化组件时调用`LoadBaml`把这些BAML加载进来。比如你在XAML里写`<Button x:Name="btnOK"/>`，g.cs里就会生成`internal Button btnOK;`，然后在`InitializeComponent()`方法里把这个字段和实际加载出来的按钮对象关联起来。这就是为什么你可以在代码隐藏里直接用`btnOK.Text = "确定"`——那个字段早就自动生成了。

所以你运行时调用窗体的构造函数，构造函数里调用`InitializeComponent()`，这个方法去读取嵌入在程序集里的BAML资源，一口气把所有控件创建出来、设置好属性、挂好事件处理程序，窗体就显示出来了。整个过程都是编译产物在工作，原始XAML文件甚至可以不随程序发布。

这种编译模型还有一个好处：**XAML可以在编译期做大量检查**。如果你的XAML里写错了属性名、引用了不存在的资源、绑定路径写错了，编译的时候就会报错，你马上就知道。而如果把XAML当纯文本在运行时加载，这些错误都得等到用户点开那个窗口才暴露，调试起来非常痛苦。

另外书中还提到，你当然也能选择"不编译XAML"，在运行时用`XamlReader.Load()`方法动态加载一段XAML文本。这种方式适合需要动态生成界面的场景，但因为要现场解析，性能会差一些，而且没有编译期检查，风险也大。大部分情况下还是推荐用编译好的方式。

理解了XAML编译过程，你就能明白为什么WPF程序的启动速度和运行性能都还不错——因为大部分界面构建工作在编译时就已经完成了一半，运行时只是加载二进制流然后"咔嚓"一下把对象树立起来，效率远高于一行行解析文本文件。
