# XAML基础

## XAML 基础

前面两节已经把 XAML 是什么东西、它跟老技术的区别、还有它怎么编译成程序这些背景交代清楚了。现在就到了真正动手写 XAML 的时候了。这一节叫“XAML 基础”，顾名思义，它就是要教给你 XAML 里最核心的两个概念：**命名空间**和**代码隐藏类**。这两个东西搞明白了，你才能看懂一个最简单的 `.xaml` 文件到底每一行在说啥，也才能顺畅地往里面加东西。

别看这两个知识点好像很基础，但要是不搞清楚的话，后面你遇到冒号、`x:` 前缀、各种各样的控件名字就一头雾水，所以值得多花点时间掰开揉碎来讲。

---

### XAML 名称空间

在你用 C# 写代码的时候，如果想用 `Button` 类，你得在文件开头写上一句 `using System.Windows.Controls;`，不然编译器不认识这个类。XAML 里也有同样的需求：你得告诉 XAML 解析器，你写的那些 `<Button>`、`<StackPanel>` 这些标签到底对应哪个 .NET 类，这些类在哪个程序集里。

但是 XAML 是 XML 格式的，它没有 C# 那种 `using` 语句，它是靠 **XML 命名空间** 来搞定的。XML 命名空间一般用一串网址一样的东西作为唯一标识符（URI），只不过这些 URI 只是一个字符串，你不用真的去浏览器访问它，它唯一的作用就是保证全世界不会有两个人搞出同名的格式。微软就占了好几个这种 URI 来表示 WPF 相关的命名空间。

打开任何一个 XAML 文件，你一般都会在根标签（比如 `<Window>`）上看到类似这样的属性：

```xml
xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
```

这两行就是最核心的命名空间声明了，而且几乎所有 WPF 的 XAML 文件里都会有它们，咱们一个一个来看。

**第一个：`xmlns="http://.../presentation"`**

这是默认命名空间。你可能会想：这个长长的 URI 怎么对应到 .NET 里的一堆命名空间呢？这是通过 **映射** 来完成的。WPF 的 XAML 处理器在内部有一个映射表，把这个 URI 映射到了好几个 .NET 命名空间的总和：像 `System.Windows`、`System.Windows.Controls`、`System.Windows.Shapes`、`System.Windows.Media` 等等。也就是说，只要你在标签上声明了这个默认命名空间，你就可以直接写 `<Button>`、`<TextBox>`、`<Rectangle>`，不用在控件名字前加任何前缀。因为这些类全都被这个 URI 覆盖了。

注意这里没有写成 `xmldefault="..."` 之类的，XML 的默认命名空间就是那个没有冒号后面跟着前缀的 `xmlns`。所以代表你下面所有没带前缀的元素都属于这个命名空间。

**第二个：`xmlns:x="http://.../xaml"`**

这个叫 XAML 专用命名空间。大家习惯把它的前缀写成 `x`（你也可以写别的，但惯例就是 `x`）。这个命名空间对应的不是具体控件，而是 XAML 语言本身提供的一些功能，比如：

- `x:Class`：用来指定这个 XAML 编译后生成的类的名称，和代码隐藏类关联。
- `x:Name`：给元素起一个名字，这个名字会变成代码隐藏类里的字段，让你可以在 C# 里直接调用。
- `x:Key`：用在资源字典里，给资源对象起一个唯一标识，方便后面通过 `{StaticResource}` 引用。
- `x:Type`、`x:Null`、`x:Static` 等标记扩展的支持。

可以看到，这些 `x:` 开头的属性跟具体界面的外观没太大关系，它们更多是为 XAML 这个标记语言本身服务，给编译器提供额外信息，或者帮你表达一些用普通属性不太好表达的东西。所以把它们和控件命名空间分开，是很清晰的设计。

**引入自己的命名空间**

当然，只靠默认的和 `x:` 命名空间肯定不够，因为你迟早要在 XAML 里用到自己写的类，或者用到第三方库里的控件。这时候你就需要手动声明你自己的命名空间映射。

语法是这样的：

```xml
xmlns:local="clr-namespace:MyApplication.Views"
```

这里 `local` 是你可以随便取的前缀（习惯叫 `local`，但你可以叫 `my`、`controls` 都行），等号后面的那串才是关键。它用 `clr-namespace:` 告诉解析器，我要把一个 CLR 命名空间映射进来。`MyApplication.Views` 是你项目里的一个命名空间。声明完之后，写 `<local:MyUserControl>` 就代表使用 `MyApplication.Views.MyUserControl` 这个类。

如果你的类不在当前项目里，而是在另外一个 DLL 里，那就再加上一个分号和一个 `assembly=`：

```xml
xmlns:ext="clr-namespace:SomeLibrary.Controls;assembly=SomeLibrary"
```

这一声明，XAML 就会去 `SomeLibrary.dll` 里找 `SomeLibrary.Controls` 命名空间下的所有类。

正是因为这种灵活的命名空间映射，XAML 才能把各种来源的控件无缝地揉在一个页面里，而不会出现名字冲突。比如你自己的控件和第三方库的控件都叫 `Button`，但你给它们分配了不同的前缀（比如 `my:Button` 和 `third:Button`），就完全不会打架，这和 C# 在 `using` 时碰上重名类要用全限定名是一个道理。

还有一些更细节的知识：默认命名空间映射到多个 .NET 程序集，但实质上这些类都在 `PresentationFramework.dll`、`PresentationCore.dll` 等核心 WPF 程序集里。而 `x:` 命名空间的那些特性是在 XAML 编译器/解析器这一层处理的，比单独的控件类更底层。整个命名空间机制让 XAML 文件变成了一个可以“自由组装对象”的乐高世界，只要你能映射到对应的 CLR 类型，你就可以直接用 XML 标签把它创建出来，非常强大。

### 代码隐藏类

XAML 负责界面长什么样，但一个程序光有脸不行，还得有脑子——也就是业务逻辑。这个脑子在哪儿呢？就在所谓的 **“代码隐藏”** （code-behind）文件里。

在 Visual Studio 里添加一个“窗口 (WPF)”之类的项，你会发现它帮你生成了两个成对的文件：比如 `MainWindow.xaml` 和 `MainWindow.xaml.cs`。它们就是一对搭档，XAML 负责界面，.cs 负责逻辑。这两个文件是怎么关联起来的呢？关键就在于 **`x:Class`** 属性。

打开 `MainWindow.xaml`，你会在根标签 `<Window>` 上看到：

```xml
<Window x:Class="MyApplication.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="MainWindow" Height="350" Width="525">
    <Grid>
    </Grid>
</Window>
```

看到那个 `x:Class="MyApplication.MainWindow"` 了吗？它就是告诉 XAML 编译器：**“你把我这个 XAML 文件编译生成的一个类，它的完全限定名就叫 `MyApplication.MainWindow`。”**

然后你打开 `MainWindow.xaml.cs` 文件，会看到：

```csharp
namespace MyApplication
{
    public partial class MainWindow : Window
    {
        public MainWindow()
        {
            InitializeComponent();
        }
    }
}
```

注意这里用了 `partial class MainWindow`，也就是说这个 `MainWindow` 类是“分成两部分”的：一部分由你写的 C# 代码组成（就是这个 .cs 文件），另一部分由 XAML 编译时自动生成的代码组成（就是我们上一节提到的 g.cs 文件）。`x:Class` 指定的类名把这两部分拼成了一个完整的类。

编译的时候，XAML 编译器会读取 XAML 文件，生成一个包含 `InitializeComponent()` 方法和所有带 `x:Name` 的控件的字段声明的 C# 文件（g.cs）。你写的 .cs 文件可以调用 `InitializeComponent()` 来加载 BAML 并把界面“撑”起来，还可以直接使用那些字段来操控控件。比如你在 XAML 里写：

```xml
<Button x:Name="btnOK" Content="确定" Click="btnOK_Click"/>
```

那么自动生成的代码里就有：

```csharp
internal Button btnOK;
```

而在你的 .cs 文件里，你就可以放心地写 `btnOK.Content = "已点击";`，因为编译后的类里确实有这个字段。之所以你能直接在代码里用 `btnOK` 而不用先声明，就是靠这个部分类机制。

这里面还有一个容易让新手困惑的点：**XAML 里写的 `Click="btnOK_Click"` 又是怎么关联到代码隐藏类的方法的？** 其实这也靠的是自动生成的代码。编译器看到你在 XAML 里指定了事件处理器名称，它就会在生成的 `InitializeComponent` 里自动加上一句类似 `this.btnOK.Click += new RoutedEventHandler(btnOK_Click);` 的代码。所以程序一运行，按钮一点，就调到你写的那个方法里去了。你不需要手动写订阅事件的代码，XAML 帮你搞定了这一切。

如果你的 XAML 里没有写 `x:Class`，还能不能有代码隐藏类？这取决于你怎么用这个 XAML。上一节我们提过，有时候你会动态加载一段未经编译的 XAML，那个时候就没有代码隐藏类，所有逻辑都得靠代码去动态操作 `XamlReader.Load` 拿到的对象。但正经的 WPF 开发，几乎都会用这种 `x:Class` + 部分类的配对方式，因为这样最方便、工具支持最好。

**代码隐藏类的继承关系**

再仔细看一眼 `MainWindow.xaml.cs` 的类定义：`public partial class MainWindow : Window`。这说明代码隐藏类继承自 `System.Windows.Window`。这个继承关系并不是在 XAML 里写的（XAML 里你只是用了 `<Window>` 标签），但 XAML 的根标签类型必须和代码隐藏类的基类一致。你如果用 `<UserControl>` 作为根标签，那你的代码隐藏类就必须继承自 `UserControl`。

这背后也全靠 `x:Class` 和编译器的配合。编译器看到根标签是 `<Window>`，又看到 `x:Class="MyApplication.MainWindow"`，它就知道要生成一个名叫 `MainWindow` 的派生自 `Window` 的类。你写的 .cs 文件也声明 `partial class MainWindow : Window`，两边一拍即合，完整的类就出来了。

**为什么要分成两个文件？**

这其实是 WPF 的一大设计哲学：**关注点分离**。前端的 XAML 可以交给美观设计师去用 Blend 拖拖拽拽，后端的 C# 可以交给开发人员去写业务逻辑。两个人甚至可以同时编辑同一个窗体的不同部分，只要协调好控件的名字和事件，就不会相互干扰。而以前的 Windows Forms 那种把所有界面代码都生成在一个 `Designer.cs` 里，任何人手改都容易跟设计器冲突，分离式开发体验就差了一截。代码隐藏类这种模式把界面和逻辑彻底解耦了，这也是后续 MVVM 模式能顺利落地的基础（MVVM 里甚至尽量让代码隐藏类里几乎没代码，把逻辑都拉到 ViewModel 去，XAML 的声明式特性让这一步成为可能）。

**总结一下**

XAML 基础就这两大块：命名空间和代码隐藏类。

- 命名空间让你能在 XML 里用各种来源的控件，核心就是那一行默认的 WPF 命名空间和 `x:` 命名空间，以及自己用 `clr-namespace` 引入自定义或第三方的类。
- 代码隐藏类通过 `x:Class` 把 XAML 和 C# 文件连接起来，让界面和逻辑既能分离，又能很方便地互相配合。`x:Name` 和事件处理器赋值背后都是编译器帮你搭的桥，你只管在 XAML 里声明，在 .cs 里写逻辑就好。

把这两个基础打结实了，后面的什么属性、事件、标记扩展、资源这些高级话题，你学起来就会顺畅很多——因为万变不离其宗，它们终究都是在遵守命名空间规则的前提下，在由 `x:Class` 组合而成的这个对象大厦上添砖加瓦。
