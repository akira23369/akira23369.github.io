# 笔记42《命令》9.2节——WPF命令模型

## 9.2 WPF命令模型

上一节 9.1 把命令的“世界观”给你建立起来了——命令是什么、为什么要用命令、四个核心角色各司什么职。这一节咱们要钻进 WPF 的命令模型内部，把那些抽象的接口和类一个一个拆开看。

WPF 的命令系统不是魔法，它基于几个非常具体的 .NET 类型。理解了这几个类型的继承关系和协作方式，你不仅能用好内置命令，还能自己写出和 WPF 原生命令一样强大的自定义命令。整条命令体系的类继承链非常短，核心就三个接口/类：`ICommand`、`RoutedCommand`、`RoutedUICommand`，外加一组预置的静态命令库。下面逐一击破。

---

### 9.2.1 ICommand 接口

`ICommand` 是 WPF 命令体系的**根接口**。任何命令对象，不管是微软给的还是你自己写的，都必须实现这个接口。它定义了命令最核心的“灵魂契约”。

接口定义在 `System.Windows.Input` 命名空间下，签名非常简洁：

```csharp
public interface ICommand
{
    // 执行命令
    void Execute(object parameter);

    // 判断命令当前是否可以执行
    bool CanExecute(object parameter);

    // 当“能否执行”的状态发生变化时触发
    event EventHandler CanExecuteChanged;
}
```

只有三个成员，但每一个都有重要职责。

#### Execute(object parameter)

这个方法就是命令的**执行逻辑**。当用户点击绑定该命令的按钮、或是按下关联的快捷键时，WPF 最终会调用这个方法。

`parameter` 是命令参数，可以由命令源传入。比如“打开文件”命令，参数可能是文件路径；“复制”命令可能不需要参数。谁触发命令，谁提供参数——按钮可以通过 `CommandParameter` 属性来指定。

```csharp
// 自定义命令的 Execute 实现示例
public void Execute(object parameter)
{
    string filePath = parameter as string;
    if (!string.IsNullOrEmpty(filePath))
    {
        File.WriteAllText(filePath, "保存的内容");
    }
}
```

**重要**：`Execute` 应该在 UI 线程上被调用（因为命令通常由 UI 控件触发），但接口本身没有强制这个约定。如果你自己写命令类，不要在 `Execute` 里做长时间阻塞操作，否则界面会卡死。

#### CanExecute(object parameter)

这个方法返回一个 `bool`，表示命令**当前是否可用**。WPF 的控件（按钮、菜单项）会自动调用这个方法来决定自己是亮着还是灰着。

同样接收 `parameter`，因为能否执行可能取决于参数。比如“粘贴”命令，如果剪贴板是空的，`CanExecute` 应该返回 `false`；如果剪贴板里有东西，返回 `true`。

```csharp
public bool CanExecute(object parameter)
{
    // 如果文本框里没有选中文字，剪切和复制就不可用
    return myTextBox != null && myTextBox.SelectionLength > 0;
}
```

WPF 的 `CommandManager` 会定期或在特定时机（如控件焦点变化、属性变化）自动调用所有活动命令的 `CanExecute`，来检查命令状态是否需要刷新。但很多时候，你需要**手动**通知 WPF“嘿，我的状态变了，你赶紧重新查一下”。这就靠第三个成员。

#### CanExecuteChanged 事件

当命令的可执行状态发生变化时，命令对象应该触发这个事件。WPF 的控件（命令源）在绑定了命令后，会自动订阅 `CanExecuteChanged`，收到事件后立刻重新调用 `CanExecute` 来更新自己的 `IsEnabled`。

触发这个事件的典型时机：
- 相关数据发生变化（比如剪贴板内容变了、选中文字变了、文档修改状态变了）。
- 命令参数发生变化。
- 程序的整体状态变化（比如从“只读模式”切换到“编辑模式”）。

```csharp
// 当影响 CanExecute 结果的因素变化时，手动触发
public void RaiseCanExecuteChanged()
{
    CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}
```

**一个很常见的做法**：把 `CanExecuteChanged` 的实现委托给 `CommandManager.RequerySuggested` 事件。`CommandManager.RequerySuggested` 是 WPF 提供的一个全局静态事件，它在系统检测到某些输入事件（如鼠标移动、键盘敲击、焦点变化等）时自动触发。很多简单命令直接把 `CanExecuteChanged` 转发给它，省得自己判断什么时候该通知：

```csharp
public event EventHandler CanExecuteChanged
{
    add { CommandManager.RequerySuggested += value; }
    remove { CommandManager.RequerySuggested -= value; }
}
```

**注意**：这个偷懒做法会让 `CanExecute` 被频繁调用（每次鼠标动一下都调一次），在复杂命令或大量命令同时存在时可能影响性能。更精细的做法是只在确实可能影响状态的时候触发自己的 `CanExecuteChanged`。

#### ICommand 的实现模式

在实际开发里，你不会每次都裸写 `ICommand` 的实现。最经典的模式是写一个通用的 `RelayCommand`（或叫 `DelegateCommand`），把 `Execute` 和 `CanExecute` 通过构造函数注入，像这样：

```csharp
public class RelayCommand : ICommand
{
    private readonly Action<object> _execute;
    private readonly Predicate<object> _canExecute;

    public RelayCommand(Action<object> execute, Predicate<object> canExecute = null)
    {
        _execute = execute ?? throw new ArgumentNullException(nameof(execute));
        _canExecute = canExecute;
    }

    public bool CanExecute(object parameter) => _canExecute == null || _canExecute(parameter);

    public void Execute(object parameter) => _execute(parameter);

    public event EventHandler CanExecuteChanged
    {
        add { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }
}
```

然后在 ViewModel 里创建命令：

```csharp
public ICommand SaveCommand { get; }

public MyViewModel()
{
    SaveCommand = new RelayCommand(
        execute: p => { /* 保存逻辑 */ },
        canExecute: p => !string.IsNullOrEmpty(this.DocumentText)
    );
}
```

这是 MVVM 架构中最常用的命令模式。你几乎不会在 WPF 项目里看到裸的 `ICommand` 实现，要么用 `RelayCommand`，要么用各种 MVVM 框架里封装好的命令类。

### 9.2.2 RoutedCommand 类

你可能会想：`ICommand` 接口只有三个成员，那 WPF 的复制、粘贴、撤销这些内置命令，它们怎么做到“在不同的控件上有不同的执行逻辑”的？这就引出了第二个核心类——**`RoutedCommand`**。

`RoutedCommand` 实现了 `ICommand`，但它不自己写死执行逻辑。相反，它利用 WPF 的路由事件机制，把 `Execute` 和 `CanExecute` 作为**路由事件**沿控件树冒泡（或隧道），沿途寻找**绑定了该命令且知道怎么处理它的元素**。

这听起来有点绕，打个比方：

- 普通 `ICommand`（如 `RelayCommand`）= 一辆自带发动机和方向盘的车，自己决定怎么走。
- `RoutedCommand` = 一列火车的车头，它自己没有动力，但它可以推着车厢沿轨道走，动力由沿途的站点提供。哪个站点认得这列火车，就给它供电。

`RoutedCommand` 内部有两个关键的路由事件：`PreviewExecutedEvent` 和 `ExecutedEvent`（隧道和冒泡），以及对应的 `PreviewCanExecuteEvent` 和 `CanExecuteEvent`。当你调用 `RoutedCommand.Execute` 时，它不干别的，就是在命令目标所在的元素树里引发一次路由事件，让元素树自己决定谁来处理。

#### RoutedCommand 的 Execute 和 CanExecute 流程

**Execute 流程**：

假设用户点击了一个按钮，按钮的 `Command` 是 `ApplicationCommands.Copy`，`CommandTarget` 是一个 `TextBox`：

1. 按钮作为命令源，调用 `ApplicationCommands.Copy.Execute(null, myTextBox)`。
2. `RoutedCommand.Execute` 内部：创建一个 `ExecutedRoutedEventArgs`，把命令目标设为 `myTextBox`，然后在这个目标元素上引发 `CommandManager.ExecutedEvent`（这是一个冒泡路由事件）。
3. 路由事件从 `myTextBox` 开始往上冒泡。
4. `myTextBox` 的 `CommandBindings` 集合里，有没有绑定 `ApplicationCommands.Copy` 并且提供了 `Executed` 处理程序的？有！`TextBox` 在内部就预设了 `Copy` 的命令绑定，它的 `Executed` 处理程序执行 `Clipboard.SetText(selectedText)`。
5. 事件被处理，流程结束。

如果 `TextBox` 没有绑定这个命令，事件继续往上冒到它的父容器（比如 `Grid`、`Window`）。上层容器也可以通过 `CommandBindings` 来提供处理逻辑。如果冒到根都没有人处理，命令什么都不做。

**CanExecute 流程**：

和 Execute 流程几乎一样，只不过引发的是 `CanExecuteEvent`。沿途的 `CommandBinding` 可以设置 `e.CanExecute = true` 来告诉命令“我能处理”。如果没人设置，`CanExecute` 默认返回 `false`，绑定该命令的按钮就会变灰。

#### RoutedCommand 的关键属性

- **`InputGestures`**：命令关联的默认输入手势集合。比如 `ApplicationCommands.Copy` 的默认手势是 `Ctrl+C`。当你把命令绑定到窗口时，这些手势会自动生效。
- **`OwnerType`**：命令的“所有者类型”，通常用于分类和命名约定。

#### 路由命令和命令绑定的关系

这里要强调一个很重要的区别：
- `RoutedCommand` 只是一个**信使**。它说“我要执行了，谁来处理？”然后沿树喊一圈。
- **命令绑定（CommandBinding）** 才是真正的**执行者**。它提供 `Executed` 和 `CanExecute` 的事件处理程序。

命令绑定通常定义在某个 `UIElement` 的 `CommandBindings` 集合里：

```xml
<Window.CommandBindings>
    <CommandBinding Command="ApplicationCommands.Copy" 
                    Executed="CopyCommand_Executed"
                    CanExecute="CopyCommand_CanExecute" />
</Window.CommandBindings>
```

```csharp
private void CopyCommand_Executed(object sender, ExecutedRoutedEventArgs e)
{
    MessageBox.Show("复制命令被执行了！");
}

private void CopyCommand_CanExecute(object sender, CanExecuteRoutedEventArgs e)
{
    e.CanExecute = true;   // 允许执行
}
```

如果没有命令绑定来处理它，`RoutedCommand` 就是一个空壳，什么都不会发生。这也是 `RoutedCommand` 和直接实现 `ICommand` 的自定义命令的最大区别——后者自带执行逻辑，前者依赖外部绑定提供逻辑。

#### 为什么要用 RoutedCommand？

这种“把逻辑推到控件树上”的做法看起来很迂回，但它有一个巨大的好处：**同一命令可以在不同控件上有不同的行为。**

“粘贴”在 `TextBox` 里是插入文字，在 `RichTextBox` 里是插入富文本，在文件管理器里是复制文件。如果粘贴是一个自带逻辑的 `ICommand`，它就得知道所有可能的执行方式，这不可能。换成 `RoutedCommand`，每个控件自己在 `CommandBindings` 里提供自己的粘贴实现，命令本身不用关心谁怎么贴。控件的内置逻辑（如 `TextBox` 的复制粘贴）已经绑好了，你直接用就行。

后面 9.3 节会详细展开命令绑定和整个执行流程，这里先把 `RoutedCommand` 的设计动机吃透。

### 9.2.3 RoutedUICommand 类

`RoutedUICommand` 是 `RoutedCommand` 的子类。它只多加了一个东西：**`Text` 属性**。

```csharp
public class RoutedUICommand : RoutedCommand
{
    public string Text { get; set; }
    // 构造函数等省略
}
```

这个 `Text` 属性的作用是给命令一个**人类可读的名字**，比如“保存”、“复制”、“粘贴”。它本身不影响命令的任何执行逻辑，纯粹是为 UI 服务的——菜单项、按钮、状态栏提示等可以自动提取这个文字来显示，而不需要你手动在每个控件上都设一遍 `Content`。

WPF 内置的所有标准命令（`ApplicationCommands.Copy`、`NavigationCommands.Refresh` 等）全部是 `RoutedUICommand` 的实例，不是裸的 `RoutedCommand`。每个命令都有自己的 `Text`，比如：

- `ApplicationCommands.Copy.Text` → "Copy"
- `ApplicationCommands.Save.Text` → "Save"
- `EditingCommands.ToggleBold.Text` → "Bold"

当你在 XAML 里写 `<Button Command="ApplicationCommands.Copy" />` 时，按钮不仅会绑定命令的执行逻辑，还会**自动使用命令的 `Text` 作为按钮显示文字**（如果按钮自己没有设 `Content` 的话）。这就是为什么你有时候看到按钮只写了 `Command` 没写 `Content`，但按钮上却有文字——那是命令自带的 `Text`。

**你可以覆盖它**：如果你显式指定了 `Content="拷贝"`，按钮显示“拷贝”，而不是命令的默认 `Text`"Copy"。

**Text 和本地化**：`RoutedUICommand.Text` 是硬编码在 WPF 框架里的字符串（通常是英文）。如果你的程序要做多语言，这些内置文字需要覆盖。`RoutedUICommand` 本身不提供多语言机制，通常做法是在命令源上显式设置多语言文字，或者用自定义命令代替内置命令。这对于需要完美中文化的应用来说是一个需要留意的点。

#### RoutedUICommand vs RoutedCommand vs ICommand

现在可以画一张清晰的继承图了：

```
ICommand（接口：Execute / CanExecute / CanExecuteChanged）
  └─ RoutedCommand（通过路由事件沿树查找处理逻辑）
       └─ RoutedUICommand（多了 Text 属性，用于界面显示）
```

- `ICommand`：最纯粹的命令契约。
- `RoutedCommand`：利用路由机制，把执行逻辑外包给控件树上的命令绑定。
- `RoutedUICommand`：带显示文本的路由命令，WPF 内置命令都长这样。

你自定义的命令可以是这三者中的任何一个：
- 想要完全自定义逻辑且不需要路由分发 → 实现 `ICommand`（如 `RelayCommand`）。
- 想要利用路由机制在不同控件上分发执行 → 继承 `RoutedCommand` 或 `RoutedUICommand`（这种情况比较少见，因为路由命令通常只用于内置命令）。
- 实际项目里 95% 的自定义命令都是直接实现 `ICommand`（或 `RelayCommand`），因为它们是自己带逻辑的，不需要沿树分发。

### 9.2.4 命令库

WPF 在五个静态类里集中提供了大量预置的 `RoutedUICommand` 实例。这些静态类的属性就是一个个命令对象，你可以直接在 XAML 和代码里使用。

#### 五大命令库

**1. ApplicationCommands**

最常用的应用程序级别命令。包括：
- 文档操作：`New`（新建）、`Open`（打开）、`Save`（保存）、`SaveAs`（另存为）、`Close`（关闭）、`Print`（打印）、`PrintPreview`（打印预览）。
- 剪贴板操作：`Cut`（剪切）、`Copy`（复制）、`Paste`（粘贴）。
- 编辑操作：`Undo`（撤销）、`Redo`（重做）、`Delete`（删除）、`SelectAll`（全选）。
- 查找操作：`Find`（查找）、`Replace`（替换）。
- 其他：`Help`（帮助）、`Properties`（属性）、`Stop`（停止）。

每一个都是 `RoutedUICommand` 的实例。你可以在任何地方使用它们，而底层处理逻辑由聚焦的元素提供（或由你手动绑定提供）。

**2. NavigationCommands**

页面导航相关，用于 XAML 浏览器应用（XBAP）或独立 WPF 应用的页间跳转：
- `BrowseBack`（后退）、`BrowseForward`（前进）、`BrowseHome`（主页）、`BrowseStop`（停止浏览）。
- `NextPage`（下一页）、`PreviousPage`（上一页）、`FirstPage`（第一页）、`LastPage`（最后一页）。
- `Refresh`（刷新）、`Search`（搜索）。

桌面应用中用得比较少，主要服务于 `Frame` 和 `Page` 的导航功能。

**3. EditingCommands**

文本编辑控件专用，主要是 `RichTextBox`：
- 字体格式：`ToggleBold`（加粗）、`ToggleItalic`（斜体）、`ToggleUnderline`（下划线）。
- 对齐：`AlignLeft`、`AlignCenter`、`AlignRight`、`AlignJustify`。
- 段落格式：`IncreaseIndentation`、`DecreaseIndentation`。
- 列表：`ToggleBullets`、`ToggleNumbering`。
- 其他：`ToggleSubscript`、`ToggleSuperscript` 等。

这些命令大多数在 `RichTextBox` 中有内置的命令绑定，直接用就行。

**4. ComponentCommands**

用于标准组件行为，比如列表的上下移动：
- `MoveUp`、`MoveDown`、`MoveLeft`、`MoveRight`。
- `SelectToEnd`、`SelectToHome`、`SelectToPageUp`、`SelectToPageDown`。
- `ScrollPageUp`、`ScrollPageDown`、`ScrollToEnd`、`ScrollToHome`。

一部分列表类和滚动类控件内置了对这些命令的绑定。

**5. MediaCommands**

多媒体播放控制：
- `Play`（播放）、`Pause`（暂停）、`Stop`（停止）。
- `NextTrack`（下一曲）、`PreviousTrack`（上一曲）。
- `IncreaseVolume`（增大音量）、`DecreaseVolume`（减小音量）、`MuteVolume`（静音）。
- `TogglePlayPause`（切换播放/暂停）。

这些命令通常结合 `MediaElement` 控件使用。不过 `MediaElement` 本身并没有内置这些命令的绑定，你需要手动添加命令绑定来桥接命令和播放器。

#### 命令库的静态属性使用方式

在 XAML 中，直接引用静态属性：

```xml
<Button Command="ApplicationCommands.Save" Content="保存" />
<MenuItem Command="ApplicationCommands.Copy" />
<KeyBinding Key="S" Modifiers="Control" Command="ApplicationCommands.Save" />
```

在代码中：

```csharp
// 直接调用命令的 Execute
ApplicationCommands.Save.Execute(null, this);

// 或者订阅路由事件做命令绑定
this.CommandBindings.Add(new CommandBinding(
    ApplicationCommands.Save,
    (s, e) => { /* 保存逻辑 */ },
    (s, e) => { e.CanExecute = true; }
));
```

#### 命令库中命令的默认输入手势

许多内置命令自带了默认的输入手势（如 `Ctrl+C` 对应复制），这些手势在 `RoutedCommand.InputGestures` 集合里定义。当你把命令绑定加到窗口上时，这些手势自动生效，不需要额外写 `KeyBinding`。

## 9.2 节总结

9.2 节把 WPF 命令模型的底层实现拆了一遍：

**ICommand 接口**：
- WPF 所有命令的根接口。三个成员：`Execute`（执行逻辑）、`CanExecute`（是否可用）、`CanExecuteChanged`（状态变化通知）。
- 实现 `ICommand` 是自定义命令最常用的方式。`RelayCommand` 是实际项目中最流行的实现模式。
- `CanExecuteChanged` 可通过嫁接给 `CommandManager.RequerySuggested` 来简化，但需注意性能。

**RoutedCommand 类**：
- 实现了 `ICommand`，但不自带执行逻辑。它利用 WPF 的路由事件机制，把 `Execute` 和 `CanExecute` 作为冒泡事件在控件树上传播。
- 控件需要通过 `CommandBindings` 来为路由命令提供实际的 `Executed` 和 `CanExecute` 处理程序。
- 好处是同一命令可以沿树分发，不同控件可以提供不同的处理逻辑。
- 输入手势（如 `Ctrl+C`）通过 `InputGestures` 集合管理。

**RoutedUICommand 类**：
- `RoutedCommand` 的子类，额外增加 `Text` 属性——命令的人类可读名称。
- WPF 内置的五类标准命令全部是 `RoutedUICommand` 实例。
- 支持本地化（内置文本为英文，需手动覆盖或自定义文字）。

**命令库**：
- 五个静态类提供预置命令：`ApplicationCommands`（文档、剪贴板、编辑）、`NavigationCommands`（页面导航）、`EditingCommands`（文本格式）、`ComponentCommands`（组件操作）、`MediaCommands`（多媒体）。
- 可直接在 XAML 或代码中引用这些 `RoutedUICommand` 实例，配合命令绑定或依赖已有控件内置的绑定直接使用。

理解了这三个接口/类和五个命令库，你就抓住了 WPF 命令系统的骨架。下一节 9.3 会深入“执行命令”的完整流程——命令源怎么触发命令、命令绑定怎么桥接逻辑、多命令源怎么协调、命令文本怎么微调、怎么禁用命令等等。有了本节的类型基础，那些内容就能畅通无阻地推进了。
