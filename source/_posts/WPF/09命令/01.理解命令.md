# 笔记41《命令》9.1节——理解命令

## 9.1 理解命令

前面第 5 章你学了路由事件，知道了 WPF 怎么处理用户的鼠标点击、键盘按键。第 8 章你学了数据绑定，知道了怎么把后台数据的属性自动同步到界面上。这两个东西你都会了，那做一个小功能应该没问题了吧？

比如做一个“保存”按钮，点击后把文本框里的内容存到文件。你可以怎么写？

**传统做法**：在 XAML 里拖一个 `Button`，设 `Click="SaveButton_Click"`，然后在代码隐藏里写：

```csharp
private void SaveButton_Click(object sender, RoutedEventArgs e)
{
    string content = myTextBox.Text;
    File.WriteAllText("data.txt", content);
    statusBar.Text = "已保存";
}
```

这个做法能用，但它有三个问题：

**问题一：代码和界面耦合太死。** 这段逻辑只能由这个按钮触发。如果你还想通过菜单栏的“保存”菜单项、工具栏上的保存图标、或者快捷键 `Ctrl+S` 来执行同样的操作，你就得把这段逻辑复制三份，或者在不同的事件处理里互相调用。按钮一改名、菜单项一删除，代码就得跟着改。

**问题二：启用/禁用状态不好管。** 如果文本框是空的，保存没意义，你希望“保存”按钮自动变灰禁用。这需要你在 `TextBox.TextChanged` 事件里判断文字是否为空，然后设置 `saveButton.IsEnabled = !string.IsNullOrEmpty(myTextBox.Text)`。如果有三个入口（按钮、菜单、工具栏），每个都要禁用/启用，代码到处飞。

**问题三：快捷键不好做。** 你想让 `Ctrl+S` 触发保存，就得在窗口上挂 `KeyDown` 事件，判断 `e.Key == Key.S && Keyboard.Modifiers == ModifierKeys.Control`，然后调保存逻辑。窗口一多，快捷键管理就像面条一样纠缠。

**WPF 的命令机制，就是为解决这三个问题而设计的。** 它把用户的“操作意图”（我想保存）从具体的“触发方式”（按钮、菜单、快捷键）里抽象出来，变成一个独立的**命令对象**。命令对象封装了：

- **要干什么**（执行的代码）
- **现在能不能干**（是否可用的判断逻辑）
- **和什么关联**（快捷键、手势）

然后，按钮、菜单项、工具栏按钮、快捷键绑定，都可以指向同一个命令对象。这样你只需要在命令对象里写一次逻辑，所有入口自动共用。而且命令对象能自动通知所有绑定的控件“我现在不可用了，你们自己灰掉吧”，不需要写一堆 `IsEnabled` 的控制代码。

这就是“命令”的核心思想：**把用户的动作抽象成命令，和触发它的界面元素完全解耦。**

---

### 9.1.1 从事件到命令的思维转变

在传统的面向事件编程里，你的思维是线性的：

1. 用户在按钮上点了鼠标。
2. `Click` 事件触发。
3. 事件处理程序执行一段代码。

这是**由外向内**的——界面上的某个东西发生了，你去响应它。按钮代码知道一切：它知道文本框在哪（`myTextBox`），知道要写文件，知道要更新状态栏。

在命令模式里，你的思维是反过来的：

1. 定义一个“保存命令”，它不关心谁来触发它。它只知道“我可以执行的条件是文本框不为空”，“我执行的时候会写文件和更新状态”。
2. 按钮、菜单、快捷键，都去绑定这个命令。
3. 命令自己监控条件变化（比如文本框的文字变了），自动通知所有绑定的控件要不要灰掉。

这是**由内向外**的——核心逻辑定义了它自己的行为规则，界面元素只是这个规则的触发器和展示器。

**一个简单的类比**：

- 传统事件 = 你家的灯和开关是焊死的。开关一按，灯的电路接通，亮了。你想再加一个遥控器来控制同一盏灯，得重新布线。
- 命令 = 你家的灯有一个“开/关”的指令接口。墙壁开关发出“开”指令，遥控器发出“开”指令，手机 App 发出“开”指令。灯自己不管是谁发的指令，只要收到“开”就亮。而且灯还能告诉所有开关“我现在已经亮了，你再按‘开’没意义了”。

### 9.1.2 命令的四个核心角色

WPF 的命令模型有四个关键角色，它们各司其职：

**角色一：命令本身（Command）**

命令就是一个对象，它实现了 `ICommand` 接口。它定义了：

- **`Execute(object parameter)` 方法**：命令真正执行时要做什么。这是“保存文件”的具体代码。
- **`CanExecute(object parameter)` 方法**：返回 `bool`，表示命令当前能不能执行。“文本框为空时不能保存”的判断就写在这里。
- **`CanExecuteChanged` 事件**：当能/不能执行的状态发生变化时触发。WPF 的控件会监听这个事件，自动更新自己的 `IsEnabled` 状态。

命令对象本身不关心是谁触发了它，也不关心执行结果反映到哪个控件上。它只负责“我干什么”和“我能不能干”。

**角色二：命令源（Command Source）**

命令源是**触发命令的那个东西**——按钮、菜单项、输入绑定（快捷键）。任何实现了 `ICommandSource` 接口的控件都可以成为命令源。`Button`、`MenuItem`、`ToggleButton`、`RadioButton` 等自带 `Command` 属性（这是它们的公共属性，类型是 `ICommand`），你把命令对象赋给它，它就自动成为命令源。

当用户点击按钮时，按钮内部调用 `command.Execute(parameter)`。同时，按钮会自动监听 `command.CanExecuteChanged` 事件，随时更新自己的 `IsEnabled`。

**角色三：命令目标（Command Target）**

命令目标是**命令要在谁身上执行**。比如“复制”命令的目标是 `TextBox`——把哪个文本框选中的文字复制到剪贴板。命令目标通常是由聚焦的元素自动决定的，但也可以显式指定。

**角色四：命令绑定（Command Binding）**

命令绑定把**命令对象**和**执行逻辑**桥接起来。这是 WPF 特有的一个中间层。有些命令（比如 WPF 内置的剪切、复制、粘贴、撤销、重做）本身只有定义（像是一个接口声明），真正的执行逻辑在不同的控件里是不一样的。比如“粘贴”命令在文本框里是插入文字，在图片编辑器里是插入图片。这种“同一命令，不同控件有不同执行逻辑”的需求，就是靠命令绑定来完成的。

后面 9.2 和 9.3 节会详细拆解这四个角色，这里先建立起整体框架。

### 9.1.3 命令 vs 路由事件 vs 数据绑定

这三个东西长得有点像，都是 WPF 响应变化的机制，但它们的分工非常明确，一张表就能看清楚：

| 特性 | 路由事件 | 数据绑定 | 命令 |
|------|---------|---------|------|
| 干什么 | 通知“发生了什么” | 传递“数据是什么” | 表达“要做什么” |
| 关注点 | 鼠标、键盘、触控的物理事件 | 属性值的数据同步 | 用户的操作意图 |
| 方向 | 沿控件树上下传播 | 从源到目标（或双向） | 从命令源到命令目标 |
| 典型例子 | `MouseLeftButtonDown` | `{Binding Path=Name}` | `ApplicationCommands.Save` |

- **路由事件**处理的是用户和设备**怎么触碰**了界面。
- **数据绑定**处理的是界面控件和后台数据**怎么保持同步**。
- **命令**处理的是用户的**操作意图**——不是“鼠标按下了”，而是“用户想保存”。

它们三个是协同作战的关系：
- 用户在按钮上点了鼠标（路由事件 `Click`）→ 按钮触发绑定的命令（`command.Execute`）→ 命令执行时可能更新数据模型 → 数据绑定自动把新数据反映到界面上。

这是一个完整的从“物理输入”到“逻辑操作”到“数据刷新”的链条。

### 9.1.4 内置命令和自定义命令

WPF 预置了很多常用命令，放在几个静态类里，你不需要自己写：

- **`ApplicationCommands`**：应用程序常用的命令。如 `New`（新建）、`Open`（打开）、`Save`（保存）、`SaveAs`（另存为）、`Close`（关闭）、`Cut`（剪切）、`Copy`（复制）、`Paste`（粘贴）、`Undo`（撤销）、`Redo`（重做）、`Print`（打印）、`Help`（帮助）等。
- **`NavigationCommands`**：页面导航相关。如 `BrowseBack`、`BrowseForward`、`Refresh`、`Search` 等。
- **`EditingCommands`**：文本编辑相关。如 `ToggleBold`、`ToggleItalic`、`AlignLeft`、`AlignCenter` 等。
- **`ComponentCommands`**：组件相关。如 `MoveUp`、`MoveDown`、`SelectAll`、`ScrollPageUp` 等。
- **`MediaCommands`**：媒体控制。如 `Play`、`Pause`、`Stop`、`NextTrack`、`PreviousTrack`、`IncreaseVolume` 等。

这些内置命令大部分是**路由命令（RoutedCommand）**，它们的行为和路由事件很像——沿控件树冒泡，由命中了命令绑定的元素来处理。后面 9.2 节会深入讲 `RoutedCommand`。

你当然也可以创建自己的命令。自定义命令通常是实现 `ICommand` 接口的普通类，或者使用 `RelayCommand` / `DelegateCommand` 这样的现成包装（MVVM 框架里很常见）。

### 9.1.5 一个简单的命令实例（感性认识）

在讲一大堆概念之前，先用一个短小的例子看看命令长什么样。这个例子用 WPF 内置的 `ApplicationCommands.Copy` 命令，不需要你写任何执行逻辑。

```xml
<Window x:Class="CommandDemo.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="命令示例">
    <StackPanel>
        <TextBox x:Name="myTextBox" Height="100" AcceptsReturn="True" />
        <Button Command="ApplicationCommands.Copy" 
                CommandTarget="{Binding ElementName=myTextBox}" 
                Content="复制" />
    </StackPanel>
</Window>
```

运行效果：
- 你在 `TextBox` 里选中一段文字，点击“复制”按钮，选中的文字就进了剪贴板。
- 如果没选中任何文字，“复制”按钮自动变灰（禁用状态）。
- 你不需要写一行 C# 代码来处理 `Click` 事件，不需要手动判断文字是否选中。

为什么按钮会自动变灰？因为 `ApplicationCommands.Copy` 这个内置命令，它的 `CanExecute` 逻辑会检查当前是否有文字被选中。按钮作为命令源，自动监听 `CanExecuteChanged`，当选中状态变化时，按钮的 `IsEnabled` 自动跟着变。

`CommandTarget="{Binding ElementName=myTextBox}"` 显式指定了命令的目标是这个 `TextBox`。如果不指定，命令目标默认是当前焦点所在的元素（也是这个 `TextBox`），所以这里写和不写效果一样，但显式指定更清晰。

### 9.1.6 命令在 WPF 架构中的位置

命令不是凭空出现的，它依托于你前面学过的依赖项属性和路由事件：

- **命令的基础设施**：`ICommand` 接口的 `CanExecuteChanged` 事件，本质上就是一个普通的 .NET 事件。WPF 通过事件机制来监听命令状态的变化。
- **命令和路由机制的结合**：WPF 的内置命令（如剪切、复制、粘贴）是路由命令（`RoutedCommand`）。它们利用了路由事件的冒泡和隧道机制——命令从命令源出发，沿控件树向上冒泡，沿途寻找绑定了处理该命令的命令绑定。这和路由事件的冒泡机制如出一辙。
- **命令和目标属性**：`Button.Command`、`MenuItem.Command` 都是依赖项属性。这意味着你可以在 XAML 里用绑定来动态切换命令，也可以在样式里统一设置。

所以，命令这一章不是孤立的，它是路由事件（第5章）和依赖项属性（第4章）之上的一个高层抽象。它把物理事件翻译成逻辑指令，把界面控制的复杂度封装在命令对象内部。

## 9.1 节总结

9.1 节是命令这一章的思想入门，要记住的核心概念就这几个：

**命令要解决的问题**：
- 传统事件方式的三个痛点：逻辑绑定具体控件（无法复用）、启用/禁用状态不好管、快捷键难维护。
- 命令把“操作意图”抽象成一个独立对象，和触发方式完全解耦。

**命令的四个核心角色**：
- **命令**：`ICommand` 对象，定义“做什么”（Execute）和“能不能做”（CanExecute）。
- **命令源**：按钮、菜单等，触发命令。
- **命令目标**：命令在谁身上执行（比如复制哪个文本框的文字）。
- **命令绑定**：把命令的定义和实际的执行逻辑桥接起来（特别适用于内置路由命令）。

**命令 vs 路由事件 vs 数据绑定**：
- 路由事件通知“发生了什么”，命令表达“要做什么”，数据绑定传递“数据是什么”。三者协同。

**内置命令**：
- WPF 预置了大量常用命令（复制、粘贴、撤销、打开、保存等），放在 `ApplicationCommands`、`EditingCommands` 等静态类里。

**从事件到命令的思维转变**：
- 事件是“由外向内”的响应，命令是“由内向外的”规则定义。
- 命令让界面逻辑从“代码隐藏”向“可绑定、可测试的命令对象”进化，为 MVVM 铺路。

这一节是给你建立命令的“世界观”的。下一节 9.2 会深入 WPF 命令模型的实现细节——`ICommand` 接口到底长什么样，`RoutedCommand` 怎么利用路由机制，命令库提供了哪些现成的东西。你带着“为什么需要命令”和“四个角色”这两个框架进去，每一个技术细节就能立刻对号入座。
