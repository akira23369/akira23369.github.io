# 笔记44《命令》9.4节——高级命令

## 9.4 高级命令

前三节你已经把 WPF 命令模型的基础设施全搞清楚了：命令是什么、ICommand 接口怎么实现、RoutedCommand 怎么利用路由机制、命令源怎么触发命令、命令绑定怎么桥接逻辑。这些是“标准动作”——用 WPF 内置的复制、粘贴、撤销，或者自己写一个 RelayCommand，都顺理成章。

但真实项目里的需求往往比标准动作更复杂。这一节就是来应对那些“非标准”场景的：

- 你不满足于只用内置命令，想从零创造一个完全自定义的命令（**9.4.1**）。
- 同一个命令在界面的不同地方要执行不同的逻辑（比如两个“粘贴”按钮，一个贴文字，一个贴图片）（**9.4.2**）。
- 命令需要带参数来区分不同的上下文（比如“打开文件”命令要知道打开哪个文件）（**9.4.3**）。
- 命令的执行状态需要被跟踪，或者需要做一个“切换”型的命令（比如“静音/取消静音”）（**9.4.4**）。

下面逐个击破。

---

### 9.4.1 自定义命令

WPF 提供了五组内置命令（ApplicationCommands、EditingCommands 等），覆盖了很多常见场景。但你的业务逻辑里一定会有 WPF 没帮你提前定义好的操作——比如“同步数据”、“生成报表”、“批量审批”、“导出 PDF”。这些都需要你自己创建命令对象。

自定义命令有三种路径，各有适用场景。

#### 路径一：实现 ICommand 接口（最常用、最灵活）

这是 9.2.1 节详细讲过的。你自己写一个类，实现 `ICommand` 的三个成员（`Execute`、`CanExecute`、`CanExecuteChanged`）。

**手工实现版**：

```csharp
public class ExportPdfCommand : ICommand
{
    private readonly DocumentViewModel _viewModel;

    public ExportPdfCommand(DocumentViewModel viewModel)
    {
        _viewModel = viewModel;
    }

    public bool CanExecute(object parameter)
    {
        // 只有文档不为空时才能导出
        return _viewModel.CurrentDocument != null;
    }

    public void Execute(object parameter)
    {
        // 导出逻辑
        PdfExporter.Export(_viewModel.CurrentDocument);
    }

    public event EventHandler CanExecuteChanged
    {
        add { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }
}
```

**RelayCommand 版（实战中最常用）**：

你在 ViewModel 里不用每次写一个新类，用泛型委托包装：

```csharp
public class RelayCommand : ICommand
{
    private readonly Action<object> _execute;
    private readonly Predicate<object> _canExecute;

    public RelayCommand(Action<object> execute, Predicate<object> canExecute = null)
    {
        _execute = execute ?? throw new ArgumentNullException(nameof(execute));
        _canExecute = canExecute;
    }

    public bool CanExecute(object parameter) 
        => _canExecute == null || _canExecute(parameter);

    public void Execute(object parameter) 
        => _execute(parameter);

    public event EventHandler CanExecuteChanged
    {
        add { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }
}
```

在 ViewModel 里创建命令：

```csharp
public class DocumentViewModel
{
    public ICommand ExportPdfCommand { get; }

    public DocumentViewModel()
    {
        ExportPdfCommand = new RelayCommand(
            execute: p => PdfExporter.Export(this.CurrentDocument),
            canExecute: p => this.CurrentDocument != null
        );
    }

    // 当 CurrentDocument 变化时，手动通知命令状态刷新
    private Document _currentDocument;
    public Document CurrentDocument
    {
        get => _currentDocument;
        set
        {
            _currentDocument = value;
            OnPropertyChanged();
            // 如果用的是 RelayCommand，CommandManager.RequerySuggested 
            // 可能不会自动触发。更稳妥的做法是自己暴露一个 RaiseCanExecuteChanged 
            // 方法，在这里手动调。
        }
    }
}
```

**注意**：`CommandManager.RequerySuggested` 的自动触发依赖于 UI 输入事件（鼠标移动、键盘敲击等）。如果你的命令状态变化是由纯数据属性更改引起的（比如从数据库加载完毕、网络状态改变），`CommandManager.RequerySuggested` 不会自动触发。这时你有两种选择：

1. 手动调用 `CommandManager.InvalidateRequerySuggested()` 强制全局刷新。
2. 在自定义命令里自己暴露 `RaiseCanExecuteChanged()` 方法，在 ViewModel 属性变化时手动触发。

业界更推荐第二种，因为它更精准，性能开销小。

```csharp
public class RelayCommand : ICommand
{
    // ...
    public void RaiseCanExecuteChanged()
    {
        CanExecuteChanged?.Invoke(this, EventArgs.Empty);
    }
}
```

```csharp
public Document CurrentDocument
{
    set 
    { 
        _currentDocument = value; 
        OnPropertyChanged();
        ((RelayCommand)ExportPdfCommand).RaiseCanExecuteChanged();
    }
}
```

#### 路径二：继承 RoutedCommand（需要路由分发时）

如果你想创建一个和 WPF 内置命令一样、能沿控件树冒泡并由不同控件提供不同处理逻辑的命令，你就需要继承 `RoutedCommand`（或 `RoutedUICommand`）。

这种场景比较少见，通常在你写自定义控件库，并且希望给用户留下“可以自己写命令绑定来扩展行为”的钩子时才会用。

```csharp
public class MyCustomCommands
{
    public static readonly RoutedUICommand RefreshData = 
        new RoutedUICommand("刷新数据", "RefreshData", typeof(MyCustomCommands));
}
```

然后使用方式和内置命令完全一样——在某个控件上加 `CommandBinding`，在命令源上引用这个命令。

```xml
<Window.CommandBindings>
    <CommandBinding Command="local:MyCustomCommands.RefreshData" 
                    Executed="RefreshData_Executed" />
</Window.CommandBindings>

<Button Command="local:MyCustomCommands.RefreshData" Content="刷新" />
```

**什么时候用 `RoutedCommand`？** 当命令的行为不是由命令本身决定的，而是由“命令目标”或“命令目标所在的控件树上下文”决定的。比如你自定义了一个“删除”命令，希望它在文件列表里删文件，在邮件列表里删邮件，在任务列表里删任务——这就需要沿树分发，由各自控件去处理。

#### 路径三：使用现有 MVVM 框架的命令类

几乎每个 MVVM 框架（Prism、MVVM Light、CommunityToolkit.Mvvm 等）都提供了比裸 RelayCommand 更强大的命令类。有的支持异步执行（`AsyncRelayCommand`），有的支持自动管理 `CanExecute`，有的支持取消。实际项目中，你很少需要自己写 `ICommand` 的实现——框架已经帮你写好了。

**CommunityToolkit.Mvvm 的示例**（微软官方推荐）：

```csharp
[RelayCommand]
private async Task SaveAsync()
{
    await File.WriteAllTextAsync("data.txt", this.Content);
}
```

一个特性就搞定一个命令，无需手动 new 任何东西。

### 9.4.2 在不同位置使用相同的命令

同一个命令对象，可以被多个命令源引用——这在 9.3.3 节已经演示过了。工具栏按钮和菜单项可以共享同一个 `SaveCommand`。

但这一小节要讨论的是更微妙的情况：**同一个命令，在不同的“位置”需要有不同的行为。** 比如你的界面上有两个独立的文本编辑区域（一个是邮件正文编辑器，一个是签名编辑器）。两个编辑器上面都有一个“粘贴”按钮。你希望第一个按钮把剪贴板内容贴到正文里，第二个按钮贴到签名里。

**怎么做？**

**方法一：不同的命令绑定，挂在不同层级**

两个“粘贴”按钮都用 `ApplicationCommands.Paste` 命令。但你把命令绑定挂在不同的父容器上，各自覆盖行为：

```xml
<!-- 邮件正文区域 -->
<GroupBox Header="正文">
    <GroupBox.CommandBindings>
        <CommandBinding Command="ApplicationCommands.Paste" 
                        Executed="PasteToBody_Executed" />
    </GroupBox.CommandBindings>
    <TextBox x:Name="bodyTextBox" />
</GroupBox>

<!-- 签名区域 -->
<GroupBox Header="签名">
    <GroupBox.CommandBindings>
        <CommandBinding Command="ApplicationCommands.Paste" 
                        Executed="PasteToSignature_Executed" />
    </GroupBox.CommandBindings>
    <TextBox x:Name="signatureTextBox" />
</GroupBox>
```

当焦点在正文文本框时，点击粘贴按钮，命令冒泡先经过正文的 `GroupBox`，找到了第一个绑定，执行 `PasteToBody_Executed`。焦点在签名框时，同理执行第二个绑定。

**方法二：使用命令参数区分**

同一个命令绑定里，根据命令参数做不同的逻辑：

```xml
<Button Command="ApplicationCommands.Paste" CommandParameter="Body" Content="贴到正文" />
<Button Command="ApplicationCommands.Paste" CommandParameter="Signature" Content="贴到签名" />
```

```csharp
private void Paste_Executed(object sender, ExecutedRoutedEventArgs e)
{
    string target = e.Parameter as string;
    if (target == "Body")
        bodyTextBox.Paste();
    else if (target == "Signature")
        signatureTextBox.Paste();
}
```

**方法三：不同的命令实例**

其实最直接的方式就是：**不用同一个命令对象，创建两个独立的自定义命令。** 每个按钮绑定自己的命令，各管各的。除非这两个操作在语义上确实是“同一种操作”（都是粘贴），只是目标不同，才考虑共用一个命令。很多时候硬要让不同行为的控件共享同一个命令是过度设计了。

**原则**：命令共享适合“同一操作的不同入口”（工具栏+菜单+快捷键）。不适合“不同操作碰巧长得像”——这时候应该用不同的命令对象。

### 9.4.3 使用命令参数

命令参数（`CommandParameter`）是命令模型里非常重要但经常被低估的一环。它让你在触发命令时可以携带额外的上下文信息。

#### 基本用法

命令源（按钮、菜单项等）通过 `CommandParameter` 属性指定参数：

```xml
<Button Command="ApplicationCommands.Open" 
        CommandParameter="C:\Documents\report.docx" 
        Content="打开报告" />
```

在命令的 `Execute` 和 `CanExecute` 中，`parameter` 参数就是这个值：

```csharp
private void Open_Executed(object sender, ExecutedRoutedEventArgs e)
{
    string filePath = e.Parameter as string;
    if (!string.IsNullOrEmpty(filePath))
    {
        Process.Start(filePath);
    }
}

private void Open_CanExecute(object sender, CanExecuteRoutedEventArgs e)
{
    string filePath = e.Parameter as string;
    e.CanExecute = File.Exists(filePath);
}
```

#### 常见的传参场景

**场景一：数据列表中的“删除”按钮**

在一个列表里，每一项旁边都有一个删除按钮。按钮的 `CommandParameter` 绑定到当前项的数据对象：

```xml
<ListBox ItemsSource="{Binding Users}">
    <ListBox.ItemTemplate>
        <DataTemplate>
            <StackPanel Orientation="Horizontal">
                <TextBlock Text="{Binding Name}" />
                <Button Content="删除" 
                        Command="{Binding DataContext.DeleteUserCommand, 
                                  RelativeSource={RelativeSource FindAncestor, 
                                  AncestorType={x:Type Window}}}"
                        CommandParameter="{Binding}" />
            </StackPanel>
        </DataTemplate>
    </ListBox.ItemTemplate>
</ListBox>
```

这里的 `CommandParameter="{Binding}"` 意思就是把当前列表项的数据对象（如一个 `User` 对象）作为参数传过去。ViewModel 中的删除命令：

```csharp
DeleteUserCommand = new RelayCommand(
    execute: p => {
        var user = p as User;
        this.Users.Remove(user);
    },
    canExecute: p => p is User
);
```

**场景二：用一个命令处理多个按钮**

比如一个计算器面板，数字按钮 0~9 都触发同一个命令，参数传数字：

```xml
<Button Content="1" Command="{Binding NumberCommand}" CommandParameter="1" />
<Button Content="2" Command="{Binding NumberCommand}" CommandParameter="2" />
<!-- ... -->
```

```csharp
NumberCommand = new RelayCommand(
    execute: p => this.Display += p.ToString()
);
```

**场景三：菜单项根据上下文传不同参数**

右键上下文菜单中，同一命令根据右键点击的位置传不同参数：

```xml
<ListBox>
    <ListBox.ContextMenu>
        <ContextMenu>
            <MenuItem Header="复制" 
                      Command="ApplicationCommands.Copy"
                      CommandParameter="{Binding RelativeSource={RelativeSource AncestorType={x:Type ContextMenu}}, 
                                         Path=PlacementTarget.SelectedItem}" />
        </ContextMenu>
    </ListBox.ContextMenu>
</ListBox>
```

这里通过 `PlacementTarget` 找到右键点击的那个 `ListBox`，再取它的 `SelectedItem` 作为参数。

#### 参数的类型是 object

`CommandParameter` 的类型是 `object`（它的依赖项属性类型就是 `object`），所以你可以传任何东西——字符串、数值、数据对象、甚至整个集合。但这也意味着你在接收端要做好类型检查和转换。

#### 参数和 CanExecute 的关系

`CanExecute` 也接收 `parameter`。你可以在“能否执行”的判断里利用参数信息。比如“打开文件”命令，参数路径指向的文件不存在就不要亮。

### 9.4.4 跟踪和翻转命令

有些命令不是一次性的，而是有**状态**的。最常见的两种：

- **跟踪型命令**：命令的执行状态需要被记录下来（比如撤销/重做栈）。
- **翻转型命令**：命令是一个开关，每次执行在不同的状态之间切换（比如“静音/取消静音”、“加粗/取消加粗”）。

#### 跟踪命令与撤销/重做

WPF 的 `ApplicationCommands.Undo` 和 `ApplicationCommands.Redo` 就是典型的跟踪型命令。它们本身不定义“撤销什么”——它们依赖于控件内部维护的撤销栈。

`TextBox` 和 `RichTextBox` 内置了完整的撤销/重做栈。每次用户输入、删除、粘贴，操作都被压入栈。当用户按 `Ctrl+Z`（触发 Undo 命令），`TextBox` 内部的 `Undo` 命令绑定从栈里弹出一个操作并回滚。

如果你想在自己的应用里实现“撤销/重做”，通常不是通过 WPF 的命令绑定机制，而是自己在数据层维护一个操作栈（比如 `IUndoableOperation` 列表），然后让你的 `UndoCommand` 和 `RedoCommand` 去操作这个栈。WPF 的内置 `ApplicationCommands.Undo` 只是一个触发器，真正的逻辑还得你写。

#### 翻转命令（Toggle Command）

很多命令是“开/关”性质的：粗体、斜体、静音、全屏。用户点击一次打开，再点一次关闭。

WPF 的 `ToggleButton`（和它的子类 `CheckBox`、`RadioButton`）天然适合做翻转命令的载体。`ToggleButton` 有一个 `IsChecked` 属性，你可以在命令的 `Execute` 里根据 `IsChecked` 的状态来决定行为。

但更常见的做法是：**让命令本身无状态，把状态维护在 ViewModel 里。** 翻转按钮的 `IsChecked` 绑定到 ViewModel 的 bool 属性，点击时命令切换这个属性的值。

```xml
<ToggleButton Content="静音" 
              IsChecked="{Binding IsMuted}" 
              Command="{Binding MuteCommand}" />
```

```csharp
MuteCommand = new RelayCommand(
    execute: p => { this.IsMuted = !this.IsMuted; }
);
```

或者更优雅的：不用命令，直接用数据绑定 + 属性的 setter 逻辑。翻转操作如果只是改一个 bool 值，完全不需要引入命令——直接绑定 `IsChecked` 到属性，在属性的 setter 里写业务逻辑就行。命令更适合翻转操作还需要带参数或者涉及多步骤复杂逻辑的场景。

**WPF 内置翻转命令**：`EditingCommands.ToggleBold`、`ToggleItalic`、`ToggleUnderline` 等就是翻转命令。它们会根据 `RichTextBox` 当前选中文本的状态，决定是“加粗”还是“取消加粗”。这个逻辑是在 `RichTextBox` 内部的命令绑定里实现的，对用户透明。

#### 跟踪命令源的选中状态

有时候你需要知道“当前是否有 ToggleButton 处于选中状态”。比如工具栏上的“粗体”按钮应该在光标处于粗体文本时自动显示按下状态。WPF 通过 `ToggleButton.IsChecked` 的绑定和 `CommandBinding` 里的 `CanExecute` 配合，可以实现这种同步。由于涉及控件模板和命令绑定的深层交互，这通常是 WPF 富文本编辑器控件内部已经封装好的行为。

## 9.4 节总结

9.4 节把命令模型从“用好内置”推到了“自定义一切”的级别：

**自定义命令（9.4.1）**：
- 三条路径：实现 `ICommand`（最常用，RelayCommand 是标准做法）、继承 `RoutedCommand`（需要路由分发时）、使用 MVVM 框架的命令类。
- 注意 `CanExecuteChanged` 的触发：`CommandManager.RequerySuggested` 只对 UI 事件敏感，数据驱动的状态变化需要手动触发 `RaiseCanExecuteChanged` 或调用 `CommandManager.InvalidateRequerySuggested()`。

**在不同位置使用相同的命令（9.4.2）**：
- 不同层级挂不同的 `CommandBinding`，利用路由冒泡实现“同命令不同行为”。
- 通过 `CommandParameter` 区分上下文。
- 原则：语义上同一种操作才共享命令，不同操作应分开为不同命令实例。

**使用命令参数（9.4.3）**：
- `CommandParameter` 让命令源携带上下文信息。
- 典型场景：列表中每项带删除按钮（参数=该项数据）、数字面板（参数=数字）、右键菜单（参数=点击目标的数据）。
- 参数类型是 `object`，接收端需类型检查和转换。

**跟踪和翻转命令（9.4.4）**：
- 跟踪型命令（如 Undo/Redo）依赖内部状态栈，WPF 只提供触发机制，实际栈由你或控件维护。
- 翻转型命令（如静音、加粗）常用 `ToggleButton` 承载，状态维护建议放在 ViewModel 的 bool 属性里，用数据绑定同步，命令只负责触发切换或执行附带逻辑。

学完这一节，你对命令的掌控力已经从“会用现成的”升级到了“能自己设计命令体系来组织整个应用的交互逻辑”。命令这一章到这里全部结束。最后一节 9.5 是本章小结，会把所有知识点串成一张完整的命令体系脑图。
