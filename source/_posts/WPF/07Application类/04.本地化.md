# 笔记36《Application类》7.4节——本地化

## 7.4 本地化

学到这里，你的 WPF 程序已经有了布局、有了控件、有了资源、有了生命周期管理。但这个程序说哪种语言？如果你的界面上所有的文字都是硬编码的中文，那它就只能给中国人用。当你的软件要卖到美国、日本、德国时，你得让界面能自动切换成英文、日文、德文。这就是**本地化（Localization）**。

很多人把“本地化”和“国际化”混为一谈，这里先分清楚：

- **国际化（Internationalization，简称 i18n）**：在设计软件的时候就考虑到未来要支持多语言，把界面做得“容易翻译”。这主要是架构层面的事——不用硬编码字符串、布局能适应不同文字长度、日期数字格式能随文化变化。
- **本地化（Localization，简称 l10n）**：针对某一个具体的语言和地区（如“简体中文（中国）”、“英语（美国）”、“日语（日本）”），把界面上的文字翻译过去，调整布局让文字能完整显示，处理该地区特有的数字、货币、日期格式。

这一节 7.4 就是在讲 WPF 为本地化提供的一整套方案：怎么让你的界面能做本地化（7.4.1），怎么为翻译做准备（7.4.2），以及怎么组织和管理翻译过程（7.4.3）。

---

### 7.4.1 构建能够本地化的用户界面

在你写下第一行界面代码之前，就应该考虑“这段文字以后要翻译成别的语言，会不会出问题？”。如果你的界面用绝对布局（Canvas）把所有东西定死了位置，按钮的文字改成德文后比原来长了一倍，直接被截断或溢出到别的控件上——那你的界面就没有做好国际化的准备。这一小节讲的就是怎么从根上把界面做成“语言友好”的。

#### 本地化的四大问题

界面文字翻译时，会面临四个主要的“并发症”：

**问题一：文字长度变化。**

同一个意思，在不同语言里长度可以天差地别。比如中文“保存”就两字，英文 "Save" 四个字母，德文 "Speichern" 九个字母，法文 "Enregistrer" 十一个字母。如果你把一个按钮宽度写死了 50 像素，中文刚好，德文就会截半。

**问题二：文字方向变化。**

大部分语言是从左到右读，但阿拉伯语和希伯来语是从右到左读。如果你的界面布局假设了文字方向，在这两种语言下会完全乱掉。WPF 的 `FlowDirection` 属性可以轻松应对，后面会讲。

**问题三：控件尺寸和位置的变化。**

不只是按钮文字变长，标签、列表项、菜单项都可能变长。原本两列对齐的表单，当标签列最长项变长后，整列都会被撑宽，如果布局不够灵活，就会出现重叠或错位。

**问题四：区域格式差异。**

数字、货币、日期、时间的格式在不同地区完全不同。美国写 1,234.56，德国写 1.234,56（小数点变逗号，千位分隔符变点）。日期美国是月/日/年，英国是日/月/年。这些都不应该在你的代码里写死。

#### WPF 的五大本地化友好设计

好消息是，只要你按照前面第三章讲的布局原则来设计界面，你的界面天然就解决了大部分问题。WPF 在框架层面为本地化提供了五大支持：

**1. 自适应布局（Automatic Layout）**

这是第三章整章都在讲的核心哲学——别再像 Windows Forms 那样用绝对像素坐标和固定尺寸了。用 `StackPanel`、`DockPanel`、`Grid`（尤其是 `Auto` 和 `*` 尺寸），让按钮、标签、文本框的大小和位置完全由内容和容器动态决定。这样当文字变长时，控件自动变宽，其他控件自动让位，不会重叠。

**对比示例**：

坏的做法（固定宽度，本地化噩梦）：
```xml
<Button Content="保存" Width="50" />
```
中文没问题，德文直接只剩一半。

好的做法（自适应宽度，本地化友好）：
```xml
<Button Content="保存" Padding="10,5" />
```
按钮宽度由文字加内边距动态决定，中文按钮小，德文按钮大，一切自动。

**2. 网格和比例尺寸（Grid and Star Sizing）**

`Grid` 的 `*` 比例尺寸让各列按比例分配剩余空间。当某一列的标签文字变长后，该列会变宽，其他列自动缩小让位，保持比例关系。结合 `SharedSizeGroup` 能让多个独立区域的同类型列宽一致。

**3. FlowDirection（文字方向）**

WPF 的 `FrameworkElement.FlowDirection` 属性用来控制文字和布局的方向：

- `LeftToRight`（默认）：从左到右。
- `RightToLeft`：从右到左（用于阿拉伯语和希伯来语）。

这个属性是依赖项属性且支持**继承**——你只需要在根窗口上设一次 `FlowDirection="RightToLeft"`，整个界面的文字方向、控件对齐方式、甚至 `StackPanel` 的排列方向都会翻转。左侧的导航面板会自动移到右边，文字靠右对齐，一切都是镜像的。

```xml
<Window FlowDirection="RightToLeft">
    <!-- 整个窗口内容都是右到左布局 -->
</Window>
```

**注意**：`FlowDirection` 翻转的是**布局方向**，而不是文字的书写方向。文字的书写方向由字体和输入法决定，`FlowDirection` 只管面板的对齐和顺序。

**4. 内容控件和字符串资源分离**

WPF 内容模型让你可以在 XAML 里直接用 `Content="保存"`，但更好的做法是**永远不要在 XAML 里硬编码中文（或任何自然语言文字）**。应该把文字放在资源字典里，通过绑定或静态资源引用。这样翻译时只需要替换资源文件，不用改一行 XAML。

后面 7.4.2 会展开讲资源提取工具 `LocBaml` 来做这件事。

**5. 字体回退和复合字体**

WPF 支持 `FontFamily` 列出多个字体，按顺序查找。这让国际化应用的字体配置更容易——英文用 Segoe UI，中文用微软雅黑，日文用 Meiryo。你可以定义一个复合字体（Composite Font）把这些全部包在一起，界面不用针对每个语言改字体。

```xml
<TextBlock FontFamily="Segoe UI, Microsoft YaHei, Meiryo, sans-serif" 
           Text="Hello 你好 こんにちは" />
```

#### 一个本地化友好的界面实例

把上面的原则综合到一个小表单里：

```xml
<Window x:Class="LocalizedApp.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="{x:Static res:Strings.MainWindowTitle}" SizeToContent="WidthAndHeight">
    <Grid Margin="10">
        <Grid.ColumnDefinitions>
            <ColumnDefinition Width="Auto" SharedSizeGroup="LabelCol" />
            <ColumnDefinition Width="200" />
        </Grid.ColumnDefinitions>
        <Grid.RowDefinitions>
            <RowDefinition Height="Auto" />
            <RowDefinition Height="Auto" />
            <RowDefinition Height="Auto" />
            <RowDefinition Height="Auto" />
        </Grid.RowDefinitions>

        <TextBlock Grid.Row="0" Grid.Column="0" Text="{x:Static res:Strings.NameLabel}" 
                   VerticalAlignment="Center" Margin="0,0,10,5" />
        <TextBox Grid.Row="0" Grid.Column="1" Margin="0,0,0,5" />

        <TextBlock Grid.Row="1" Grid.Column="0" Text="{x:Static res:Strings.EmailLabel}" 
                   VerticalAlignment="Center" Margin="0,0,10,5" />
        <TextBox Grid.Row="1" Grid.Column="1" Margin="0,0,0,5" />

        <TextBlock Grid.Row="2" Grid.Column="0" Text="{x:Static res:Strings.PhoneLabel}" 
                   VerticalAlignment="Center" Margin="0,0,10,5" />
        <TextBox Grid.Row="2" Grid.Column="1" Margin="0,0,0,5" />

        <StackPanel Grid.Row="3" Grid.ColumnSpan="2" Orientation="Horizontal" 
                    HorizontalAlignment="Right" Margin="0,10,0,0">
            <Button Content="{x:Static res:Strings.SaveButton}" Margin="0,0,10,0" 
                    Padding="10,5" />
            <Button Content="{x:Static res:Strings.CancelButton}" Padding="10,5" />
        </StackPanel>
    </Grid>
</Window>
```

所有文字都是从资源类 `res:Strings` 引用的，没有硬编码。标签列用 `SharedSizeGroup` 保证不同组对齐，列宽 `Auto`，按钮 `Padding` 舒适。窗口 `SizeToContent="WidthAndHeight"` 让窗口大小完全跟随内容，不管翻译后文字多长都不会被截断。

### 7.4.2 使应用程序为本地化做好准备

上一小节讲了界面怎么设计才“好翻译”。这一小节讲的是具体的技术操作：**怎么把项目配置成可以产出多个语言版本**。

WPF 提供了一套基于**附属程序集（Satellite Assembly）**的本地化方案。核心思路是：

1. 所有的用户可见文字都用 XAML 的资源系统管理。
2. 翻译时把这些文字提取出来，生成对应语言的资源文件。
3. 每种语言编译成一个独立的附属程序集 dll。
4. 程序运行时，自动检测当前操作系统的语言，加载对应的附属程序集，文字就变过来。

**操作步骤**：

**第一步：标记 XAML 中需要本地化的元素**

在 XAML 文件（如 `MainWindow.xaml`）的根标签上添加命名空间声明，并添加一个特殊属性 `Uid`：

```xml
<Window x:Class="LocalizedApp.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:sys="clr-namespace:System;assembly=mscorlib"
        x:Uid="MainWindow">
    
    <Grid x:Uid="Grid_1">
        <Button x:Uid="Button_Save" Content="保存" />
    </Grid>
</Window>
```

每一个需要翻译的控件，都要加上一个**唯一的 `x:Uid`**。这些 Uid 是后续提取工具识别哪个文字属于哪个控件的依据。

**但是**手动给每个控件写 `Uid` 太痛苦了。Visual Studio 提供一个快捷方式：在解决方案资源管理器中，打开你要本地化的 XAML 文件，在编辑器中右键 → “打开方式” → 选择“带编码的 XML 编辑器”或者直接使用 VS 扩展。对于标准做法，WPF SDK 提供了一个叫 **`updateuid`** 的 MSBuild 任务，可以自动给所有未设 `Uid` 的元素生成一个唯一的 Uid。你可以通过 Visual Studio 的开发者命令行运行：

```
msbuild /t:updateuid MyProject.csproj
```

这会在每个控件的身上自动添加 `x:Uid="自动生成的ID"`。

**第二步：提取本地化信息到 CSV 文件**

微软提供了 **LocBaml** 这个工具，它是一个命令行程序，能把编译好的程序集中的本地化字符串提取成 CSV 文件。

LocBaml 不是 Visual Studio 自带的，需要从 WPF 示例项目中获取源代码编译，或者网上找预编译版本。使用方式：

```
LocBaml /parse MyApp.resources.dll /out:MyApp.csv
```

生成的 CSV 文件有四列：
1. 资源键（Baml 名称，内部用）
2. 控件的 Uid
3. 属性名（如 `Content`、`Text`、`Header`）
4. 原始值（也就是你 XAML 里写的中文文字）

这个 CSV 就是你要交给翻译人员去翻译的文件。

**第三步：翻译 CSV**

把 CSV 文件发给翻译人员。他们只需要修改第四列的值（比如把中文改成英文），其他列不动。

翻译完的 CSV 文件，给每一列加上对应的语言标识。比如英文翻译为 `MyApp_en-US.csv`，日文为 `MyApp_ja-JP.csv`。

**第四步：生成附属程序集**

用 LocBaml 把翻译好的 CSV 反向注入到新的资源文件中：

```
LocBaml /generate MyApp.resources.dll /trans:MyApp_en-US.csv /cult:en-US /out:en-US
```

这会生成一个文件夹 `en-US`，里面放着一个 `MyApp.resources.dll`。这个 dll 就是英文的附属程序集。把它放到应用程序启动目录下的 `en-US` 子文件夹里。

同理生成日文的放在 `ja-JP` 文件夹，德文的放在 `de-DE` 文件夹。

最终发布目录结构：

```
C:\Program Files\MyApp\
    MyApp.exe
    MyApp.resources.dll    （默认语言，这里是中文）
    \en-US
        MyApp.resources.dll （英语资源）
    \ja-JP
        MyApp.resources.dll （日语资源）
    \de-DE
        MyApp.resources.dll （德语资源）
```

**第五步：运行时自动切换语言**

程序运行时，WPF 会自动根据 `Thread.CurrentThread.CurrentUICulture` 来决定加载哪个语言的附属程序集。`CurrentUICulture` 默认会继承自操作系统的显示语言。中文 Windows 就加载中文资源，英文 Windows 自动加载 `en-US` 文件夹下的资源。

你不需要写任何代码来做切换——`ResourceManager` 和附属程序集机制在 .NET 底层就全自动了。

如果你想在程序里手动覆盖语言（比如做一个语言切换菜单），可以在 `Application.OnStartup` 里强制设置：

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);
    Thread.CurrentThread.CurrentUICulture = new CultureInfo("en-US");
    // 注意：修改后需要重新加载窗口才能看到效果
}
```

但要注意，已经显示的窗口不会自动刷新，你需要在设置新语言后重新创建主窗口。

### 7.4.3 管理翻译过程

上一小节的 LocBaml + CSV 流程看起来挺清晰，但在真实商业项目里，你会发现它有不少限制和痛点。这一小节就是关于怎么在实际团队中更高效地管理本地化流程。

#### LocBaml 的局限性

- **Uid 管理**：自动生成 Uid 后，如果你在后续版本里新增控件、删除旧控件，重新运行 `updateuid` 可能会导致原来已经翻译好的控件 Uid 发生变化，导致翻译对应不上。所以需要把 Uid 当作**永久标识符**，一旦发布就不能改。
- **CSV 文件合并**：当一个版本有了新的翻译，同时旧版本的 CSV 也有修改，把两者合在一起很容易出冲突。LocBaml 本身没有合并工具。
- **翻译人员体验**：CSV 文件没有上下文信息——翻译人员不知道 "Save" 是按钮上的文字还是菜单项上的，不知道这个控件的最大长度限制是多少。这导致翻译质量打折。
- **没有翻译记忆机制**：每次版本升级，即使大部分文字没变，你也得重新全部翻译一遍。

#### 更专业的本地化方法

对于大型项目，通常不用裸 LocBaml，而是用更专业的工具和流程。

**方案一：WPF 本地化扩展 + 翻译管理系统（TMS）**

使用商业翻译管理系统（如 SDL Trados、MemoQ、Crowdin、POEditor、Lokalise 等）来管理翻译。这些系统：

- 支持 XLIFF 标准格式（XLIFF 是翻译交换标准，带有上下文信息、翻译记忆、术语库）。
- 自动检测哪些文字是新加的、哪些是改动的、哪些删了。
- 提供翻译记忆：相同的文字只翻译一次，下次自动推荐。
- 提供在线协作界面，翻译人员可以在浏览器里看到每个字符串在哪个控件上、属于哪个页面。

配合 WPF 本地化扩展库，如 **WPF Localization Extension**（开源项目），它让你直接把资源字符串写在 RESX 文件里，然后在 XAML 里用标记扩展引用，彻底不需要 LocBaml 那一套生成流程。

用法示例：

```xml
<Window xmlns:lex="http://wpflocalizeextension.codeplex.com">
    <Button Content="{lex:Loc Key=SaveButtonText}" />
</Window>
```

然后在 RESX 资源文件里定义 `SaveButtonText` 的英文值、中文值、日文值。标准 .NET RESX 本地化流程自动生成附属程序集，不需要 CSV 和手动回注。

**方案二：使用 RESX 资源文件 + Binding**

你也可以完全脱离 WPF 专属的 LocBaml，走 .NET 原生的资源文件方案：

1. 在项目里添加 RESX 资源文件（`Strings.resx` 放默认语言，`Strings.en-US.resx` 放英语，`Strings.ja-JP.resx` 放日语）。
2. 在 RESX 文件里添加键值对：`SaveButtonText` → `"保存"`，翻译文件里 `SaveButtonText` → `"Save"`。
3. 在 XAML 里通过 `x:Static` 或绑定引用这些资源：

```xml
<Button Content="{x:Static res:Strings.SaveButtonText}" />
```

这就是 7.4.1 最后那个示例的写法。

**优点**：
- Visual Studio 内置支持 RESX 编辑器，可视化编辑资源。
- 翻译文件也是标准 RESX，可以直接发给翻译人员（或通过 TMS 集成）。
- 没有 CSV 生成和 LocBaml 的额外步骤。
- 可以通过 `ResourceManager` 在代码里动态获取。

**缺点**：
- 所有需要翻译的文字都必须从 XAML 的硬编码字符串迁移到 RESX 资源引用，工作量比较大（对已有项目）。
- 对 XAML 中很少被翻译的纯技术属性（如 `x:Name`、`Grid.Row` 的值等）也需要保持不放在资源中，这没有 LocBaml 自动识别方便。

**方案三：混合方案**

在大型真实项目中，很多团队采用混合方案：

1. XAML 中控件文字用 RESX + `x:Static` 引用。
2. 代码隐藏里任何面向用户的文字也通过 `ResourceManager` 读取 RESX。
3. 极少数的动态文字（比如用户自定义模板里的）在运行时通过代码从 RESX 查。
4. 将 RESX 上传到 TMS（如 Crowdin/Lokalise）管理翻译版本和协作。
5. 最终编译时生成附属程序集，自动由 .NET 的多语言资源加载机制处理。

这样既享受标准 .NET 资源管理的好处，又有专业翻译工具的流程支持。

#### 本地化测试清单

完成翻译工作后，你需要用各种语言运行程序来测试界面是否正常。重点检查：

1. **文字是否完整显示**（没有被截断）。
2. **控件是否重叠**（尤其是德文、阿拉伯语）。
3. **布局方向对不对**（阿拉伯语从右向左，界面镜像是否正确）。
4. **日期、时间、数字格式**是否符合当地习惯。
5. **快捷键（访问键）是否重复或丢失**（不同语言下 Alt+字母快捷键可能冲突）。
6. **图标和图片**是否包含文化敏感内容（比如手势、动物、符号在不同文化下含义不同）。
7. **排序规则**（列表排序是否符合该语言的字母表顺序？用 `StringComparer.CurrentCulture` 而不是硬编码排序）。

WPF 的 `Window.Language` 属性可以让你在不切换系统语言的情况下，单独为一个窗口设置不同的区域语言，方便测试：

```xml
<Window Language="ja-JP" ...>
```

## 7.4 节总结

7.4 节把 WPF 的本地化从设计理念到工程实践全讲了一遍：

**构建能够本地化的用户界面（7.4.1）**：
- 本地化的四大挑战：文字长度变化、文字方向变化、控件尺寸位置变化、区域格式差异。
- WPF 的五大本地化友好特性：自适应布局、Grid 比例尺寸、FlowDirection 文字方向、内容与文字资源分离、字体回退。
- 指导原则：永远不要硬编码自然语言文字，永远不要写死控件尺寸，永远用动态布局。

**使应用程序为本地化做好准备（7.4.2）**：
- WPF 原生方案：`x:Uid` + LocBaml 提取 CSV → 翻译 → 生成附属程序集 dll。
- 附属程序集基于 .NET 的卫星资源机制，随 `CurrentUICulture` 自动加载。
- 发布结构：exe + 每种语言一个子文件夹，里面放对应的 `resources.dll`。

**管理翻译过程（7.4.3）**：
- LocBaml 的局限性：Uid 管理麻烦、CSV 无上下文、无翻译记忆。
- 专业方案：RESX 资源文件 + `x:Static` 引用 + 翻译管理系统（TMS）+ XLIFF 标准。
- 也可以通过 WPF Localization Extension 等开源库简化 RESX 绑定。
- 测试清单：字符串截断、重叠、方向、格式、快捷键、文化敏感性。

本地化不是“先把中文版做完，以后再翻译”。如果一开始不考虑，后期强加本地化会非常痛苦，因为界面布局已经定死在了原始语言上。最好的做法是从项目的第一天就遵循 WPF 的自适应布局原则，把文字放在资源里，给控件足够空间。这样当你需要推出英文版、日文版、阿拉伯语版时，就是一个平滑的翻译和测试过程，而不是一场界面重构灾难。
