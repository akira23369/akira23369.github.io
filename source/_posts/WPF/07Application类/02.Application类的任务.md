# 笔记34《Application类》7.2节——Application类的任务

## 7.2 Application类的任务

上一节把 `Application` 对象的生命周期讲透了——它怎么创建、怎么自定义、怎么关闭、在哪些时刻会触发什么事件。但 `Application` 对象在它的生命周期里，除了被动地等着事件发生，还能主动干很多事。这些事不是某个控件的职责，而是**整个应用程序级别**的任务，只能由 `Application` 这个“大总管”来管。

这一节 7.2 就是把这些任务一个个摊开来讲：

- **显示初始界面**：程序启动时，主窗口出来之前，先显示一个闪屏（Splash Screen）或加载提示，让用户知道程序没死。
- **处理命令行参数**：从命令行接收参数来改变程序行为（比如 `myapp.exe /debug` 开启调试模式，或者 `myapp.exe document.docx` 直接打开文件）。
- **访问当前 Application 对象**：在程序的任何角落安全地拿到这个唯一的 `Application` 实例。
- **窗口之间进行交互**：在一个窗口里访问另一个窗口的数据或控件，实现跨窗口协同。
- **单实例应用程序**：限制程序同时只能运行一个实例，用户双击 exe 只会激活已经运行的实例，不会打开第二个。

下面逐个深入。

---

### 7.2.1 显示初始界面

很多桌面应用在主窗口完全加载之前，会先显示一个“闪屏”（Splash Screen）——一张带程序 Logo 和名称的图片，或者一个简单的进度提示。这有两个目的：

1. **给用户即时反馈**：大型应用启动可能需要几秒钟（加载配置、初始化数据库、检查更新等），如果双击后啥也没有，用户会以为没点中，又点一下，结果开了俩。
2. **品牌展示**：在等待的时候展示程序 Logo、版本号、公司名，提升专业感。

WPF 提供了两种实现初始界面的方式：自动闪屏和手动定制。

#### 方式一：内置闪屏（最简单的静态图片）

WPF 支持直接指定一张图片作为闪屏，在程序启动的**最早阶段**自动显示，完全不需要写一行代码。

**操作步骤**：

1. 将一张图片添加到 WPF 项目中（例如 `SplashScreen.png`）。
2. 在解决方案资源管理器中选中该图片，在属性窗口中将**生成操作（Build Action）**设为 `SplashScreen`。

编译运行后，这张图片会在 `Application` 对象创建之前就显示出来（在 WPF 初始化底层图形引擎的同时），然后在主窗口 `Loaded` 之后自动消失。

**原理**：当 WPF 看到生成操作为 `SplashScreen` 的图片时，会自动在编译产物中嵌入它，并修改 `Main` 方法的代码，在 `Application.Run` 之前调用 `SplashScreen.Show()`。这个过程不需要你改任何 C# 代码。

**优点**：
- 零代码，速度快。
- 闪屏显示极早，用户双击后几乎立刻看到图片。

**缺点**：
- 只能是静态图片，不能带进度条、动态文字、动画等。
- 消失时机是主窗口第一次渲染完成后，无法精确控制。

**自定义消失时机**：如果你想手动控制闪屏关闭，可以在 `App.xaml.cs` 的 `OnStartup` 里拿到 `SplashScreen` 对象并控制它：

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);
    
    SplashScreen splash = new SplashScreen("SplashScreen.png");
    splash.Show(true);  // true 表示自动关闭由代码控制
    
    // 模拟加载
    System.Threading.Thread.Sleep(3000);
    
    // 手动关闭
    splash.Close(TimeSpan.FromSeconds(0.5));  // 0.5秒淡出
}
```

但这种方式闪屏出现时机会稍晚（因为已经进入了 `OnStartup` 流程），不如构建为 `SplashScreen` 的方式早。

#### 方式二：自定义初始窗口（灵活但复杂）

如果需要带进度条、状态文字、取消按钮等复杂闪屏，内置闪屏就不够用了。你可以自己做一个 `Window`，在 `OnStartup` 里显示它，加载完成后关闭它并显示主窗口。

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    // 创建并显示闪屏窗口
    SplashWindow splash = new SplashWindow();
    splash.Show();

    // 模拟初始化（这里放真正的初始化逻辑）
    splash.UpdateStatus("正在加载配置...");
    System.Threading.Thread.Sleep(1000);
    
    splash.UpdateStatus("正在连接数据库...");
    System.Threading.Thread.Sleep(2000);
    
    splash.UpdateStatus("即将完成...");
    System.Threading.Thread.Sleep(500);

    // 关闭闪屏，显示主窗口
    splash.Close();
    
    MainWindow main = new MainWindow();
    main.Show();
    
    // 注意：如果用了自定义闪屏，App.xaml 的 StartupUri 需要去掉，
    // 主窗口完全由你自己控制显示。
}
```

`SplashWindow` 是你自己设计的一个窗口，里面可以放 `ProgressBar`、`TextBlock` 状态文字、`Image` Logo 等。`UpdateStatus` 是你暴露的公共方法，用来更新闪屏上的文字和进度。

**注意**：这种方法下，闪屏窗口也是一个完整的 WPF 窗口，它有自己的消息循环。但由于主窗口还没显示，`ShutdownMode` 的行为要注意——如果闪屏窗口关闭时程序就退出了，那就说明你把闪屏当成了主窗口。正确做法是在闪屏关闭后显示主窗口，且 `ShutdownMode` 应该基于主窗口或显式控制。

**闪屏的最佳实践**：主窗口初始化太慢才需要闪屏。如果你的应用秒开，就别画蛇添足。另外，闪屏上的信息要真实——不要显示虚假进度条（永远 99%），让用户对你的程序第一印象变差。

### 7.2.2 处理命令行参数

很多程序支持命令行参数来控制行为。比如 Visual Studio 用 `devenv.exe /diff` 打开差异比较，浏览器用 `chrome.exe --incognito` 打开隐身模式。WPF 让你能轻松拿到这些参数，并在 `OnStartup` 里根据地做不同的事。

#### 获取命令行参数

命令行参数通过 `Environment.GetCommandLineArgs()` 获取，返回一个 `string[]` 数组。第一个元素永远是程序 exe 自身的路径，后面的元素才是用户传的参数。

更方便的方式是在 `OnStartup` 事件的参数 `StartupEventArgs e` 里直接拿到参数：

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    // e.Args 里只有用户传的参数，不包含 exe 路径
    foreach (string arg in e.Args)
    {
        Console.WriteLine($"命令行参数: {arg}");
    }

    // 常用场景：根据参数决定行为
    if (e.Args.Contains("/debug"))
    {
        EnableDebugMode();
    }
    else if (e.Args.Contains("/silent"))
    {
        this.ShutdownMode = ShutdownMode.OnExplicitShutdown;
        RunBackgroundTask();
    }
    else if (e.Args.Length > 0)
    {
        string filePath = e.Args[0];
        OpenFile(filePath);
    }
}
```

#### 常用命令行模式

**模式一：开关参数（如 `/debug`、`-verbose`）**

这些参数没有值，只是作为一个标志。

```csharp
bool debugMode = e.Args.Any(a => a.Equals("/debug", StringComparison.OrdinalIgnoreCase));
```

**模式二：键值对参数（如 `/mode=report`、`-config=config.json`）**

```csharp
string mode = e.Args.Where(a => a.StartsWith("/mode="))
                    .Select(a => a.Split('=')[1])
                    .FirstOrDefault() ?? "default";
```

**模式三：位置参数（如 `myapp.exe document.docx`）**

第一个非开关参数就是一个位置参数，通常表示要打开的文件路径。

```csharp
string fileToOpen = e.Args.FirstOrDefault(a => !a.StartsWith("/") && !a.StartsWith("-"));
if (!string.IsNullOrEmpty(fileToOpen))
{
    MainWindow.OpenDocument(fileToOpen);
}
```

#### 把命令行参数传给主窗口

在 `OnStartup` 里拿到参数后，你通常需要把它们传给主窗口。最简单的方式是通过主窗口的构造函数或公共属性：

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);
    
    MainWindow main = new MainWindow();
    
    if (e.Args.Length > 0)
    {
        main.FileToOpen = e.Args[0];
    }
    
    main.Show();
}
```

或者直接在 `MainWindow` 的构造里接收参数：

```csharp
public MainWindow(string[] args)
{
    InitializeComponent();
    if (args.Length > 0) { OpenFile(args[0]); }
}
```

在 `App.xaml` 不设 `StartupUri`，在 `OnStartup` 里创建主窗口并传参。这是最常见的模式。

#### 超越简单参数：使用命令行解析库

如果你的程序参数又多又复杂（各种选项、别名、必需参数、验证规则），手动解析字符串数组会很快变成灾难。这时可以用第三方的命令行解析库，例如 `CommandLineParser`（NuGet 上很流行）或者 `System.CommandLine`。它们能自动把参数映射到 C# 对象上，处理错误和帮助信息，极大降低复杂度。但对于简单场景，手写几行分析就够了。

### 7.2.3 访问当前 Application 对象

在程序的任何一个角落，你都可以通过静态属性 `Application.Current` 获取到当前正在运行的 `Application` 对象的引用。这给你提供了一个全局访问点，让你在任何窗口、控件、ViewModel 甚至工具类里都能拿到这个“大总管”。

```csharp
Application app = Application.Current;
```

#### 常见用途

**1. 获取应用程序级别的资源和属性**

在 `App.xaml` 里定义的全局资源，可以在代码里通过 `Application.Current.Resources["key"]` 来获取：

```csharp
SolidColorBrush brush = (SolidColorBrush)Application.Current.Resources["PrimaryBrush"];
```

你也可以在 `App` 类里定义自己的属性，在程序的任意位置访问：

```csharp
public partial class App : Application
{
    public string CurrentUser { get; set; } = "未登录";
}

// 在任何地方
string user = ((App)Application.Current).CurrentUser;
```

**2. 关闭程序**

任何地方都能通过 `Application.Current.Shutdown()` 退出程序。

**3. 获取程序的主窗口**

`Application.Current.MainWindow` 返回当前的主窗口对象。如果你需要跨窗口操作，这是一个入口。

**4. 访问所有打开的窗口**

`Application.Current.Windows` 是一个 `WindowCollection` 集合，包含当前所有打开的窗口。你可以遍历它来找到特定的窗口：

```csharp
foreach (Window win in Application.Current.Windows)
{
    if (win is SettingsWindow settingsWin)
    {
        settingsWin.RefreshData();
    }
}
```

#### 线程注意事项

`Application.Current` 只能在**创建 `Application` 对象的那条线程**（即 UI 线程/主线程）上访问。如果你在后台线程上访问它，会抛异常。如果你需要从后台线程操作 UI，必须用 `Dispatcher.Invoke` 或 `async/await` 回到 UI 线程。后面多线程章节会详细讲。

#### 设计建议

虽然 `Application.Current` 是个方便的全局访问点，但不要滥用。到处用全局静态访问会让代码耦合度高、难测试。更好的做法是在需要的地方通过构造函数注入或数据绑定传递资源，只在确实需要全局访问的地方（如工具方法、全局错误处理）才用 `Application.Current`。

### 7.2.4 在窗口之间进行交互

一个 WPF 程序经常有多个窗口——主窗口、设置窗口、新建文档窗口、预览窗口等。这些窗口之间经常需要通信：设置窗口改了主题，主窗口要立刻刷新；日志窗口需要实时显示主窗口的操作日志；或者你只是想在子窗口关闭后获取用户在子窗口中输入的数据。

WPF 提供了好几种跨窗口交互的方式，各有各的适用场景。

#### 方式一：通过 Application 对象访问窗口

利用 `Application.Current.Windows` 可以遍历所有打开的窗口，找到目标窗口再操作：

```csharp
// 从设置窗口更新主窗口的状态栏
private void ApplySettings()
{
    foreach (Window win in Application.Current.Windows)
    {
        if (win is MainWindow main)
        {
            main.UpdateStatus("设置已应用");
        }
    }
}
```

**优点**：随时可用，不需要事先保存引用。
**缺点**：耦合——你需要知道目标窗口的具体类型和方法名。窗口一改名，所有地方都得改。

#### 方式二：持有窗口引用

在打开子窗口的代码里，显式保存子窗口的引用，直接和它交互：

```csharp
// 主窗口
private void OpenSettings()
{
    SettingsWindow settings = new SettingsWindow();
    settings.Owner = this;  // 设置所有者，子窗口总在前面
    settings.ShowDialog();  // 模态打开，直到子窗口关闭才返回
    
    // 从设置窗口读取数据
    string selectedTheme = settings.SelectedTheme;
    ApplyTheme(selectedTheme);
}
```

在设置窗口里暴露公共属性：

```csharp
public partial class SettingsWindow : Window
{
    public string SelectedTheme { get; private set; }

    private void SaveButton_Click(object sender, RoutedEventArgs e)
    {
        SelectedTheme = "Dark";
        this.DialogResult = true;  // 设置对话框结果
        this.Close();
    }
}
```

**优点**：简单直接，最常用的模式。
**缺点**：只能在打开窗口的那个地方交互。如果需要在程序其他地方跨越窗口通信，不够灵活。

#### 方式三：通过事件通信（解耦推荐）

在一个窗口里定义事件，另一个窗口订阅事件，实现松耦合通信。

```csharp
// 设置窗口定义事件
public partial class SettingsWindow : Window
{
    public event Action<string> ThemeChanged;

    private void ApplyThemeButton_Click(object sender, RoutedEventArgs e)
    {
        ThemeChanged?.Invoke("Dark");
        this.Close();
    }
}

// 主窗口打开设置窗口并订阅事件
private void OpenSettings()
{
    SettingsWindow settings = new SettingsWindow();
    settings.ThemeChanged += OnThemeChanged;
    settings.Owner = this;
    settings.ShowDialog();
}

private void OnThemeChanged(string theme)
{
    ApplyTheme(theme);
}
```

**优点**：发布者和订阅者解耦，符合良好设计原则。
**缺点**：需要手动管理事件订阅，如果忘记取消订阅，可能在窗口关闭后还持有引用导致内存泄漏。可以通过弱事件模式（`WeakEventManager`）来避免，但那是进阶内容。

#### 方式四：通过共享的 ViewModel（MVVM 标准做法）

如果用了 MVVM 架构，窗口之间的通信通常通过一个共享的 `ViewModel` 对象或者一个中介者（Messenger/EventAggregator）来完成。这是最解耦也最科班的方式。

```csharp
// 使用 MvvmLight 的 Messenger 示例
Messenger.Default.Send(new ThemeChangedMessage("Dark"));
```

接收方注册消息：

```csharp
Messenger.Default.Register<ThemeChangedMessage>(this, msg => {
    ApplyTheme(msg.Theme);
});
```

**优点**：完全解耦，发送者和接收者互相不知道对方的存在。适合大型复杂项目。
**缺点**：需要理解 MVVM 框架，学习曲线稍陡。对于简单项目可能过度设计。

#### 方式五：通过静态属性或全局单例（慎用）

你可以在 `App` 类上放静态属性来传递信息：

```csharp
public partial class App : Application
{
    public static string GlobalStatus { get; set; }
}

// 在任何地方
App.GlobalStatus = "更新完成";
```

**优点**：极其简单。
**缺点**：全局变量，任何地方都可以改，缺乏保护，容易失控。只适合非常简单的场景（如全局状态栏文字），不适合重要的业务数据传递。

#### 选择指南

| 场景 | 推荐方式 |
|------|---------|
| 模态对话框，关闭时返回数据 | 方式二：持有窗口引用 |
| 非模态窗口，需要持续双向通信 | 方式三：事件 |
| MVVM 项目，多处需要通信 | 方式四：ViewModel / Messenger |
| 偶尔临时访问已知窗口 | 方式一：遍历 Windows |
| 极简全局状态（如标题栏文字） | 方式五：静态属性 |

### 7.2.5 单实例应用程序

很多桌面应用希望用户只能打开一个实例。比如浏览器、笔记软件、音乐播放器——用户不管点多少次 exe，应该要么激活已经打开的窗口，要么在已打开的窗口里打开一个新标签页，而不是再开一个新的进程。这叫**单实例应用程序**。

WPF 没有内置的一键单实例开关，但实现起来并不复杂，核心原理是：**用操作系统的命名互斥体（Named Mutex）来检测是否已经有另一个实例在运行。** 如果检测到有，当前新实例就把指令转发给旧实例，然后自己退出。

#### 方案一：使用 Mutex 检测重复实例

这是最经典的万能方案，纯 .NET 即可实现，不依赖 WPF 特定功能。

**完整实现步骤**：

```csharp
public partial class App : Application
{
    private static Mutex _mutex;
    private const string AppMutexName = "MyAppUniqueName";

    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);

        bool createdNew;
        _mutex = new Mutex(true, AppMutexName, out createdNew);

        if (!createdNew)
        {
            // 已经有另一个实例在运行
            MessageBox.Show("程序已在运行。", "提示", 
                            MessageBoxButton.OK, MessageBoxImage.Information);
            this.Shutdown();
            return;
        }

        // 这是第一个实例，正常启动
        new MainWindow().Show();
    }

    protected override void OnExit(ExitEventArgs e)
    {
        base.OnExit(e);
        _mutex?.ReleaseMutex();
        _mutex?.Dispose();
    }
}
```

在 `App.xaml` 中去掉 `StartupUri`（因为我们在 `OnStartup` 里手动创建主窗口了）。

**原理**：
- `new Mutex(true, "唯一名称", out bool createdNew)` 创建或打开一个命名互斥体。
- `createdNew` 为 `true` 表示互斥体是被当前进程创建的，意味着当前进程是第一个实例。
- `createdNew` 为 `false` 表示互斥体已经存在（由之前的实例创建），意味着当前进程是第二个实例，应该退出。
- 在 `OnExit` 里释放和销毁互斥体，这样第一个实例关闭后，未来又可以照常打开新实例。

**缺点**：如果第一个实例最小化到了系统托盘，或者被其他窗口挡住了，用户再双击 exe 没反应（只弹了个“已在运行”的提示），体验不好。用户期望的是“我一双击，要么跳出一个新窗口，要么把旧窗口拉到前台”。

#### 方案二：激活已运行的实例（体验升级）

不仅检测到已有实例存在，还要把已有实例的主窗口拉到前台，并且把当前实例的命令行参数传给它。

实现思路：
1. 第一个实例启动时，注册一个命名管道（Named Pipe）或 Windows 消息来监听后续实例的请求。
2. 第二个实例启动时，检测到已有实例，不自己启动，而是通过管道/消息把命令行参数发给第一个实例，然后退出。
3. 第一个实例收到消息后，把自己的主窗口拉到前台，并根据参数执行操作（如打开新文件、新建标签页）。

这个方案实现细节较多，WPF 里常用 **`System.Threading.Mutex` + `NamedPipeServerStream`** 或使用 WCF 简化通信，也可以利用 Windows 的消息机制（`PostMessage` + `HwndSource.AddHook`）。

**简化版：仅激活已有窗口（不传参数）**

如果不需要传递命令行参数，只是想把旧窗口拉到前台，可以简单利用 `Process` 类找到已有进程并激活其窗口：

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    Process currentProcess = Process.GetCurrentProcess();
    Process[] runningProcesses = Process.GetProcessesByName(currentProcess.ProcessName);

    if (runningProcesses.Length > 1)
    {
        // 已有实例在运行，尝试激活它并退出
        IntPtr hWnd = runningProcesses[0].MainWindowHandle;
        if (hWnd != IntPtr.Zero)
        {
            ShowWindow(hWnd, SW_RESTORE);   // 恢复窗口（如果最小化了）
            SetForegroundWindow(hWnd);       // 拉到前台
        }
        this.Shutdown();
        return;
    }

    // 第一个实例，正常启动
    new MainWindow().Show();
}

// Win32 API 声明
[DllImport("user32.dll")]
private static extern bool SetForegroundWindow(IntPtr hWnd);
[DllImport("user32.dll")]
private static extern bool ShowWindow(IntPtr hWnd, int nCmdShow);
private const int SW_RESTORE = 9;
```

**注意**：这种方法依赖于通过进程名找到窗口句柄，在特殊情况下（如窗口句柄变化、多窗口程序）可能不靠谱。更健壮但更复杂的方案是前面说的命名管道通信。

#### 方案三：使用 Microsoft.VisualBasic.ApplicationServices 的 SingleInstanceApplication

如果你不介意依赖 `Microsoft.VisualBasic.dll`，它内置了一个 `WindowsFormsApplicationBase` 类（虽然名字叫 WindowsForms，但它完全支持 WPF），提供了一套现成的单实例机制，包括把参数传给第一个实例的事件。这个方案省去了手写管道通信的麻烦，但因为它引入了一个非典型的依赖（VB相关库），在纯 C# 项目中使用较少。

#### 单实例最佳实践总结

1. **Mutex 是基础**：无论哪种方案，检测是否已有实例都靠 Mutex。
2. **激活已有窗口是加分项**：不仅仅告诉用户“已经在运行”，而是把旧窗口提到前台，提升体验。
3. **传递命令行参数是高级需求**：如果你的程序需要双击文档自动在已有窗口中打开，就需要实现进程间通信（管道/WCF/Windows消息）。
4. **别忘了释放 Mutex**：在 `OnExit` 里 `ReleaseMutex` 和 `Dispose`，否则第一个实例关闭后互斥体可能残留一段时间（GC 可能没有立即回收），导致用户短时间内无法重新打开程序。

## 7.2 节总结

7.2 节把 `Application` 对象在日常开发中最实用的五个任务全讲清楚了：

**显示初始界面**：
- **内置闪屏**：把图片生成操作设为 `SplashScreen`，零代码最早显示，但只能是静态图。
- **自定义闪屏窗口**：自己写一个 `Window` 在 `OnStartup` 里显示，可以做进度条、状态文字，灵活性高但需要手动管理。

**处理命令行参数**：
- `OnStartup(StartupEventArgs e)` 里通过 `e.Args` 获取参数数组（不包含 exe 路径）。
- 常见模式：开关参数、键值对参数、位置参数（如文件路径）。
- 参数通常通过构造函数或公共属性传递给主窗口。
- 复杂参数场景建议使用命令行解析库。

**访问当前 Application 对象**：
- `Application.Current` 在程序的任何地方都能获取到全局唯一的 `Application` 对象。
- 用于访问全局资源、关闭程序、获取主窗口、遍历所有打开窗口。
- **只能在 UI 线程上访问**。
- 建议不要滥用，保持代码松耦合。

**窗口之间交互**：
- 方式一：遍历 `Application.Current.Windows` 找到目标窗口操作。
- 方式二：持有窗口引用，通过公共属性或方法通信（最直接，适合模态对话框）。
- 方式三：通过事件实现松耦合通信（发布-订阅模式）。
- 方式四：通过共享 ViewModel / Messenger（MVVM 标准做法，最解耦）。
- 方式五：静态全局属性（简单但易失控，谨慎使用）。

**单实例应用程序**：
- 核心原理：用命名 Mutex 检测是否已有实例在运行。
- 基本版：检测到已有实例就弹提示退出。
- 升级版：激活已有实例的主窗口并拉到前台。
- 高级版：通过命名管道等 IPC 机制传递命令行参数给第一个实例。
- 注意在退出时释放 Mutex。

`Application` 对象就是 WPF 程序的“管家大脑”。它管着程序的生老病死（7.1 节），执行着跨窗口、跨实例的全局任务（7.2 节）。学会用好它，你的 WPF 程序就从一堆孤立的窗口变成了一个协调运作的整体。接下来 7.3 节会讲程序集资源（怎么管理图片、字体、声音文件等），7.4 节讲本地化（让程序支持多语言）。
