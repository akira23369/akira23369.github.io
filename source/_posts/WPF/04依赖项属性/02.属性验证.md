## 属性验证

上一节讲了依赖项属性是什么、怎么注册、WPF 怎么用它。你知道了依赖项属性不是简单的 get/set，它的值是 WPF 中央系统动态计算出来的，而且有很多“值来源”（绑定、动画、样式、继承等）在竞争。那现在就有一个非常现实的问题：**如果有人给属性设了一个不合理的值，怎么办？**

比如一个表示“年龄”的属性，你当然不希望它被设成 -5 或者 99999；再比如一个表示“进度”的属性，它必须永远被限制在 0 到 100 之间；又比如 `Slider` 控件的 `Value` 属性，它必须时刻夹在 `Minimum` 和 `Maximum` 之间，不管用户拖到哪儿、代码怎么设、绑定源怎么变，最终值永远落在合理范围内。

普通 CLR 属性的做法是在 set 里写 if 判断，不合法的要么抛异常要么悄悄修正。但是依赖项属性不行——因为依赖项属性可能被 `SetValue` 直接赋值、被样式赋值、被动画赋值、被绑定赋值、被强制回调修改，你在 CLR 包装器里写的任何逻辑都可能被绕过。所以 WPF 把属性验证这件事也整合到了依赖项属性的元数据里，提供了两种回调机制：

1. **验证回调（ValidateValueCallback）**：纯粹的“检查关卡”，判断新值是否合法。不合法就拒绝，直接抛异常。
2. **强制回调（CoerceValueCallback）**：更聪明的“修正关卡”，它不拒绝值，而是根据当前对象的状态，把不合理的值修正成一个合理值，然后返回修正后的值。

这两个机制协同工作，构成了依赖项属性的“属性安全网”。下面分别拆开讲。

---

### 验证回调

**验证回调是什么？**

验证回调是一个在属性值被真正接受之前调用的方法，它的任务只有一个：**检查这个新值是否合法**。如果合法，返回 `true`；如果不合法，返回 `false`，WPF 会直接抛出一个 `ArgumentException` 异常，整个设值操作失败，属性值保持原样不变。

验证回调是**纯粹**的——它不应该修改任何东西，不应该有副作用，不应该去改别的属性，甚至不应该把值修正了再返回。它就是一道关卡，只做“合格/不合格”的判断。

**为什么要验证回调？**

因为在依赖项属性系统里，一个属性的值可能从各种渠道来：XAML 解析时设的、代码里 `SetValue` 设的、数据绑定源变化的、样式应用的、动画产生的……如果每个设值的地方都要自己写一遍验证逻辑，那代码就散得到处都是，而且容易漏。把验证逻辑写在属性注册时定义的回调里，等于在这条属性的“入口”上装了一个安检门，不管谁设的值，都得从这个门过。这保证了属性值永远在合法范围内，不管来源是什么。

**怎么定义验证回调？**

验证回调的委托类型是 `ValidateValueCallback`：

```csharp
public delegate bool ValidateValueCallback(object value);
```

它接受一个 `object` 类型的新值（因为依赖项属性可以存储任何类型），返回 `true` 表示通过，`false` 表示不通过。

在注册属性时，通过 `PropertyMetadata` 的构造函数参数，或者直接设置 `PropertyMetadata` 对象的 `ValidateValueCallback` 属性来指定。

**完整示例：一个年龄属性**

假设你写了一个自定义控件，里面有个 `Age` 属性，要求年龄必须在 0 到 150 之间。

```csharp
public class PersonControl : Control
{
    // 第一步：定义验证回调方法
    private static bool ValidateAge(object value)
    {
        int age = (int)value;
        return age >= 0 && age <= 150;
    }

    // 第二步：注册依赖项属性，在元数据里传入验证回调
    public static readonly DependencyProperty AgeProperty =
        DependencyProperty.Register(
            "Age",
            typeof(int),
            typeof(PersonControl),
            new PropertyMetadata(0, null, CoerceAge),  // 后面会讲强制回调（第二个参数是可选的属性变更通知，此处暂不涉及）
            ValidateAge                                  // 验证回调通过 Register 的第4个重载参数传入
        );

    // 注意：上面用的是 Register 的一个重载版本，
    // 它的参数依次是：属性名、类型、所有者类型、属性元数据、验证回调。
    // 完整的参数顺序请查 MSDN，不同 .NET 版本略有差别。
    // 此处为示意，准确写法如下：

    /*
    public static readonly DependencyProperty AgeProperty =
        DependencyProperty.Register(
            "Age",
            typeof(int),
            typeof(PersonControl),
            new PropertyMetadata(0),   // 默认值
            ValidateAge                // 验证回调
        );
    */
    // 如果有强制回调也需在元数据里设置，见 4.2.2 节。

    // 第三步：CLR 包装器
    public int Age
    {
        get { return (int)GetValue(AgeProperty); }
        set { SetValue(AgeProperty, value); }
    }
}
```

现在，任何试图给 `Age` 赋一个非法值的操作都会导致异常：

```csharp
var person = new PersonControl();
person.Age = 25;   // 成功
person.Age = -10;  // 抛出 ArgumentException！因为 -10 没通过 ValidateAge 的检查
```

同样，如果你在 XAML 里写 `<local:PersonControl Age="-5" />`，编译时不会报错，但运行时加载 BAML 时就会因为验证失败而抛异常。

**如果同时有绑定呢？**

绑定时，如果源数据传过来的值不合法，验证回调同样会拦截。比如你绑定的数据对象里 `Age` 是 -5，当绑定引擎调用 `SetValue` 时，验证回调会拒绝这个值并抛异常。不过别担心，WPF 的绑定系统有异常处理机制，它通常会在输出窗口打印绑定错误信息，不会直接崩掉整个程序。你也可以在绑定上设置 `Binding.ValidatesOnExceptions` 为 `True`，配合 `ValidationRules` 实现更友好的校验展示。

**验证回调的局限**

验证回调只告诉你“这个值能不能接受”，但它不能做复杂的、依赖其他属性值的判断。比如“开始日期不能晚于结束日期”，这种判断需要看两个属性的当前值，单靠一个验证回调做不到，因为它只拿到新值，不知道别的属性的状态。这种场景就需要强制回调，或者更上层的 ViewModel 层去处理。

另外，验证回调不能修正值。你觉得 -5 不合理，想自动改成 0？对不起，验证回调只能拒绝，不能动手修改。要自动修正值，得用下一节的强制回调。

**验证回调 vs 在 CLR 包装器里写验证**

再次强调：不要在 CLR 包装器的 set 里写验证逻辑。因为依赖项属性的赋值通道很多，XAML 加载、绑定、动画、样式 Setter 都直接走 `SetValue`，完全不经过你的 CLR 包装器。到时候你觉得“我明明在 set 里做了判断，为啥还能设进去非法值”，就晚了。验证回调是唯一能拦截所有设值通道的关卡。

### 强制回调

**强制回调是什么？**

强制回调是依赖项属性系统另一个重要的回调机制。和验证回调不同，强制回调的目的不是“拒绝非法值”，而是**把不合理的值强制修正到一个合理范围，然后使用修正后的值**。

它的委托类型是 `CoerceValueCallback`：

```csharp
public delegate object CoerceValueCallback(DependencyObject d, object baseValue);
```

参数：
- `d`：拥有该属性的 `DependencyObject` 实例。注意强制回调是实例级别的，所以它能访问实例的其他属性，做出复杂的判断。
- `baseValue`：在强制之前计算出来的“基础值”，这个基础值是经过了优先级排序之后、但还没经过强制修正的那个值。

返回值：修正后的值（可以和 `baseValue` 相同，也可以不同）。WPF 最终会使用这个返回值写入属性，并在取值时（`GetValue`）返回这个值。

**什么时候需要强制回调？**

经典场景就是你希望某个属性的值永远处在另一些属性约束的范围内。比如：

- `Slider.Value` 必须在 `Slider.Minimum` 和 `Slider.Maximum` 之间。
- `ScrollViewer` 的滚动偏移量不能超出内容实际可滚动的范围。
- 一个任务进度百分比必须在 0 到 100 之间，即使外部赋了 150，也自动截成 100。
- 一个日期选择器里，“结束日期”必须大于等于“开始日期”。如果用户把开始日期改到了结束日期之后，强制回调会自动把结束日期修正到最新的开始日期。

这些修改不是拒绝值，而是把值“夹”回合法区间，这正是强制回调的拿手好戏。

**怎么定义强制回调？**

在注册属性时（或后面修改元数据时），给 `PropertyMetadata` 设置 `CoerceValueCallback`：

```csharp
public class Slider : Control
{
    // 注册 ValueProperty，同时指定强制回调
    public static readonly DependencyProperty ValueProperty =
        DependencyProperty.Register(
            "Value",
            typeof(double),
            typeof(Slider),
            new PropertyMetadata(0.0, null, CoerceValue), // 第三个参数是强制回调
            ValidateValue                                // 第四个是验证回调
        );

    // 强制回调方法
    private static object CoerceValue(DependencyObject d, object baseValue)
    {
        Slider slider = (Slider)d;
        double value = (double)baseValue;

        // 强制夹在 Minimum 和 Maximum 之间
        value = Math.Max(slider.Minimum, Math.Min(slider.Maximum, value));
        return value;
    }

    // 验证回调方法（先执行）
    private static bool ValidateValue(object value)
    {
        double val = (double)value;
        return !double.IsNaN(val) && !double.IsInfinity(val);
    }

    // CLR 包装器
    public double Value
    {
        get { return (double)GetValue(ValueProperty); }
        set { SetValue(ValueProperty, value); }
    }
}
```

运行逻辑：
1. 用户拖动滑块，底层的 `Value` 被 `SetValue` 设为 120。
2. 首先执行验证回调 `ValidateValue`：120 不是 NaN 也不是无穷大，合法，通过。
3. 然后执行强制回调 `CoerceValue`：拿到基础值 120，发现 `Maximum` 是 100，于是把 120 修正为 100。
4. 最终 `Value` 属性的有效值是 100。

**绑定、动画等也与强制回调配合**

当 `Value` 绑定到一个数据源上，数据源变化导致新值过来，强制回调同样会生效。动画改变 `Value` 时，强制回调也会在动画值生效前执行修正。这保证了不管值是通过什么渠道来的，最终呈现的值永远是合法的、受约束的。

**强制回调的触发时机**

很多初学者以为强制回调只是“在 SetValue 时触发一次”。但实际上，强制回调可能在以下几种情况下被调用：

1. **显式 SetValue 时**：你主动设了一个新值。
2. **绑定值更新时**：数据绑定源变化推过来新值。
3. **样式或触发器改变了属性值时**。
4. **关联属性变化时**：这是最关键也最容易忽略的一点。依赖项属性系统允许你在元数据里声明“当属性 A 变化时，属性 B 的值需要重新强制”。比如 `Slider.Minimum` 或 `Slider.Maximum` 变化时，`Slider.Value` 的强制回调必须重新执行，因为约束边界变了，原来合法的值现在可能不合法了。

**怎么声明关联强制？**

在 `PropertyMetadata` 里有个 `CoerceValueCallback` 是静态的一套，但要让一个属性的变化触发另一个属性的强制，需要在属性变更通知回调（`PropertyChangedCallback`）里手动调用 `CoerceValue` 方法。

典型代码（以 Slider 为例）：

```csharp
// 注册 Minimum 属性
public static readonly DependencyProperty MinimumProperty =
    DependencyProperty.Register(
        "Minimum",
        typeof(double),
        typeof(Slider),
        new PropertyMetadata(0.0, OnMinimumChanged));

// 当 Minimum 变化时，强制重新计算 Value
private static void OnMinimumChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
{
    Slider slider = (Slider)d;
    slider.CoerceValue(ValueProperty); // 这会导致 Value 的强制回调重新执行
}
```

`CoerceValue` 方法是 `DependencyObject` 上的一个方法，它强制系统重新评估指定属性的强制回调，并且用最新的状态重新计算合法值。这样当 `Minimum` 改变后，`Value` 就能立即被重新夹持到新的合法范围内。

**验证回调 vs 强制回调的执行顺序**

当一个新的值到来时，执行顺序是：

1. **先执行验证回调**：判断新值是否可接受。
2. 验证通过后，**执行强制回调**：把值修正为合理范围。
3. 如果强制回调返回的值与基础值不同，**不会再次执行验证回调**（因为强制回调产生的值被认为是系统内部修正过的，受信任的）。

所以验证回调是“安检”，强制回调是“民警”——安检先看你能不能进，民警再根据现场情况把你带到该待的地方。

**强制回调与属性优先级**

在依赖项属性的值优先级体系里，强制回调产生的值拥有最高优先级（参见 4.1.4 节的优先级列表）。不管本地值、动画、绑定给的什么值，强制回调都能压倒它们，把值修正为它认为正确的值。这保证了“业务规则永远高于外部输入”。

**强制回调的静态方法 vs 实例方法**

注意上面写的强制回调方法 `CoerceValue` 是 `private static` 的。为什么是静态的？因为回调是在类型级别注册的，而且 WPF 可能在没有任何控件实例的情况下要先知道这个回调的签名。但是回调的第一个参数 `DependencyObject d` 就是那个实例对象，所以你在回调里面可以通过 `d` 访问到实例的所有其他属性，并不矛盾。

**完整例子：一个范围的开始-结束属性对**

为了更好地理解强制回调，再看一个“日期范围控件”的简化版。它有两个 `DateTime` 依赖项属性：`StartDate` 和 `EndDate`。要求 `EndDate` 永远 >= `StartDate`。如果改 `StartDate` 导致它超过 `EndDate`，则自动把 `EndDate` 拉到和 `StartDate` 一样；如果改 `EndDate` 导致它小于 `StartDate`，则自动把 `EndDate` 修正为 `StartDate`。

```csharp
public class DateRangeControl : Control
{
    // ========== StartDate ==========
    public static readonly DependencyProperty StartDateProperty =
        DependencyProperty.Register(
            "StartDate",
            typeof(DateTime),
            typeof(DateRangeControl),
            new PropertyMetadata(DateTime.Today, OnStartDateChanged));

    public DateTime StartDate
    {
        get { return (DateTime)GetValue(StartDateProperty); }
        set { SetValue(StartDateProperty, value); }
    }

    // 当 StartDate 改变时，强制 EndDate 重新修正
    private static void OnStartDateChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        DateRangeControl control = (DateRangeControl)d;
        control.CoerceValue(EndDateProperty); // 触发 EndDate 的强制回调
    }

    // ========== EndDate ==========
    public static readonly DependencyProperty EndDateProperty =
        DependencyProperty.Register(
            "EndDate",
            typeof(DateTime),
            typeof(DateRangeControl),
            new PropertyMetadata(DateTime.Today, null, CoerceEndDate));

    public DateTime EndDate
    {
        get { return (DateTime)GetValue(EndDateProperty); }
        set { SetValue(EndDateProperty, value); }
    }

    // EndDate 的强制回调：保证 >= StartDate
    private static object CoerceEndDate(DependencyObject d, object baseValue)
    {
        DateRangeControl control = (DateRangeControl)d;
        DateTime endDate = (DateTime)baseValue;
        if (endDate < control.StartDate)
        {
            return control.StartDate;
        }
        return endDate;
    }
}
```

运行分析：

- 如果你设 `control.EndDate = 某个早于 StartDate 的日期`，强制回调会直接把它修正为 `StartDate`。
- 如果你把 `StartDate` 改到一个比当前 `EndDate` 还晚的日期，`OnStartDateChanged` 被调用，它触发 `CoerceValue(EndDateProperty)`，强制回调重新执行，发现 `EndDate < StartDate`，于是再次把 `EndDate` 修正为新的 `StartDate`。

这样的模式在 WPF 内置控件里到处可见，典型如 `RangeBase`（Slider 和 ScrollBar 的基类），`Value` 属性的强制回调就是依赖于 `Minimum` 和 `Maximum` 的值。

**强制回调的注意事项**

1. **不要递归爆炸**：在强制回调里不要直接或间接地设置同一个属性的值，否则可能会形成循环调用。WPF 本身有环检测，但最好逻辑上避免。
2. **不要做耗时操作**：强制回调可能在一次布局过程中被调用很多次（比如多个关联属性变化），所以应保持轻量，只做简单的数学限制或比较。
3. **不应用来触发 UI 逻辑**：强制回调的职责是“修正值”，不是“响应值变化做业务”。UI 更新、日志记录、外部通知等应该放在属性变更通知回调（`PropertyChangedCallback`）里。

## 总结

4.2 节把依赖项属性的安全网机制讲全了。核心就是两个回调：

**验证回调（ValidateValueCallback）**：
- 目的：判断新值是否合法，不合法直接拒绝（抛异常）。
- 特点：纯函数，不能有副作用，不能修正值。
- 适用：固定范围检查（如“年龄不能为负”、“端口号 0~65535”）。
- 注册方式：在 `DependencyProperty.Register` 的参数中指定。

**强制回调（CoerceValueCallback）**：
- 目的：根据对象当前状态，把值修正到一个合理范围。
- 特点：可以访问实例其他属性，可以返回修正后的值，会覆盖输入值。
- 适用：值需要动态约束（如“Slider.Value 必须在 Minimum 和 Maximum 之间”、“结束日期 >= 开始日期”）。
- 注册方式：在 `PropertyMetadata` 中设置，并且常常需要在关联属性变化时手动调用 `CoerceValue` 来触发重新修正。

**两者关系**：
- 验证先执行，强制后执行。
- 验证负责“拦”，强制负责“改”。
- 两个都不是必需的，但有了它们，你的依赖项属性就能像 WPF 内置属性一样健壮：不管你绑什么、动画怎么动、外部怎么赋值，属性值永远在合法约束范围内。

理解这两个回调以后，你再回头看 WPF 内置控件那些属性（比如 `Range` 系列的 `Value`、`Minimum`、`Maximum`），就能看出背后那套验证和强制网络的影子。将来你写自定义控件时，这四个依赖项属性的特性——验证、强制、属性变更通知、元数据默认值——就是构筑高质量属性的四大基石。
