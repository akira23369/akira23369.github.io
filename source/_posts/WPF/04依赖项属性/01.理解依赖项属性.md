## 理解依赖项属性

前面的章节里，你学会了怎么用 XAML 搭界面、怎么用各种面板布局控件。但在写 XAML 的时候，你可能已经注意到一个现象：几乎每个控件都有一大堆属性可以设置，什么 `Width`、`Height`、`Background`、`FontSize`、`Margin`、`Grid.Row`……有些属性属于这个控件自己，有些是从别的地方“贴”过来的（比如 `Grid.Row` 就是 `Grid` 类定义的附加属性）。而且这些属性有个很神奇的共同点：它们都能跟数据绑定、动画、样式、资源引用这些东西无缝配合，还能在你不设值的时候自动从父元素或者皮肤里“继承”一个默认值。

普通的 .NET 属性能干这些事吗？完全不能。普通的 .NET 属性就是一个简单的 get/set 包装，背后直接对应类里的一个字段。你要是写 `public int Age { get; set; }`，它就老老实实存个值，别的什么都不会。但 WPF 控件上的那些属性，显然不是普通属性，它们背后有一套极其强大的基础设施在撑着。这套基础设施，就是 WPF 里最核心的概念之一——**依赖项属性（Dependency Property）**。

学 WPF 如果不把依赖项属性搞明白，后面你学数据绑定、动画、样式、模板、触发器等，都是浮沙筑高台，表面上会用，但一出错就不知道怎么排查。而一旦你真正理解了依赖项属性的设计动机和运作机制，你会发现整个 WPF 就像一张精密的网，所有特性都在这张网上自然生长出来。

这一节 4.1 就是要把依赖项属性的底裤扒开，让你看清它是什么、怎么定义的、怎么注册的、WPF 是怎么利用它的，最后再讲两种特殊形式：共享依赖项属性和附加依赖项属性。

---

### 为什么需要依赖项属性？

**先看普通属性的痛点**

在标准的 .NET 类里，属性长这样：

```csharp
public class Person
{
    private string _name;
    public string Name
    {
        get { return _name; }
        set { _name = value; }
    }
}
```

（或者自动属性 `public string Name { get; set; }`，编译器背后也是生成了一个字段。）

这种属性有什么问题？站在 WPF 的角度，问题一大堆：

1. **占用内存大**。每个实例都存一份字段。假如 `Button` 类有 80 个属性，你界面上放了 1000 个按钮，那光是按钮的属性字段就要占 80×1000 = 8 万个字段的内存。而实际上大多数属性用的都是默认值，根本没被修改过，白白浪费内存。

2. **不支持动态值解析**。普通属性你设了什么就是什么。如果想让一个文本框的 `Text` 属性自动跟某个数据对象的属性保持同步（数据绑定），或者想让一个按钮的 `Background` 在鼠标移上去时自动变色（触发器），普通属性完全没法做到，因为它的值是死的。

3. **不支持继承**。有些属性，比如 `FontSize`，你希望设在最外层窗口上，里面所有的控件自动继承这个字号，只有少数特例才自己覆盖。普通属性不具备这种“沿视觉树向下传递”的能力。

4. **不支持多种来源的优先级**。假如一个按钮的 `Background` 同时被好几方指定了：你在代码里设了 `btn.Background = Red`，在 XAML 里设了 `<Button Background="Blue" />`，在外层样式里设了 `Background="Green"`，在动画里又把它变黄了。到底该听谁的？普通属性没有“值的优先级”这个概念，后写的覆盖前面的，根本无法管理这种复杂需求。

5. **不支持“空值”占位**。普通属性要么有值，要么没有（如果是引用类型就是 `null`）。但 WPF 里经常需要一种状态：“这个属性我没设，你帮我从样式/资源/父元素那里查一个来用”。

WPF 的控件动不动就有上百个属性，如果全部用普通属性，光是内存消耗就会拖垮整个渲染系统，更别说实现上面那些高级特性了。所以 WPF 设计了一套全新的属性系统——**依赖项属性系统**。

**依赖项属性的设计哲学**

依赖项属性的核心思想一句话就能说完：**属性值不存对象里，而是由一个外部的中央仓库统一管理，需要用的时候动态计算出来。**

你可以把 WPF 的依赖项属性系统想象成一个巨大的字典，这个字典的键是“哪个对象的哪个属性”，值是该属性的“当前有效值”。当某个控件需要用到某个属性的值时（比如渲染时需要知道自己的 `Width`），它就去查这个中央仓库。仓库里有这个值？直接返回。没有？那就根据一套优先级规则去各种地方找——也许是父元素继承下来的，也许是样式里设的，也许是资源字典里引用的，也许最后回落到一个默认值。

这种方式一举解决了上述所有问题：

- **省内存**：只有被修改过的属性才存值，没被修改的属性就用默认值，默认值只需要在属性定义时存一份，所有实例共享。
- **支持动态解析**：因为每次取值都要经过中央仓库的计算流程，所以可以在取值时动态检测数据绑定、动画、样式、触发器等各种来源。
- **支持继承**：计算流程里专门有一步是“从父元素沿视觉树查找”。
- **支持优先级**：WPF 给每种值的来源都分配了不同的优先级，比如动画优先级高于直接赋值，直接赋值高于样式，样式高于继承……冲突时按优先级裁定，不会乱套。
- **支持值变更通知**：当依赖项属性的值发生变化时，WPF 会自动通知所有关心这个属性的东西（比如绑定目标刷新、触发 UI 重绘、触发动画等）。

就是因为这套共享的中央管理机制，WPF 才能把普通属性变成“依赖项”，意思是这个属性的值**依赖**于各种外部的因素（数据源、样式、动画、父元素等），而不是独立存在。它是整个 WPF 数据绑定、动画、样式系统的地基。

### 注册依赖项属性

理解了为什么需要依赖项属性，现在看怎么动手定义一个。依赖项属性不能像普通属性那样直接写个 `get; set;`，它需要向 WPF 的依赖项属性系统“注册”。

**注册依赖项属性的典型代码**

假设你自定义了一个控件，想给它加一个 `MyValue` 依赖项属性：

```csharp
public class MyControl : Control
{
    // 第一步：声明一个静态只读的 DependencyProperty 字段
    public static readonly DependencyProperty MyValueProperty =
        DependencyProperty.Register(
            "MyValue",                           // 属性的名字（字符串）
            typeof(int),                         // 属性的类型
            typeof(MyControl),                   // 该属性属于哪个类
            new PropertyMetadata(0)              // 属性的默认值和回调
        );
}
```

这行代码是整个依赖项属性系统的入口。`DependencyProperty.Register` 方法向中央仓库登记了一个新的依赖项属性，返回一个 `DependencyProperty` 对象。这个对象就是该属性在依赖项属性系统中的“身份证”。它的四个参数：

1. **属性名（`"MyValue"`）**：必须和后面 CLR 包装器的名字对应上。
2. **属性类型（`typeof(int)`）**：这个属性存什么类型的值。
3. **所有者类型（`typeof(MyControl)`）**：这个属性是哪个类注册的。
4. **属性元数据（`new PropertyMetadata(0)`）**：默认值（这里是 0），以及可能附加的验证回调、强制回调、属性变更通知回调等。这是第四步的参数，在 4.2 节会详细展开后面的回调，这里你只要知道默认值是通过它给的就行。

**`DependencyProperty` 字段的命名约定**

注意到字段名字叫 `MyValueProperty`，后缀 `Property` 是 WPF 里的强制命名约定。如果你不遵守这个约定，XAML 解析器、数据绑定引擎和一些设计工具可能会找不到这个属性。比如你叫 `MyValueProp`，编译能过，但 XAML 里写 `MyValue="100"` 可能不认。

**为什么要用 `static readonly`？**

因为 `DependencyProperty` 对象描述的是这个属性本身的元信息，它不属于任何一个实例，而是属于整个类型。就像类的类型信息一样，全类共享一份就够了。所以它必须是静态的，且初始化后不再改变（`readonly`）。

**注册的位置**

一般写在控件类的定义内部，作为一个静态字段。也可以写在静态构造函数里动态注册，但最常用的就是内联初始化。

**依赖项属性系统内部的存储**

当 `Register` 被调用时，WPF 内部会建立一个全局的键值映射，键是 `DependencyProperty` 对象，值是每个实例的属性值。运行时，每个 `DependencyObject` 实例（所有 WPF 控件都派生自它）内部有一个高效的数据结构（`EffectiveValueEntry` 数组）来存储这个实例的那些“被修改过的”依赖项属性值。没有修改过的属性根本不占存储空间，取值时直接返回元数据里的默认值。

### 添加属性包装器

注册完 `DependencyProperty` 后，你的控件现在确实拥有了一个依赖项属性，但 C# 代码里还不能像普通属性那样用 `myControl.MyValue = 10`。因为 `DependencyProperty` 是给底层系统用的，CLR 代码需要一个友好的接口来访问它。

这就需要**属性包装器（CLR 包装器）**。它就是一个看起来跟普通属性一模一样的 get/set，但内部不是操作私有字段，而是调用 `GetValue` 和 `SetValue` 方法：

```csharp
public class MyControl : Control
{
    public static readonly DependencyProperty MyValueProperty =
        DependencyProperty.Register("MyValue", typeof(int), typeof(MyControl),
            new PropertyMetadata(0));

    // CLR 包装器
    public int MyValue
    {
        get { return (int)GetValue(MyValueProperty); }
        set { SetValue(MyValueProperty, value); }
    }
}
```

**`GetValue` 和 `SetValue` 是哪儿来的？**

这两个方法定义在 `DependencyObject` 基类里。所有 WPF 的可视元素（`UIElement`、`FrameworkElement`、`Control` 等）都继承自 `DependencyObject`，所以都天然具备调用 `GetValue` / `SetValue` 的能力。

- `GetValue(DependencyProperty dp)`：从依赖项属性系统里获取当前实例该属性的“有效值”。它走优先级解析流程，可能触发继承、样式查找、绑定解析等。
- `SetValue(DependencyProperty dp, object value)`：给当前实例的该属性设置一个“本地值”（优先级最高的一类值之一）。这会覆盖动画、样式等其他来源的值。

**包装器里不要加额外逻辑**

这一点非常重要！依赖项属性的包装器只能有 `GetValue` 和 `SetValue` 这两个调用，绝对不能在里面加任何额外的业务逻辑。原因是：WPF 内部在很多情况下会绕过 CLR 包装器，直接调用 `GetValue` / `SetValue`。比如 XAML 解析器在创建对象并赋值时，它就通过 `DependencyProperty` 对象直接去调 `SetValue`，根本不会碰你的 CLR 包装器。如果你在包装器的 set 里加了一段验证逻辑，结果运行时 XAML 赋值绕过去了，你的逻辑就被漏掉。验证逻辑应该放在属性元数据的回调里（4.2 节讲）。

因此，依赖项属性的 CLR 包装器就是一个纯粹的中转站，只做类型转换（`GetValue` 返回 `object`，你需要强转）和暴露给 C# 代码使用。

**XAML 解析器怎么找到包装器的？**

XAML 解析器在看到 `<MyControl MyValue="100" />` 时，并不是直接调用 CLR 包装器的 `set_MyValue` 方法，而是查找 `MyControl` 类的静态成员 `MyValueProperty`，然后通过这个 `DependencyProperty` 调用 `SetValue`。它之所以能找到 `MyValueProperty`，靠的就是命名约定：属性名 + "Property" 后缀。如果字段名不遵守约定，XAML 赋值就会失败。

这也从侧面说明了，依赖项属性本质上不是 CLR 属性，CLR 包装器只是给开发者提供语法糖的“假象”。真正的属性存在依赖项属性系统这个“平行世界”里，CLR 包装器是连通这两个世界的桥梁。

### WPF 使用依赖项属性的方式

前面讲的是怎么定义依赖项属性，但 WPF 自带的上百个依赖项属性到底是怎样被整个框架充分利用的？这才是依赖项属性真正闪光的地方。它支撑起了 WPF 至少六大核心特性的实现。

**1. 数据绑定（Data Binding）**

这是依赖项属性最常见的用途。当你写 `Text="{Binding UserName}"` 时，目标属性必须是依赖项属性，否则绑定引擎没法访问它。因为绑定引擎在运行时通过 `DependencyObject.GetValue` 和 `DependencyObject.SetValue` 来读取和写入目标属性的值，它根本不认普通的 CLR 属性。

所以你在 WPF 里能绑定的属性，几乎全都是依赖项属性：`TextBox.Text`、`Button.IsEnabled`、`ListBox.SelectedItem`……你自定义控件里的属性要想支持绑定，也必须注册成依赖项属性。

**2. 样式（Style）与 Setter**

样式里的 `Setter` 本质上是给目标属性设定一个值。这个“设定”不是简单的 CLR 赋值，而是通过依赖项属性系统，以样式优先级写入属性值。因为有了优先级机制，样式设置的值可以被更具体的东西（如本地值、触发器、动画）覆盖。普通属性做不到这种层级覆盖。

```xml
<Style TargetType="Button">
    <Setter Property="Background" Value="Red" />
</Style>
```

这里的 `Property="Background"` 实际上在运行时会被解析为 `Button.BackgroundProperty` 这个依赖项属性。如果没有依赖项属性系统，样式 Setter 根本不知道往哪里设值。

**3. 动画（Animation）**

动画是通过线性插值不断改变一个属性的值来产生视觉效果。这个被改变的属性必须是依赖项属性。动画引擎通过 `DependencyProperty` 在背后以极高的频率调用 `SetValue` 来更新属性值，而且动画的值拥有比本地值更高的优先级（这样动画结束后属性可以回弹到原来的值，不会永久改变）。

```csharp
var animation = new DoubleAnimation(0, 300, TimeSpan.FromSeconds(1));
myButton.BeginAnimation(Button.WidthProperty, animation);
```

如果 `Width` 是普通 CLR 属性，动画写入的新值就直接覆盖了旧值，动画结束后你无法自动恢复原值。而依赖项属性的优先级系统会记录动画值是一个单独的值源，动画结束后自动移除动画值源，属性自然回落到上一个优先级的来源（比如本地值或样式值）。这个“自动回弹”行为全靠依赖项属性。

**4. 属性值继承（Value Inheritance）**

前面提过，有些属性会自动从父元素传递给子元素。比如你在 `Window` 上设了 `FontSize="20"`，窗口里所有 `TextBlock`、`Button` 的字号都会变成 20，除非子元素显式覆盖。这种能力叫“属性值继承”。

但不是所有依赖项属性都自动支持继承。在注册属性时，可以通过元数据标明这个属性是“可继承的”。框架内置的 `FontSize`、`FontFamily`、`DataContext` 等就是如此。

实现继承的原理：在依赖项属性的值解析过程中，如果查找当前实例的本地值没有，就到父元素的依赖项属性系统上去查同一个属性，一直向上到视觉树的根。父元素的值如果也没有，就回落到默认值。

**5. 资源引用（StaticResource / DynamicResource）**

在 XAML 里你可以用 `{StaticResource MyBrush}` 引用资源字典里的一个画刷对象。这个资源引用的目标属性也必须是依赖项属性。因为资源查找时需要延迟求值（XAML 解析时资源可能还没加载完），依赖项属性系统提供了将 `ResourceReferenceExpression` 挂到属性上，等资源就绪再计算最终值的机制。

**6. 触发器（Trigger）**

触发器用来在某个条件满足时改变属性值。比如“鼠标悬停时按钮背景变蓝”。这些被改变的属性也全是依赖项属性。

```xml
<Trigger Property="IsMouseOver" Value="True">
    <Setter Property="Background" Value="Blue" />
</Trigger>
```

触发器通过依赖项属性系统写入值，且优先级低于本地值，所以当你用代码显式设了 `Background` 后，触发器不再生效。

**7. 强制与验证回调（Coerce / Validate）**

依赖项属性可以在注册时指定一个“强制回调”和一个“验证回调”。强制回调允许你在设置属性值之前或某些外部条件变化时，强制把值修正到一个合法范围。比如 `Slider` 的 `Value` 必须夹在 `Minimum` 和 `Maximum` 之间。验证回调则是在设值之前判断新值是否合法，不合法直接抛异常拒绝。

这两个回调是依赖项属性专有的，普通 CLR 属性只能在 set 里写验证，但无法处理多属性联动强制的情况。

**8. 依赖项属性的值优先级**

WPF 给所有可能的属性值来源排了一个严格的优先级顺序。当多个来源同时为同一个依赖项属性提供了值时，取优先级最高的那个。这个优先级从高到低大致如下（简化版）：

1. 强制回调（Coercion）返回的值（最高）
2. 活动动画
3. 本地值（通过代码或 XAML 直接赋的值，包括 Setter）
4. 模板属性触发器（Template Trigger）
5. 样式触发器
6. 样式 Setter
7. 默认样式（基于主题）
8. 继承值
9. 元数据默认值

这个优先级机制就是依赖项属性系统被叫做“依赖”的原因：属性的最终值依赖于所有这些来源的竞争结果。

**依赖项属性的“依赖”二字，现在应该明白了**

它不是“依赖注入”那种依赖，而是“最终值依赖于多重因素”。一个依赖项属性的有效值可能来自绑定、资源、继承、动画、样式、触发器、强制回调等等，而且这些因素可以随时动态变化。依赖项属性系统不停地重新计算有效值，确保 UI 实时的呈现最新的结果。

### 共享的依赖项属性

这一小节讲的是一个比较特殊的场景：有时两个不同的类，居然想共享同一个依赖项属性。这听起来有点不可思议，但在 WPF 里确实存在，而且很常见。

**场景：文本格式化属性**

WPF 里有一些控件可以包含文本内容，比如 `TextBlock`、`TextBox`、`Button`、`Label` 等。这些文本的格式化需要使用很多属性：`FontSize`、`FontFamily`、`Foreground`、`FontWeight` 等等。这些属性在多个控件里都存在，而且行为完全一致。如果每个控件都自己注册一遍同名的依赖项属性，不仅重复劳动，而且会导致在样式和模板里不能跨类型统一设置。

WPF 的做法是：把这些文本格式化属性定义在一个单独的静态类 `TextElement` 里，然后让需要这些属性的控件通过 `AddOwner` 的方式“共享”这些依赖项属性。

**`AddOwner` 方法**

`DependencyProperty` 类有一个 `AddOwner` 方法，允许另一个类型把这个属性“挂到”自己名下，就好像它自己注册了这个属性一样。

典型代码：

```csharp
// TextElement 注册了 FontSizeProperty
public static readonly DependencyProperty FontSizeProperty =
    TextElement.FontSizeProperty.AddOwner(typeof(MyControl));
```

之后，`MyControl` 就拥有了 `FontSize` 这个依赖项属性，可以用 `myControl.FontSize` 来访问，在 XAML 里也可以直接写 `<MyControl FontSize="20"/>`。而且这个 `FontSizeProperty` 和 `TextElement.FontSizeProperty` 实际上是同一个对象，所以值存储是共享的，样式里也可以统一设置。

**共享属性的好处**

1. **统一管理**：属性逻辑（默认值、验证、强制、可继承性）定义一次，到处使用。
2. **样式友好**：如果你写一个样式目标为 `TextElement`，设置 `FontSize`，所有共享了该属性的控件都会受这个样式影响。这在你需要统一全应用文字大小时非常方便。
3. **减少内存占用**：同一个依赖项属性只有一个静态对象，所有使用它的类共享同一个 `DependencyProperty` 标识，内部存储也是基于这个标识进行的。

**哪些属性是共享的？**

`TextElement` 类上有一大堆属性：`FontSize`、`FontFamily`、`FontStyle`、`FontWeight`、`Foreground`、`TextAlignment` 等等。控件如 `Control` 和 `TextBlock` 都通过 `AddOwner` 获得了这些属性。`Control` 还把自己得到的属性进一步分享给了它的子类，比如 `Button`、`Label` 等。

另外，`TextBlock` 自己也有一些文本属性，但你会发现 `Button` 等控件其实也拥有这些属性——因为 `Button` 内部模板使用了 `TextBlock`，它需要这些属性来格式化按钮上的文字。

**`AddOwner` 可以修改元数据**

调用 `AddOwner` 时，你还可以传入一个新的 `PropertyMetadata`，覆盖原属性的一些元数据设置。比如原属性默认值是 11，你可以在 `AddOwner` 时改成 12。但是要注意，这会改变所有此类型的实例的默认值，所以要谨慎使用。

### 附加的依赖项属性

在布局章的时候你已经大量用过附加属性了：`Grid.Row`、`Canvas.Left`、`DockPanel.Dock`。这些属性不属于使用它们的元素自己，而是由另一个类（`Grid`、`Canvas`、`DockPanel`）定义的，然后“附加”到元素上使用。附加属性在依赖项属性系统里是一种特殊形式，它们本质也是依赖项属性，只是注册方式稍有不同，并且有配套的静态 Get/Set 方法。

**定义附加属性**

普通依赖项属性用 `DependencyProperty.Register` 注册，附加属性用 **`DependencyProperty.RegisterAttached`** 注册。

```csharp
public class MyPanel : Panel
{
    public static readonly DependencyProperty RowProperty =
        DependencyProperty.RegisterAttached(
            "Row",                 // 属性名
            typeof(int),           // 属性类型
            typeof(MyPanel),       // 所有者类型
            new PropertyMetadata(0) // 默认元数据
        );

    // 配套的静态 Get/Set 方法
    public static int GetRow(DependencyObject obj)
    {
        return (int)obj.GetValue(RowProperty);
    }

    public static void SetRow(DependencyObject obj, int value)
    {
        obj.SetValue(RowProperty, value);
    }
}
```

注意和普通依赖项属性定义的几点不同：

1. 注册用的是 `RegisterAttached` 而不是 `Register`。
2. 除了 `DependencyProperty` 字段，还必须提供一对**公有的静态方法** `GetXxx` 和 `SetXxx`。这里的方法名必须严格符合 `Get属性名`、`Set属性名` 的格式。这两个方法不是给自己用的，而是给任何 `DependencyObject` 用的。因为附加属性的目标对象不是属性所有者自己，而是别的任意元素。
3. 通常不会为附加属性提供 CLR 实例包装器（因为属性不属于目标元素自己）。XAML 里通过 `MyPanel.Row="1"` 这种语法，解析器会找到 `SetRow` 方法并调用。

**XAML 解析附加属性的过程**

看到 `<Button Grid.Row="1" />` 时，XAML 解析器：
1. 发现 `Grid.Row` 是一个带点的属性名。
2. 查找 `Grid` 类上的静态方法 `SetRow` 和 `GetRow`，以及对应的 `DependencyProperty` 字段 `RowProperty`。
3. 调用 `Grid.SetRow(button, 1)`，内部通过 `button.SetValue(RowProperty, 1)` 把值存到按钮这个实例的依赖项属性存储中。

这说明附加属性虽然是 `Grid` 类注册的，但属性值实际上是存在被附加的那个元素（这里是 `Button`）身上。`Grid` 只是“定义者”和“访问接口提供者”。等到 `Grid` 做布局计算时，它遍历自己 Children 里的每个子元素，调用 `Grid.GetRow(child)` 去读取存这个元素身上的行号，然后据此安排位置。

**附加属性为什么必须用依赖项属性？**

因为附加属性的值也需要参与绑定、动画、样式等高级特性。比如你可以把 `Canvas.Left` 绑定到一个数据模型的 X 坐标，实现元素跟随数据移动。如果附加属性只是一个普通的静态 Get/Set 外加一个字典存储，就无法享受依赖项属性的优先级、继承（虽然附加属性一般不继承）、动画等好处。

实践中，附加属性还经常被用来扩展已有控件的行为，比如所有 MVVM 框架都利用附加属性来实现命令绑定、焦点管理、拖拽行为等。这是 WPF 非常灵活的一点，后面到 MVVM 和进阶话题时会大量涉及。

## 总结

4.1 节是依赖项属性这一章的根基，信息密度很大。我们把它拆成几个核心要点收一下：

1. **依赖项属性是什么**：一种由 WPF 全局系统集中管理的属性，属性值不直接存对象里，而是在需要时动态计算出来。它的值“依赖”于绑定、样式、动画、继承等多种来源。

2. **为什么需要它**：省内存（默认值共享）、支持数据绑定、动画、样式、触发器、属性继承等高级特性，这些都是普通 CLR 属性无法做到的。

3. **怎么定义一个依赖项属性**：用 `DependencyProperty.Register` 注册一个静态只读的 `DependencyProperty` 字段，然后写一个 CLR 包装器（get/set 内部只调 `GetValue` / `SetValue`）。

4. **WPF 怎么用依赖项属性**：数据绑定、样式 Setter、动画、属性值继承、资源引用、触发器、强制验证回调，这些 WPF 核心子系统全都构筑在依赖项属性之上。依赖项属性值有多重来源，WPF 按照一套严格的优先级顺序决定最终有效值。

5. **共享依赖项属性**：不同类可以通过 `AddOwner` 共用同一个依赖项属性，实现属性逻辑统一管理和样式友好。典型例子是 `TextElement` 的那些文本属性。

6. **附加依赖项属性**：用 `RegisterAttached` 注册，配合静态 Get/Set 方法，允许一个类把属性“附加”到别的类的实例上。典型就是布局面板用的 `Grid.Row`、`Canvas.Left` 等。

把这六个点理解透了，你再看 WPF 里任何一个控件的任何一个属性，脑子里就不再只是一个 get/set，而是能想象出它背后那套庞大的依赖项属性网络在如何运转。这种理解会在你后面的学习中不断被验证和加深——学数据绑定时你会发现“哦原来绑定目标必须是用依赖项属性”，学动画时你会恍然大悟“原来动画能自动回弹就是因为优先级机制”，写自定义控件时你会知道“我这个属性想让外面绑定，必须注册成依赖项属性”。

接下来 4.2 节会深入依赖项属性的验证和强制回调，教你如何在属性值变化时插入自己的逻辑，实现更安全的属性系统。
