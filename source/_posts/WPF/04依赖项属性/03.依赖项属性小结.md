## 小结

第4章学完了。这一章是整个 WPF 里最能体现“框架设计智慧”的章节之一。依赖项属性这个东西，表面上看只是把普通属性换了一种写法，实际上它是 WPF 那么多高级特性（数据绑定、动画、样式、触发器、属性继承、资源引用……）能够无缝运转的根基。把这章吃透了，你后面学那些特性的时候就会感觉顺理成章；如果这章迷迷糊糊地过去，后面每一次碰到“为什么绑定不上”、“为什么动画不生效”、“为什么样式设了没用”这种问题时，你都得满头大汗地回头翻。

所以这一节小结，咱们就把依赖项属性的来龙去脉、核心要点、以及它在整个 WPF 体系里的位置，从头到尾再捋一遍。

---

## 一、为什么要发明依赖项属性？

这个问题是理解一切的前提。普通 .NET 属性（CLR 属性）很简单，就是一个 get/set 包装一个私有字段，值直接存在对象里。但是 WPF 的需求完全不是“简单存个值”这么单纯：

**第一个问题：内存浪费。** WPF 控件动不动有几十上百个属性，假如你在界面上放了 1000 个按钮，每个按钮有 80 个属性，全部用普通属性的话就要占用 8 万个字段的内存。而实际上绝大多数属性用的都是默认值，根本没被修改过，这些默认值每个实例都存一份，极度浪费。

**第二个问题：不支持动态值表达式。** 你想让一个文本框的 `Text` 属性和后台数据对象自动同步（数据绑定），或者想让一个按钮的颜色随着鼠标悬停自动改变（触发器），或者想让某个值在一段时间内平滑变化（动画）。这些效果都要求属性不能是一个死值，而必须能在运行时被动态计算。普通属性做不到这一点。

**第三个问题：不支持值的优先级管理。** 假如一个按钮的 `Background` 同时被好几处指定了：你代码里设了红色，XAML 里设了蓝色，样式里设了绿色，动画里又把它改成黄色，最后该听谁的？普通属性只能靠“最后写的覆盖前面的”，没有一套完善的多来源优先级机制。

**第四个问题：不支持属性值沿视觉树继承。** 你在顶层窗口上设置了 `FontSize="16"`，希望里面所有的控件默认都用这个字号。普通属性做不到这种“向下传递”——除非你给每个控件都手动设一遍。

**第五个问题：不支持属性变更通知机制。** 当一个属性变化时，布局需要重新计算、绑定目标需要刷新、动画需要更新状态。如果属性就是一个简单的字段赋值，根本没有地方挂这些“联动逻辑”。

这五个问题，随便哪一个都是普通属性无法解决的。微软的工程师们没有选择在每个地方都用代码硬凑这些功能，而是重新设计了一整套属性系统——**依赖项属性系统**。它的核心思想就是：**属性值不直接存在对象里，而是由一个全局的中央仓库统一管理，需要用时根据一套优先级规则动态计算出来。**

有了依赖项属性，上面五个问题全部迎刃而解：
1. **省内存**：没被修改的属性不占实例内存，所有实例共享一份默认值。
2. **支持动态解析**：每次 `GetValue` 取值时，系统都会根据数据绑定、动画、样式、继承等来源动态计算当前有效值。
3. **内置优先级**：WPF 给动画、本地值、样式、继承等来源分配了不同优先级，冲突时按优先级裁决。
4. **支持属性值继承**：某些属性（如 `FontSize`）会自动从父元素往下传递。
5. **内置变更通知**：属性值变化时，系统自动通知所有相关方（布局、绑定、动画等）。

理解了这个“为什么”，整个第 4 章就不是一堆机械的 API 调用，而是一个有灵魂的设计。依赖项属性的“依赖”，指的就是属性值**依赖于**多种外部因素的综合作用，而不是独立地、静态地存储。

## 二、依赖项属性是怎么定义的？

定义依赖项属性和定义普通属性完全不一样，它需要三个步骤：

**第一步：注册。** 用 `DependencyProperty.Register`（或 `RegisterAttached`）向 WPF 的全局属性系统登记这个属性。这相当于给属性申请一个“身份证”——`DependencyProperty` 对象。

```csharp
public static readonly DependencyProperty MyValueProperty =
    DependencyProperty.Register(
        "MyValue",                      // 属性的字符串名称
        typeof(int),                    // 属性的值类型
        typeof(MyControl),              // 属性属于哪个类
        new PropertyMetadata(0)         // 元数据（默认值、回调等）
    );
```

这个 `DependencyProperty` 对象是静态的、只读的，全类共用一份。它的名字必须严格遵守“属性名 + Property”的后缀约定，否则 XAML 解析器和绑定引擎可能找不到这个属性。

**第二步：添加 CLR 包装器。** 有了 `DependencyProperty` 对象之后，为了在 C# 代码里能用自然的方式读写属性（`myCtrl.MyValue = 10`），需要写一个看起来像普通属性的 CLR 包装器。但这个包装器内部**只做一件事**：调用 `DependencyObject` 基类的 `GetValue` 和 `SetValue` 方法。

```csharp
public int MyValue
{
    get { return (int)GetValue(MyValueProperty); }
    set { SetValue(MyValueProperty, value); }
}
```

**必须谨记**：包装器里绝对不能加任何额外逻辑（如验证、通知等），因为 WPF 在很多情况下（XAML 加载、绑定、动画、样式 Setter）会直接通过 `DependencyProperty` 去调 `GetValue` / `SetValue`，绕过你的 CLR 包装器。所有验证和附加逻辑应该通过元数据的回调来实现。

**第三步：配置元数据。** `PropertyMetadata` 里可以设置：
- **默认值**：构造函数第一个参数。
- **属性变更通知回调**（`PropertyChangedCallback`）：值变化后触发，用于响应变化做业务或 UI 更新。
- **强制回调**（`CoerceValueCallback`）：修正值的逻辑（见后面第六点）。
- **验证回调**（`ValidateValueCallback`）：检查值是否合法（见后面第六点）。

这三步走完了，你就拥有了一个完整的、能享受 WPF 所有高级特性的依赖项属性。

## 三、注册依赖项属性的细节

4.1.2 节专门讲了 `Register` 方法。几个关键点再强调一下：

- **`Register` vs `RegisterAttached`**：普通依赖项属性用 `Register`，附加属性用 `RegisterAttached`。两者的区别在于附加属性需要额外提供静态 `GetXxx`/`SetXxx` 方法，因为它要被用在不是自己的类上。
- **元数据**：`PropertyMetadata` 是所有元数据的基类。对于 `FrameworkElement` 及其子类，通常使用 `FrameworkPropertyMetadata`，因为它增加了更多布局相关的选项（比如是否可以继承、是否影响测量/排列、是否支持数据绑定默认等）。
- **默认值**：默认值在 `PropertyMetadata` 构造时指定。要注意的是，引用类型的默认值一定要小心不要被多个实例共享修改（比如默认值是 `new List<int>()` 会造成所有未设值的实例共享同一个 List 实例）。一般引用类型的默认值要么设为 `null`，要么在 `PropertyChangedCallback` 里做惰性初始化，要么使用 `Freezable`（后面章节会接触）。
- **属性名和字段名的约定**：属性名（如 `MyValue`）和依赖项属性字段名（`MyValueProperty`）必须对应，后缀 `Property` 不可省略。

## 四、附加属性：不属于我的属性也能贴到我身上

4.1.6 节讲了附加属性。它是 WPF 布局系统灵活性的关键技术基础。

**和普通依赖项属性的区别**：
- 普通依赖项属性：我自己注册，我自己用（比如 `Button.Width`）。
- 附加属性：别人注册，但可以贴到我身上用（比如 `Grid.Row` 是 `Grid` 注册的，但贴在 `Button` 上）。

**定义方式**：用 `RegisterAttached` 注册，同时提供一对静态的 `GetXxx` 和 `SetXxx` 方法。XAML 解析器在看到 `Grid.Row="1"` 时，会调用 `Grid.SetRow(button, 1)`。

**值存在哪**：附加属性的值是存在被附加的那个对象（`Button`）的依赖项属性存储里的，而不是存在属性定义者（`Grid`）身上。定义者只是提供了“操作接口”。

**为什么必须用依赖项属性**：因为附加属性也需要参与绑定、动画、样式等高级特性。同时，附加属性还可以被用来扩展已有控件的行为（如 MVVM 中的命令绑定、焦点管理），这也是依赖项属性系统带来的扩展性红利。

## 五、依赖项属性支撑起了整个 WPF 的特性大厦

4.1.4 节是这一章里最“开阔视野”的一节。它讲了依赖项属性不是孤立的，而是和 WPF 几乎所有核心子系统深度集成的。

**数据绑定**：绑定的目标属性必须是依赖项属性。绑定引擎通过 `GetValue` 和 `SetValue` 来读写目标值，完全不走 CLR 包装器。所以你自己定义的属性如果想支持绑定，必须注册成依赖项属性。

**样式 Setter**：样式里的 `Setter` 本质上是给依赖项属性设一个“样式优先级”的值。有了优先级机制，样式值才能被本地值或动画覆盖。普通属性没有优先级概念，样式无法和本地值和平共处。

**动画**：动画是通过在短时间内连续修改依赖项属性的值来产生过渡效果。动画写入的值拥有比本地值更高的优先级，动画结束后自动清除动画值，属性回复到动画前的状态。这个“自动回弹”完全依赖依赖项属性的优先级体系。

**属性值继承**：某些属性（如 `FontSize`、`DataContext`）可以沿视觉树从父元素传递给子元素。这通过在注册时设置 `FrameworkPropertyMetadata` 的 `Inherits` 属性为 `true` 来启用。依赖项属性的值解析流程里会包含“向父元素查找”这一步。

**资源引用**：`{StaticResource}` 和 `{DynamicResource}` 的工作，依赖于依赖项属性系统能在资源未就绪时挂一个占位符，等资源加载完成再刷出最终值。

**触发器**：`Trigger`、`DataTrigger` 等也是通过依赖项属性系统，以特定的优先级写入属性的值。当触发条件不再满足时，它写入的值会被移除，属性自动回落到上一个优先级的值。

**强制与验证**：依赖项属性系统内建的强制回调和验证回调，为属性提供了“安全网”，这是普通属性无法集中实现的。

这一连串的“接口对接”说明了一个事实：**依赖项属性是整个 WPF 属性系统的中央枢纽，所有要动态改变控件外观和行为的功能，都要通过它来工作。**

## 六、属性验证：安全网机制

4.2 节讲的两个回调——验证回调和强制回调——是依赖项属性的“保安系统”。

**验证回调（ValidateValueCallback）**：
- 作用：纯粹的“安检门”，判断新值是否合法。不合法的直接抛异常拒绝，属性值不动。
- 特点：纯函数，不能有副作用，不能改值，只判断对错。
- 适用场景：固定的、不依赖其他属性的范围检查（如“年龄不能为负数”、“端口号 0~65535”）。
- 注意：验证回调返回 `false` 会抛 `ArgumentException`，所以使用时要考虑调用方是否能处理这个异常。

**强制回调（CoerceValueCallback）**：
- 作用：更聪明的“修正官”，根据对象当前状态，把不合理的值修正为合理值并返回。
- 特点：可以访问实例的其他属性，可以根据综合状态动态修正，返回修正后的值进入最终生效。
- 适用场景：值需要被其他属性动态约束的情况（如 `Slider.Value` 受 `Minimum` 和 `Maximum` 约束，`EndDate` 必须大于等于 `StartDate`）。
- 触发时机：不仅 SetValue 时触发，关联属性变化时也可以通过调用 `CoerceValue` 方法手动触发重新修正。

**两者的关系和执行顺序**：
1. 新值到来 → 先过验证回调 → 不通过就抛异常，流程终止。
2. 验证通过 → 过强制回调 → 得到修正后的值 → 最终写入属性。

**与关联属性的联动**：当一个属性的值变化可能影响另一个属性的合法范围时，需要在第一个属性的变更通知回调里手动调用 `DependencyObject.CoerceValue` 方法，强制第二个属性重新走一遍强制回调。这是实现多属性协同约束的标准模式。

验证和强制回调让依赖项属性从“被动存储”变成了“主动防御”，这是 WPF 内置控件（如 `Slider`、`ScrollBar`、`DatePicker` 等）之所以健壮的重要原因。

## 七、依赖项属性 vs 普通 CLR 属性：一张对比表

为了帮你快速回忆和对比，这里放一张简表：

| 方面           | 普通 CLR 属性        | 依赖项属性            |
| ------------ | ---------------- | ---------------- |
| 存储           | 值直接存在实例字段里       | 值存在全局系统，按需计算     |
| 内存           | 每个实例都存一份值        | 未修改时共享默认值，节省内存   |
| 数据绑定目标       | 不支持              | 支持               |
| 样式 Setter 目标 | 不支持              | 支持               |
| 动画目标         | 不支持              | 支持（动画值独立优先级，可回弹） |
| 属性值继承        | 不支持              | 支持（需在元数据开启）      |
| 值优先级         | 没有，后写覆盖前写        | 严格的多来源优先级体系      |
| 验证和强制        | 只能在 set 里手写，易被绕过 | 系统级回调，覆盖所有设值通道   |
| 变更通知         | 需手动实现            | 内建，任何变化自动通知相关方   |

## 八、学完第4章你应该达到的状态

1. **能解释依赖项属性的本质**：它不是简单属性，而是一套中央管理的、支持多来源值和优先级解析的属性系统，是 WPF 高级特性的底层枢纽。

2. **能独立注册一个依赖项属性**：会写 `DependencyProperty.Register`，知道参数的含义，会写 CLR 包装器，且清楚包装器里不能加逻辑。

3. **能区分普通属性和依赖项属性的使用场景**：明白为什么普通属性不能用于绑定/动画/样式，什么时候必须上依赖项属性。

4. **理解附加属性**：知道它和普通依赖项属性的区别，会定义附加属性，能解释布局面板（`Grid.Row`、`Canvas.Left`）的工作原理。

5. **能用验证和强制回调保护属性**：会为属性添加合法的值范围检查，会处理多属性联动的约束修正。

6. **能从 WPF 整体角度看待依赖项属性**：知道数据绑定、动画、样式、触发器、属性继承、资源引用都是建立在依赖项属性系统上的“上层建筑”。
