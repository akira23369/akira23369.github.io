## WPF 事件

前两节把路由事件的机制讲透了——怎么注册、怎么引发、冒泡和隧道是怎么走的。从这一节开始，咱们要正式认识 WPF 里各种现成的具体事件了。毕竟你实际写程序时，绝大多数时候不是在定义自己的路由事件，而是在用 WPF 已经给你准备好的那些事件：鼠标点了一下、键盘按了个键、窗口打开了、窗口关了、控件加载完了……

这些事件看起来一个一个散着，但其实可以非常清晰地分成两大类：**生命周期事件**和**输入事件**。

- **生命周期事件**：反映一个元素或窗口从“创世”到“毁灭”的各个阶段。比如初始化好了、加载完成了、被激活了、被关闭了、被卸载了。这类事件帮你掌握一个控件或窗口的整个生存状态，是做初始化、资源分配、清理收尾的切入口。
- **输入事件**：反映用户和程序之间的物理交互。比如鼠标按下、松开、移动、滚轮滚动；键盘按下、松开；触控手指的点击、拖动、缩放。这些事件是 WPF 交互系统的命脉，绝大部分用户操作的逻辑都挂在这上面。

5.3 节就是对这两大类事件做一个总体介绍。咱们先讲生命周期事件，再讲输入事件。

---

### 生命周期事件

任何一个 WPF 元素，从它被 new 出来到最终被垃圾回收，中间会经历一系列“人生阶段”。每个阶段的转换，WPF 都会触发特定的事件。这些事件就叫**生命周期事件**。

生命周期事件不是路由事件（它们大多只是普通的 CLR 事件，或是直接事件，不会冒泡和隧道），但它们贯穿每个元素的生老病死，理解它们能帮你把初始化代码、清理代码、状态管理放在最合适的时机。

#### 一、所有元素的通用生命周期事件

所有 WPF 的可视元素都继承自 `FrameworkElement`，而 `FrameworkElement` 定义了一套通用的生命周期事件。只要你是在跟界面上的任何东西打交道（控件、面板、图形、文字……），这些事件都会按固定顺序发生。

完整的生命周期顺序如下：

**1. Initialized（初始化完成）**

- **触发时机**：元素被创建，并且它的依赖项属性已经初始化完毕，XAML 里写的属性值都已经加载好了。但是**元素还没有被加入到任何逻辑树或视觉树里**，它还是一个“孤儿”。
- **用途**：适合做一些不依赖于其他元素、不依赖于布局、不依赖于数据上下文的初始化工作。比如设置一些内部状态变量，初始化不涉及外观的私有数据结构。
- **事件参数**：普通的 `EventArgs`。
- **注意**：此时元素的 `Parent` 属性还是 `null`，你拿不到它未来会在哪个容器里，也拿不到 `DataContext`（除非你手动设了）。

**2. Loaded（加载完成）**

- **触发时机**：元素**已经被加入到逻辑树和视觉树中**，布局系统已经完成了第一次测量和排列，元素有了最终的尺寸和位置。这个时候它的 `Parent`、`VisualParent` 都已经就位，数据上下文（`DataContext`）通常也已经从父元素继承过来了。
- **用途**：这是**最常用**的初始化时机。大部分需要在界面显示后做的逻辑都放这里——比如填充默认数据、计算相对位置、开始动画、注册一些依赖于其他元素的事件、调整布局相关的东西。
- **事件参数**：`RoutedEventArgs`（是的，`Loaded` 和 `Unloaded` 是 CLR 事件的同时也是路由事件，它们的路由策略是 `Direct`，但可以通过 `AddHandler` 在父容器上统一监听子树中所有元素的 `Loaded`）。
- **特别重要**：`Loaded` 事件是**冒泡**的（实际上是 CLR 事件直接触发，但它的底层路由事件版本是 `FrameworkElement.LoadedEvent`，策略是 `RoutingStrategy.Direct`，所以你不能在父容器上通过冒泡收到子元素的 `Loaded` 事件。但父元素自己的 `Loaded` 会在它自己加载完成时触发，这时可以确定它的所有子元素也都已经加载完毕了）。很多书上讲 `Loaded` 是冒泡的，其实在实际开发时你直接在元素上挂 `Loaded="..."` 就行，父容器要统一处理子元素 `Loaded` 则需要用 `EventManager.RegisterClassHandler` 或者在代码里统一订阅，这个比较进阶，暂时知道即可。
- **和 `DataContext` 的关系**：`Loaded` 时，元素的 `DataContext` 通常已经从父元素传递下来了（因为 `DataContext` 是依赖项属性，会沿视觉树继承）。所以你在 `Loaded` 事件里通过 `DataContext` 获取 ViewModel 是非常安全的。而 `Initialized` 时 `DataContext` 可能还是 `null`。

**3. Unloaded（卸载完成）**

- **触发时机**：元素被从逻辑树和视觉树中**移除**时触发。比如你关闭了一个窗口，窗口里的所有元素都会依次触发 `Unloaded`；或者你把某个控件从 `Panel.Children` 里 Remove 掉了；或者你切换了选项卡，把一整个 TabItem 的内容区换掉了。 
- **用途**：清理资源、取消订阅事件、停止计时器、停止动画，防止内存泄漏。`Loaded` 里注册的东西，通常要在 `Unloaded` 里反注册。
- **事件参数**：`RoutedEventArgs`。
- **注意**：`Unloaded` 不一定意味着元素就死了。WPF 的元素可以被移除后再被加回来（比如 Tab 切换场景），此时会再次触发 `Loaded`。所以 `Unloaded` 只是“暂时离开视觉树”，不是“彻底销毁”。

#### 二、Window 类的专有生命周期事件

`Window` 除了继承上面 `FrameworkElement` 的那三个通用事件外，还有自己的六个核心生命周期事件（加上继承来的一共更多，但这六个是 Window 特有的）。这些事件反映了一个窗口从生到死的更精细的过程。

**1. SourceInitialized（窗口句柄创建完成）**

- **触发时机**：`Window` 的底层 Win32 句柄（HWND）已经创建完毕，但窗口还没有显示出来。这是 `Window` 生命周期里**最早**的一个事件。
- **用途**：需要和 Win32 API 交互、修改窗口样式、做窗口子类化（HwndSource Hook）等底层操作时，必须在这个事件之后才能做，因为这时 HWND 已经有效。
- **事件参数**：`EventArgs`。
- **底层说明**：WPF 窗口最终还是依靠 Win32 窗口句柄来和操作系统打交道。`SourceInitialized` 标志着 WPF 和底层 Win32 已经对接成功。一般的 WPF 开发几乎用不到这个事件，但如果你要调用 `SetWindowLong`、`SetWindowPos` 之类的 Win32 API 来定制窗口边框、最大化行为等，就得在这里下手。

**2. Initialized（初始化完成）**

- 这个是 `FrameworkElement` 提供的，`Window` 也继承了过来。在窗口所有属性加载完毕、但还没加入视觉树时触发。对于 `Window` 来说，此时它的内容（`Content`）可能也已经初始化，但还没有开始布局和呈现。

**3. Activated（被激活）**

- **触发时机**：窗口成为**前台活动窗口**时触发。用户点了一下这个窗口的标题栏，或者用 Alt+Tab 切过来，或者程序调用了 `Window.Activate()`，都会触发。
- **用途**：刷新界面数据、恢复动画、更新状态栏内容、检查新消息等。对应地，当窗口失去激活状态时会触发 `Deactivated`。
- **事件参数**：`EventArgs`。
- **注意**：一个应用程序中可以同时有多个窗口处于打开状态，但**只有一个窗口是激活的**（拥有焦点输入）。`Activated` 和 `Deactivated` 告诉你“是不是当前正在被用户交互的那个窗口”。

**4. Loaded（加载完成）**

- 继承自 `FrameworkElement`。窗口的布局和渲染全部完成，可以被用户看到了。`Window` 的 `Loaded` 事件在它自己加载完成时触发，此时它的所有子元素也已经全部加载完毕。所以窗口的 `Loaded` 是初始化整个窗口内容的最常用位置。

**5. ContentRendered（内容渲染完成）**

- **触发时机**：窗口的内容**第一次**被渲染到屏幕上之后。和 `Loaded` 的区别是，`Loaded` 在布局完成时触发，但可能还没有实际把像素画到屏幕上；`ContentRendered` 确保用户已经可以看到窗口的内容了。
- **用途**：如果你需要确保用户已经看见了某些东西，再做后续操作（比如弹一个对话框、开始一个需要用户看到的动画、启动一个后台任务且此任务依赖界面上已经显示的元素尺寸），就适合放在 `ContentRendered` 里。
- **事件参数**：`EventArgs`。
- **只触发一次**：`ContentRendered` 只在第一次渲染后触发，之后窗口内容变化不再触发。而 `Loaded` 在窗口被反复关闭重开时可能多次触发。

**6. Deactivated（被停用）**

- **触发时机**：窗口从激活状态变为非激活状态时触发。用户切到别的窗口、点了桌面、按了 Alt+Tab 都会导致这个事件。
- **用途**：暂停动画、停止实时刷新、保存当前状态、降低 CPU 占用。

**7. Closing（正在关闭）**

- **触发时机**：用户点击了窗口的关闭按钮（右上角 X），或者程序调用了 `Window.Close()`，在窗口**真正关闭之前**触发。
- **用途**：这是最后的拦截机会。你可以在 `Closing` 事件里设置 `CancelEventArgs.Cancel = true` 来**阻止窗口关闭**。典型场景：文档还没保存，弹个对话框问用户“是否保存？[是][否][取消]”，如果用户选取消，就设置 `e.Cancel = true`。
- **事件参数**：`CancelEventArgs`，有 `Cancel` 属性。

**8. Closed（已关闭）**

- **触发时机**：窗口已经**彻底关闭了**。此时窗口的 HWND 已经被销毁，视觉树也已经被拆除。`Closed` 标志着这个窗口的终结。
- **用途**：释放那些不能等到垃圾回收再释放的资源（如文件锁、数据库连接）、从全局管理器中注销自己、保存最终日志。
- **事件参数**：`EventArgs`。
- **注意**：`Closed` 触发后，窗口对象可能还被 C# 引用持有着，但 UI 已经不可见了。如果你在 `Closed` 之后还尝试操作窗口里的控件，会抛异常。

#### 生命周期事件的完整顺序

把 `Window` 和 `FrameworkElement` 的生命周期事件串起来，一个窗口从生到死的完整顺序是：

1. **构造函数**（C# 代码里 new Window，这不是事件，但这是生命的起点）
2. **SourceInitialized**（窗口的 Win32 句柄就绪）
3. **Initialized**（所有依赖项属性加载完毕）
4. **Loaded**（加入视觉树，布局完成）
5. **ContentRendered**（内容第一次渲染到屏幕）
6. **Activated**（窗口成为前台活动窗口）
7. （用户使用窗口的过程中，可能反复切换导致 `Deactivated` 和 `Activated` 交替触发多次）
8. **Closing**（用户或代码请求关闭窗口，可以取消）
9. **Deactivated**（窗口失去激活状态）
10. **Closed**（窗口已完全关闭，不可逆）
11. **Unloaded**（从视觉树移除）

对于窗口内部的子元素来说，它们的 `Initialized` → `Loaded` → `Unloaded` 会在窗口的 `Loaded` 和 `Closed` 之间各自依次发生。容器里所有子元素的 `Loaded` 都保证在父元素的 `Loaded` 触发之前完成。

### 输入事件

输入事件是 WPF 事件体系里另一大块——也是你日常打交道最多的那一块。每次鼠标动一下、键盘敲一下、手指碰一下屏幕，都会触发一系列精心设计的事件。这些事件**全部都是路由事件**（绝大多数是成对的隧道+冒泡事件），遵循前面讲的冒泡和隧道传播规则。

输入事件不是零散的，它们分四个层次：**鼠标输入**、**键盘输入**、**触控输入**、**以及更高层的命令输入**。5.3.2 节这里只是一个总体介绍，后面 5.4、5.5、5.6 会分别深入键盘、鼠标、触控。

#### 输入事件的核心特征

所有输入事件都共享以下特征：

1. **全部是路由事件**。它们都从命中测试得到的 `OriginalSource` 开始，按照隧道或冒泡方式传播。这意味着你可以在控件树的任意层次统一处理，不必把处理程序贴到每一个底层元素上。

2. **成对出现（隧道 + 冒泡）**。绝大多数输入事件都有隧道版本和冒泡版本。隧道版本名字以 `Preview` 开头，从根向下传到目标元素；冒泡版本从目标元素向上冒回根。这让你可以选择在事件到达目标之前拦截（隧道），还是在目标处理后再做些收尾（冒泡）。

   典型例子：
   - `PreviewMouseLeftButtonDown`（隧道） → `MouseLeftButtonDown`（冒泡）
   - `PreviewKeyDown`（隧道） → `KeyDown`（冒泡）
   - `PreviewMouseMove`（隧道） → `MouseMove`（冒泡）
   - `PreviewTouchDown`（隧道） → `TouchDown`（冒泡）

3. **事件参数包含丰富的上下文信息**。每种输入事件都有自己专用的事件参数类型，提供这次输入的详细信息。比如鼠标事件携带坐标、按钮类型、点击次数；键盘事件携带键码、是否重复、键盘设备信息；触控事件携带触控点 ID、压力、接触面积等。

4. **可以被标记为已处理**。任何一层元素在收到输入事件后，都可以设 `e.Handled = true` 来阻止事件继续传播。这让你可以在某个控件内部把事件“消化掉”，不让它往上冒干扰外层逻辑。`Button` 就是典型的例子——它在内部处理鼠标事件并标记已处理，然后生成一个更高层的 `Click` 事件给外部使用。

#### 输入事件的分类

WPF 的输入事件主要对应用户的三种交互设备：

**1. 鼠标事件**

鼠标事件是最丰富、最常用的输入事件。核心事件包括（左边的隧道版本省略 Preview 前缀，以下是冒泡版本的名字）：

- `MouseLeftButtonDown` / `MouseLeftButtonUp`：鼠标左键按下/松开。
- `MouseRightButtonDown` / `MouseRightButtonUp`：鼠标右键按下/松开。
- `MouseMove`：鼠标移动（每移动一个像素都可能触发，频率很高）。
- `MouseWheel`：鼠标滚轮滚动。
- `MouseEnter`：鼠标光标进入元素边界。
- `MouseLeave`：鼠标光标离开元素边界。

另外还有一个非常常用的高级事件 `Click`，它不是直接的输入事件，而是 `ButtonBase` 在内部处理了 `MouseLeftButtonDown` + `MouseLeftButtonUp` 之后合成出来的“点击确认”事件。大多数时候你用 `Click` 就够了，不用管底层的 Down/Up。

**2. 键盘事件**

键盘事件的触发和焦点（Focus）紧密相关——只有拥有焦点的元素才能收到键盘事件。核心事件：

- `KeyDown`：键盘上的键被按下。
- `KeyUp`：键盘上的键被松开。
- `TextInput`：有实际文本字符输入时触发（这个不是路由事件，是附加在 `UIElement` 上的 CLR 事件，但处理时机在 `KeyDown` 之后）。

键盘事件是应用程序做快捷键、文本输入、焦点导航等交互的基础。

**3. 触控与手写笔事件**

WPF 从 .NET 4 开始对触控输入提供了原生支持。核心事件：

- `TouchDown` / `PreviewTouchDown`：手指触摸屏幕。
- `TouchUp` / `PreviewTouchUp`：手指抬起。
- `TouchMove` / `PreviewTouchMove`：手指在屏幕上移动。
- `StylusDown` / `StylusUp` / `StylusMove`：手写笔（触控笔）的事件，和触控事件类似但精度更高、压力感应更强。

WPF 还在触控基础上提供了更高级的**操作（Manipulation）** 事件，比如 `ManipulationStarting`、`ManipulationDelta`（处理平移、缩放、旋转），以及惯性（Inertia）效果。这使得处理复杂的手势变得非常简单，不需要你从零计算手指位置的变化。这些在 5.6 节会细讲。

#### 输入事件的路由示例

为了让你更具体地理解输入事件的路由过程，我们拿一个最常见的场景过一遍：用户在一个 `TextBox` 上按了一个键。

控件树结构：
```
Window
 └─ Grid
     └─ DockPanel
         └─ TextBox (当前拥有焦点)
```

当用户按下键盘上的 "A" 键：

**隧道阶段**（从根向下）：
1. `Window` 收到 `PreviewKeyDown`。如果在这里设 `e.Handled = true`，事件就此终结，`TextBox` 收不到任何通知。这种拦截常用于全局快捷键（比如 Esc 关闭窗口）。
2. `Grid` 收到 `PreviewKeyDown`。
3. `DockPanel` 收到 `PreviewKeyDown`。
4. `TextBox` 收到 `PreviewKeyDown`。`TextBox` 通常不会在隧道阶段做处理，它选择让事件继续。

**冒泡阶段**（从目标向上）：
1. `TextBox` 收到 `KeyDown`。`TextBox` 在内部处理这个事件，把字符 "a" 插入文本，然后把 `e.Handled` 设为 `true`。
2. 因为事件已经被标记已处理，`DockPanel`、`Grid`、`Window` 默认不会再收到 `KeyDown`。

另外，`TextBox` 在处理完 `KeyDown` 之后，如果确定这次按键产生了实际文本输入，还会触发 `TextInput` 事件。`TextInput` 不在路由中，是直接事件。

整个过程清晰展示了“祖先拦截（隧道）”和“目标处理（冒泡）”的协作模式。

## 总结

5.3 节是后面 5.4~5.6 节的总览。把这两大类事件概括一下：

**生命周期事件**：
- 反映元素和窗口从创建到销毁的过程。
- 通用元素生命周期：`Initialized` → `Loaded` → 正常使用 → `Unloaded`。
- `Window` 专有生命周期，总共 8 个：`SourceInitialized`（底层句柄创建）、`Initialized`、`Activated`（激活）、`Loaded`、`ContentRendered`（第一次渲染完成）、`Deactivated`（失活）、`Closing`（可取消）、`Closed`（不可逆）。加上继承的 `Unloaded`，构成完整的窗口生灭图谱。
- 最常用的写初始化代码的时机：窗口的 `Loaded` 事件（此时所有子元素已就绪，DataContext 已可用）。清理资源：`Unloaded` 或 `Closed`。

**输入事件**：
- 反映用户与程序的物理交互：鼠标、键盘、触控。
- 全部是路由事件，绝大多数成对（隧道 Preview 版 + 冒泡版）。
- 隧道从根到目标（适合拦截），冒泡从目标到根（适合目标处理后逐层通知）。
- 后续 5.4（键盘）、5.5（鼠标）、5.6（触控）会把这些事件的细节展开讲。

掌握生命周期事件，你就知道什么时候该干什么——初始化放 `Loaded`，清理放 `Unloaded`/`Closed`，拦截关闭放 `Closing`。掌握输入事件的路由模型，你就知道怎么在控件树的任意层次优雅地处理用户交互，而不用给每个小控件一个个贴处理程序。
