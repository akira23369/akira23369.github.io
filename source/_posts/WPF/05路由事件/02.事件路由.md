## 事件路由

5.1 节讲了路由事件是什么、怎么注册、怎么引发、怎么处理。你已经知道了路由事件可以在控件树上传播，有三种路由策略（冒泡、隧道、直接）。但光知道这些还不够——要想真正驾驭 WPF 的输入和交互系统，你必须精确理解事件在树上到底是怎么“走”的，每一步携带什么信息，走的过程中谁能拦截、谁能放行，以及附加事件这个“别人家的事我也能听”的机制是怎么工作的。

5.2 节就是把这些事件传播的细节全部拆开给你看。

---

### RoutedEventArgs 类

每次路由事件被引发，WPF 都会创建一个事件参数对象，沿着控件树传递。路由事件的事件参数必须派生自 **`RoutedEventArgs`** 类。这个类是路由事件信息传输的“信封”，理解它的属性是理解路由过程的起点。

#### 核心属性

**`RoutedEvent`**
- 类型：`RoutedEvent`
- 含义：当前正在传播的是哪个路由事件。这个属性指向事件注册时返回的那个静态 `RoutedEvent` 对象（比如 `Button.ClickEvent`）。沿途的处理程序可以通过这个属性判断“来的是哪个事件”。

**`Source`**
- 类型：`object`
- 含义：事件的**逻辑来源**。即引发这个事件的那个元素（逻辑树上的节点）。通常情况下这就是你最关心的“谁发出了事件”。比如你点了按钮，`e.Source` 就是那个按钮。

**`OriginalSource`**
- 类型：`object`
- 含义：事件的**原始物理来源**。在复杂的控件模板里，一个 `Button` 内部可能包含 `Border`、`ContentPresenter`、`TextBlock` 等子元素。如果鼠标恰好点在按钮内部的 `TextBlock` 上，底层输入系统最先命中的目标是这个 `TextBlock`，它就是 `OriginalSource`。而 `Source` 则被 WPF 调整为逻辑树上的 `Button`。

多数时候你用 `Source` 就够了。但在某些需要精确判断命中位置的场景（比如你自定义了一个绘图面板，需要知道鼠标到底点在了哪个微小元素上），就需要用 `OriginalSource`。

**`Handled`**
- 类型：`bool`，默认 `false`
- 含义：事件是否已经被标记为“已处理”。这是路由事件最重要的控制属性。任何一个事件处理程序都可以设置 `e.Handled = true`。一旦设为 `true`，事件**通常**不会再沿路由方向继续传播（后文会细讲例外情况）。

#### RoutedEventArgs 的派生类

实际开发中，你很少直接接触光秃秃的 `RoutedEventArgs`。WPF 为不同种类的事件衍生了更具体的事件参数类，它们都继承自 `RoutedEventArgs`，新增了和该事件相关的额外信息：

- **`KeyEventArgs`**（键盘事件）：额外的 `Key` 属性告诉你按下了哪个键，`IsDown`、`IsRepeat` 等。
- **`MouseButtonEventArgs`**（鼠标按钮事件）：额外的 `MouseButton`、`ClickCount`（双击检测）、`GetPosition` 方法等。
- **`MouseWheelEventArgs`**（鼠标滚轮事件）：额外的 `Delta` 属性告诉你滚了多少。
- **`TouchEventArgs`**（触控事件）：提供触控点的详细信息。
- **`DragEventArgs`**（拖放事件）：提供拖放数据。

所有这些类都有 `Source`、`OriginalSource`、`Handled` 这三个核心属性（继承自 `RoutedEventArgs`），所以处理起来行为一致。

#### 构造 RoutedEventArgs 并引发事件

回顾上一节引发事件的代码：

```csharp
protected virtual void OnMyClick()
{
    RoutedEventArgs args = new RoutedEventArgs(MyClickEvent, this);
    RaiseEvent(args);
}
```

这里：
- `MyClickEvent` 是注册好的静态 `RoutedEvent`，赋值给 `args.RoutedEvent`，这样 WPF 就知道要走哪个事件的路由路径。
- `this` 作为第二个参数赋值给 `args.Source`，表示事件源就是当前控件。

如果你需要传递额外信息，可以定义一个派生自 `RoutedEventArgs` 的自定义参数类，并在构造时塞值。

### 冒泡路由事件

**冒泡（Bubble）** 是路由事件最常用、最直观的策略。它的传播路线是：**从事件源开始，沿着控件树一层层向上（向根方向）传播**。

#### 具体传播过程

假设控件树是：

```
Window
 └─ Grid
     └─ StackPanel
         └─ Button   <-- 用户点这里
```

如果 `Button` 触发了一个冒泡路由事件（比如 `Click`），传播顺序是：

1. **`Button`** 自己先收到事件（如果它有直接订阅的处理程序）。
2. 冒泡到 **`StackPanel`**。
3. 冒泡到 **`Grid`**。
4. 冒泡到 **`Window`**。
5. 如果还没被处理，可能继续往上到 `Application` 级别，最后到达根。

每一层的处理程序都可以做三件事：
- **处理事件**：执行自己的逻辑。
- **什么都不做**：事件继续往上冒。
- **标记已处理**：`e.Handled = true`，事件停止继续向上传播。

#### 冒泡的优势：父容器统一处理

父容器可以监听子元素的冒泡事件，这在实际开发中极其方便。经典例子：一个工具栏里有 10 个按钮，你在工具栏（父容器）上挂一个 `Click` 事件处理：

```xml
<ToolBar ButtonBase.Click="OnToolBarButtonClick">
    <Button Content="新建" />
    <Button Content="打开" />
    <Button Content="保存" />
    <Button Content="剪切" />
    <Button Content="复制" />
    <Button Content="粘贴" />
    <!-- 以后加新按钮不用再写订阅代码 -->
</ToolBar>
```

```csharp
private void OnToolBarButtonClick(object sender, RoutedEventArgs e)
{
    Button btn = e.Source as Button;
    switch (btn.Content?.ToString())
    {
        case "新建": /* ... */ break;
        case "打开": /* ... */ break;
        // ...
    }
}
```

一个处理程序管控所有按钮。如果没有冒泡机制，你得给每个按钮都写一个 `Click="xxx"`，代码量暴增，维护起来也容易漏。

#### 冒泡过程中 `sender` 的指向

在路由事件的处理方法里，`sender` 参数**永远指向挂载处理程序的那个元素**，而不是事件源。


比如你在 `StackPanel` 上挂载了 `Button.Click` 的处理方法：

```csharp
stackPanel.AddHandler(Button.ClickEvent, new RoutedEventHandler(OnClick));
```

那么当按钮被点击、事件冒泡到 `StackPanel` 时，`OnClick` 里的 `sender` 就是 `stackPanel`。

**那怎么知道是哪个按钮被点的？** 用 `e.Source` 或 `e.OriginalSource`。

这个规则非常重要，很多新手写在父容器上的事件处理，想当然地以为 `sender` 是被点的按钮，结果一转类型就抛异常。

**用冒泡的经典例子来感受**
```xml
<StackPanel x:Name="MyPanel" Button.Click="OnPanelClick">
    <Button x:Name="MyButton" Content="点我"/>
</StackPanel>
```

我们在 `StackPanel` 上为 `Button.Click` 附加了处理程序 `OnPanelClick`。
当点击按钮时，`Click` 事件会先从按钮产生，然后**冒泡**向上传递到 `StackPanel`。  
这时 `OnPanelClick` 被调用：

```cs
private void OnPanelClick(object sender, RoutedEventArgs e)
{
    // sender 是谁？
}
```
- **`sender` 是 `MyPanel`（StackPanel）**，因为处理程序是挂在 `StackPanel` 上的。
- **最初引发事件的按钮**，需要通过 `e.OriginalSource` 来获取，也就是 `MyButton`。

#### 中途拦截冒泡

在事件冒泡路径上的任何一层，都可以设 `e.Handled = true` 来“吞掉”事件，阻止它继续往上。比如你做了一个自定义按钮，在内部把 `MouseLeftButtonDown` 事件标记为已处理，这样外层容器就不会再收到这个鼠标按下事件。`ButtonBase` 就是这样做的——它在内部处理鼠标事件并标记已处理，然后触发新的 `Click` 冒泡事件。

### 处理挂起的事件

这一小节的标题原文可能是 "Handling a Suppressed Event" 或类似表达，核心意思是：**当事件已经被别人标记为 `Handled = true` 之后，我还有没有办法再处理它？**

答案是**有**，但需要显式声明。

#### `handledEventsToo` 参数

在代码中挂载路由事件处理程序时，`UIElement.AddHandler` 方法有一个重载版本，接受一个 `bool handledEventsToo` 参数：

```csharp
myElement.AddHandler(
    Button.ClickEvent,           // 要监听的事件
    new RoutedEventHandler(OnClick),  // 处理方法
    true                         // handledEventsToo = true
);
```

当这个参数设为 `true` 时，意味着：**即使这个事件在到达当前元素时已经被标记为 `Handled = true`，我也仍然要收到通知并执行处理方法。**

这对于某些需要“全局监听”或“兜底处理”的场景非常有用。比如你想要监听整个窗口里所有鼠标按下事件，无论中间哪个控件把事件拦住，你都想收到通知做日志记录。那就在 `Window` 上挂载 `MouseLeftButtonDown` 事件并设置 `handledEventsToo = true`。

#### 在 XAML 里怎么设？

XAML 里暂时没有直接给 `handledEventsToo` 设值的语法（它是代码层面的选项）。所以如果你需要这个特性，一般就在代码隐藏的构造函数里用 `AddHandler` 来挂。

#### 使用场景

最常见的场景就是 `Button.Click` 事件。`Button` 控件在内部会处理 `MouseLeftButtonDown` 并标记为已处理，然后产生一个更高层的 `Click` 事件。如果在 `Button` 外面的容器上挂 `MouseLeftButtonDown`，你会发现普通方式挂上去的事件收不到（因为被按钮内部吞掉了）。如果你确实需要监听**原始的鼠标按下**（比如要做全局点击热图统计），就需要用 `handledEventsToo = true` 来绕过这个“已处理”标记。

### 附加事件

**附加事件（Attached Event）** 是路由事件系统里一个很像“附加属性”的机制：**事件由某个类定义，但可以被其他不具备该事件的元素监听和处理。**

#### 为什么要附加事件？

回想依赖项属性那章的附加属性：`Grid.Row` 是 `Grid` 类定义的，但贴在 `Button` 上使用。附加事件同理：有些事件是某个类定义的，但它发生的时候，你希望**另一个类**的元素能订阅并处理它。

最典型的例子又是 `Button.Click`。`Click` 事件是 `ButtonBase` 类定义的。`StackPanel` 没有 `Click` 事件，但 `StackPanel` 可以监听放在它里面的按钮的 `Click` 冒泡事件。这在 XAML 里写出来就是：

```xml
<StackPanel Button.Click="OnButtonClicked">
    <Button Content="按钮" />
</StackPanel>
```

这里 `Button.Click` 就是一个附加事件的用法——`Click` 事件不属于 `StackPanel`，但你可以用 `定义类.事件名` 的语法在 `StackPanel` 上挂载处理。

#### 附加事件的本质

附加事件**并不是一个独立的事件类型**。它本质上就是冒泡路由事件。只是因为事件定义在另一个类上，而监听者不是该类的实例，所以在 XAML 里需要用“类名.事件名”的语法来挂载。

在底层，XAML 解析器看到 `Button.Click="handler"` 写在一个 `StackPanel` 上，就会把它翻译成：

```csharp
stackPanel.AddHandler(Button.ClickEvent, new RoutedEventHandler(handler));
```

所以附加事件就是路由事件的自然表现——冒泡事件天生就可以被路径上的任何元素处理，不管这个事件是不是定义在它自己身上。附加事件只是给这种用法提供了一个 XAML 语法糖。

#### 常见的附加事件

- `ButtonBase.Click`：在父容器上统一处理按钮点击。
- `ScrollViewer.ScrollChanged`：在包含滚动面板的容器上监听滚动。
- `Mouse.MouseDown`、`Keyboard.KeyDown`：通过 `Mouse` 和 `Keyboard` 等静态类挂载全局输入监听（注意这些类是 `System.Windows.Input.Mouse`，不是 `UIElement`）。

#### 自定义附加事件

虽然“附加事件”本质就是冒泡事件，但你也可以显式地按照附加事件的“标准格式”去定义它：在注册路由事件时，像附加属性那样提供静态的 `AddXxxHandler` 和 `RemoveXxxHandler` 方法。这在自定义控件开发中偶尔用到，目的是让你定义的事件能优雅地被其他类的元素监听。

```csharp
public class MyPanel : Panel
{
    public static readonly RoutedEvent TapEvent =
        EventManager.RegisterRoutedEvent(
            "Tap", RoutingStrategy.Bubble,
            typeof(RoutedEventHandler), typeof(MyPanel));

    // 静态的 Add/Remove 方法
    public static void AddTapHandler(DependencyObject d, RoutedEventHandler handler)
    {
        if (d is UIElement ui)
            ui.AddHandler(TapEvent, handler);
    }

    public static void RemoveTapHandler(DependencyObject d, RoutedEventHandler handler)
    {
        if (d is UIElement ui)
            ui.RemoveHandler(TapEvent, handler);
    }
}
```

这样外部使用起来就很自然：

```xml
<Grid local:MyPanel.Tap="OnTapped">
    <!-- 内容 -->
</Grid>
```

### 隧道路由事件

**隧道（Tunnel）** 是路由事件的另一种传播策略。它的传播方向与冒泡**相反**：**从控件树的根开始，沿着树一层层向下（向事件源方向）传播，直到到达事件源。**

#### 隧道事件的命名约定

WPF 里绝大多数隧道路由事件都以 **`Preview`** 前缀命名。比如：

- `PreviewMouseLeftButtonDown`（隧道） → `MouseLeftButtonDown`（冒泡）
- `PreviewKeyDown`（隧道） → `KeyDown`（冒泡）
- `PreviewMouseMove`（隧道） → `MouseMove`（冒泡）

这种成对出现的“隧道+冒泡”事件，是 WPF 输入系统的基础模式。每次鼠标按下，实际上是先触发隧道序列，到达目标后再触发冒泡序列。

#### 隧道路由的传播过程

假设控件树同样是：

```
Window
 └─ Grid
     └─ StackPanel
         └─ Button   <-- 用户点这里
```

当用户点击按钮时，如果该事件有隧道版本（如 `PreviewMouseLeftButtonDown`），传播顺序是：

**隧道阶段：**
1. **`Window`** 最先收到 `PreviewMouseLeftButtonDown`。
2. 传到 **`Grid`**。
3. 传到 **`StackPanel`**。
4. 传到 **`Button`**（目标）。

**冒泡阶段：**
1. **`Button`** 收到 `MouseLeftButtonDown`。
2. 冒泡到 **`StackPanel`**。
3. 冒泡到 **`Grid`**。
4. 冒泡到 **`Window`**。

#### 为什么要设计隧道事件？

隧道事件给了**祖先元素**一个“提前拦截和处理”的机会。

典型场景：你做了一个表单，里面有很多文本框。你希望在窗口层面按 `Esc` 键能关闭窗口。但如果当前焦点在某个文本框里，该文本框可能会先处理 `KeyDown` 事件并把它标记为已处理（比如用来做输入验证），你就收不到了。

有了隧道事件，你可以在 `Window` 上挂 `PreviewKeyDown`。因为隧道是从根向下的，`Window` 永远是路径上第一个收到事件的，你在这里就可以拦截 `Esc` 键并关闭窗口，根本不给下面的文本框处理的机会。

```csharp
// 在 Window 的构造函数或 OnKeyDown 替代里：
AddHandler(PreviewKeyDownEvent, (s, e) => {
    if (e.Key == Key.Escape) {
        this.Close();
        e.Handled = true;  // 阻止继续向下传播，文本框收不到
    }
}, true);
```

#### 隧道事件的处理和冒泡的关系

- 隧道事件被标记为 `Handled = true` 后，事件停止向下传播，目标元素和后续元素都收不到这个隧道事件。
- 但注意：**隧道事件被标记已处理，并不阻止相应的冒泡事件仍然被引发。** WPF 的输入系统在隧道阶段结束后，仍会启动冒泡阶段。当然，如果你在隧道阶段把关联的冒泡事件的输入处理拦截了（比如把鼠标事件的关键状态改了），冒泡行为可能受到影响。但一般来说，隧道和冒泡是两个独立的传播阶段。

#### 在 XAML 中使用隧道事件

和冒泡一样，隧道事件也可以在 XAML 里挂载：

```xml
<Grid PreviewKeyDown="OnPreviewKeyDown">
    <TextBox />
</Grid>
```

代码隐藏里和冒泡事件的处理一模一样，只是事件名称前多了 `Preview`。

## 总结

5.2 节把路由事件的传播细节全讲透了：

1. **`RoutedEventArgs` 类**：路由事件携带的“信封”。核心属性 `RoutedEvent`（哪个事件）、`Source`（逻辑源）、`OriginalSource`（物理源）、`Handled`（是否已处理）。各种派生类（`KeyEventArgs`、`MouseButtonEventArgs` 等）添加了各自域特有的额外信息。

2. **冒泡路由事件（Bubble）**：事件从源向上传播到根。父容器可以统一处理子元素的同类事件，极大减少代码量和耦合。中途可以设 `Handled = true` 阻止继续传播。`sender` 永远指向挂载处理程序的元素，`e.Source` 才是事件源。

3. **处理挂起的事件**：用 `AddHandler(..., handledEventsToo: true)` 可以让处理程序接收那些已经被标记为 `Handled = true` 的事件。适用于“全局监听”场景。

4. **附加事件**：本质就是冒泡路由事件，只是事件定义者和监听者不是同一个类。在 XAML 里用 `定义类.事件名="处理程序"` 的形式挂载。`Button.Click` 在 `StackPanel` 上的使用就是典型。

5. **隧道路由事件（Tunnel）**：从根向下传播到事件源。命名以 `Preview` 开头。给祖先元素一个在目标元素之前拦截事件的机会。隧道和冒泡成对出现，共同构成 WPF 输入事件的两阶段传播。

理解这一节之后，你再看 WPF 的任何鼠标、键盘、触控事件，脑子里都会自动浮现它们沿控件树上下穿梭的画面。后续 5.3~5.6 节讲的就是这些具体的输入事件类型如何运用这套路由机制。
