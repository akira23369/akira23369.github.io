## 理解路由事件

前面第 4 章学了依赖项属性，你知道了 WPF 的属性系统不是简单的 get/set，而是一套中央管理、支持多来源值和优先级解析的强大机制。这一章要学的是 WPF 另一根顶梁柱——**路由事件（Routed Event）**。

.NET 里本来就有事件机制，基于委托，谁订阅谁处理，非常直白。那 WPF 为什么又要重新发明一套事件系统呢？同样是因为 WPF 的界面是控件树，传统的事件模型在树形结构里表现出了严重的局限性。路由事件就是为了解决这些局限性而生的。

---

### 为什么需要路由事件？

#### 传统 .NET 事件的局限

在 Windows Forms 或纯 CLR 编程里，事件模式很简单：对象 A 定义一个事件，对象 B 去订阅它。事件发生时，A 直接调用 B 订阅的处理方法。这种模式在扁平结构里工作得很好。

但 WPF 的界面是**控件树**——按钮放在 StackPanel 里，StackPanel 放在 Grid 里，Grid 放在 Window 里，一层套一层。在这种树形结构里，出现了三个传统事件解决不了的需求：

**需求一：父元素需要感知子元素的事件**

假设你做了一个工具栏，里面放了 20 个按钮。传统模式下，你得给每个按钮单独订阅 `Click` 事件，写 20 个处理方法（或者写 20 行订阅代码指向同一个方法）。这既繁琐又难维护——以后加新按钮还得再订阅一次。

你直觉上希望能这样：直接在工具栏这个父容器上挂一个 `Click` 监听，不管哪个按钮被点了，父容器都能感知到，并且能区分是哪个按钮被点的。这在传统事件模型里做不到——事件只能在定义它的那个对象上直接触发，不会自动传给父容器。

**需求二：事件需要沿着控件树传递**

有些事件跟整棵树的状态都有关。比如鼠标按下事件，它发生在一个具体的 `TextBox` 上，但它的父 `Grid`、祖父 `Window` 可能也关心这个事件——比如 Window 要做点击计数、Grid 要做焦点管理。在传统事件里，每个关心者都得直接订阅那个 TextBox 的事件，TextBlock 一变，所有订阅代码都得改。

**需求三：输入事件需要精确控制处理顺序**

鼠标点了一下，这个位置可能有多个重叠元素。传统的命中测试只能报告最上面的那个元素被点中了，但实际需求可能更复杂：也许要先让最底层的容器预处理一下，再让上面的具体控件处理，最后顶层窗口再做收尾。这需要一个“事件穿过多层”的机制，传统事件不支持。

#### 路由事件的设计思想

WPF 的路由事件核心思想一句话：**事件不只在发生它的那个元素上触发，而是沿着控件树向上（或向下）传播，沿途的每个元素都有机会处理这个事件。**

这就像一个物理上的“路由”——事件从起点出发，按照指定路线经过树上的各个节点，每个节点都可以选择处理它、忽略它、或者标记它已经被处理过了。这种传播机制一举解决了上面三个需求：

- **父容器可以监听所有子元素的同类事件**（比如在工具栏上统一处理所有按钮的 Click）。
- **事件可以沿树传递，任意层的元素都可以参与处理**。
- **传播路径上先到先得，可以中途标记“已处理”阻止继续传播**。

路由事件是 WPF 输入系统和交互模型的核心。所有的鼠标事件、键盘事件、触控事件、拖放事件，全是路由事件。理解了它，你才能搞懂 WPF 的焦点、输入、命令等高级机制是怎么运作的。

### 定义、注册和封装路由事件

和依赖项属性一样，路由事件也不能用普通的 C# 事件语法来定义，它需要向 WPF 的事件系统注册。注册后得到一个 `RoutedEvent` 对象，这个对象就是该事件在路由事件系统中的“身份证”。

#### 注册路由事件

```csharp
public class MyControl : Control
{
    // 1. 声明一个静态只读的 RoutedEvent 字段
    public static readonly RoutedEvent MyClickEvent =
        EventManager.RegisterRoutedEvent(
            "MyClick",                     // 事件名称（字符串）
            RoutingStrategy.Bubble,        // 路由策略（冒泡、隧道、直接）
            typeof(RoutedEventHandler),    // 事件处理委托类型
            typeof(MyControl)              // 事件所有者类型
        );
}
```

`EventManager.RegisterRoutedEvent` 是注册入口，返回一个 `RoutedEvent` 对象。参数：

1. **事件名称**（`"MyClick"`）：和依赖项属性的命名规则类似，这个名称必须和后面 CLR 包装器的名字对应，字段名也必须是“事件名 + Event”后缀。
2. **路由策略**（`RoutingStrategy.Bubble`）：决定事件在控件树上的传播方向。有三种：
   - `Bubble`（冒泡）：从事件源向上传播到根（最常用）。
   - `Tunnel`（隧道）：从根向下传播到事件源。
   - `Direct`（直接）：不传播，和传统事件一样只在事件源上触发。
3. **委托类型**（`typeof(RoutedEventHandler)`）：事件处理方法的签名。WPF 路由事件的委托一般都派生自 `RoutedEventHandler`，它接受 `object sender` 和 `RoutedEventArgs e` 两个参数。
4. **所有者类型**（`typeof(MyControl)`）：这个事件属于哪个类。

#### 添加 CLR 事件包装器

注册完 `RoutedEvent` 之后，为了让 C# 代码能用 `+=` 和 `-=` 来订阅/取消订阅事件，需要一个 CLR 事件包装器：

```csharp
public event RoutedEventHandler MyClick
{
    add   { AddHandler(MyClickEvent, value); }
    remove { RemoveHandler(MyClickEvent, value); }
}
```

这里和普通事件的区别：
- 普通 C# 事件背后是一个委托字段，`+=` 就是往委托链上挂方法。
- 路由事件的 CLR 包装器背后调用的是 `UIElement` 基类的 `AddHandler` 和 `RemoveHandler` 方法，把处理方法注册到路由事件系统里。

这个包装器只是给 C# 代码提供方便的语法糖。在 XAML 里写 `MyClick="handler"` 时，XAML 解析器直接通过 `RoutedEvent` 对象去注册处理程序，同样绕过 CLR 包装器。

#### 命名约定

依赖项属性是 `属性名 + Property` 后缀（如 `MyValueProperty`），路由事件是 `事件名 + Event` 后缀（如 `MyClickEvent`）。这个约定同样很重要，XAML 解析器依赖它来找到正确的 `RoutedEvent` 对象。

### 共享路由事件

和依赖项属性一样，路由事件也支持“共享”。不同的类可以共用同一个 `RoutedEvent` 对象。

#### 为什么需要共享路由事件？

WPF 里有很多“通用事件”，比如 `MouseLeftButtonDown`（鼠标左键按下）、`KeyDown`（键盘按下）。这些事件在很多控件上都有，而且行为完全一致。如果每个控件都各自注册一遍，不仅浪费，而且让某些统一处理变难。

和依赖项属性类似，WPF 把这类通用事件定义在一些基类上，其他类通过 `AddOwner` 方法共享使用。

#### `AddOwner` 方法

```csharp
// Button 类共享了 UIElement 的 MouseLeftButtonDownEvent
public static readonly RoutedEvent MouseLeftButtonDownEvent =
    UIElement.MouseLeftButtonDownEvent.AddOwner(typeof(Button));
```

这样 `Button` 类就也拥有了 `MouseLeftButtonDown` 这个路由事件，你可以在 XAML 里写 `<Button MouseLeftButtonDown="handler" />`。

共享后的 `RoutedEvent` 对象仍然是同一个（所有共享者引用同一个对象），所以事件路由时行为完全一致。这一点对后面学到的附加事件（5.2.4 节）也至关重要。

#### 输入事件的共享架构

WPF 的输入事件（鼠标、键盘、触控）基本都定义在以下基类上，然后由各控件共享：

- `UIElement`：核心输入事件，如 `MouseLeftButtonDown`、`KeyDown` 等。
- `ContentElement`：用于非可视元素（如文档流中的文本元素）。
- `Control`：继承自 `UIElement`，增加了更多控件专有事件。

你平时看到的 `Button.Click`，其实是 `ButtonBase` 类自己注册的路由事件（Click 不是输入事件，是更高级的控件事件）。而 `Button.MouseEnter` 就是从 `UIElement` 共享来的。

### 引发路由事件

定义好路由事件之后，什么时候让它发生？这需要在特定条件下“引发”事件。

#### 用 `RaiseEvent` 触发

`UIElement` 基类提供了一个 `RaiseEvent` 方法，用于触发路由事件：

```csharp
public void RaiseEvent(RoutedEventArgs e)
```

你需要构造一个 `RoutedEventArgs`（或其子类）对象，路由事件标识（`RoutedEvent`）、设置好事件源（`Source`），然后调用 `RaiseEvent`。调用后，WPF 会根据事件注册时指定的路由策略，自动沿控件树传播。

#### 标准引发模式

WPF 里标准的做法是在一个受保护的虚方法里调用 `RaiseEvent`，这样派生类可以重写该方法来在事件触发前后做处理：

```csharp
public class MyControl : Control
{
    public static readonly RoutedEvent MyClickEvent =
        EventManager.RegisterRoutedEvent(
            "MyClick", RoutingStrategy.Bubble,
            typeof(RoutedEventHandler), typeof(MyControl));

    public event RoutedEventHandler MyClick
    {
        add { AddHandler(MyClickEvent, value); }
        remove { RemoveHandler(MyClickEvent, value); }
    }

    // 引发事件的受保护虚方法
    protected virtual void OnMyClick()
    {
        RoutedEventArgs args = new RoutedEventArgs(MyClickEvent, this);
        RaiseEvent(args);
    }

    // 在某个地方调用 OnMyClick 来触发事件
    protected override void OnMouseLeftButtonDown(MouseButtonEventArgs e)
    {
        base.OnMouseLeftButtonDown(e);
        OnMyClick();  // 鼠标左键按下时触发 MyClick 事件
    }
}
```

#### 为什么要用虚方法包装？

这和传统 .NET 的 `OnXxx` 模式一样：让派生类可以通过重写 `OnMyClick` 方法，在事件触发前加逻辑、阻止事件触发、或者在事件触发后做清理。许多 WPF 内置控件的事件都有对应的 `OnXxx` 虚方法，比如 `Button.OnClick`、`UIElement.OnMouseLeftButtonDown` 等。

#### 事件的 `Source` 和 `OriginalSource`

`RoutedEventArgs` 有两个重要的源属性：

- **`Source`**：事件的逻辑源，即通过哪个元素引发的事件。
- **`OriginalSource`**：事件的原始源，即从命中测试或输入系统得到的真正底层元素。在复杂的控件模板中，`OriginalSource` 可能是控件模板内部的某个子元素（比如按钮内部的 `TextBlock`），而 `Source` 则是模板外层的控件（比如 `Button` 自己）。

通常情况下你关心的是 `Source`，因为它是逻辑上的事件发出者。但在某些需要精确判断的场景（比如确定鼠标到底点在模板的哪个子元素上），就需要用 `OriginalSource`。

### 处理路由事件

事件被引发了，沿途的元素怎么处理它？这就涉及到事件处理程序的挂载方法。

#### XAML 中挂载（最常用）

```xml
<StackPanel Button.Click="OnButtonClicked">
    <Button Content="按钮1" />
    <Button Content="按钮2" />
</StackPanel>
```

这里有个关键点：`StackPanel` 自己没有 `Click` 事件（这是 `ButtonBase` 的事件），但因为它是一个父容器，而 `Click` 是冒泡路由事件，所以它能监听到子元素 `Button` 冒上来的 `Click` 事件。这就是前面说的“父容器统一处理子元素事件”的典型写法。

代码隐藏里：

```csharp
private void OnButtonClicked(object sender, RoutedEventArgs e)
{
    Button clickedButton = e.Source as Button;  // e.Source 是实际被点的按钮
    MessageBox.Show($"你点击了: {clickedButton.Content}");
}
```

#### 代码中挂载

```csharp
myStackPanel.AddHandler(Button.ClickEvent, new RoutedEventHandler(OnButtonClicked));
```

这里需要用 `Button.ClickEvent`（那个静态 `RoutedEvent` 字段）来指定要监听的事件。

#### 标记事件“已处理”

在事件处理方法里，你可以设置 `RoutedEventArgs.Handled = true;` 来**标记该事件已经被处理完毕**。这样做有两个后果：

1. **阻止事件继续传播**：在冒泡和隧道路由中，事件不会再继续向上（或向下）传播给后续的元素。这个元素就是该事件的“终点站”。
2. **通知路由系统**：其他处于传播路径后段的元素不会再收到这个事件。但如果某些元素用 `AddHandler(..., handledEventsToo: true)` 明确注册了“即使已处理也要通知”的回调，它们仍然能收到。这给了你一种“终极通知”的兜底机制。

示例：按钮的 `Click` 事件，默认情况下 `Button` 在内部处理完 `MouseLeftButtonDown` 后，会触发 `Click` 冒泡事件。如果你在父容器收到 `Click` 事件时设置 `Handled = true`，更上层的容器就不会再收到这个 Click 了。


#### .net事件模式——sender是什么？
详细知识点可以搜
- **“事件的标准签名”**
- **“sender 和 e 模式”**
- **“EventHandler 模式”**
- **“.NET 事件设计规范”**

为什么到处都是同样的写法？
因为 .NET 框架在设计之初就定下了一个**统一的规范**，要求所有事件（不管是按钮点击、文件监视、计时器到期……）都尽量遵循这个签名：
```cs
void SomeEvent(object sender, EventArgs e);
```

这背后依赖一个内置的委托类型：
- `EventHandler` — 用于不带特殊数据的事件
- `EventHandler<TEventArgs>` — 用于带自定义数据的事件（泛型）


sender是 **引发该事件的对象（事件源）** （如果是冒泡过程中，sender就是**永远指向当前事件处理程序实际“绑定”的那个元素，而不是最初触发事件的源头元素，源头元素用e.Source。**）

- `sender`：**谁**触发了事件（哪个控件）
- `e`：**发生了什么**细节（具体怎么触发的、附带什么数据）

在 WPF（以及整个 .NET 事件模型）里，所有控件都是**对象**。  
比如一个按钮是 `Button` 对象，一个文本框是 `TextBox` 对象。  
当用户**点击按钮**时，这个**按钮对象**就“引发”（触发）了 `Click` 事件。

所以：
- 按钮点击 → “引发该事件的对象”就是**这个按钮**
- 文本框里键盘按下 → “引发该事件的对象”就是**这个文本框**

假设你有一个按钮，并给它绑定了 `Click` 事件：
```cs
private void MyButton_Click(object sender, RoutedEventArgs e)
{
    // sender 就是被点击的那个按钮对象的引用
    Button clickedButton = sender as Button;  // 转换为 Button 类型
    MessageBox.Show("你点击了：" + clickedButton.Content);
}
```

如果页面上有多个按钮，**都用这同一个事件处理方法**：
```cs
button1.Click += MyButton_Click;
button2.Click += MyButton_Click;
```
点击 `button1` 时，`sender` 就是 `button1` 的引用；点击 `button2` 时，`sender` 就是 `button2` 的引用。这样你就能知道用户到底点了哪一个。

## 总结

路由事件是 WPF 事件系统的基石。它解决了控件树结构下三个传统事件无法处理的需求：

1. **父元素监听子元素事件**：事件沿树传播，父容器可以统一处理子元素的同类事件。
2. **多层参与处理**：事件在传播路径上每层都可以插手，先到先得。
3. **处理顺序控制**：通过冒泡（上）和隧道（下）两种策略，以及 `Handled` 标记，精确控制事件处理流程。

**定义路由事件的三件套**：
- 用 `EventManager.RegisterRoutedEvent` 注册静态 `RoutedEvent` 字段。
- 写 CLR 事件包装器（`add`/`remove` 调 `AddHandler`/`RemoveHandler`）。
- 在合适的时机调用 `RaiseEvent` 触发事件。

**核心参数**：
- `RoutingStrategy`：`Bubble`（冒泡，子→父）、`Tunnel`（隧道，父→子）、`Direct`（仅事件源）。
- `Handled`：在事件处理方法里设为 `true` 可阻止继续传播。
- `Source` vs `OriginalSource`：逻辑源 vs 物理核源。

理解了这些基础之后，下一节 5.2 就要深入事件路由的具体行为——冒泡、隧道、附加事件、以及 `RoutedEventArgs` 的更多细节。
