# 笔记38《元素绑定》8.1节——将元素绑定到一起

## 8.1 将元素绑定到一起

从现在开始，你要接触 WPF 最核心、最强大的特性之一——**数据绑定（Data Binding）**。这一整章（第8章）都在讲绑定，而 8.1 节是绑定的起点：先不扯什么数据库、什么 MVVM、什么 ViewModel，就从最简单的场景开始——**把两个 WPF 控件直接绑在一起，让一个控件跟着另一个控件自动变化，不需要写一行事件处理代码。**

这个简单的能力是理解后面所有复杂绑定场景的钥匙。当你能让一个控件的属性跟着另一个控件的属性自动变化时，你就能理解为什么 WPF 可以做到“界面和数据彻底分离”。

---

### 8.1.1 绑定表达式

#### 为什么要绑定两个控件？

先看一个传统的做法。假设界面上有一个 `Slider`（滑动条）和一个 `TextBlock`（文本块）。你希望拖动滑动条时，文本块自动显示滑动条的当前值。

在 Windows Forms 或传统的事件驱动模式里，你会这样写：

```csharp
// 传统事件方式
slider.ValueChanged += (s, e) => {
    textBlock.Text = slider.Value.ToString("F2");
};
```

这种方式的问题很明显：
- 每个联动关系都需要写一段事件代码。
- 界面多了以后，代码隐藏文件里塞满了这种琐碎的“搬运”逻辑。
- 一旦 `Slider` 换成了别的控件，或者显示格式变了，就得去改代码。

WPF 的做法完全不同：**在 XAML 里直接用绑定表达式把两个属性关联起来。**

```xml
<StackPanel>
    <Slider x:Name="slider" Minimum="0" Maximum="100" Value="50" />
    <TextBlock Text="{Binding ElementName=slider, Path=Value, StringFormat={}{0:F2}}" 
               FontSize="20" />
</StackPanel>
```

运行后：
- 初始时 `TextBlock` 显示 "50.00"（因为 Slider 的初始 Value 是 50）。
- 拖动滑动条，文本自动跟着变。
- 完全不需要 C# 代码。

**这就是元素绑定的威力——在 XAML 里直接声明控件之间的关系，WPF 帮你自动维护同步。**

#### 绑定表达式的语法

`{Binding ...}` 是 WPF 标记扩展的一种。它的完整语法包含多个可选的子属性，用逗号或空格分隔：

```
{Binding ElementName=源元素名称, Path=源属性名, 其他可选参数}
```

**核心子属性**：

- **`ElementName`**：指定源元素的名字（即 `x:Name` 指定的名字）。绑定目标会观察这个元素的属性变化。
- **`Path`**：指定要绑定的**源属性**。也就是你关心源元素的哪个属性发生了变化。注意，`Path` 的值是属性的名称（字符串），不是控件的类型。`Path=Value` 表示绑定到 `slider.Value` 属性。
- **`StringFormat`**：格式化字符串。和 C# 的 `string.Format` 用法一致。`{}{0:F2}` 表示把值格式化为保留两位小数的数字。前面的 `{}` 是 XAML 标记扩展的转义——因为花括号在 XAML 里是标记扩展的定界符，直接写 `{0:F2}` 会被当成另一个标记扩展，所以用 `{}{0:F2}` 来转义。
- **`Converter`**：值转换器，后面 8.2 节会讲。用于把源值转换成目标需要的格式。
- **`Mode`**：绑定模式，8.1.3 节详细讲。
- **`UpdateSourceTrigger`**：更新触发方式，8.1.7 节讲。

**最简写法**：

```xml
<TextBlock Text="{Binding ElementName=slider, Path=Value}" />
```

**绑定源是依赖项属性（绝大多数情况）**

你可能会问：`Slider.Value` 是什么属性？它是依赖项属性（Dependency Property），第4章详细讲过。WPF 的绑定引擎在运行时通过 `slider.GetValue(Slider.ValueProperty)` 来读取源值，并通过 `PropertyChangedCallback` 来监听值的变化。这就是为什么前面花了整整一章讲依赖项属性——因为**绑定目标必须是依赖项属性，绑定源最好也是依赖项属性**（源可以是普通 CLR 属性，但需要实现 `INotifyPropertyChanged`，后面会讲）。

**Path 可以深入到子属性**

`Path` 不仅可以是直接的属性名，还可以是属性链。比如源元素的 `Content` 属性本身是一个对象，你想绑定到这个对象的某个属性：

```xml
<TextBlock Text="{Binding ElementName=button, Path=Content.ActualWidth}" />
```

甚至可以使用索引器：

```xml
<TextBlock Text="{Binding ElementName=listBox, Path=Items[0]}" />
```

不过元素绑定的常见场景 Path 一般都是直接属性名。

### 8.1.2 绑定错误

绑定不是魔法，也可能会出错。当绑定的 `ElementName` 找不到源元素，或者 `Path` 指定的属性不存在，或者类型转换失败时，WPF 不会在运行时弹出错误对话框，而是**静默失败**——目标属性的值保持原样或使用默认值，同时在 Visual Studio 的输出窗口（Output Window）打印错误信息。

#### 为什么 WPF 选择静默失败？

因为绑定是松耦合的——XAML 在编译时无法检查绑定的目标元素是否真的存在（元素可能在运行时动态创建），也无法检查属性名是否正确（`Path` 是字符串）。所以 WPF 的策略是：能绑就绑，绑不上就保持原样，把错误信息打到调试窗口，让开发者自己去查。

#### 常见的绑定错误

**错误一：ElementName 不存在**

```xml
<TextBlock Text="{Binding ElementName=NoSuchSlider, Path=Value}" />
```

输出窗口会显示类似：

```
System.Windows.Data Error: 4 : Cannot find source for binding with reference 
'ElementName=NoSuchSlider'.
```

**错误二：Path 指定的属性不存在**

```xml
<TextBlock Text="{Binding ElementName=slider, Path=NonExistentProperty}" />
```

输出窗口会显示：

```
System.Windows.Data Error: 40 : BindingExpression path error: 
'NonExistentProperty' property not found on 'object' ''Slider' ...
```

**错误三：类型不匹配且没有类型转换器**

如果源属性的类型和目标属性的类型不匹配，且 WPF 找不到合适的类型转换器，绑定也会失败。比如把 `Slider.Value`（`double`）绑给 `TextBlock.Text`（`string`）——这个是能成功的，因为 WPF 内置了 `double` 到 `string` 的转换。但反过来，把 `TextBlock.Text`（`string`）绑给 `Slider.Value`（`double`），字符串如果不是数字格式，更新源时就会失败。

**错误四：绑定目标不是依赖项属性**

绑定的目标属性**必须**是依赖项属性。如果你试图把绑定设在一个普通 CLR 属性上，编译时能过（因为 XAML 解析器没法判断目标是不是依赖项属性），但运行时会抛异常。

#### 怎么排查绑定错误？

1. **打开输出窗口**：在 Visual Studio 中，调试时点“视图” → “输出”，或者直接按 `Ctrl+Alt+O`。绑定错误会打印在这里。
2. **增加绑定追踪级别**：在选项里可以设置 WPF 的数据绑定追踪详细级别，输出更多信息。
3. **使用 FallbackValue**：给绑定指定一个后备值，当绑定失败时目标属性使用这个值，界面不会突兀。

```xml
<TextBlock Text="{Binding ElementName=slider, Path=Value, FallbackValue='N/A'}" />
```

4. **使用 TargetNullValue**：当源属性值为 `null` 时使用的默认值。

```xml
<TextBlock Text="{Binding ElementName=slider, Path=Value, TargetNullValue='无值'}" />
```

#### 绑定错误和设计时的区别

在 Visual Studio 设计器里编辑 XAML 时，绑定不会实际执行（因为设计时没有运行时的数据上下文），所以设计器里可能看不到绑定效果或看到设计时数据。这是正常的。设计时数据可以通过 `d:DataContext` 和 `d:DesignData` 来模拟，属于进阶内容。

### 8.1.3 绑定模式

绑定有一个非常重要的属性 **`Mode`**，决定数据流的方向——是控件 A 推到控件 B？还是控件 B 推到控件 A？还是双向互推？

`Mode` 的类型是 `BindingMode` 枚举，有四个值：

#### OneWay（默认模式……吗？）

数据从**源**流向**目标**。源属性变了，目标自动更新。目标变了，源不更新。这是单向绑定。

```xml
<TextBlock Text="{Binding ElementName=slider, Path=Value, Mode=OneWay}" />
```

`Slider.Value` 变了 → `TextBlock.Text` 自动更新。如果用户直接在 `TextBlock` 上改文字（这是不可能的，因为 `TextBlock` 只读），不会有任何东西反向更新 `Slider`。

**但注意**：`Mode=OneWay` 是`Binding` 类的默认值，但是**不同目标属性的默认模式可能不同**。WPF 在定义每个依赖项属性时，可以通过元数据指定该属性的默认绑定模式。比如 `TextBox.Text` 的默认模式是 `TwoWay`（因为输入框通常需要双向同步），而 `TextBlock.Text` 的默认模式是 `OneWay`（因为文本块是只读展示）。

所以你在写绑定时，很多时候不写 `Mode` 也能得到正确的行为，因为 WPF 已经替你选好了最自然的模式。但明确写出 `Mode` 可以增加可读性，并避免因默认模式不如预期而产生的 bug。

#### TwoWay（双向）

数据在源和目标之间**双向流动**。任何一端变化，另一端自动同步。

```xml
<TextBox Text="{Binding ElementName=slider, Path=Value, Mode=TwoWay}" />
```

用户在文本框里输入一个数字 → `TextBox.Text` 变 → 绑定引擎把这个新值写回 `Slider.Value`。`Slider.Value` 变了 → 也会更新回 `TextBox.Text`。

双向绑定是最强大的，也是表单类应用的核心——用户修改的数据能自动写回数据模型，数据模型的更新也能自动反映到界面。但也需要注意：**双向绑定时，类型转换和验证就变得非常重要**。用户可能在文本框里输入了不是数字的字符，绑定引擎尝试把 `"abc"` 赋给 `double` 类型的 `Value` 属性时就会失败。这时候需要借助验证规则（`ValidationRules`，后面会讲）或 `ExceptionValidationRule` 来处理。

**双向绑定的默认模式**：很多交互控件（如 `TextBox.Text`、`CheckBox.IsChecked`、`Slider.Value`）默认就是 `TwoWay`。

#### OneTime（一次性）

数据只在**绑定建立时**从源流向目标一次。之后源再怎么变，目标都不管。更像是“从源取初始值”。

```xml
<TextBlock Text="{Binding ElementName=slider, Path=Value, Mode=OneTime}" />
```

只在加载时读取一次 `Slider.Value`，之后拖动滑动条，文本不再变化。

**适用场景**：
- 显示初始值，之后不需要同步（比如窗口标题、静态标签）。
- 源数据是计算出来的，不需要实时更新（省性能）。
- 目标属性值在运行时不会被修改。

#### OneWayToSource（反向单向）

这是 `OneWay` 的镜像：数据从**目标**流向**源**。目标属性变了，自动更新源属性。源属性变了，目标不更新。

```xml
<Slider Value="{Binding ElementName=textBox, Path=Text, Mode=OneWayToSource}" />
```

用户拖动滑动条不会影响文本框，但用户在文本框里输入数字会反向更新滑动条的位置。

**适用场景**：
- 一个只用于展示的元素去更新后面的数据模型。
- 交互控件（如 `Slider`、`TextBox`）需要把值写回数据源，但数据源的变化不需要实时反映在这个控件上。

这个模式在实际中用得相对少，但特定场景下确实需要。

#### 四个模式的对比表

| 模式 | 源→目标 | 目标→源 | 典型场景 |
|------|---------|---------|---------|
| `OneWay` | ✅ 自动更新 | ❌ 不更新 | 展示型控件（`TextBlock`、`Label`）展示数据 |
| `TwoWay` | ✅ 自动更新 | ✅ 自动更新 | 编辑型控件（`TextBox`、`CheckBox`、`Slider`） |
| `OneTime` | ✅ 仅初始化时更新一次 | ❌ 不更新 | 静态标签，不需要同步的初始值 |
| `OneWayToSource` | ❌ 不更新 | ✅ 自动更新 | 目标向源写值，但源不反馈回目标 |

### 8.1.4 使用代码创建绑定

绑定不仅能在 XAML 里写，也能在 C# 代码里动态创建。这在需要根据运行时条件动态调整绑定的场景下非常有用。

#### 基本 API

用 `System.Windows.Data.Binding` 类创建绑定对象，然后用目标元素的 `SetBinding` 方法把它挂载到目标属性上：

```csharp
// 创建绑定对象
Binding binding = new Binding
{
    Source = mySlider,        // 指定源对象
    Path = new PropertyPath(Slider.ValueProperty),  // 指定源属性
    Mode = BindingMode.OneWay,
    StringFormat = "当前值: {0:F1}"
};

// 把绑定挂载到目标元素的属性上
myTextBlock.SetBinding(TextBlock.TextProperty, binding);
```

注意这里的 `Source` 直接指定了源对象 `mySlider`。这和在 XAML 里写 `ElementName=mySlider` 是等价的，但代码里直接给 `Source` 赋值一个对象引用更直接。

#### 代码绑定 & 元素名绑定 的等价写法

XAML 中：
```xml
<TextBlock Text="{Binding ElementName=slider, Path=Value, Mode=OneWay}" />
```

代码中：
```csharp
Binding binding = new Binding
{
    ElementName = "slider",
    Path = new PropertyPath("Value"),
    Mode = BindingMode.OneWay
};
myTextBlock.SetBinding(TextBlock.TextProperty, binding);
```

代码里 `ElementName` 是字符串，XAML 中是标记扩展参数，完全等价。

#### 用代码清除绑定

你可以通过 `BindingOperations.ClearBinding` 移除一个属性上的绑定，恢复为直接赋值：

```csharp
BindingOperations.ClearBinding(myTextBlock, TextBlock.TextProperty);
```

或者用 `ClearAllBindings` 清除某个对象所有属性的绑定。

#### 什么时候用代码绑定？

- 需要根据运行时条件动态构建绑定路径或转换器的。
- 在循环中为批量生成的控件设置绑定的。
- 需要在代码中动态改变绑定目标的。
- 自定义控件内部为内部元素架设绑定的。

对于绝大多数静态 UI，XAML 绑定是最简洁清晰的。

### 8.1.5 使用代码检索绑定

你不仅可以通过代码创建绑定，还可以在运行时查询某个目标属性上是否已经有绑定、是什么样的绑定。这在调试和某些动态行为中很有用。

```csharp
Binding binding = BindingOperations.GetBinding(myTextBlock, TextBlock.TextProperty);
if (binding != null)
{
    Console.WriteLine($"源: {binding.Path.Path}, 模式: {binding.Mode}");
}
```

`BindingOperations.GetBinding` 返回当前挂载在该属性上的 `Binding` 对象。如果没有绑定，返回 `null`。

此外，`BindingOperations.GetBindingExpression` 返回更底层的 `BindingExpression` 对象，它包含绑定的运行时状态：

```csharp
BindingExpression bindingExpr = 
    BindingOperations.GetBindingExpression(myTextBlock, TextBlock.TextProperty);
if (bindingExpr != null)
{
    Console.WriteLine($"状态: {bindingExpr.Status}");        // Active / Inactive 等
    Console.WriteLine($"源值: {bindingExpr.ResolvedSource}"); 
    // 拿到当前绑定的源对象
}
```

这在调试绑定问题时非常有用——你可以实时看到绑定是否处于活动状态、是否解析成功、当前源对象是谁。

### 8.1.6 多绑定

有时候，一个目标属性的值不是由单一源决定的，而是由**多个源**组合决定。比如：
- 一个 `TextBlock.Text` 要显示 “张三，年龄 30，来自北京”，其中姓名、年龄、城市分别来自三个不同的 `TextBox`。
- 一个按钮的 `IsEnabled` 需要所有输入框都不为空才能点。
- 一个颜色的 RGB 三个通道分别来自三个滑动条。

WPF 提供了两种多源绑定的方式：**`MultiBinding`**（把多个值合成一个）和 **`PriorityBinding`**（按优先级选择第一个可用的源）。

#### MultiBinding（多值绑定）

`MultiBinding` 把多个绑定“绑”在一起，交给一个**多值转换器（IMultiValueConverter）**来把它们合成为一个最终值。

**示例**：把三个滑动条（R、G、B）的值合成为一个 `SolidColorBrush`，赋给一个矩形的 `Fill`。

XAML：

```xml
<Rectangle Width="100" Height="100">
    <Rectangle.Fill>
        <MultiBinding Converter="{StaticResource RgbToColorConverter}">
            <Binding ElementName="rSlider" Path="Value" />
            <Binding ElementName="gSlider" Path="Value" />
            <Binding ElementName="bSlider" Path="Value" />
        </MultiBinding>
    </Rectangle.Fill>
</Rectangle>
```

转换器：

```csharp
public class RgbToColorConverter : IMultiValueConverter
{
    public object Convert(object[] values, Type targetType, object parameter, CultureInfo culture)
    {
        byte r = System.Convert.ToByte(values[0]);
        byte g = System.Convert.ToByte(values[1]);
        byte b = System.Convert.ToByte(values[2]);
        return new SolidColorBrush(Color.FromRgb(r, g, b));
    }

    public object[] ConvertBack(object value, Type[] targetTypes, object parameter, CultureInfo culture)
    {
        // 双向转换略，这里只需要单向
        throw new NotImplementedException();
    }
}
```

`values` 数组里的元素顺序和 `<MultiBinding>` 里面 `<Binding>` 的声明顺序一致。任何一个子绑定的源值变了，转换器都会被重新调用，生成新的目标值。

**适用场景**：
- 合成多个来源为一个显示值（显示字符串）。
- 多重条件判断（如多个复选框全部勾选才启用按钮）。
- 多个控件联动（一个目标值的多个维度由不同源决定）。

#### PriorityBinding（优先级绑定）

`PriorityBinding` 也接受多个子绑定，但它**不是合成它们**，而是**按优先级逐个尝试**。排在第一位的绑定如果能成功解析出值，就用它；如果第一个失败（如源为 null、绑定中断等），自动尝试第二个，以此类推。

**典型场景**：一个显示区域需要展示“最好能有的信息”，如果主信息还没加载好，就先显示次信息。

```xml
<TextBlock>
    <TextBlock.Text>
        <PriorityBinding>
            <Binding Path="FullName" />                       <!-- 优先显示全名 -->
            <Binding Path="Username" />                       <!-- 全名没加载好就显示用户名 -->
            <Binding Source="N/A" />                          <!-- 都没有就显示兜底值 -->
        </PriorityBinding>
    </TextBlock.Text>
</TextBlock>
```

如果 `FullName` 属性有值就显示它；如果没有（`null` 或数据未就绪），就降到 `Username`；如果还没有，就用静态值 "N/A"。

`PriorityBinding` 不需要转换器，因为同一时刻只有一个子绑定生效。它主要解决**加载过程中的数据可用性**问题——比如数据从数据库异步读取，UI 先显示缓存值或占位符。

**Multibinding vs PriorityBinding 对比**：

| 特性 | MultiBinding | PriorityBinding |
|------|-------------|-----------------|
| 决策方式 | 所有子绑定值一起传给转换器合成 | 依次尝试，用第一个可用的 |
| 需要转换器 | 是（`IMultiValueConverter`） | 否 |
| 典型场景 | 合成多个来源为一个结果 | 按优先级回退，加载占位 |
| 动态性 | 任何子源变化都重新合成 | 当前生效的子源变化就更新 |

### 8.1.7 绑定更新

在双向绑定（`TwoWay`）或反向单向绑定（`OneWayToSource`）中，绑定引擎需要知道**什么时候该把目标属性的新值写回源属性**。这个时机由 **`UpdateSourceTrigger`** 属性控制。

#### UpdateSourceTrigger 的三种值

**`UpdateSourceTrigger.PropertyChanged`**

目标属性**每发生一点变化**，就立刻写回源。这是最及时的更新方式，但也意味着最频繁的更新。

```xml
<TextBox Text="{Binding CurrentValue, UpdateSourceTrigger=PropertyChanged}" />
```

用户在文本框里每敲一个字符，`CurrentValue` 属性就被更新一次。在实时搜索、实时校验的输入框里很有用。

**`UpdateSourceTrigger.LostFocus`**

当目标控件**失去键盘焦点**时才写回源。这是 `TextBox.Text` 属性的**默认行为**。

```xml
<TextBox Text="{Binding UserName, UpdateSourceTrigger=LostFocus}" />
```

用户在输入框里敲完一串文字，点了一下别的控件（或者按 Tab），文本才正式提交到源属性。这是最自然的行为——你不会希望用户正在输入过程中，每敲一个字都触发保存或验证。

**`UpdateSourceTrigger.Explicit`**

绑定引擎**不自动更新源**，完全由开发者在代码里手动调用更新。

```xml
<TextBox Text="{Binding UserName, UpdateSourceTrigger=Explicit}" />
```

代码里手动触发：

```csharp
BindingExpression bindingExpr = 
    myTextBox.GetBindingExpression(TextBox.TextProperty);
bindingExpr?.UpdateSource();  // 手动把目标值推到源
```

适用场景：需要在用户点击“确认”按钮或通过某种验证后才同步数据。

#### 不同控件的默认 UpdateSourceTrigger

WPF 在定义每个依赖项属性时，会指定一个默认的 `UpdateSourceTrigger`：

- `TextBox.Text`：默认是 `LostFocus`。
- `CheckBox.IsChecked`：默认是 `PropertyChanged`（勾选了马上同步）。
- `Slider.Value`：默认是 `PropertyChanged`（拖动了马上同步）。
- `ComboBox.SelectedItem`：默认是 `PropertyChanged`。

大多数情况默认值就是合理的，但当你需要不同的行为时，知道怎么改能省很多事。

### 8.1.8 绑定延迟

有些时候，你不希望目标属性的变化**立刻**写回源。比如用户在搜索框里快速打字，你希望等他停手半秒后再真正发起搜索请求，而不是每敲一个字都搜一次。WPF 提供了 `Delay` 属性来实现这个目的。

**`Delay` 属性**：类型是 `int`，单位是**毫秒**。它让绑定在目标值变化后，**等待一段时间**，如果在这段时间内目标值又变了，就重置等待计时器。只有连续不变达到 `Delay` 指定的时间后，才会真正更新源。

```xml
<TextBox Text="{Binding SearchText, Delay=500}" />
```

用户在搜索框输入 "Hello"：
- 敲 `H` → 计时器启动（等待 500ms）。
- 敲 `e` → 计时器重置。
- 敲 `l` → 计时器重置。
- ……
- 用户停止输入 500ms 后 → `SearchText` 才被更新为 "Hello"，触发搜索。

**重要细节**：

- `Delay` 只对 `TwoWay` 和 `OneWayToSource` 模式有效（因为它只影响目标到源的更新延迟）。
- `Delay` 配合 `UpdateSourceTrigger.PropertyChanged` 使用是最典型的“输入防抖”模式。
- `Delay` 也是 `Binding` 的一个属性，默认为 0（无延迟）。

**和 UpdateSourceTrigger 的关系**：

`Delay` 和 `UpdateSourceTrigger` 可以组合使用：

```xml
<!-- 每次输入都即时变化，但有 300ms 防抖 -->
<TextBox Text="{Binding SearchText, 
              UpdateSourceTrigger=PropertyChanged, 
              Delay=300}" />

<!-- 失去焦点时立刻更新，不延迟 -->
<TextBox Text="{Binding SearchText, 
              UpdateSourceTrigger=LostFocus, 
              Delay=0}" />
```

在 `LostFocus` 模式下，`Delay` 意义不大——用户离开控件时通常不再快速变化。

## 8.1 节总结

8.1 节是整个数据绑定旅程的起点，聚焦在最直观的场景——**把两个控件直接绑在一起**。虽然简单，但里面已经包含了绑定系统的所有核心概念：

**绑定表达式**：
- `{Binding ElementName=源, Path=属性}` 是基本语法。
- 源控件的属性通过依赖项属性机制被绑定引擎监听。
- `Path` 可以深入到子属性和索引器。

**绑定错误**：
- 绑定失败时 WPF 静默处理，错误信息打印到输出窗口。
- 常见错误：`ElementName` 找不到、`Path` 属性名错误、类型不匹配、目标不是依赖项属性。
- 调试手段：查看输出窗口、使用 `FallbackValue` 和 `TargetNullValue`。

**绑定模式**：
- `OneWay`：源变目标也变（默认模式，展示型控件）。
- `TwoWay`：双向同步（编辑型控件常用）。
- `OneTime`：只初始化一次，之后不管。
- `OneWayToSource`：反向单向，目标推源。

**代码创建和检索绑定**：
- `new Binding { Source/ElementName, Path }` + `SetBinding` 动态创建绑定。
- `BindingOperations.GetBinding` / `GetBindingExpression` 检索和调试现有绑定。

**多绑定**：
- `MultiBinding` + `IMultiValueConverter`：把多个值合成为一个。
- `PriorityBinding`：按优先级切换可用的子绑定，实现数据回退。

**绑定更新**：
- `UpdateSourceTrigger`：控制目标何时写回源（`PropertyChanged`、`LostFocus`、`Explicit`）。
- `Delay`：毫秒级防抖延迟，配合输入框避免过于频繁的更新。

理解透这一节，你就抓住了 WPF 绑定的核心骨架。后面的 8.2 节会从“绑定到控件”扩展到“绑定到非元素对象”——数据对象、资源对象、甚至相对元素，数据绑定的真正威力将在那里全面展开。
